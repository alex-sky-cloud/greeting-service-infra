ошибка обрабатывается **для конкретного `id` внутри его внутреннего `Mono`**, после чего этот `id` пропускается, а обработка остальных `id` продолжается.

```java
Flux.just(id1, id2, id3)
    .flatMap(id -> orderService.process(id)
        .onErrorResume(e -> {
            log.warn("skip order {}", id, e);
            return Mono.empty();
        }))
    .subscribe();
```

Предположим:

- `id1` обработался успешно;
- при обработке `id2` `orderService.process(id2)` завершился ошибкой;
- `id3` должен всё равно быть обработан.

Тогда происходит следующее:

1. `flatMap` создаёт отдельный внутренний `Mono` для каждого `id`.
2. Ошибка `id2` попадает в его локальный `onErrorResume`.
3. `onErrorResume` заменяет ошибочный `Mono` на `Mono.empty()`.
4. `Mono.empty()` означает: **для данного `id` не будет результата, но внутренний publisher завершился нормально**.
5. Поэтому внешний `Flux` не получает `onError` и не отменяет обработку остальных `id`.
6. `id3` продолжает обрабатываться.

Важно: `Mono.empty()` **не блокирует поток** и не делает «следующий запрос» сам по себе. Он просто немедленно завершает обработку **текущего элемента без результата**. Следующий `id` обрабатывается потому, что внешний `Flux` ещё не завершился ошибкой.

## Зачем это нужно

Типичный бизнес-кейс — **пакетная обработка независимых сущностей**, где ошибка одной записи не должна останавливать весь пакет.

Например:

- ночная обработка заказов;
- массовая отправка уведомлений;
- импорт пользователей из CSV;
- синхронизация каталога товаров;
- обработка сообщений из очереди;
- пересчёт статусов заказов.

Допустим, есть 10 000 заказов. Один заказ повреждён: не найден клиент, невалиден адрес или внешний сервис временно отказал. Если ошибка должна остановить весь batch, обработка размещается снаружи `flatMap`:

```java
Flux.just(id1, id2, id3)
    .flatMap(orderService::process)
    .onErrorResume(e -> {
        log.error("batch failed", e);
        return Mono.empty();
    });
```

Здесь ошибка из `id2` уже дошла до внешнего `Flux`: batch прекращается, активные внутренние подписки могут быть отменены, а `id3` может не обработаться.

Если же политика бизнеса — «заказ с ошибкой пропустить, зафиксировать проблему и продолжить», обработчик ставится **внутри**:

```java
Flux.just(id1, id2, id3)
    .flatMap(id ->
        orderService.process(id)
            .onErrorResume(e -> {
                log.warn("Order {} was skipped", id, e);
                return Mono.empty();
            })
    );
```


## Почему `Mono.empty()`

`Mono.empty()` подходит, когда результат для проблемного элемента не нужен: мы решили **пропустить** заказ.

Но пропускать ошибку молча обычно плохая идея. Минимум — логировать её; лучше также отправлять идентификатор в retry/DLQ/таблицу ошибок:

```java
.flatMap(id ->
    orderService.process(id)
        .onErrorResume(e ->
            failedOrderRepository.save(id, e.getMessage())
                .then(Mono.empty())
        )
)
```

Так основной поток продолжает работу, но проблемный заказ не теряется: его можно повторно обработать позже.

## Нюанс `flatMap`

`flatMap` обрабатывает элементы конкурентно. Поэтому `id3` может стартовать **ещё до того, как упал `id2`**. Это зависит от скорости publisher’ов и настроенного уровня параллелизма.

Если важен порядок строго `id1 -> id2 -> id3`, используют `concatMap`:

```java
Flux.just(id1, id2, id3)
    .concatMap(id ->
        orderService.process(id)
            .onErrorResume(e -> {
                log.warn("skip order {}", id, e);
                return Mono.empty();
            })
    )
    .subscribe();
```

Тогда после ошибки у `id2` вернётся `Mono.empty()`, и только затем начнётся обработка `id3`.
