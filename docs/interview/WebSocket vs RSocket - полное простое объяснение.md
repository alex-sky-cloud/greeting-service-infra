

# WebSocket vs RSocket: полное простое объяснение


***

## Короткий ответ

**WebSocket — это «труба» (транспорт). RSocket — это «протокол разговора» внутри этой трубы.**

RSocket работает **поверх** WebSocket (или TCP, или Aeron). В реактивном приложении вы *можете* использовать чистый WebSocket, но тогда **всё придётся писать самим**: контроль потока, маршрутизацию, корреляцию запросов, мультиплексирование, восстановление сессии. RSocket даёт это «из коробки».

***

## Почему не просто WebSocket? (таблица с понятными пояснениями)

| Задача | WebSocket (чистый) — что делаете вы | RSocket (поверх WebSocket) — что даёт протокол |
| :-- | :-- | :-- |
| **Backpressure** (контроль потока) | Сами пишете: пауза/резюме, буферы, ACK, таймауты. Клиент может утонуть в данных. | Встроено: клиент шлёт `request(10)` → сервер присылает ровно 10 → клиент обработал → шлёт `request(10)` дальше. Автоматически. |
| **Маршрутизация** (куда девать сообщение) | Придумываете JSON `type`, пишете `switch/case`, парсите сами. | Есть поле **metadata** — кладете туда маршрут (`"user.getProfile"`, `"metrics.cpu"`). Библиотека сама разбирает и отдаёт нужному хендлеру. |
| **Корреляция запросов** (какой ответ к какому запросу) | Генерите `correlationId`, храните `Map<id, Future>`, матчите ответы вручную. | У каждого логического стрима есть **Stream ID**. Протокол сам сопоставляет запрос и ответ. Вы не думаете об ID. |
| **Мультиплексирование** (несколько потоков в одном коннекте) | Пишете свой фрейминг: заголовки `streamId`, собираете фрагменты, управляете окнами. | Встроено: один коннект = много независимых **логических стримов** (каждый со своим Stream ID, своим `request(n)`, своей жизнью). |
| **Восстановление сессии** (после обрыва связи) | Реконнект → ре-авторизация → ресабскрайб → просите историю → дедуплицируете — всё руками. | **Resume Token**: при обрыве клиент переподключается с токеном + номером последнего кадра → сервер досылает пропущенное → продолжение как будто не было обрыва. |


***

## Каждый термин — простыми словами и аналогией


***

### 1. Backpressure (обратное давление / контроль потока)

**Суть:** Сервер шлёт быстрее, чем клиент успевает читать.

**Аналогия — кран и стакан:**
Вы (клиент) пьете воду через трубочку. Сервер — кран.

- **Без backpressure:** Кран открыт на полную. Вы подавиляетесь, вода льётся мимо — **перегрузка, OOM, краш**.
- **С backpressure (RSocket `request(n)`):** Вы говорите: «Налей мне ровно 100 мл». Выпили — сказали: «Ещё 100 мл». Кран никогда не льёт больше, чем вы просили.

**В коде (Reactor / Spring):**

```java
// RSocket — клиент явно контролирует темп
Flux<Event> events = rSocketClient.requestStream(request)
    .limitRate(10);               // -> шлёт request(n=10)
    .doOnNext(e -> process(e));   // обработал 10 -> автоматически шлёт request(n=10) дальше

// WebSocket — вам нужно самим писать pause/resume, буферизацию, ack'и
webSocketSession.send(Flux.range(1, 1_000_000)
    .map(i -> new TextMessage("event " + i))); // клиент утонет, если не успевает
```


***

### 2. Маршрутизация (Routing)

**Суть:** В одном соединении идут разные типы сообщений. Как понять, куда направить каждое?

**Аналогия — один разговор на несколько тем:**
Вы по телефону обсуждаете: погоду, отчёт по продажам, планирование отпуска — всё вперемешку. Без правил — хаос.

**В WebSocket:** Придумываете формат сами:

```json
{ "type": "chat", "payload": "привет" }
{ "type": "metrics", "payload": { "cpu": 80 } }
{ "type": "command", "id": 42, "action": "restart" }
```

Пишете `switch(type)` на клиенте и сервере.

**В RSocket:** Есть **metadata** — отдельное поле в кадре для маршрута. Обычно строка: `"user.service.getProfile"`, `"metrics.cpu"`, `"chat.room.123"`. Библиотека сама разбирает и отдаёт нужному обработчику.

***

### 3. Корреляция запросов (Correlation ID)

**Суть:** Клиент послал 10 запросов параллельно. Сервер ответил 10 сообщениями. Как клиенту понять, какой ответ к какому запросу?

**Аналогия — конверты без адресатов:**
Вы кидаете в почтовый ящик 10 конвертов с вопросами. Приходят 10 ответов — но на конвертах нет имен. Какой к какому?

**В WebSocket:** Придумываете свой `correlationId` / `requestId`, кладете в JSON, храните `Map<id, CompletableFuture>`, матчите сами.

**В RSocket:** У каждого логического стрима есть **Stream ID** (число). Протокол сам сопоставляет запрос и ответ. Вам не нужно думать об ID.

***

### 4. Мультиплексирование (Multiplexing)

**Суть:** Несколько независимых потоков данных в **одном** TCP/WebSocket-соединении.

**Аналогия — одна труба, разные жидкости:**
Одна водопроводная труба. По ней одновременно текут: горячая вода, холодная вода, отопление, осмотический фильтр — и они не смешиваются, не мешают друг другу.

**В WebSocket:** Одно сообщение = один кадр. Хотите параллельные потоки? Пишете свой мультиплексор: кадр с заголовком `streamId: 1`, `streamId: 2`... Собираете фрагменты, упорядочиваете, управляете окнами каждого стрима.

**В RSocket:** Встроено. Один коннект = много **логических стримов** (каждый со своим Stream ID). Каждый стрим имеет свой `request(n)`, свои данные, свой жизненный цикл. Библиотека делает всё за вас.

**Пример — один коннект между сервисами:**

- Стрим 1: метрики каждую секунду (request-stream)
- Стрим 2: команды управления (request-response)
- Стрим 3: чат-сообщения (channel — двунаправленный)
- Стрим 4: файловый аплоад (fire-and-forget чанками)

Все идут одновременно, не блокируя друг друга.

***

### 5. Восстановление сессии (Session Resumption)

**Суть:** Соединение оборвалось (сеть дрогнула, мобильный переключился Wi-Fi → LTE, деплой сервера). Нужно продолжить с того места, не теряя данных.

**Аналогия — телефонный разговор с перерывом:**
Связь пропала на 5 секунд. Вы перезваниваете и говорите: «Продолжим с фразы "итого 1500 рублей"». Не нужно начинать разговор с начала.

**В WebSocket:** Нет встроенного механизма. При переподключении:

- Пересоздаёте коннект
- Повторно аутентифицируетесь
- Переподписываетесь на топики
- Просите сервер прислать историю / last event ID
- Сопоставляете, что уже было, чего не хватает — **всё руками**

**В RSocket:** Есть **Resume Token**.

1. Клиент и сервер обмениваются токеном при подключении.
2. При обрыве клиент переподключается с этим токеном + номером последнего полученного кадра.
3. Сервер находит сессию, досылает пропущенные кадры, продолжает стримы.
4. Клиент получает **плавное продолжение** — как будто обрыва не было.

***

## Как это выглядит в логах (наглядно)

**WebSocket (ваш код):**

```
→ SEND {"type":"metrics_subscribe","id":1}
→ SEND {"type":"chat_join","room":"general","id":2}
← RECV {"id":1,"data":{"cpu":80}}      // какой это id? сам ищешь в мапе
← RECV {"room":"general","msg":"hi"}   // а этот? парсишь type/room
// обрыв сети
// твоя логика: reconnect -> resubscribe -> запрашивать историю -> дедуплицировать
```

**RSocket (библиотека делает за вас):**

```
→ REQUEST_STREAM(metadata="metrics.cpu", streamId=1) request(10)
→ REQUEST_CHANNEL(metadata="chat.room.general", streamId=3) request(∞)
← NEXT(streamId=1, payload={cpu:80})   // библиотека уже отдала правильному хендлеру
← NEXT(streamId=3, payload="hi")
// обрыв сети
→ RESUME(token="abc123", lastReceived=42)  // одна строчка конфига
← NEXT(streamId=1, payload={cpu:81})       // продолжение без потерь
```

## Четыре модели взаимодействия в RSocket (нет в чистом WebSocket)

| Модель | Описание | Пример |
| :-- | :-- | :-- |
| **Request-Response** | Один запрос → один ответ | `getUserById(id)` |
| **Request-Stream** | Один запрос → стрим ответов | `subscribeToMetrics()` — сервер шлёт метрики, пока клиент не скажет стоп |
| **Fire-and-Forget** | Один запрос → без ответа | `sendLogEntry(log)` — отправил и забыл |
| **Channel (Bi-dir)** | Двунаправленный стрим | Чат, 협업-редактор, игровой стейт |

В WebSocket всё это — вы пишете сами поверх текстовых/бинарных кадров.

***

## Когда что выбирать

### ✅ WebSocket достаточно (проще, нативно в браузере)

- Браузерный чат, уведомления, real-time UI (дашборды, 협업-редакторы)
- Простая пуш-модель: сервер шлёт, клиент показывает
- Нагрузка предсказуемая, backpressure не критичен
- Нужна максимальная совместимость (все браузеры, старые прокси)


### ✅ RSocket выигрывает (реактивная service-to-service архитектура)

- **Стриминг больших объёмов**: сервис А → 1 млн событий → сервис Б (который может быть медленнее). Без backpressure Б упадёт.
- **Долгие реактивные пайплайны**: `Flux`/`Mono` через сеть — `request(n)` пробрасывается сквозь границы сервисов.
- **Мультиплексирование**: один коннект — десятки логических стримов (метрики, логи, команды, квери).
- **Мобильные / нестабильные сети**: сессия восстанавливается после смены сети без переподписки.
- **Polyglot микросервисы**: Java-производитель, Go-потребитель, JS-фронт — общаются на одном протоколе без gRPC/HTTP overhead.

***

## Итог одной фразой

> **WebSocket даёт трубу. RSocket даёт протокол общения внутри трубы: кто сколько пьёт, кто за чем отвечает, как не перепутать разговоры, и как продолжить после обрыва.**
