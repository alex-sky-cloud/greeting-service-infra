
### `cache()`

**Пояснение:**

`cache()` сохраняет результат выполнения источника в памяти приложения (Heap) и повторно отдаёт его новым подписчикам. 
В отличие от `share()`, поздний подписчик получает уже сохранённый результат, а не только события, пришедшие после момента его подключения.

```java
Mono<TariffTable> tariffsMono =
    tariffClient.loadTariffs()
        .cache();

tariffsMono.subscribe(t -> log.info("request-1: {}", t));
tariffsMono.subscribe(t -> log.info("request-2: {}", t));
```

**Плата за использование:**

Главный расходуемый ресурс — **оперативная память JVM (heap)**. 
- После первой успешной загрузки `cache()` удерживает `TariffTable` в памяти вместе со всеми вложенными объектами: списком тарифов, DTO, строками, `BigDecimal` и т. д.

Для `Mono<TariffTable>` в кэше хранится:

- один объект `TariffTable`;
- весь объектный граф, на который он ссылается;
- небольшой служебный объект Reactor с сигналом успешного завершения или ошибкой.

То есть приблизительно:

$$
\text{Память кэша} \approx \text{размер TariffTable со всеми вложенными объектами}
$$

Например, если таблица тарифов занимает в heap около 5 МБ, то один `Mono.cache()` будет удерживать примерно эти 5 МБ, пока кэш не истечёт или `Mono` не станет недостижимым для GC.

**Источник:** https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html

> “Turn this Mono into a hot source and cache last emitted signals for further Subscriber.”

Ru:

> «Превращает этот `Mono` в горячий источник и кэширует последние отправленные сигналы для последующих подписчиков».

***

**Сколько данных хранится:**

В данном примере используется `Mono`, поэтому кэшируется **один результат**: один `TariffTable`.

```java
Mono<TariffTable> tariffsMono =
    tariffClient.loadTariffs()
        .cache();
```

Это не универсальный кэш с ключами. Если нужно хранить отдельные тарифы для разных городов, типов доставки или клиентов, `Mono.cache()` сам по себе не создаст записи вида:

```text
cityId -> TariffTable
```

Для такого сценария нужен отдельный key-based кэш, например Caffeine, Redis, Spring Cache или `Map` с контролируемой очисткой.

***

**Сколько времени хранится:**

Вариант без параметров:

```java
.cache()
```

хранит результат **до тех пор, пока существует ссылка на этот `Mono`**. 
 - Если `tariffsMono` находится в singleton Spring-bean, таблица тарифов может оставаться в памяти (Heap java) до остановки приложения.

Чтобы ограничить время хранения, нужно указать TTL:

```java
Mono<TariffTable> tariffsMono =
    tariffClient.loadTariffs()
        .cache(Duration.ofMinutes(30));
```

После истечения 30 минут следующий подписчик запустит новый вызов `loadTariffs()`, а в кэш попадёт новое значение.

**Источник:** https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html

> “Turn this Mono into a hot source and cache last emitted signals for further Subscriber, with an expiry timeout.”

Ru:

> «Превращает этот `Mono` в горячий источник, кэширует последние сигналы для последующих подписчиков и задаёт время их истечения».

***

**Расход ресурсов:**


| Ресурс | Что расходуется |
| :-- | :-- |
| Heap | Размер `TariffTable` и всех вложенных объектов |
| CPU при cache hit | Минимально: Reactor берёт сохранённый результат и отправляет его подписчику |
| CPU при первом вызове | Полная стоимость загрузки: сеть, ожидание удалённой системы, десериализация и создание DTO |
| Сеть | Не расходуется при повторных подписках до истечения кэша |
| GC | Чем больше и дольше удерживается `TariffTable`, тем больше долгоживущих объектов должен обслуживать GC |
| Disk | Не используется: `Mono.cache()` хранит данные только в памяти процесса |
| Память между pod/JVM | Не общая: каждый экземпляр приложения хранит собственную копию кэша |

**Итог:**

Для `Mono<TariffTable>` `cache()` — это обмен памяти на снижение сетевой и CPU-нагрузки. Он держит в heap одну загруженную таблицу тарифов; без TTL — потенциально до завершения приложения, с `cache(Duration)` — в пределах заданного времени.

Да: второй подписчик получает старые метрики **не из стека первого подписчика**. Он получает их через объект `Flux`, содержащий `cache`, который сам и его накопленные данные всё ещё доступны в **heap**.

## Откуда второй подписчик возьмёт данные

Представь, что cached publisher сохранён в поле singleton-bean:

```java
class MetricsService {
    private final Flux<Metric> metrics = source.cache();
}
```

Цепочка ссылок выглядит так:

```text
Spring singleton / MetricsService (heap)
        ↓
Flux с оператором cache (heap)
        ↓
внутренний буфер cache (heap)
        ↓
Metric #1, Metric #2, ... (heap)
```

Когда через час вызывается:

```java
metrics.subscribe(...)
```

во время выполнения метода `subscribe()` в **стеке нового потока** действительно появляется временная локальная ссылка на `metrics`.

Но дальше она указывает на уже существующий объект `Flux cache` в **heap**. Он и отдаёт ранее накопленные `Metric`.

То есть:

- Stack нового вызова `subscribe()` содержит временную ссылку на `Flux`.
- `Flux cache` в heap уже содержит ссылки на накопленные метрики.
- Старый stack первого подписчика уже неважен: его frame завершился и уничтожен.
- Кэш существует, пока на cached `Flux` есть достижимая сильная ссылка — например, из поля bean-а.

JVM Spec: frame создаётся на вызов метода и уничтожается после его завершения; heap, напротив, общий для потоков и выделяет память под экземпляры объектов и массивы.[^1]

## Про скорость stack и heap

Да, stack обычно воспринимают как более простой и дешёвый по управлению механизм: frame добавляется/удаляется вместе с вызовом метода.

Но здесь нельзя «положить cache в stack», потому что stack-frame должен исчезнуть после завершения вызова, а кэш должен прожить час и быть доступным другому подписчику — возможно, вообще на другом потоке.

Поэтому долгоживущие данные обязаны быть достижимы через heap-объекты.

## Бесконечный `cache()`

Да, именно так: этот код опасен для бесконечного источника:

```java
Flux<Metric> cached = infiniteMetricsSource.cache();
```

`Flux.cache()` без параметров удерживает **неограниченное число** `onNext`-сигналов. Это прямо написано в официальном Javadoc Reactor:

> “Will retain an unbounded volume of onNext signals.”[^2]

Следствие: если source продолжает генерировать уникальные объекты, а `cached` остаётся достижим, heap будет расти. В какой-то момент JVM не сможет выделить очередной объект — получите `OutOfMemoryError: Java heap space`.

GC тут не спасёт: метрики достижимы по цепочке `bean → Flux cache → buffer → Metric`, значит они не являются мусором.

## Как делают обычно

### 1. Хранить только последние N метрик

```java
Flux<Metric> cached = source.cache(1_000);
```

Поздний подписчик получит максимум последние 1 000 метрик, затем live-поток. Reactor подтверждает: `cache(int history)` хранит до `history` сигналов `onNext`.[^2]

### 2. Хранить историю только за период

```java
Flux<Metric> cached = source.cache(Duration.ofHours(1));
```

Но важно: этот overload ограничивает время жизни элементов, **не число элементов**. Если частота метрик очень высока, за час может накопиться много объектов. Javadoc: `cache(Duration)` сохраняет неограниченную историю, но задаёт индивидуальный TTL для элемента.[^2]

### 3. Ограничить и размер, и время

```java
Flux<Metric> cached =
    source.cache(10_000, Duration.ofHours(1));
```

Это наиболее безопасная форма для вашей задачи: поздний подписчик увидит историю не старше часа, но не более 10 000 последних метрик.

## Главное правило

Для бесконечного source никогда не используйте голый `cache()` без осознанной причины. Используйте `cache(history, ttl)` либо храните историю во внешнем/ограниченном хранилище — БД, Redis, time-series DB — если часовая история может быть большой или должна переживать перезапуск JVM.
