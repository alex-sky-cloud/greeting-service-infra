## Zip — когда без одной детали ответ бессмысленен

**Кейс**: 
 - бронирование авиабилета. 
 - Пользователь выбрал рейс, и приложению нужно показать финальную цену в рублях. 
 - Для этого нужны **два независимых** ответа:
   - цена билета в долларах от сервиса авиакомпании и текущий курс доллара от банковского сервиса. 
   - Показать цену без курса нельзя — число будет неверным, поэтому приложение обязано подождать оба ответа и только потом посчитать итог.

```java
Mono.zip(
    flightService.getPrice(flightId),      // например, вернёт 350 (USD)
    currencyService.getRate("USD"),        // например, вернёт 92.5 (курс к рублю)
    (price, rate) -> price.multiply(rate)  // получаем 350 * 92.5 = итоговая цена в рублях
);
```

Если сервис курса валют не ответит вовремя — цена билета, даже если она давно получена, будет "висеть" без применения, потому что `zip` не отдаст результат, пока не придут обе части.

- Источник: https://blog.vinsguru.com/reactive-programming-reactor-combining-multiple-sources-of-flux-mono/

EN:

> "Zip will work as long as both sources emit data. Any of the sources completes/throws error, it will stop."

**RU**:

> "Zip работает, пока оба источника выдают данные. 
> 
> Если один из источников завершится или выдаст ошибку — обработка останавливается."

## mergeWith — когда важна скорость, а не порядок

Кейс: 
 - онлайн-чат поддержки, у которого на фронтенде есть только **одно** окно с лентой сообщений и **одно** подключение к серверу (например, WebSocket-сессия). На backend есть два раздельных потока событий: сообщения, которые печатает клиент, и сообщения, которые печатает оператор — они возникают в разное время и никак не связаны друг с другом.

Проблема в том, что в это единственное окно чата нужно отправлять сообщения **из обоих потоков сразу**, причём в реальном порядке появления — если бы вы обрабатывали потоки раздельно (два отдельных `.subscribe()`), пришлось бы дублировать логику отправки в сокет два раза и следить, чтобы оба подписчика не писали в один сокет одновременно и не создавали гонку (race condition). `mergeWith` решает это одним вызовом: он берёт поток, на котором его вызвали (`clientMessages`), добавляет к нему второй поток из аргумента (`operatorMessages`) и превращает их в один результирующий поток, на который достаточно подписаться один раз.

```java
// на входе два раздельных потока: клиент печатает — operatorMessages молчит, и наоборот
Flux<ChatMessage> chatFeed = clientMessages.mergeWith(operatorMessages);

// подписка происходит один раз, а не два — на объединённый результат
chatFeed.subscribe(message -> webSocketSession.send(message.toJson()));
```

Пример по времени: клиент написал в 12:00:01, оператор ответил в 12:00:03, клиент написал снова в 12:00:04 — все три сообщения уйдут в `webSocketSession` именно в этом порядке появления, как в реальном разговоре, а не сгруппированными парами, как это было бы в `zip`.

- Источник: https://stackoverflow.com/questions/48478420/spring-reactor-merge-vs-concat

EN:

> "The essential difference between merge and concat is that in merge, both streams are live... all variations of merge subscribe to the publishers eagerly."

RU:

> "Ключевое отличие merge от concat в том, что в merge оба потока живые одновременно... все варианты merge подписываются на источники сразу и одновременно."

## concatWith — когда порядок критичен

Кейс: обработка банковского платежа. Перед тем как списать деньги со счёта, система обязана сначала полностью завершить проверку баланса (достаточно ли средств), и только после успешного завершения этой проверки — запустить сам процесс списания. Эти два шага нельзя выполнять одновременно: если списание начнётся до того, как проверка баланса закончилась, банк может списать деньги, которых на счету уже не было.

Если бы здесь использовали `mergeWith`, оба потока — проверка баланса и списание — подписались бы одновременно, и списание могло бы выполниться параллельно с проверкой, а не после неё. Именно поэтому нужен `concatWith`: он гарантирует, что второй поток даже не начнёт подписку, пока первый не отработает полностью и не завершится.

```java
// balanceCheck — поток, который проверяет остаток на счету и завершается
// chargeTransaction — поток списания, начинается только после завершения balanceCheck
balanceCheck.concatWith(chargeTransaction);
```

То есть сначала система дождётся ответа "баланс достаточен, проверка завершена", и только в этот момент запустит списание — списание физически не может начаться раньше.

- Источник: https://www.baeldung.com/reactor-combine-streams

EN:

> "The concatenation is achieved by sequentially subscribing to the first source then waiting for it to complete before subscribing to the next."

RU:

> "Конкатенация достигается последовательной подпиской: сначала подписываемся на первый источник, ждём его завершения, потом подписываемся на следующий."

## Как выбрать на практике

Берите `zip`, когда данные из разных источников бессмысленны сами по себе и должны быть "сшиты" в один результат — как цена билета без курса валюты. Берите `mergeWith`, когда нужно объединить два независимых потока в один канал для общей обработки или отправки, и важна скорость, а не порядок — как сообщения клиента и оператора в одном окне чата. Берите `concatWith`, когда критичен строгий порядок выполнения шагов, даже если это добавляет задержку — как проверка баланса перед списанием денег.
