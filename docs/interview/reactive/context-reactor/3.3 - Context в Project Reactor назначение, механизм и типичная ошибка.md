## 1. Что такое Context

`Context` — неизменяемое (immutable) key-value хранилище, привязанное к конкретной подписке (`Subscriber`), которое передаётся вдоль цепочки операторов вместе с сигналом подписки. Он не зависит ни от потока выполнения, ни от сетевого слоя (Netty, EventLoop, TCP-соединение) — это чистый механизм Reactor Core, работающий даже без единого HTTP-запроса.

## 2. Почему ThreadLocal не подходит

В реактивной цепочке выполнение может переключаться между потоками через `subscribeOn`/`publishOn`. Данные, записанные в `ThreadLocal` на одном потоке, не видны после переключения на другой поток — значения будут потеряны или перепутаны между параллельными запросами, использующими общий пул потоков.

## 3. Как Context на самом деле путешествует по цепочке

Источник: https://projectreactor.io/docs/core/release/reference/advancedFeatures/context.html

**EN:**
```
the Context is propagated from the bottom of the chain towards the top... its
content can only be seen by operators above it.
```

**RU:**
```
Context распространяется от низа цепочки к верху... его содержимое видно
только операторам, находящимся выше него.
```

Ключевая деталь: `contextWrite()` физически размещается ближе к `subscribe()` (то есть к даунстрим-концу, ближе к подписчику), но записанное значение становится видимым операторам, находящимся **выше** него по цепочке — то есть ближе к источнику (апстриму). Это происходит потому, что сигнал подписки идёт от `subscribe()` вверх к источнику, и именно во время этого прохода собирается итоговый `Context`.

Источник: https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html

**EN:**
```
this operator should generally be used as close as possible to the end of
the chain / subscription point.
```

**RU:**
```
этот оператор обычно следует использовать как можно ближе к концу цепочки
или к точке подписки.
```

```
Источник → repository → deferContextual → flatMap → contextWrite() → subscribe()
   ↑           ↑              ↑              ↑            │
 видит       видит          видит          видит      записывает
```

Практическая аналогия: если метод контроллера — это условный "подписчик" (даунстрим), а вызов репозитория — это "источник" (апстрим), то `contextWrite()` физически пишется в коде ниже вызова репозитория, то есть ближе к `subscribe()`/возврату из контроллера. Но именно поэтому репозиторий, находясь выше по цепочке относительно места записи, и получает доступ к записанному значению.

## 4. Неправильный пример: contextWrite() ближе к источнику

```java
Mono.just("start")
    .contextWrite(ctx -> ctx.put("userId", "u-123"))
    // ОШИБКА: contextWrite() стоит В НАЧАЛЕ цепочки, ближе к источнику.
    // Всё, что находится НИЖЕ него (Mono.deferContextual внутри flatMap, сам flatMap),
    // физически располагается ближе к subscribe() и по правилу "видно только выше"
    // не может увидеть записанное значение — оно осталось "над" ними.
    // Примечание: deferContextual — статический фабричный метод Mono, а не метод
    // экземпляра, поэтому его нельзя вызвать через точку после .contextWrite(...);
    // он оборачивается внутрь flatMap, как показано ниже.
    .flatMap(start -> Mono.deferContextual(ctx -> {
        // Пытаемся прочитать userId, но контекст записан ВЫШЕ этой точки,
        // а не ниже — поэтому он здесь недоступен
        String userId = ctx.getOrDefault("userId", "unknown");
        return Mono.just("Order for user: " + userId);
    }))
    .flatMap(result -> {
        System.out.println(result); // ВЫВЕДЕТ: "Order for user: unknown"
        return Mono.just(result);
    })
    .subscribe();
```

## 5. Правильный пример: contextWrite() ближе к subscribe()

`contextWrite()` физически всегда должен идти после (снизу) тех операторов, которые должны видеть записанное значение — то есть ближе к `subscribe()`, а не в начале цепочки, как многие интуитивно ожидают.

```java
Mono.deferContextual(ctx -> {
        // Правильно: на этом этапе userId УЖЕ доступен, потому что contextWrite()
        // расположен НИЖЕ (ближе к subscribe()), а Context виден всем операторам ВЫШЕ него.
        String userId = ctx.getOrDefault("userId", "unknown");
        return Mono.just("Order for user: " + userId);
    })
    .flatMap(result -> {
        System.out.println(result); // ВЫВЕДЕТ: "Order for user: u-123"
        return Mono.just(result);
    })
    .contextWrite(ctx -> ctx.put("userId", "u-123")) // запись контекста — ближе к subscribe()
    .subscribe();
```

## 6. Чтение контекста

Есть два основных способа прочитать `Context` внутри цепочки:

```java
// Способ 1: deferContextual — читаем контекст лениво, в момент подписки
Mono<String> withContext = Mono.deferContextual(ctx ->
    Mono.just("userId = " + ctx.getOrDefault("userId", "n/a"))
);

// Способ 2: transformDeferredContextual — доступ к контексту вместе с исходным Mono/Flux
Mono<String> transformed = Mono.just("payload")
    .transformDeferredContextual((mono, ctx) ->
        mono.map(payload -> payload + " for user " + ctx.get("userId"))
    );

// Итоговая подписка с записью значения в контекст
withContext
    .contextWrite(ctx -> ctx.put("userId", "u-123"))
    .subscribe(System.out::println); // userId = u-123
```
