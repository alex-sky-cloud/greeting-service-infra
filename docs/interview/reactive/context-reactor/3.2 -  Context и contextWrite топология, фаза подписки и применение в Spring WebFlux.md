<a id="topologiya"></a>
## Топология цепочки: данные текут downstream

В Reactive Streams **upstream/downstream** описывает положение компонентов в графе и направление сигналов данных. Источник `Mono.just("invoice-42")` находится upstream; конечный `Subscriber` — downstream. `contextWrite` в данной записи расположен ниже `flatMap` и ближе к конечному `subscribe()`, поэтому топологически он downstream относительно `flatMap` и `Mono.just`.

```java
Mono<String> invoiceMono =
    Mono.just("invoice-42")                         // (1) источник: upstream
        .flatMap(id -> Mono.deferContextual(          // (2) оператор преобразования
            ctx -> Mono.just(ctx.get("traceId") + ": " + id)
        ))
        .contextWrite(ctx -> ctx.put("traceId", "T-1")); // (3) downstream-оператор

invoiceMono.subscribe(System.out::println);          // (4) конечный Subscriber: downstream
```

Сигналы данных в этой цепочке направлены так:

```text
Mono.just("invoice-42") → flatMap(...) → contextWrite(...) → Subscriber
       upstream                                                    downstream
```

Значит, `contextWrite` — не источник данных и не становится upstream из-за того, что выполняется раньше источника во время подписки. Его позиция в графе определяется направлением данных, а не хронологическим порядком вызовов.

https://projectreactor.io/docs/core/release/reference/advancedFeatures/context.html

**EN:**
> In order to populate the Context, which can only be done at subscription time, you need to use the contextWrite operator. contextWrite(ContextView) merges the ContextView you provide and the Context from downstream (remember, the Context is propagated from the bottom of the chain towards the top).

**RU:**
> Чтобы заполнить Context, что можно сделать только во время подписки, нужно использовать оператор contextWrite. contextWrite(ContextView) объединяет предоставленный ContextView и Context, пришедший от downstream (напомним, Context распространяется от низа цепочки к верху).

<a id="faza-podpiski"></a>
## Фаза подписки: subscribe идёт upstream

Нужно различать топологию цепочки и порядок действий во времени. Вызов `invoiceMono.subscribe(...)` запускает **фазу построения подписки**. Она распространяется в направлении, обратном данным: от downstream к upstream.

Порядок для учебного примера:

1. Конечный `Subscriber` создаётся вызовом `invoiceMono.subscribe(...)`.
2. Внешний оператор `contextWrite` первым получает внутренний вызов `subscribe`.
3. `contextWrite` берёт Context, видимый со стороны downstream (для этого примера первоначально пустой), создаёт новый неизменяемый Context с `traceId = "T-1"` и передаёт обновлённый Context дальше upstream.
4. Подписка доходит до `flatMap`, затем до `Mono.just("invoice-42")`.
5. Только после того как источник получил подписку, он может начать посылать сигналы данных вниз по цепочке.

```text
Фаза подписки и распространение Context:

Subscriber.subscribe()
        │
        ▼
contextWrite: Context.empty() → Context{traceId=T-1}
        │
        ▼
flatMap
        │
        ▼
Mono.just("invoice-42")
```

Итак, утверждение «`contextWrite` выполняется первым» верно **только для фазы подписки**. Оно не означает, что `contextWrite` является upstream-источником. Он остаётся downstream-оператором по отношению к потоку данных.

https://projectreactor.io/docs/core/release/reference/advancedFeatures/context.html

**EN:**
> Actually, a Context is tied to each Subscriber in a chain. It uses the Subscription propagation mechanism to make itself available to each operator, starting with the final subscribe and moving up the chain.

**RU:**
> На самом деле, Context привязан к каждому Subscriber в цепочке. Он использует механизм распространения Subscription, чтобы стать доступным каждому оператору, начиная с финального subscribe() и двигаясь вверх по цепочке.

<a id="chtenie-context"></a>
## Когда фактически читается Context

После завершения фазы подписки начинается эмиссия. Теперь сигналы `onNext`, `onComplete` и `onError` идут в обычном направлении: от источника к конечному подписчику.

```text
Фаза эмиссии данных:

Mono.just("invoice-42")
        │ onNext("invoice-42")
        ▼
flatMap
        │ создаёт и подписывается на inner Mono.deferContextual(...)
        ▼
contextWrite
        │
        ▼
Subscriber получает "T-1: invoice-42"
```

Важно: `flatMap` **не читает** `traceId` в момент, когда сигнал подписки проходит через него. Внешний `flatMap` получает значение `"invoice-42"` во время `onNext`. Лишь тогда он вызывает mapper, создающий inner Publisher `Mono.deferContextual(...)`. При подписке на этот inner Publisher `deferContextual` получает уже сформированный `ContextView` и читает `traceId`.

```java
Mono<String> invoiceMono =
    Mono.just("invoice-42")
        // Mono.just эмитит "invoice-42" после завершения фазы подписки
        .flatMap(id -> Mono.deferContextual(ctx ->
            // deferContextual читает Context при подписке на inner Mono;
            // к этому времени Context уже содержит traceId, добавленный ниже
            Mono.just(ctx.get("traceId") + ": " + id)
        ))
        .contextWrite(ctx -> ctx.put("traceId", "T-1"));
        // contextWrite создаёт Context до начала эмиссии Mono.just

invoiceMono.subscribe(System.out::println);
// Вывод: T-1: invoice-42
```

**Вывод:** правильная хронология такова: сначала формируется цепочка подписки и Context; затем `Mono.just` эмитит `invoice-42`; после этого `flatMap` создаёт inner Publisher; и только затем `deferContextual` читает `traceId`.

<a id="vnutrennie-subscribe"></a>
## Как операторы вызывают subscribe

Фраза «`flatMap` вызывает `subscribe`» буквальна, хотя это происходит во внутренней реализации Reactor, а не в пользовательском лямбда-коде. `Mono` и `Flux` — реализации Reactive Streams `Publisher`, а операторы строят Publisher-обёртки вокруг своих upstream-источников. Каждый оператор получает downstream `Subscriber`, при необходимости оборачивает его собственным внутренним `Subscriber` и подписывает его на upstream.

https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html

**EN:**
> public abstract void subscribe(CoreSubscriber<? super T> actual) — An internal Publisher.subscribe(Subscriber) that will bypass Hooks.onLastOperator(Function) pointcut.

**RU:**
> public abstract void subscribe(CoreSubscriber<? super T> actual) — внутренний метод Publisher.subscribe(Subscriber), который используется в обход хука Hooks.onLastOperator(Function).

Ниже — концептуальный, а не компилируемый псевдокод механики:

```java
// Пользователь вызывает subscribe на внешнем Mono — результате contextWrite.
contextWriteOperator.subscribe(actualSubscriber);

// contextWrite создаёт Subscriber с изменённым currentContext()
// и передаёт его upstream-оператору.
flatMapOperator.subscribe(contextWriteSubscriber);

// flatMap создаёт свой внутренний Subscriber и передаёт его источнику.
monoJust.subscribe(flatMapSubscriber);

// Только теперь источник может вызвать flatMapSubscriber.onNext("invoice-42").
```

Когда `flatMap` уже получил `onNext("invoice-42")`, он применяет mapper и подписывается на Publisher, возвращённый mapper-ом. В примере это inner `Mono.deferContextual(...)`. Поэтому `flatMap` потенциально выполняет две роли: участвует в подписке на свой upstream и, получив элемент, организует подписку на inner Publisher.

<a id="pravilo-contextwrite"></a>
## Правило расположения contextWrite

`Context` неизменяем. Каждый `contextWrite` создаёт производный Context для своей upstream-части цепочки; он не мутирует глобальное хранилище и не меняет Context других подписок.

Правило расположения: ставьте `contextWrite` **ниже тех операторов, которые должны прочитать значение**, то есть максимально близко к концу реактивной цепочки и к точке `subscribe()`. Важно понимать смысл правила: речь о близости к подписчику, а не о близости к источнику.

https://projectreactor.io/docs/core/release/reference/advancedFeatures/context.html

**EN:**
> Context is propagated from the bottom of the chain towards the top, so the general rule is to put contextWrite as close as possible to the end of the reactive chain (as close as possible to the subscribe() call).

**RU:**
> Context распространяется от низа цепочки к верху, поэтому общее правило — располагать contextWrite как можно ближе к концу реактивной цепочки (как можно ближе к вызову subscribe()).

```java
// НЕПРАВИЛЬНО: запись находится выше чтения.
Mono<String> wrong = Mono.just("invoice-42")
    .contextWrite(ctx -> ctx.put("traceId", "T-1"))
    // Значение видно только upstream-операторам, а этот flatMap расположен ниже записи.
    .flatMap(id -> Mono.deferContextual(ctx ->
        Mono.just(ctx.getOrDefault("traceId", "MISSING") + ": " + id)
    ));

// Результат: MISSING: invoice-42

// ПРАВИЛЬНО: запись ниже чтения и ближе к subscribe().
Mono<String> correct = Mono.just("invoice-42")
    .flatMap(id -> Mono.deferContextual(ctx ->
        Mono.just(ctx.getOrDefault("traceId", "MISSING") + ": " + id)
    ))
    .contextWrite(ctx -> ctx.put("traceId", "T-1"));

// Результат: T-1: invoice-42
```

**Вывод:** не стоит интерпретировать `contextWrite` как обычную команду, которая исполняется при сборке цепочки сверху вниз. При assembly-фазе он лишь создаёт объект оператора. Фактическое создание Context происходит позднее, при подписке.

<a id="webflux-subscribe"></a>
## Spring WebFlux: где находится настоящая подписка

В Spring WebFlux входящий HTTP-запрос не является `Subscriber` в смысле Reactive Streams и сам не вызывает пользовательский `.subscribe()`. Он запускает серверную обработку: HTTP-адаптер вызывает обработчик и получает от него `Mono<Void>`, представляющий обработку всего запроса и запись HTTP-ответа. На этот итоговый Publisher подписывается инфраструктура сервера.

Упрощённая структура выглядит так:

```text
Reactor Netty получает HTTP-запрос
        │
        ▼
Spring HttpHandler.handle(request, response) возвращает Mono<Void>
        │
        ▼
WebFilter #1 → WebFilter #2 → DispatcherHandler → controller/handler
        │
        ▼
Итоговый Mono<Void> подписывается инфраструктурой HTTP-сервера
```

Пользовательский `WebFilter` не является конечным `Subscriber`. Он возвращает `Mono<Void>`, обычно полученный от `chain.filter(exchange)`, и оборачивает его. Поэтому именно `WebFilter` — естественная граница приложения для установки данных запроса в Reactor Context.

https://docs.spring.io/spring-framework/reference/web/webflux-webclient/client-context.html

**EN:**
> The Reactor Context needs to be populated at the end of a reactive chain in order to apply to all operations.

**RU:**
> Reactor Context нужно заполнять в конце реактивной цепочки, чтобы он применился ко всем операциям.

```java
@Component
final class TraceIdWebFilter implements WebFilter {

    private static final String TRACE_ID = "traceId";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, WebFilterChain chain) {
        String incomingTraceId = exchange.getRequest()
            .getHeaders()
            .getFirst("X-Trace-Id");

        String traceId = incomingTraceId != null
            ? incomingTraceId
            : UUID.randomUUID().toString();

        return chain.filter(exchange)
            // chain.filter(exchange) возвращает Mono<Void> всей оставшейся цепочки:
            // последующие WebFilter, DispatcherHandler и controller.
            .contextWrite(ctx -> ctx.put(TRACE_ID, traceId));
            // contextWrite оборачивает эту цепочку и добавляет traceId во время
            // будущей серверной подписки. Поэтому traceId доступен всем операторам
            // upstream, то есть внутри обработчиков запроса.
    }
}
```

Когда инфраструктура WebFlux подписывается на итоговый `Mono<Void>`, subscription-сигнал сначала проходит через `contextWrite` фильтра. Затем Context с `traceId` становится доступным в оставшейся цепочке: в контроллере, сервисе, R2DBC-вызове, `WebClient`-фильтре и других операторах, которые читают его через `deferContextual` или `transformDeferredContextual`.

Не следует писать `.subscribe()` внутри `WebFilter`, контроллера или сервиса ради запуска обработки: это создаёт отдельную, неконтролируемую подписку и отделяет её от жизненного цикла HTTP-ответа, обработки ошибок, cancellation и Context исходного запроса. В типичном WebFlux-коде приложение возвращает `Mono`/`Flux`, а подписку осуществляет фреймворк.

<a id="biznes-primer"></a>
## Бизнес-пример: traceId для счёта

Представим API биллингового сервиса `GET /invoices/{id}`. Запрос проходит через `TraceIdWebFilter`; затем контроллер вызывает R2DBC-репозиторий и сервис конвертации валют через `WebClient`. Требование: все логи и исходящий HTTP-запрос должны содержать один и тот же `traceId`, даже если выполнение переключится между потоками Netty, пулом R2DBC и scheduler-ами Reactor.

```java
@RestController
final class InvoiceController {

    @GetMapping("/invoices/{id}")
    Mono<InvoiceResponse> getInvoice(@PathVariable UUID id) {
        return invoiceRepository.findById(id)
            // findById возвращает Mono<Invoice>: запрос будет выполнен только
            // после серверной подписки; метод не получает traceId параметром.
            .flatMap(invoice -> currencyClient.convert(invoice.amount(), invoice.currency())
                // convert возвращает Mono<Money>; это асинхронный HTTP-вызов.
                .flatMap(convertedAmount -> Mono.deferContextual(ctx -> {
                    // Context читается, когда inner Mono будет подписан.
                    // traceId добавлен ниже — в WebFilter — до начала эмиссии данных.
                    String traceId = ctx.get("traceId");

                    log.info("traceId={}, invoiceId={}, convertedAmount={}",
                        traceId, invoice.id(), convertedAmount);

                    return Mono.just(new InvoiceResponse(
                        invoice.id(),
                        convertedAmount, traceId
                    ));
                }))
            );
            // В контроллере subscribe() не вызывается: Mono возвращается WebFlux.
    }
}
```

**Как это работает в запросе:**

1. `TraceIdWebFilter` извлекает `X-Trace-Id` либо создаёт новый идентификатор и возвращает `chain.filter(exchange).contextWrite(...)`.
2. Инфраструктура HTTP-сервера подписывается на итоговый `Mono<Void>` обработки запроса.
3. Во время фазы подписки `contextWrite` фильтра добавляет `traceId` и передаёт обновлённый Context upstream — к маршрутизации, контроллеру и пользовательской реактивной цепочке.
4. Репозиторий получает счёт, `flatMap` запускает `currencyClient.convert`, а `deferContextual` читает уже установленный `traceId` при подписке на свой inner Publisher.
5. Данные и итоговый HTTP-ответ идут downstream; `traceId` остаётся привязанным к одной подписке, а не к конкретному Thread.

**Итог:** `WebFilter` — правильное место прикладного уровня для начального `contextWrite`, потому что он оборачивает весь последующий request-processing chain. Самый нижний `.subscribe()` скрыт в серверной инфраструктуре; его не нужно и не следует вызывать вручную в прикладном коде.
