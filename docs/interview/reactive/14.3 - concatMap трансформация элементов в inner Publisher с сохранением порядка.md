<a name="chto-oznachaet-concatmap"></a>
## Что означает concatMap

`concatMap` трансформирует каждый элемент внешнего `Flux` в inner Publisher через функцию-маппер, а затем объединяет все inner Publisher'ы в единый выходной поток строго последовательно, сохраняя порядок элементов.

https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html

**EN:**
> `concatMap(Function<? super T,? extends Publisher<? extends V>> mapper)` — Transform the elements emitted by this Flux asynchronously into Publishers, then flatten these inner publishers into a single Flux, sequentially and preserving order using concatenation.

**RU:**
> `concatMap(Function<? super T,? extends Publisher<? extends V>> mapper)` — асинхронно трансформирует элементы, испускаемые данным Flux, в Publisher'ы, затем разворачивает эти внутренние (inner) publisher'ы в единый Flux последовательно и с сохранением порядка, используя конкатенацию.

---

<a name="moment-sozdaniya-inner-publisher"></a>
## Момент создания inner Publisher

В отличие от `Flux.concat(Publisher<Publisher<T>>, prefetch)`, где внешний источник уже эмитит готовые Publisher'ы, в `concatMap` внешний Flux эмитит обычные значения (например, ID пользователя), и inner Publisher создаётся динамически в момент вызова функции-маппера — до этого никакого готового Publisher не существует.

https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html

**EN:**
> `concatMap(Function<? super T,? extends Publisher<? extends V>> mapper, int prefetch)` — Transform the elements emitted by this Flux asynchronously into Publishers, then flatten these inner publishers into a single Flux, sequentially and preserving order using concatenation.

**RU:**
> `concatMap(Function<? super T,? extends Publisher<? extends V>> mapper, int prefetch)` — асинхронно трансформирует элементы, испускаемые данным Flux, в Publisher'ы, затем разворачивает эти внутренние publisher'ы в единый Flux последовательно и с сохранением порядка, используя конкатенацию.

<a name="kto-iniciiruet-perehod"></a>
## Кто инициирует переход к следующему элементу

Переход к следующему элементу внешнего источника инициирует не downstream-сабскрайбер, а сигнал `onComplete` от текущего активного inner Publisher: только после его получения оператор запрашивает следующий элемент у внешнего Flux и оборачивает его в новый inner Publisher.

https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html

**EN:**
> `doOnComplete(Runnable onComplete)` — Add behavior (side-effect) triggered when the Flux completes successfully.

**RU:**
> `doOnComplete(Runnable onComplete)` — добавляет побочный эффект (behavior), который срабатывает, когда Flux успешно завершается сигналом onComplete.

<a name="otlichie-ot-flatmap"></a>
## Отличие от flatMap

`flatMap` подписывается на несколько inner Publisher'ов одновременно (параллельно), позволяя элементам из разных источников чередоваться в выходном потоке, тогда как `concatMap` держит активным только один inner Publisher за раз, строго сохраняя порядок группировки.

https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html

**EN:**
> `flatMap(Function<? super T,? extends Publisher<? extends R>> mapper)` — Transform the elements emitted by this Flux asynchronously into Publishers, then flatten these inner publishers into a single Flux through merging, which allow them to interleave.

**RU:**
> `flatMap(Function<? super T,? extends Publisher<? extends R>> mapper)` — асинхронно трансформирует элементы, испускаемые данным Flux, в Publisher'ы, затем разворачивает эти внутренние publisher'ы в единый Flux через слияние (merging), что допускает их чередование.

<a name="biznes-primer"></a>
## Бизнес-пример: заказы пользователей

Представим сервис аналитики заказов: внешний `Flux<Long> userIds` эмитит ID пользователей одного за другим, а `concatMap(userId -> orderRepository.findOrdersByUserId(userId))` для каждого ID создаёт inner Publisher — реактивный запрос к базе через R2DBC, возвращающий все заказы конкретного пользователя. Пока запрос для пользователя №1 не вернёт `onComplete` (то есть все его 10 заказов не будут получены), `concatMap` не начнёт запрос для пользователя №2 — на выходе получается строго упорядоченный поток: сначала все заказы пользователя №1, затем пользователя №2, и так далее, без перемешивания между пользователями. Это критично, например, для построения последовательного отчёта или экспорта в CSV, где нарушение порядка групп привело бы к некорректному документу.
