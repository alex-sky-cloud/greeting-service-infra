## 1. Разделение потока на rails: parallel()

`parallel()` делит исходный `Flux` на N независимых подпотоков — "rails" (по умолчанию N = количество ядер CPU). Само по себе разделение на rails **не** даёт параллельного выполнения — это просто логическая группировка элементов round-robin способом, без назначения потоков выполнения.

```java
Flux.range(1, 100).parallel(4); // 4 rails, но пока без потоков
```

## 2. Назначение потоков: runOn()

`runOn(Scheduler)` — вот тот оператор, который реально даёт параллелизм: каждой rail назначается свой воркер-поток из указанного `Scheduler`. Только после этого вызова элементы из разных rails действительно обрабатываются одновременно, на разных потоках.

```java
Flux.range(1, 100)
    .parallel(4)
    .runOn(Schedulers.parallel());
```

## 3. Возврат в обычный Flux: sequential()

После обработки данных на rails их нужно слить обратно в единый `Flux` — для этого используется `sequential()`. Важно: `sequential()` **не гарантирует** сохранение исходного порядка элементов, так как rails работают параллельно с разной скоростью; порядок будет округлённо round-robin, но не строго исходный. Если порядок важен — нужен `flatMapSequential` или ручная буферизация с сортировкой.

## 4. Альтернатива: publishOn(Schedulers.parallel())

Можно применить `publishOn(Schedulers.parallel())` напрямую к обычному `Flux`, без `parallel()`/`runOn()`:

```java
Flux.range(1, 100)
    .publishOn(Schedulers.parallel())
    .map(this::heavyComputation);
```

Это переключает поток выполнения на шедулер `parallel`, но элементы всё равно обрабатываются **последовательно, один за другим** — просто каждый раз на потоке, взятом из пула. Это конкурентность (использование разных потоков по очереди), а не истинный параллелизм.

## 5. Почему parallel()+runOn() выгоднее

| Критерий | publishOn(parallel()) | parallel() + runOn(parallel()) |
|---|---|---|
| Тип выполнения | Конкурентность (по очереди на разных потоках) | Истинный параллелизм (одновременно на N потоках) |
| Загрузка CPU-ядер | Использует только один поток в момент времени | Использует все N ядер одновременно |
| Пропускная способность на CPU-bound задачах | Ниже — нет реального распараллеливания вычислений | Выше — линейный прирост от количества ядер |
| Подходит для | I/O-задач, лёгких вычислений | Тяжёлых CPU-bound вычислений (сериализация, шифрование, генерация PDF и т.п.) |
| Управление количеством rails | Нет — единый поток обработки | Явное — parallel(N) задаёт число параллельных дорожек |

Главная выгода `parallel()+runOn()` — реальное разделение нагрузки между несколькими ядрами процессора одновременно, а не просто асинхронное переключение единого потока обработки. Для CPU-bound задач (например, конвертация в PDF, сжатие, шифрование) это даёт прямой прирост производительности, пропорциональный числу ядер, чего `publishOn` в одиночку не обеспечивает.

## 6. Итоговый пример кода

```java
Flux.range(1, 100)
    .parallel(4)
    .runOn(Schedulers.parallel())
    .map(this::heavyComputation)
    .sequential()
    .subscribe();
```
