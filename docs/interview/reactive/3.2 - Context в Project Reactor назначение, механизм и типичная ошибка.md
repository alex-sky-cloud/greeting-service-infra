## 1. Что такое Context

`Context` — неизменяемое (immutable) key-value хранилище, привязанное к конкретной подписке (`Subscriber`), которое передаётся вдоль цепочки операторов вместе с сигналом подписки. Он не зависит ни от потока выполнения, ни от сетевого слоя (Netty, EventLoop, TCP-соединение) — это чистый механизм Reactor Core, работающий даже без единого HTTP-запроса.

## 2. Почему ThreadLocal не подходит

В реактивной цепочке выполнение может переключаться между потоками через `subscribeOn`/`publishOn`. Данные, записанные в `ThreadLocal` на одном потоке, не видны после переключения на другой поток — значения будут потеряны или перепутаны между параллельными запросами, использующими общий пул потоков.

## 3. Как Context на самом деле путешествует по цепочке

Ключевая деталь: `Context` заполняется **снизу вверх** — то есть значения, записанные оператором `contextWrite()`, видны только тем операторам, которые находятся **выше** него по цепочке (ближе к источнику). Это происходит потому, что сигнал подписки идёт от `subscribe()` вверх к источнику, и именно во время этого прохода собирается итоговый `Context`.

```
Источник → map → contextWrite() → flatMap → subscribe()
   ↑          ↑         │             ↑
   видит    видит   записывает    НЕ видит
```

## 4. Неправильный пример: contextWrite() в конце цепочки

```java
Mono.deferContextual(ctx -> {
        // Пытаемся прочитать userId, но его ещё нет в контексте на этом этапе
        String userId = ctx.getOrDefault("userId", "unknown");
        return Mono.just("Order for user: " + userId);
    })
    .flatMap(result -> {
        System.out.println(result); // ВЫВЕДЕТ: "Order for user: unknown"
        return Mono.just(result);
    })
    // ОШИБКА: contextWrite() стоит В КОНЦЕ цепочки, после deferContextual/flatMap.
    // Он пишет значение "ниже" по цепочке, а видно оно будет только операторам ВЫШЕ
    // относительно места вызова contextWrite(). Но deferContextual уже отработал раньше,
    // потому что подписка идёт снизу вверх — на момент чтения контекста userId ещё не был записан.
    .contextWrite(ctx -> ctx.put("userId", "u-123"))
    .subscribe();
```

## 5. Правильный пример: contextWrite() в конце (снизу), видим сверху

`contextWrite()` физически всегда должен идти после (снизу) тех операторов, которые должны видеть записанное значение — то есть ближе к `subscribe()`, а не в начале цепочки, как многие интуитивно ожидают.

```java
Mono.deferContextual(ctx -> {
        // Правильно: на этом этапе userId УЖЕ доступен, потому что contextWrite()
        // расположен НИЖЕ (ближе к subscribe()), а Context виден всем операторам ВЫШЕ него.
        String userId = ctx.getOrDefault("userId", "unknown");
        return Mono.just("Order for user: " + userId);
    })
    .flatMap(result -> {
        System.out.println(result); // ВЫВЕДЕТ: "Order for user: u-123"
        return Mono.just(result);
    })
    .contextWrite(ctx -> ctx.put("userId", "u-123")) // запись контекста — ближе к subscribe()
    .subscribe();
```

## 6. Чтение контекста

Есть два основных способа прочитать `Context` внутри цепочки:

```java
// Способ 1: deferContextual — читаем контекст лениво, в момент подписки
Mono<String> withContext = Mono.deferContextual(ctx ->
    Mono.just("userId = " + ctx.getOrDefault("userId", "n/a"))
);

// Способ 2: transformDeferredContextual — доступ к контексту вместе с исходным Mono/Flux
Mono<String> transformed = Mono.just("payload")
    .transformDeferredContextual((mono, ctx) ->
        mono.map(payload -> payload + " for user " + ctx.get("userId"))
    );

// Итоговая подписка с записью значения в контекст
withContext
    .contextWrite(ctx -> ctx.put("userId", "u-123"))
    .subscribe(System.out::println); // userId = u-123
