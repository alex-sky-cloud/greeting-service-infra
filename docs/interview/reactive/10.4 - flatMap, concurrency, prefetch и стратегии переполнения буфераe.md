# flatMap, concurrency, prefetch и стратегии переполнения буфера

## fn — функция-трансформатор

`fn` — первый аргумент `flatMap`, функция, которая превращает один элемент входного потока в новый асинхронный `Publisher`. В бизнес-кейсе обработки заказов из Kafka она превращает сырое сообщение в `Mono<Order>`, сохраняющий заказ через R2DBC:

```java
Flux<ConsumerRecord<String, String>> kafkaRecords = receiver.receive();

kafkaRecords
    .flatMap(record -> orderRepository
        .save(parseOrder(record.value()))
        .doOnError(e -> log.error("Order save failed: {}", record.key(), e)))
    .subscribe();
```

## concurrency — ограничение параллельных подписок

Concurrency задаёт, сколько inner-publisher'ов подписаны одновременно, и этим же значением определяется размер первого запроса к upstream-источнику.

Источник: https://eherrera.net/project-reactor-course/03-working-with-map-and-flatmap/flatmap.html

**EN:**
```
The concurrency argument controls how many inner publishers can be subscribed to
and merged in parallel. For example, with a Flux of four elements, a concurrency
of 2 means flatMap will make two requests to the Flux.
```

**RU:**
```
Аргумент concurrency контролирует, сколько inner-publisher'ов могут быть
подписаны и объединены параллельно. Например, для Flux из четырёх элементов
concurrency равный 2 означает, что flatMap сделает два запроса к этому Flux.
```

Пример: интернет-магазин ограничивает количество параллельных сохранений заказов в БД до 10, чтобы не перегрузить пул соединений R2DBC:

```java
kafkaRecords
    .flatMap(record -> orderRepository.save(parseOrder(record.value())), 10)
    .subscribe();
```

## prefetch — подкачка данных внутри inner-publisher'а

Prefetch определяет, сколько элементов запрашивается у каждого отдельного inner-publisher'а за одну партию, а не у внешнего источника.

Источник: https://eherrera.net/project-reactor-course/03-working-with-map-and-flatmap/flatmap.html

**EN:**
```
The prefetch argument is the number of elements requested to each inner
publisher in each batch of requests. For example, with a prefetch of 2, after
the inner publishers have emitted two elements, the next batch (of two) will
be requested.
```

**RU:**
```
Аргумент prefetch — это количество элементов, запрашиваемых у каждого
inner-publisher'а в рамках одной партии запросов. Например, при prefetch
равном 2, после того как inner-publisher'ы эмитировали два элемента,
будет запрошена следующая партия (из двух).
```

Пример: каждый Kafka-batch содержит массив пользовательских событий, разбираемых через вложенный `Flux`. Concurrency ограничивает число параллельно обрабатываемых batch'ей, а prefetch — сколько событий заранее запрашивается у каждого такого `Flux`:

```java
kafkaRecords
    .flatMap(record -> Flux.fromIterable(parseUserEvents(record.value()))
            .subscribeOn(Schedulers.boundedElastic()),
        4,   // concurrency
        8)   // prefetch
    .subscribe(event -> analyticsService.track(event));
```

## onBackpressureError — почему переполнение буфера завершает подписку ошибкой

Источник: http://www.adamldavis.com/blog/2020/03.html

**EN:**
```
onBackpressureError(): Ends the Flux with an error (calling the downstream
Subscriber's onError) with an IllegalStateException from
Exceptions.failWithOverflow() if more items were produced upstream than
requested downstream.
```

**RU:**
```
onBackpressureError(): Завершает Flux ошибкой (вызывая onError у downstream
Subscriber) с IllegalStateException из Exceptions.failWithOverflow(),
если upstream произвёл больше элементов, чем было запрошено downstream.
```

Это подтверждает, что переполнение буфера с дефолтной стратегией (`ERROR`) действительно приводит к терминальному `onError`, отменяющему всю подписку выше по потоку.

## DROP_OLDEST — почему это применимо к курсу валют

Источник: http://www.adamldavis.com/blog/2020/03.html

**EN:**
```
onBackpressureBuffer(maxSize, BufferOverflowStrategy): Buffers items up to the
given count and allows you to specify the BufferOverflowStrategy, such as
onBackpressureBuffer(100, BufferOverflowStrategy.DROP_OLDEST)
```

**RU:**
```
onBackpressureBuffer(maxSize, BufferOverflowStrategy): Буферизует элементы до
указанного количества и позволяет задать BufferOverflowStrategy, например
onBackpressureBuffer(100, BufferOverflowStrategy.DROP_OLDEST)
```

Пример: обновления курса валют для дашборда — важна только последняя цена, поэтому старые обновления безопасно выбрасывать при переполнении:

```java
priceUpdates
    .onBackpressureBuffer(1000, BufferOverflowStrategy.DROP_OLDEST)
    .flatMap(price -> dashboardService.push(price), 5)
    .subscribe();
```

## onBackpressureDrop — почему нельзя применять к критичным данным

Источник: http://www.adamldavis.com/blog/2020/03.html

**EN:**
```
if each item in the stream is critical, do not use onBackpressureDrop().
```

**RU:**
```
если каждый элемент потока критичен, не используйте onBackpressureDrop().
```

Это прямое обоснование, почему для журнала банковских транзакций выбрана стратегия `DROP_LATEST` (сохраняющая уже накопленные записи) вместо простого drop-подхода:

```java
transactionEvents
    .onBackpressureBuffer(1000, BufferOverflowStrategy.DROP_LATEST)
    .flatMap(tx -> ledgerService.record(tx), 5)
    .subscribe();
```
