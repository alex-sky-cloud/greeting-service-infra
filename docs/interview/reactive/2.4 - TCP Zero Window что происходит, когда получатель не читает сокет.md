# TCP Zero Window что происходит, когда получатель не читает сокет

## Что значит "окно падает" — receive window физически уменьшается

Каждый TCP-пакет несёт число — сколько байт получатель ещё готов принять в свой буфер. Когда сервис завис на медленном запросе к БД, он не читает сокет, буфер ядра ОС заполняется входящими данными, и это число падает до нуля.

Источник: https://oneuptime.com/blog/post/2026-03-20-tcp-window-full-errors-wireshark/view

**EN:**
```
"TCP Window Full" appears in Wireshark when the sender has filled the
receiver's advertised window and must stop sending new data until ACKs
advance or reopen the usable send window. A sender pausing because the
window is full means data is arriving at the receiver faster than it can be
consumed or buffered.
```

**RU:**
```
"TCP Window Full" появляется в Wireshark, когда отправитель заполнил
объявленное окно получателя и должен остановить отправку новых данных,
пока ACK не продвинут окно или не откроют его снова. Пауза отправителя
из-за заполненного окна означает, что данные приходят к получателю
быстрее, чем он успевает их обрабатывать или буферизовать.
```

## Сценарий: сервис A шлёт данные сервису B, а B зависает на медленной БД

Пошаговая хронология для случая, когда поток B заблокирован на JDBC-вызове и не вычитывает сокет:

1. **0-я секунда** — A отправил данные, они лежат в TCP receive buffer сервиса B (ОС уже принял их на уровне ядра, но приложение B их не забрало)
2. **Буфер B заполняется** — если B продолжает не читать сокет, ОС сервиса B в очередном ACK сообщает A: "окно = 0"
3. **A останавливается** — как только A получает ACK с window=0, он физически перестаёт слать новые данные, даже если у него есть что отправить

Источник: https://oneuptime.com/blog/post/2026-03-20-tcp-zero-window-packet-captures/view

**EN:**
```
The sender must stop sending new data into that flow-control window,
periodically probe the window, and wait for a Window Update from the
receiver. This is TCP's emergency brake - it pauses normal transmission to
give the receiver time to drain its buffer.
```

**RU:**
```
Отправитель обязан прекратить отправку новых данных в это flow-control
окно, периодически зондировать окно и ждать Window Update от получателя.
Это "аварийный тормоз" TCP — он приостанавливает обычную передачу, чтобы
дать получателю время разгрузить свой буфер.
```

## A не молчит — он "стучится" через Zero Window Probe

A не просто ждёт бесконечно тишину — он периодически отправляет крошечный 1-байтовый пробный пакет, чтобы проверить, не освободилось ли место у B.

Источник: https://ylioo.com/networking/tcp/tcp_zero_window_probes/

**EN:**
```
Whenever the other side advertises a window size of 0, the sending side
persists in sending a segment with 1 byte of data every so often. It knows
that this data will probably not be accepted, but it tries anyway, because
each of these 1-byte segments triggers a response that contains the current
advertised window.
```

**RU:**
```
Когда другая сторона объявляет размер окна 0, отправляющая сторона
периодически посылает сегмент с 1 байтом данных. Она знает, что эти данные
скорее всего не будут приняты, но пробует всё равно, потому что каждый
такой 1-байтовый сегмент вызывает ответ с текущим объявленным окном.
```

Эти пробы идут с растущим интервалом (экспоненциальный backoff), обычно до 60 секунд между попытками. B на каждый такой проб отвечает ACK'ом с текущим размером окна — если у B всё ещё 0, диалог повторяется.

## Что произойдёт через несколько секунд

Если БД у B ответит, например, на 6-й секунде и поток B наконец вычитает сокет, ОС B освобождает буфер, и следующий ACK объявит ненулевое окно — A увидит это и мгновенно продолжит слать данные, никакого пересоздания соединения не требуется.

Источник: https://oneuptime.com/blog/post/2026-03-20-tcp-zero-window-packet-captures/view

**EN:**
```
4. When receiver drains buffer: sends Window Update (window > 0)
5. Sender resumes transmission
```

**RU:**
```
4. Когда получатель разгружает буфер: отправляет Window Update (окно > 0)
5. Отправитель продолжает передачу
```

## Что если зависание тянется намного дольше

TCP сам по себе готов терпеть zero-window состояние сколько угодно долго, пока идут ACK на пробы — он не разрывает соединение по собственной инициативе только из-за задержки. На практике критичнее application-level таймаут: `Mono.timeout()` в реактивном стеке Spring WebFlux или `socketTimeout` в блокирующем JDBC-драйвере должны сами решить, когда сдаться, а не полагаться на то, что TCP разорвёт зависшее соединение.
