# Reactive Streams vs TCP flow control

## Reactive Streams backpressure — договорённость внутри JVM

`request(n)` — это счётчик в памяти между Publisher и Subscriber внутри вашего Java-кода. Сети здесь нет вообще.

Источник: https://github.com/reactive-streams/reactive-streams-jvm

**EN:**
```
The total number of onNext's signalled by a Publisher to a Subscriber MUST
be less than or equal to the total number of elements requested by that
Subscriber's Subscription at all times.
```

**RU:**
```
Общее количество сигналов onNext от Publisher к Subscriber ДОЛЖНО быть не
больше общего количества запрошенных элементов в любой момент времени.
```

Пример из обычного Spring Boot сервиса — выгрузка заказов из БД пачками, чтобы не тянуть в память миллион записей сразу:

```java
@Service
public class OrderExportService {

    public Flux<Order> exportOrders() {
        return orderRepository.findAll() // R2DBC
            .limitRate(100); // request(100) под капотом
    }
}
```

## TCP flow control — механизм операционной системы

TCP-окно ограничивает, сколько байт можно передать по сокету, если получатель не успевает их вычитывать. Этим управляет ядро ОС, а не ваш код.

Источник: https://alivedise.github.io/backend-engineering-essentials/messaging/backpressure-and-flow-control

**EN:**
```
The receiver maintains a receive buffer and advertises its remaining capacity
as the receive window (rwnd) in every ACK packet. When the buffer fills,
rwnd drops to zero. The sender must stop transmitting until the receiver
signals available space again.
```

**RU:**
```
Получатель поддерживает буфер приёма и сообщает оставшуюся ёмкость как
receive window (rwnd) в каждом ACK-пакете. Когда буфер заполняется, rwnd
падает до нуля. Отправитель обязан прекратить передачу, пока получатель
не сообщит о наличии свободного места.
```

Пример: Spring WebFlux сервис принимает файл через WebClient. Если обработчик медленно пишет файл на диск и не читает новые байты из сокета, ОС сама, без вашего участия, сигнализирует отправителю "притормози" — это происходит на уровне ядра.

## Где они пересекаются — стриминг ответа клиенту

Reactor Netty транслирует отсутствие demand от Publisher'а в отключение чтения из сокета, и именно это со временем приводит к падению TCP-окна на другой стороне.

```java
@RestController
public class ReportController {

    @GetMapping(value = "/reports/stream", produces = MediaType.APPLICATION_NDJSON_VALUE)
    public Flux<ReportRow> streamReport() {
        return reportRepository.findAllRows(); // если клиент читает медленно,
                                                  // Reactor Netty сам притормозит чтение из сокета
    }
}
```

## Работает ли TCP backpressure только с реактивным стеком

Нет — TCP flow control встроен в сам протокол и работает независимо от модели приложения (реактивной или блокирующей), потому что это функция ядра ОС, а не библиотеки.

Источник: https://github.com/apple/swift-nio/issues/162

**EN:**
```
The idea of a back pressure is that you don't read more data than what the
stack can process. I.e. that you stop reading data you can't process anyways
at the socket level. This is particularly important with async services
because they don't block the reading side during processing (BP is
automatic/implicit w/ synchronous services).
```

**RU:**
```
Идея backpressure в том, что вы не читаете больше данных, чем стек может
обработать, то есть прекращаете читать данные, которые всё равно не можете
обработать, на уровне сокета. Это особенно важно для асинхронных сервисов,
потому что они не блокируют сторону чтения во время обработки (backpressure
автоматический/неявный у синхронных сервисов).
```

Практическая разница между стеками:

- В блокирующем стеке (например, классический `@Controller` на Tomcat с JDBC) backpressure возникает сама собой: поток обработки физически заблокирован на `read()` или на JDBC-вызове, поэтому он просто не читает следующие байты из сокета, пока не освободится — TCP-окно падает автоматически, без единой строчки кода
- В реактивном стеке (WebFlux на Netty) поток НЕ блокируется на I/O, поэтому если явно не сигнализировать через `request(n)` и не завязать это на `autoRead`, event loop продолжит читать из сокета сколько угодно быстро, забивая память приложения буферами — здесь нужен явный механизм Reactive Streams, чтобы искусственно воссоздать то, что в блокирующем стеке происходит бесплатно

Пример блокирующего Spring MVC контроллера, где backpressure не требует настройки:

```java
@RestController
public class LegacyReportController {

    @GetMapping("/reports/export")
    public void exportReport(HttpServletResponse response) throws IOException {
        try (ResultSet rs = jdbcTemplate.getDataSource()
                .getConnection().createStatement()
                .executeQuery("SELECT * FROM orders")) {
            while (rs.next()) {
                response.getOutputStream().write(serialize(rs)); // поток блокируется на write()
                // если клиент медленный, ОС сама притормозит на уровне TCP —
                // никакого дополнительного кода не нужно
            }
        }
    }
}
```

Итог: TCP flow control работает всегда, независимо от стека — это свойство протокола. Но в блокирующем стеке он естественно синхронизирован с вашей бизнес-логикой через блокировку потока, а в реактивном стеке нужен явный мост (Reactive Streams `request(n)` → `autoRead` в Netty), иначе быстрый event loop обойдёт защиту TCP и переполнит память приложения ещё до того, как TCP-окно успеет отреагировать.
