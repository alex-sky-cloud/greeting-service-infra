## 1. Общая идея

Все три оператора комбинируют несколько `Publisher` (`Mono`/`Flux`) в один, но делают это по-разному:

- `zip` — ждёт ответа от КАЖДОГО источника и объединяет их в единый объект (Tuple).
- `merge` — подписывается на все источники одновременно и сливает их элементы в общий поток, порядок не гарантирован.
- `concat` — подписывается на источники по очереди: сначала полностью проходит первый, потом переходит ко второму.

---

## 2. zip — ждать всех и объединить в один объект

`zip` подписывается на все переданные `Publisher` параллельно, но результат приходит только тогда, когда КАЖДЫЙ источник эмитировал значение. Значения объединяются в `Tuple` (до 8 источников в перегруженных версиях метода).

### Бизнес-кейс: сборка профиля клиента из трёх независимых сервисов

```java
/**
 * Собираем полный профиль клиента: аккаунт, кредитный скоринг и историю операций.
 * Все три сервиса вызываются ОДНОВРЕМЕННО (параллельно),
 * а итоговый DTO собирается только когда ответили ВСЕ три.
 */
Mono<AccountView> aggregate(String id) {
    Mono<Account> accountMono = accountService.get(id);        // поход в БД аккаунтов
    Mono<Score> scoreMono = scoreService.getScore(id);          // поход во внешний скоринговый сервис
    Mono<History> historyMono = historyService.getRecent(id);   // поход в сервис истории операций

    return Mono.zip(accountMono, scoreMono, historyMono)
        // tuple.getT1(), getT2(), getT3() — соответствуют порядку аргументов выше
        .map(tuple -> new AccountView(tuple.getT1(), tuple.getT2(), tuple.getT3()));
}
```

Если хотя бы один из трёх `Mono` завершится с ошибкой — весь `zip` завершится ошибкой, даже если два других успешно ответили.

## 3. merge — слить потоки без гарантии порядка

`merge` подписывается на все `Publisher` сразу (eagerly), и элементы попадают в результирующий поток в том порядке, в котором реально пришли — то есть порядок зависит от скорости ответа каждого источника.

### Бизнес-кейс: агрегация уведомлений из нескольких каналов в реальном времени

```java
/**
 * Собираем поток уведомлений из email-канала и push-канала в единую ленту.
 * Оба источника публикуют события параллельно и независимо,
 * порядок появления в итоговом Flux не важен — важно получить все события как можно быстрее.
 */
Flux<Notification> emailNotifications = emailService.streamNotifications(); // события из почты
Flux<Notification> pushNotifications = pushService.streamNotifications();   // события из push-сервиса

Flux<Notification> combinedFeed = Flux.merge(emailNotifications, pushNotifications);
// подписка на оба источника происходит одновременно;
// если push ответит быстрее — его события окажутся в потоке раньше, даже если email отправил запрос первым
```

## 4. concat — строго последовательное объединение

`concat` подписывается на источники по очереди: сначала полностью дожидается завершения (`onComplete`) первого `Publisher`, и только потом переходит к подписке на следующий. Порядок элементов в итоговом потоке всегда строго соответствует порядку источников.

### Бизнес-кейс: сначала отдать закэшированные данные, потом дозагрузить свежие

```java
/**
 * Отдаём клиенту сначала быстрые данные из локального кэша,
 * а после того как кэш полностью "выгружен", догружаем свежие данные из БД.
 * Порядок строго важен: кэш ДОЛЖЕН прийти раньше свежих данных, иначе итог перепутается.
 */
Flux<Order> cachedOrders = cacheService.getRecentOrders(userId);  // быстрый источник, конечный поток
Flux<Order> freshOrders = orderRepository.findAllByUser(userId);  // более медленный источник, поход в БД

Flux<Order> orderedFeed = Flux.concat(cachedOrders, freshOrders);
// freshOrders НЕ начнёт выполняться, пока cachedOrders не завершится полностью
```

## 5. Сравнительная таблица

| Оператор | Подписка на источники | Порядок элементов | Что возвращает | Поведение при ошибке одного источника |
|---|---|---|---|---|
| `zip` | Параллельно, сразу на все | Комбинируется по позициям в Tuple | Один объединённый объект (Tuple / DTO) | Весь результат завершается ошибкой |
| `merge` | Параллельно, сразу на все | Не гарантирован (по факту прихода) | Общий поток элементов из всех источников | Ошибка в одном источнике завершает весь merge с ошибкой |
| `concat` | Последовательно, по одному | Строго гарантирован (по порядку источников) | Общий поток элементов, идущих друг за другом | Ошибка в текущем источнике останавливает всю цепочку, следующие источники не запускаются |

---

## 6. Как выбрать оператор для конкретной задачи

- Нужно **вызвать несколько независимых сервисов параллельно и собрать единый DTO** (например, профиль клиента из трёх источников) — используй `zip`.
- Нужно **слить несколько потоков однотипных событий в общую ленту**, и порядок появления не важен (уведомления, логи, метрики из разных источников) — используй `merge`.
- Нужно **гарантировать порядок появления данных**, где один источник логически должен идти строго раньше другого (сначала кэш, потом БД; сначала быстрый ответ, потом дозагрузка) — используй `concat`.
