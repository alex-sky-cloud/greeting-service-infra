## 1. Назначение retryWhen

`retryWhen` перехватывает ошибку из источника и решает, стоит ли повторить подписку. Экспоненциальный backoff нужен, чтобы не долбить нестабильный сервис мгновенными повторами подряд, а увеличивать паузу между попытками, давая сервису время восстановиться.

## 2. Правильная настройка через Retry.backoff

```java
Flux.range(1, 10)
    .flatMap(this::callUnstableService)
    .retryWhen(
        Retry.backoff(3, Duration.ofSeconds(1))        // 3 попытки, начальная задержка 1с
             .maxBackoff(Duration.ofSeconds(10))         // верхний предел задержки
             .jitter(0.5)                                // случайный разброс задержки
             .filter(throwable -> throwable instanceof IOException) // повторять только для нужных ошибок
    )
    .subscribe();
```

- Первый аргумент `Retry.backoff(3, Duration.ofSeconds(1))` — максимальное число попыток (3) и начальная задержка (1 секунда). Каждая следующая попытка задержку увеличивает (обычно вдвое) — в этом и заключается экспоненциальный рост.
- `Retry.fixedDelay(n, duration)` — альтернатива без экспоненциального роста, если нужна просто фиксированная задержка между попытками.

## 3. Что происходит при превышении числа попыток

Если число попыток исчерпано, `retryWhen` не просто "перестаёт пытаться" — он выбрасывает `Exceptions.retryExhausted(...)`, оборачивающий последнюю ошибку. Эту ситуацию нужно явно обрабатывать через `onErrorResume`/`onErrorReturn`.

## 4. Зачем нужен jitter

`jitter` добавляет случайный разброс к рассчитанной экспоненциальной задержке (например, `jitter(0.5)` означает случайное отклонение до 50% от расчётного значения задержки в обе стороны). Цель — "размазать" во времени повторные попытки разных клиентов, которые столкнулись с ошибкой примерно одновременно.

## 5. Что будет без jitter: проблема thundering herd

Если множество клиентов одновременно получают ошибку от одного и того же сервиса (например, при его кратковременном падении) и все настроены на строго одинаковый экспоненциальный backoff без jitter, то все они будут повторять попытки **синхронно, в один и тот же момент времени**:

- Первая волна повторов ударит по сервису одновременно от всех клиентов ровно через 1 секунду.
- Если сервис ещё не восстановился, вторая волна ударит одновременно через 2 секунды, третья через 4 секунды, и так далее.
- Такая синхронизированная волна нагрузки называется **thundering herd** ("грохочущее стадо") — она может помешать сервису восстановиться, потому что он снова получает пиковую нагрузку именно в момент, когда пытается подняться после сбоя.

С `jitter` повторные попытки разных клиентов "размазываются" по времени случайным образом, превращая синхронизированный всплеск нагрузки в равномерный поток запросов, который сервису значительно проще выдержать при восстановлении.
