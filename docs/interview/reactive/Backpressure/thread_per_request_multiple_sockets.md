## 1. Общая модель thread-per-request

**Утверждение:** в модели thread-per-request каждый входящий запрос обрабатывается отдельным потоком из пула, а не постоянно назначенным потоком на всё соединение целиком.

- Источник: https://www.baeldung.com/java-thread-per-connection-vs-per-request

> "With the thread-per-request model, a different thread is used to handle each request, even if the connection used is persistent."

RU:

> «В модели thread-per-request для обработки каждого запроса используется отдельный поток, даже если используемое соединение постоянное (persistent).»

---

## 2. Как один поток проходит через несколько сокетов

**Утверждение:** во время обработки одного запроса поток может блокирующе работать сразу с несколькими сокетами последовательно — сначала с клиентским сокетом, потом (при необходимости) с сокетом к БД, потом с сокетом к внешнему сервису.

- Источник: https://dzone.com/articles/spring-webflux-eventloop-vs-thread-per-request-mod

> "Cases where applications make some network calls like, fetch data from a database, fetch a response from another application, file read/write etc., a request thread has to wait to get the desired response. The request thread here is blocked, and there is no CPU utilization in this period."

RU:

> «В случаях, когда приложение делает сетевые вызовы — например, получает данные из базы данных, ответ от другого приложения, читает/пишет файл — поток запроса должен ждать получения нужного ответа. Поток запроса в этот момент блокируется, и в этот период процессор не используется.»

Это прямо описывает картину: тот же самый поток, который держит клиентский сокет, при обращении к БД открывает (или занимает из пула соединений) ещё один сокет — к базе данных — и блокируется на нём, ожидая ответа, прежде чем вернуться к обработке и, возможно, открыть третий сокет к внешнему сервису.

---

## 3. Важное уточнение: сокет не «закреплён» за потоком постоянно

Формулировка «поток обслуживает закреплённый сокет» верна только для клиентского сокета *в течение одного запроса*, но не является постоянной жёсткой привязкой на уровне контейнера (например, Tomcat).

- Источник: https://dzone.com/articles/spring-webflux-eventloop-vs-thread-per-request-mod

> "The thing to note here is that there is no permanent binding of a socket to Thread. If any request thread gets blocked for an I/O call, requests can still be handled by other threads in the thread pool."

RU:

> «Здесь важно отметить, что постоянной привязки сокета к потоку не существует. Если какой-то поток запроса блокируется на I/O-вызове, другие запросы всё равно могут обрабатываться другими потоками из пула.»

---

## 4. Вывод

На время обработки конкретного запроса поток последовательно занимает (и блокируется на) сокете клиента, затем сокете к БД, затем сокете к внешнему сервису — но после завершения запроса этот же поток возвращается в пул и в следующий раз может обслуживать совершенно другой клиентский сокет. Привязка временная, на длительность одного запроса, а не постоянная на всё время жизни потока.
