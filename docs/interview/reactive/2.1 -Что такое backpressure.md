## Что такое backpressure

**Backpressure** — механизм, при котором медленный подписчик (downstream) сигнализирует быстрому издателю (upstream), сколько именно элементов он готов принять, чтобы не быть перегруженным. 
- **Практический пример**: сервис получает поток заказов из очереди сообщений быстрее, чем успевает записывать их в БД — **без** _backpressure_ очередь заказов в памяти **неограниченно растёт** и приводит к `OutOfMemoryError`.

<a id="mehanizm-request-n"></a>
## Механизм request(n)

В основе **backpressure** лежит вызов `Subscription.request(n)` — **Subscriber** явно сообщает **Publisher** число элементов, которые он готов обработать. 
- **Издатель** не имеет права слать больше, чем было запрошено, а суммарный накопленный спрос (cumulative demand) не должен превышать `Long.MAX_VALUE`.

Источник: https://www.reactive-streams.org/reactive-streams-1.0.0-javadoc/org/reactivestreams/Subscription.html

EN:

> "No events will be sent by a Publisher until demand is signaled via this method. It can be called however often and whenever needed—but the outstanding cumulative demand must never exceed Long.MAX_VALUE. An outstanding cumulative demand of Long.MAX_VALUE may be treated by the Publisher as 'effectively unbounded'."

RU:

> "Издатель не будет отправлять события, пока спрос не будет заявлен через этот метод. 
> Его можно вызывать сколько угодно раз и когда угодно — но суммарный невыполненный спрос никогда не должен превышать Long.MAX_VALUE. 
> Невыполненный суммарный спрос, равный Long.MAX_VALUE, может интерпретироваться издателем как 'фактически неограниченный'."

<a id="limitrate-razbivka-zaprosa-a-ne-poterya-elementov"></a>
## limitRate: разбивка запроса, а не потеря элементов

`limitRate(n)` — это не стратегия отбрасывания данных, а способ разбить один большой запрос (`request(Long.MAX_VALUE)`) на серию мелких запросов по n элементов. Источник физически не производит элемент, пока downstream не запросил следующую порцию — поэтому ничего не теряется, просто регулируется темп.

Источник: https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html

EN:

> "limitRate(int prefetchRate) — Ensure that backpressure signals from downstream subscribers are split into batches capped at the provided prefetchRate rather than being fully propagated upstream (i.e. prefetching)."

RU:

> "limitRate(int prefetchRate) — гарантирует, что сигналы backpressure от downstream-подписчиков разбиваются на пачки, ограниченные указанным prefetchRate, вместо того чтобы полностью передаваться вверх по цепочке (то есть выполняется предзагрузка/prefetching)."

**Бизнес-кейс:** 
 - сервис читает большой файл с транзакциями из S3 и записывает каждую строку в БД. 
 - Если не ограничить темп, `read()` вычитает весь файл в память разом, а `save()` в БД не успевает за этим потоком:

```java
@Service
class TransactionImportService {

    private final TransactionRepository transactionRepository;

    Flux<Void> importTransactions(Flux<Transaction> fileStream) {
        return fileStream
            .limitRate(50) // запрашиваем у файлового источника не более 50 строк за раз
            .flatMap(transaction ->
                Mono.fromCallable(() -> transactionRepository.save(transaction)) // запись в БД — медленная операция
                    .subscribeOn(Schedulers.boundedElastic())
            )
            .thenMany(Flux.empty());
    }
}
```

<a id="strategii-onbackpressurexxx"></a>
## Стратегии onBackpressureXxx

Если **downstream** всё-таки запросил слишком много (например, `Long.MAX_VALUE`), а источник продолжает генерировать элементы быстрее, чем они обрабатываются, применяются операторы `onBackpressureXxx` — они решают, что делать с уже произведённым избытком.

<a id="onbackpressurebuffer"></a>
### onBackpressureBuffer

**Копит** непринятые элементы **во внутренней очереди**, не теряя их, пока **downstream** не заберёт их позже. 
- Бизнес-кейс:
   - сервис отправляет заказы в Kafka, и если брокер временно тормозит, заказы важно не потерять, а придержать в буфере:

```java
@Service
class OrderEventPublisher {

    private final KafkaSender<String, OrderEvent> kafkaSender;

    Flux<Void> publishOrders(Flux<OrderEvent> orderEvents) {
        return orderEvents
            .onBackpressureBuffer(1000) // копим до 1000 неотправленных заказов, не теряя их
            .flatMap(event -> kafkaSender.send(Mono.just(toSenderRecord(event))).then());
    }
}
```
Риск переполнения буфера приводит к `OverflowException`: 
 - если брокер Kafka недоступен слишком долго и в буфере уже находится 1 000 неотправленных заказов, следующий заказ не будет помещён в буфер, а reactive pipeline завершится ошибкой. 
 - `onBackpressureBuffer(1000)` не отправляет накопленные или не поместившиеся в буфер заказы в dead-letter очередь автоматически; 
 - для исключения потери данных стратегию их устойчивого сохранения и последующей обработки необходимо реализовать отдельно.

Источник: [Reactor Core — `BufferOverflowStrategy.ERROR`](https://github.com/reactor/reactor-core/blob/main/reactor-core/src/main/java/reactor/core/publisher/BufferOverflowStrategy.java)

> “Propagate an `IllegalStateException` when the buffer is full.”

ru:

> «Распространить `IllegalStateException`, когда буфер заполнен.»

<a id="onbackpressuredrop"></a>
### onBackpressureDrop

Отбрасывает избыточные элементы без накопления — подходит для данных, потеря части которых некритична. 
 - Бизнес-кейс: 
   - сервис собирает метрики нагрузки с серверов раз в секунду, и если writer в Prometheus не успевает — лишние промежуточные значения можно просто выбросить:

```java
@Service
class MetricsCollector {

    private final MetricsWriter metricsWriter;

    Flux<Void> collectServerMetrics(Flux<ServerMetric> metricStream) {
        return metricStream
            .onBackpressureDrop(dropped -> log.warn("dropped metric: {}", dropped)) // лишние метрики просто теряются
            .flatMap(metric -> metricsWriter.write(metric));
    }
}
```

<a id="onbackpressurelatest"></a>
### onBackpressureLatest

Сохраняет только самое последнее значение среди непринятых элементов, отбрасывая промежуточные. 
- Бизнес-кейс: 
   - dashboard поддержки отображает текущий статус обработки заявки — важен только последний статус, а не вся история промежуточных обновлений:

```java
@Service
class TicketStatusDashboard {

    private final DashboardRenderer dashboardRenderer;

    Flux<Void> renderTicketStatus(Flux<TicketStatus> statusUpdates) {
        return statusUpdates
            .onBackpressureLatest() // держим только последний статус заявки, промежуточные не важны
            .flatMap(status -> dashboardRenderer.update(status));
    }
}
```

<a id="pull-vs-push-rezhimy"></a>
## Pull vs Push режимы

Reactive Streams **динамически** переключается между **pull**-режимом (когда downstream ограничивает спрос через `request(n)`) и push-режимом (когда downstream постоянно запрашивает с запасом и издатель просто шлёт данные по готовности).

Источник: https://medium.com/@knoldus/backpressure-in-akka-stream-294e5f045e07

EN:

> "Reactive Streams — whenever we come across these words, there are two things that come to our mind. The first is asynchronous stream processing, and the second is non-blocking backpressure."

RU:

> "Reactive Streams — когда мы встречаем эти слова, на ум приходят две вещи. 
> Первая — асинхронная обработка потоков, вторая — неблокирующий backpressure."

<a id="backpressure-s-nepolnostyu-reaktivnym-istochnikom"></a>

## Backpressure с неполностью реактивным источником

Если источник данных — блокирующий REST-клиент, JDBC-курсор или внешний сервис, он сам не участвует в протоколе Reactive Streams и не получает `request(n)` напрямую.

Однако блокирующий вызов можно обернуть в `Mono.fromCallable(...)`. Тогда вызов `fetchPage(...)` выполняется лениво: он не запускается при сборке pipeline, а выполняется только после подписки на соответствующий `Mono`.

Источник: [Reactive Streams — `Publisher`](https://www.reactive-streams.org/reactive-streams-1.0.3-javadoc/org/reactivestreams/Publisher.html)

EN:

> “A Publisher is a provider of a potentially unbounded number of sequenced elements, publishing them according to the demand received from its Subscriber(s).”

RU:

> «Publisher предоставляет потенциально неограниченное число упорядоченных элементов и публикует их в соответствии со спросом, полученным от Subscriber.»

- Бизнес-кейс:
    - сервис вычитывает историю платежей клиента из внешнего платёжного API;
    - API отдаёт данные постранично;
    - приложение запрашивает страницу `0`, получает её, затем на основании `hasNext` решает, нужно ли создавать запрос следующей страницы;
    - приложение не создаёт HTTP-запросы ко всем страницам заранее и не собирает все `PaymentPage` в одну коллекцию перед эмиссией записей вниз по pipeline.

***

## Пагинация через expand

`expand(...)` получает `PaymentPage`, эмитит эту страницу downstream и применяет к ней функцию, создающую publisher для следующей страницы.

В данном случае каждая страница создаёт не более одной следующей страницы:

```text
PaymentPage(0) → PaymentPage(1) → PaymentPage(2) → ...
```

Это линейная последовательность, а не дерево с несколькими ветками. Поэтому термин breadth-first здесь не влияет на порядок: у каждой страницы есть либо один потомок — следующая страница, либо потомков нет.

Источник: [Reactor Core — `Flux.expand`](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html)

EN:

> “Recursively expand elements into a graph and emit all the resulting element using a breadth-first traversal strategy.”

RU:

> «Рекурсивно раскрывает элементы в граф и эмитит все получившиеся элементы, используя стратегию обхода в ширину.»

Слово «рекурсивно» здесь не означает, что `expand(...)` сначала получает все страницы, хранит их в памяти и только после этого начинает эмиссию.

Наоборот, обработка идёт по мере получения страниц:

```text
Получена страница 0
    ↓
PaymentPage(0) эмитится вниз по pipeline
    ↓
Создаётся Mono для страницы 1
    ↓
Получена страница 1
    ↓
PaymentPage(1) эмитится вниз по pipeline
    ↓
Создаётся Mono для страницы 2
    ↓
...
```

Когда `expand(...)` получает очередную `PaymentPage`, оператор `concatMapIterable(...)` сразу начинает разворачивать её `records` в отдельные `PaymentRecord`.

## customerId и номер страницы

`customerId` — обычный параметр метода `fetchPaymentHistory(...)`.

Лямбды внутри `Flux.defer(...)` и `expand(...)` захватывают его через closure, поэтому передавать `customerId` отдельным аргументом в каждую лямбду не требуется:

```java
page -> fetchPage(customerId, page.nextPageNumber())
```

Первый запрос использует страницу `0`:

```java
fetchPage(customerId, 0)
```

Это означает, что в данном примере платёжный API использует нумерацию страниц с нуля. Это не универсальное правило: конкретный API может начинать страницы с `1` или использовать cursor-based pagination.

```java
/**
 * Одна страница истории платежей, полученная от внешнего платёжного API.
 */
record PaymentPage(
    int pageNumber,
    boolean hasNext,
    List<PaymentRecord> records
) {

    int nextPageNumber() {
        return pageNumber + 1;
    }
}

@Service
class PaymentHistoryService {

    private final PaymentGatewayClient paymentGatewayClient;

    /**
     * Выполняет один блокирующий HTTP-вызов на boundedElastic.
     *
     * Каждый вызов метода создаёт ленивый Mono:
     * HTTP-запрос не выполняется до подписки на этот Mono.
     */
    private Mono<PaymentPage> fetchPage(String customerId, int pageNumber) {
        return Mono.fromCallable(() ->
                paymentGatewayClient.fetchPage(customerId, pageNumber))
            .subscribeOn(Schedulers.boundedElastic());
    }

    /**
     * Загружает историю платежей клиента постранично.
     *
     * Механика:
     * 1) Flux.defer(...) лениво создаёт publisher стартовой страницы.
     *
     * 2) После подписки запрашивается страница 0.
     *
     * 3) expand(...) получает PaymentPage текущей страницы и эмитит её вниз.
     *
     * 4) Если hasNext == true, expand(...) создаёт Mono следующей страницы.
     *    Номер следующей страницы равен pageNumber + 1.
     *
     * 5) Если hasNext == false, возвращается Mono.empty().
     *    Это прекращает создание следующих страниц.
     *
     * 6) concatMapIterable(...) разворачивает records каждой полученной
     *    страницы в отдельные PaymentRecord, сохраняя порядок страниц.
     */
    Flux<PaymentRecord> fetchPaymentHistory(String customerId) {
        return Flux.defer(() -> fetchPage(customerId, 0))
            .expand(page -> page.hasNext()
                ? fetchPage(customerId, page.nextPageNumber())
                : Mono.empty())
            .concatMapIterable(PaymentPage::records);
    }
}
```


## Пошаговая трассировка на конкретных данных

Допустим, API возвращает три страницы:

```text
Страница 0: hasNext = true
Страница 1: hasNext = true
Страница 2: hasNext = false
```

- Шаг 1: после подписки выполняется `fetchPage(customerId, 0)`.
- Шаг 2: API возвращает:

```java
PaymentPage(
    pageNumber = 0,
    hasNext = true,
    records = [...]
)
```

- Шаг 3: `expand(...)` эмитит `PaymentPage(0)` вниз по pipeline.
- Шаг 4: `concatMapIterable(PaymentPage::records)` начинает эмитить записи страницы `0` как отдельные `PaymentRecord`.
- Шаг 5: поскольку у страницы `0` установлено `hasNext = true`, `expand(...)` создаёт `Mono` для вызова:

```java
fetchPage(customerId, 1)
```

- Шаг 6: API возвращает `PaymentPage(1)`. Эта страница эмитится вниз, а её `records` разворачиваются в `PaymentRecord`.
- Шаг 7: поскольку у страницы `1` установлено `hasNext = true`, создаётся вызов `fetchPage(customerId, 2)`.
- Шаг 8: API возвращает `PaymentPage(2)` с `hasNext = false`. Её записи передаются вниз через `concatMapIterable(...)`.
- Шаг 9: для страницы `2` `expand(...)` возвращает `Mono.empty()`. Новая страница не создаётся, и после завершения уже начатой обработки поток завершается.

Итоговый порядок данных в `Flux<PaymentRecord>`:

```text
records страницы 0
    ↓
records страницы 1
    ↓
records страницы 2
    ↓
onComplete
```

`expand(...)` не гарантирует правило «следующий HTTP-запрос начнётся только после того, как конечный subscriber полностью обработал все записи предыдущей страницы». Он создаёт publisher следующей страницы после получения текущей `PaymentPage` и проверки её `hasNext`.

Но `expand(...)` также не загружает тысячу страниц заранее. При линейной пагинации следующая страница становится известна только после получения предыдущей страницы; поэтому запросы к страницам строятся последовательно: `0 → 1 → 2 → ...`.[^1][^2]

```java
) {

    int nextPageNumber() {
        return pageNumber + 1;
    }
}

@Service
class PaymentHistoryService {

    private final PaymentGatewayClient paymentGatewayClient;

    /**
     * Выполняет один блокирующий HTTP-вызов на boundedElastic.
     *
     * Каждый вызов метода создаёт ленивый Mono:
     * HTTP-запрос не выполняется до подписки и запроса этого Mono.
     */
    private Mono<PaymentPage> fetchPage(String customerId, int pageNumber) {
        return Mono.fromCallable(() ->
                paymentGatewayClient.fetchPage(customerId, pageNumber))
            .subscribeOn(Schedulers.boundedElastic());
    }

    /**
     * Загружает историю платежей клиента постранично.
     *
     * Механика:
     * 1) Flux.defer(...) лениво создаёт publisher стартовой страницы.
     *
     * 2) После подписки и при наличии спроса запрашивается страница 0.
     *
     * 3) expand(...) получает PaymentPage текущей страницы и эмитит её вниз.
     *
     * 4) Если hasNext == true, expand(...) создаёт Mono следующей страницы.
     *    Номер следующей страницы равен pageNumber + 1.
     *
     * 5) Если hasNext == false, возвращается Mono.empty().
     *    Это прекращает создание следующих страниц.
     *
     * 6) concatMapIterable(...) разворачивает records каждой полученной
     *    страницы в отдельные PaymentRecord, сохраняя порядок страниц.
     */
    Flux<PaymentRecord> fetchPaymentHistory(String customerId) {
        return Flux.defer(() -> fetchPage(customerId, 0))
            .expand(page -> page.hasNext()
                ? fetchPage(customerId, page.nextPageNumber())
                : Mono.empty())
            .concatMapIterable(PaymentPage::records);
    }
}
```


## Пошаговая трассировка на конкретных данных

Допустим, API возвращает три страницы:

```text
Страница 0: hasNext = true
Страница 1: hasNext = true
Страница 2: hasNext = false
```

- Шаг 1: после подписки и при наличии спроса выполняется `fetchPage(customerId, 0)`.
- Шаг 2: API возвращает:

```java
PaymentPage(
    pageNumber = 0,
    hasNext = true,
    records = [...]
)
```

- Шаг 3: `expand(...)` эмитит `PaymentPage(0)` вниз по pipeline.
- Шаг 4: `concatMapIterable(PaymentPage::records)` начинает эмитить записи страницы `0` как отдельные `PaymentRecord`.
- Шаг 5: поскольку у страницы `0` установлено `hasNext = true`, `expand(...)` создаёт `Mono` для вызова:

```java
fetchPage(customerId, 1)
```

- Шаг 6: API возвращает `PaymentPage(1)`. Эта страница эмитится вниз, а её `records` разворачиваются в `PaymentRecord`.
- Шаг 7: поскольку у страницы `1` установлено `hasNext = true`, создаётся publisher для вызова `fetchPage(customerId, 2)`.
- Шаг 8: API возвращает `PaymentPage(2)` с `hasNext = false`. Её записи передаются вниз через `concatMapIterable(...)`.
- Шаг 9: для страницы `2` `expand(...)` возвращает `Mono.empty()`. Новая страница не создаётся, и после завершения обработки уже эмитированных элементов поток завершается.

Итоговый порядок данных в `Flux<PaymentRecord>`:

```text
records страницы 0
    ↓
records страницы 1
    ↓
records страницы 2
    ↓
onComplete
```

`expand(...)` не гарантирует правило «следующий HTTP-запрос начнётся только после того, как конечный subscriber полностью обработал все записи предыдущей страницы». Он создаёт publisher следующей страницы после получения текущей `PaymentPage` и проверки её `hasNext`.

Но `expand(...)` также не загружает тысячу страниц заранее. При линейной пагинации следующая страница становится известна только после получения предыдущей страницы; поэтому запросы к страницам строятся последовательно: `0 → 1 → 2 → ...`.

## Итоговая сравнительная таблица

| Способ | Бизнес-пример                                                          | Что происходит с избытком |
|---|------------------------------------------------------------------------|---|
| Ручной `request(n)` | Обработчик заявок берёт ровно столько заявок, сколько может обработать | Источник не производит лишнего |
| `limitRate(n)` | Импорт транзакций из файла порциями по 50 строк                        | То же — источник не производит лишнего |
