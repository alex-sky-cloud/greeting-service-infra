## 1. Ситуация

Поток тикеров подписывается на биржевой сервис через `flatMap`: 
 - для каждого тикера открывается собственный inner Publisher — HTTP-вызов, возвращающий котировку. 
 - Из 200 запросов 190-200 успешно завершаются, а 1-10 периодически падают с ошибкой из-за кратковременной перегрузки удалённого сервиса.

## 2. Почему ошибка одного inner Publisher не останавливает весь flatMap

**Ошибка** в Reactive Streams — **терминальный сигнал**, но если она обработана **внутри** отдельного inner Publisher'а (до того, как долетит до самого оператора `flatMap`), остальные inner Publisher'ы продолжают работать без прерывания.

[Handling Errors :: Reactor Core Reference Guide](https://projectreactor.io/docs/core/release/reference/coreFeatures/error-handling.html)

EN:
> For each key, asynchronously call the external service. If the external service call fails, fall back to the cache for that key.

RU:
> Для каждого ключа асинхронно вызывается внешний сервис. 
> Если вызов внешнего сервиса завершается ошибкой, происходит переключение на кэш для этого ключа.

## 3. Fallback на резервный адрес через onErrorResume

```java
public Flux<Quote> streamQuotes(List<String> tickers) {
    return Flux.fromIterable(tickers)
        .flatMap(ticker ->
            callPrimaryExchange(ticker)                     // основной вызов к бирже за котировкой
                .onErrorResume(e -> callBackupExchange(ticker)) // при ошибке — переключение на резервную биржу
        );
}

// Возвращает Mono<Quote> — асинхронный вызов к основному биржевому API по тикеру
private Mono<Quote> callPrimaryExchange(String ticker) {
    return webClient.get()
        .uri("https://primary-exchange.example.com/quote/{ticker}", ticker)
        .retrieve()
        .bodyToMono(Quote.class);
}

// Возвращает Mono<Quote> — асинхронный вызов к резервному биржевому API по тикеру
private Mono<Quote> callBackupExchange(String ticker) {
    return webClient.get()
        .uri("https://backup-exchange.example.com/quote/{ticker}", ticker)
        .retrieve()
        .bodyToMono(Quote.class);
}

// Класс данных котировки
record Quote(String ticker, double price, Instant timestamp) {}
```

Подписка на этот `Flux<Quote>` выглядит так:

```java
streamQuotes(List.of("AAPL", "GOOG", "MSFT"))
    .subscribe(quote -> System.out.println("Получена котировка: " + quote));
```

`onErrorResume` перехватывает ошибку конкретного inner Publisher'а и подменяет его целиковым другим Publisher'ом (вызовом к резервному адресу) — весь `flatMap` при этом продолжает штатно работать с остальными элементами.

[Project reactor: onErrorResume after flatMap](https://stackoverflow.com/questions/49431554/project-reactor-onerrorresume-after-flatmap/52221567)

EN:
> Flux.just("a", "b").flatMap(s -> s.equals("a") ? Mono.error(new RuntimeException()) : Flux.just(s + "1", s + "2")).onErrorResume(throwable -> Mono.empty())

RU:
> Flux.just("a", "b").flatMap(s -> если s равно "a", 
> то Mono.error(new RuntimeException()
> ), 
> иначе Flux.just(s + "1", s + "2")).onErrorResume(throwable -> Mono.empty())

## 4. Retry с exponential backoff перед fallback

```java
public Flux<Quote> streamQuotesWithRetry(List<String> tickers) {
    return Flux.fromIterable(tickers)
        .flatMap(ticker ->
            callPrimaryExchange(ticker)
                .retryWhen(Retry.backoff(3, Duration.ofMillis(200))  // до 3 повторов, начальная задержка 200мс
                    .maxBackoff(Duration.ofSeconds(2))                // верхний предел задержки
                    .jitter(0.5))                                     // случайный разброс задержки
                .onErrorResume(e -> callBackupExchange(ticker))      // если retry не спас — fallback на резервную биржу
        );
}
```

Для упавшего тикера сначала делается **до 3 повторных** попыток **с растущей задержкой** (200мс → 400мс → 800мс, плюс случайный джиттер), и только если все попытки провалились — срабатывает `onErrorResume`, и запрос уходит на резервную биржу.

[Handling Errors :: Reactor Core Reference Guide](https://projectreactor.io/docs/core/release/reference/coreFeatures/error-handling.html)

EN:
> You can use similar code to implement an "exponential backoff and retry" pattern, as shown in the FAQ.

RU:
> Можно использовать похожий код для реализации паттерна "экспоненциальный backoff и повтор", как показано в FAQ.

## 5. Что такое jitter

`jitter` - добавляет **случайный разброс** к рассчитанной экспоненциальной задержке (например, `jitter(0.5)` означает случайное отклонение до 50% от расчётного значения задержки в обе стороны). 
- **Цель** — "размазать" во времени повторные попытки разных клиентов, столкнувшихся с ошибкой примерно одновременно, чтобы избежать синхронизированной волны нагрузки на восстанавливающийся сервис (проблема "thundering herd").

## 6. Почему это работает именно так

`retryWhen` и `onErrorResume`, поставленные **внутри** лямбды `flatMap` (то есть применённые к отдельному Mono конкретного тикера), полностью изолированы друг от друга по тикерам — ошибка и повторная попытка одного тикера никак не влияют на обработку остальных, потому что каждый inner Publisher — самостоятельная независимая подписка.

[Need an error handler method on Flux when processing a stream of elements](https://github.com/reactor/reactor-core/issues/49)

EN:
> I'd like to have a way to handle discrete errors while processing a stream of elements.

RU:
> Хотелось бы иметь способ обрабатывать отдельные ошибки при обработке потока элементов.

Если бы `retryWhen`/`onErrorResume` стояли **снаружи** `flatMap` (после него, а не внутри лямбды), то при ошибке хотя бы одного элемента пришлось бы пересоздавать подписку на весь `flatMap` целиком, включая уже успешно обработанные элементы — значительно более дорогое поведение.

# Что доходит до клиента при ошибке в flatMap без onErrorResume

## 7. Постановка вопроса

Есть `flatMap` с конкурентностью до 256 inner Publisher'ов, каждый из которых делает отдельный вызов к биржевому сервису за котировкой. 
 - `onErrorResume` внутри не поставлен. 
 - На 103-м из 256 запросов происходит ошибка. 

**Вопрос**: доходят ли до клиента уже успешно полученные до этого момента 135 котировок, или всё пропадает вместе с ошибкой?

## 8. Что происходит с завершёнными inner Publisher'ами при ошибке

Когда `flatMap` получает сигнал ошибки от одного из inner Publisher'ов, ошибка немедленно **транслируется вниз** по цепочке как терминальный сигнал `onError`, и все ещё не завершённые inner Publisher'ы отменяются.

```java
Flux.fromIterable(tickers)
    .flatMap(ticker -> callPrimaryExchange(ticker)) // без onErrorResume — ошибка одного тикера убивает весь Flux
    .subscribe(
        quote -> render(quote),           // вызывается для каждой успешно полученной котировки
        error -> handleStreamBroken(error) // вызывается один раз при обрыве всего потока
    );
```

Но элементы, которые уже успели пройти весь конвейер операторов и попасть подписчику до момента ошибки, никуда не исчезают — они были обработаны через `onNext` раньше, чем возникла ошибка. 
- Дальнейшая _судьба этих данных_ **зависит** _от способа доставки клиенту_.

## 9. Сценарий 1: потоковая передача (SSE / NDJSON / WebSocket)

При потоковой передаче HTTP-ответ начинается сразу: 
 - сервер отправляет заголовки `200 OK` и начинает передавать данные клиенту по мере их появления в потоке.

```java
@GetMapping(value = "/quotes/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<Quote> streamQuotes(@RequestParam List<String> tickers) {
    return Flux.fromIterable(tickers)
        .flatMap(this::callPrimaryExchange); // без onErrorResume
}
```

**135** успешно полученных котировок физически уже уходят по сети клиенту до момента ошибки — они не пропадают. 
 - Но поскольку заголовки `200 OK` уже отправлены, сервер не может заменить их на `503` — статус-код нельзя переиграть после того, как он ушёл в сокет. 
 - Поэтому вместо чистого кода ошибки соединение просто **прерывается** аномально: поток данных внезапно останавливается, TCP-соединение закрывается или приходит специальное завершающее событие ошибки, если оно явно предусмотрено в протоколе.

Для UI **с графиком** котировок это **выглядит так**: 
 - график рисуется по мере поступления данных, а затем обрывается без явного предупреждения — клиенту нужно самому распознать обрыв соединения как сбой и инициировать переподключение.

## 10. Сценарий 2: обычный буферизованный JSON-ответ

Если результат сначала полностью собирается в единый JSON-массив, ситуация иная: сервер обязан дождаться завершения всего потока, прежде чем начать отправку тела ответа.

```java
@GetMapping("/quotes/batch")
public Mono<List<Quote>> getQuotesBatch(@RequestParam List<String> tickers) {
    return Flux.fromIterable(tickers)
        .flatMap(this::callPrimaryExchange)
        .collectList(); // ответ формируется только после завершения ВСЕГО потока
}
```

Заголовки ответа и тело формируются только после того, как весь `Flux` завершится — либо успехом, либо ошибкой.
 - Если ошибка происходит на 103-м элементе из 256, все 135 уже полученных, но не отправленных клиенту котировок безвозвратно теряются: 
  - клиент получает чистый `503` без единого байта полезных данных, потому что тело ответа так и не начало формироваться.

## 11. Итог для сценария с графиком котировок

**При непрерывном построении** графика (потоковая передача через **SSE** или **WebSocket**) применяется **сценарий 1**: 
 - 135 успешных котировок клиент реально увидит на графике — они уже дорисовались, — а затем соединение обрывается без явного кода ошибки. 
 - Клиенту нужно программно отслеживать разрыв соединения на своей стороне и инициировать переподключение самостоятельно.

Именно по этой причине в реальных финансовых приложениях почти всегда используют `onErrorResume`/`retryWhen` внутри `flatMap` — чтобы одна нестабильная котировка не рвала всё соединение и не заставляла клиента переподключаться с нуля каждый раз, когда один из сотен параллельных запросов даёт сбой.

___

**onErrorResume** — позволяет подписаться на резервный издатель (Publisher) при возникновении ошибки. 
 -  Это полезно, например, при неудачном вызове внешней службы — можно реализовать извлечение данных из локального кеша

```java
Flux.just("100", "200", "three", "400")
    .map(Integer::parseInt)
    .onErrorReturn(0); // При ошибке вернёт 0 и завершится

```
