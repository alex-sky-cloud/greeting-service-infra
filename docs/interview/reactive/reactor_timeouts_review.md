## 1. Ключевой тезис

Оператор `.timeout()` в реактивной цепочке — это не универсальный "предохранитель", который стоит расставлять по бизнес-коду. Реальная защита от подвисших запросов строится на уровне инфраструктуры: настроек HTTP-клиента (Netty), connection pool базы данных, и архитектурных решений для CPU-bound задач. Официальная документация по настройке WebClient прямо подтверждает этот подход:

"Keep in mind that it's better to use the more specific timeout configuration options available in Reactor Netty since they provide more control for a specific purpose and use case."
(https://www.baeldung.com/spring-webflux-timeout)

Перевод: "Помните, что лучше использовать более специфичные настройки таймаутов, доступные в Reactor Netty, поскольку они дают больше контроля для конкретной цели и случая использования."

## 2. Три сценария зависшего запроса

Когда клиент видит задержку 30+ секунд вместо привычных 100мс, важно понимать, ГДЕ реально происходит зависание, прежде чем что-то менять в коде:

1. Запрос ушёл в базу данных и не возвращается.
2. Запрос ушёл в удалённый сервис и не возвращается.
3. Обработка идёт локально (чистые вычисления), никуда не ходит по сети.

Каждый сценарий требует своего решения — и ни один из них не решается вставкой `.timeout()` в цепочку операторов бизнес-логики.

---

## 3. Сценарий 1: запрос в базу данных

Реальный разрыв "зависшего" соединения с БД происходит на уровне драйвера и connection pool (например, `socketTimeout`, таймаут транзакции на стороне самой БД), а не через оператор `.timeout()` в реактивном коде. Если БД физически не отвечает — таймаут должен сработать на уровне пула соединений/драйвера, это конфигурация инфраструктуры, а не бизнес-кода.

```java
// НЕ практика: пытаться "лечить" зависшую БД оператором в бизнес-коде
r2dbcTemplate.select(query)
    .timeout(Duration.ofSeconds(1)); // отменяет ПОДПИСКУ и кидает ошибку клиенту,
                                       // но НЕ гарантирует, что запрос в БД реально остановлен
```

Правильный путь — настройка таймаутов на уровне конфигурации пула соединений (R2DBC pool settings) и на уровне самой БД (query timeout), а не через операторы Reactor.

## 4. Сценарий 2: запрос в удалённый сервис

Таймауты для HTTP-вызовов настраиваются один раз, глобально, на уровне `HttpClient` (Reactor Netty), а не разбросаны по отдельным вызовам в бизнес-коде:

```java
HttpClient httpClient = HttpClient.create()
    .responseTimeout(Duration.ofSeconds(1))                          // время ожидания ответа
    .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 10000)             // время установки соединения
    .doOnConnected(conn -> conn
        .addHandler(new ReadTimeoutHandler(10, TimeUnit.SECONDS))    // таймаут чтения данных
        .addHandler(new WriteTimeoutHandler(10)));                   // таймаут записи данных

WebClient webClient = WebClient.builder()
    .clientConnector(new ReactorClientHttpConnector(httpClient))
    .build();
```

Если удалённый сервер не отвечает вовремя, соединение рвётся на уровне Netty (`ReadTimeoutException`, `ConnectTimeoutException`) — это единая точка конфигурации для всех вызовов через данный `WebClient`, а не разброс `.timeout()` по каждому месту вызова в коде.

## 5. Сценарий 3: внутренние CPU-вычисления

Если задержка вызвана не сетевым походом, а долгими локальными вычислениями (например, обычный синхронный `for`-цикл без точек переключения), никакой оператор Reactor физически не может прервать уже выполняющийся код. `cancel()`, вызванный через `.timeout()`, — это кооперативный сигнал: он говорит "перестань слушать этот Subscriber", но если поток занят синхронным вычислением, этот сигнал просто не проверяется, пока вычисление не закончится само:

```java
Mono.fromCallable(() -> heavyCpuComputation()) // синхронный блок без точек прерывания внутри
    .timeout(Duration.ofSeconds(1)); // timeout вернёт ошибку ВЫЗЫВАЮЩЕЙ стороне,
                                       // но heavyCpuComputation() продолжит выполняться на своём потоке до конца
```

Здесь нет решения на уровне операторов Reactor — единственный путь: не допускать долгих синхронных блоков без возможности прерывания на этапе проектирования кода, а не пытаться компенсировать это таймаутом.

## 6. Почему .timeout() в бизнес-коде — не общая практика

Ключевое замечание по итогам обсуждения: таймауты не принято писать разбросанными по бизнес-коду как "защитный слой" на каждый вызов. Правильный подход — централизованная настройка на уровне инфраструктуры:

- Для HTTP-вызовов — единая конфигурация `HttpClient`/Netty на уровне создания `WebClient`.
- Для базы данных — настройка connection pool и таймаутов на стороне самой БД.
- Для CPU-bound задач — архитектурное решение (декомпозиция вычислений), а не попытка "поймать" зависание таймаутом.

Расстановка `.timeout()` по отдельным местам бизнес-логики создаёт иллюзию защиты, но не решает исходную причину (тормозящий источник данных) и добавляет несогласованность в поведение системы (разные таймауты в разных местах вместо единой политики).

## 7. Итоговая таблица

| Сценарий | Где реально настраивается защита | Роль .timeout() в Reactor |
|---|---|---|
| Запрос в БД | Connection pool / настройки драйвера / таймаут на стороне БД | Не решает проблему, не гарантирует остановку запроса на стороне БД |
| Запрос в удалённый сервис | HttpClient / Netty (responseTimeout, ReadTimeoutHandler, ConnectTimeout) | Дублирующий, избыточный слой при верно настроенном HTTP-клиенте |
| Внутренние CPU-вычисления | Архитектурная декомпозиция, отсутствие долгих синхронных блоков | Не может прервать уже выполняющийся синхронный код (кооперативная отмена) |
