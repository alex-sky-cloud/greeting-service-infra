## 1. Контракт flatMap

**Сигнатура оператора**: 
 - `Function<T, Publisher<R>>` — функция принимает элемент типа `T` и возвращает `Publisher<R>` (новый асинхронный мини-поток). `flatMap` подписывается на эти внутренние `Publisher` конкурентно (по умолчанию до 256 одновременных подписок), и результаты вливаются в общий выходной поток по факту завершения, а не по порядку старта.

**Важное уточнение**: 
 - конкурентность здесь — это не многопоточность в смысле разных потоков CPU, а параллельная работа нескольких активных `Subscription` одновременно. 
 - Если не добавлен `subscribeOn`, все подписки всё ещё исполняются кооперативно на одном потоке.

## 2. map — синхронная распаковка на месте

`map` — простая синхронная трансформация "значение → значение" без похода куда-либо (в БД, в сеть). 
- Он не работает с `Publisher`, только с обычными значениями.

```java
/**
 * Пример: получаем сырые данные из БД (уже распакованный объект User),
 * и синхронно извлекаем из него email — никакого нового асинхронного вызова здесь не происходит.
 */
Mono<User> userMono = userRepository.findById(userId); // Mono<User> — уже готовый результат из БД

Mono<String> emailMono = userMono
    .map(User::getEmail); // просто синхронно достаём поле объекта, без нового Publisher
```

```textmate
Преобразовывает элемент, который издается этим {@link Mono}, применяя к нему синхронную функцию. 

mapper – Function синхронного преобразования
<R> - тип объекта после преобразования, то есть результирующий тип
```

```java

	public final <R> Mono<R> map(Function<? super T, ? extends R> mapper) {
		if (this instanceof Fuseable) {
			return onAssembly(new MonoMapFuseable<>(this, mapper));
		}
		return onAssembly(new MonoMap<>(this, mapper));
	}
```

## 3. flatMap — конкурентная обработка без гарантии порядка

`flatMap` порождает для каждого элемента новый `Publisher` (асинхронный вызов) и подписывается на них практически одновременно. 
 - **Порядок** результатов в выходном потоке **НЕ гарантирован** — он зависит от того, какой внутренний вызов завершился быстрее.

```java
/**
 * Пример: для каждого id товара делаем отдельный асинхронный запрос цены.
 * Порядок цен в результирующем Flux может НЕ совпадать с порядком productIds,
 * потому что разные запросы к prices-сервису могут завершаться в разное время.
 */
Flux<ProductId> productIds = Flux.just(id1, id2, id3);

Flux<Price> prices = productIds
    .flatMap(id -> priceService.getPrice(id)); // каждый вызов — отдельный асинхронный Publisher,
                                                 // все подписки идут конкурентно
```

```textmate
 Преобразовывает элементы, входного потока (Flux) , асинхронно в inner Publishers, 
а затем соединяет в один поток, эти внутренние издатели в единое Flux через слияние, 
что позволяет им взаимодействовать
```

```java

public final <R> Flux<R> flatMap(Function<? super T, ? extends Publisher<? extends R>> mapper) {
    return flatMap(mapper, Queues.SMALL_BUFFER_SIZE, Queues
            .XS_BUFFER_SIZE);
}
```

## 4. concatMap — строго последовательная обработка

`concatMap` тоже принимает `Function<T, Publisher<R>>`, но подписывается на внутренний `Publisher` для СЛЕДУЮЩЕГО элемента только после полного завершения предыдущего. 
- Порядок строго гарантирован, но обработка медленнее, чем у **flatMap**, так как нет конкурентности.

```java
/**
 * Пример: та же задача с ценами товаров, но теперь порядок важен —
 * например, нужно последовательно логировать цены в том же порядке, что и id.
 * concatMap НЕ начнёт запрос для id2, пока не получит ответ для id1.
 */
Flux<Price> orderedPrices = productIds
    .concatMap(id -> priceService.getPrice(id)); // строго по очереди, порядок id1 -> id2 -> id3 сохранён
```

## 5. Баг в проде: нарушение порядка списания средств

- Классическая ошибка — использовать `flatMap` там, 
где бизнес-логика требует строгой последовательности операций.

```java
/**
 * ЗАДАЧА: списать средства сначала с основного счёта, а при недостатке —
 * со резервного. Порядок списания критичен для корректной работы системы.
 */
Flux<AccountId> accountsToDebit = Flux.just(mainAccount, reserveAccount);

// БАГ: flatMap не гарантирует порядок — reserveAccount может списаться РАНЬШЕ mainAccount,
// если внутренний вызов paymentService.debit() для него завершится быстрее
accountsToDebit
    .flatMap(accId -> paymentService.debit(accId, amount))
    .subscribe();
```

```java
/**
 * ИСПРАВЛЕНИЕ: concatMap гарантирует, что списание с reserveAccount
 * начнётся только ПОСЛЕ завершения списания с mainAccount.
 */
accountsToDebit
    .concatMap(accId -> paymentService.debit(accId, amount)) // строгий порядок: main -> reserve
    .subscribe();
```

## 6. Утечка ресурсов из-за неограниченной конкурентности

- Если внутри `flatMap` открывается ресурс (например, соединение с внешней системой), 
- а источник эмитит очень много элементов очень быстро, 
- `flatMap` по умолчанию откроет до 256 параллельных подписок одновременно. 
  - Это может исчерпать пул соединений или память, если каждая внутренняя операция держит ресурс в открытом состоянии.

```java
/**
 * ПРОБЛЕМА: если orderIds эмитит десятки тысяч элементов,
 * flatMap попытается открыть до 256 одновременных соединений с внешним сервисом,
 * что может истощить connection pool или память.
 */
Flux<OrderId> orderIds = orderRepository.findAllPendingOrderIds(); // может быть очень много элементов

orderIds
    .flatMap(id -> externalAuditService.sendAuditRecord(id)) // неограниченная конкурентность
    .subscribe();
```

```java
/**
 * РЕШЕНИЕ: явно ограничиваем количество одновременных подписок,
 * чтобы не превысить возможности connection pool внешнего сервиса.
 */
orderIds
    .flatMap(id -> externalAuditService.sendAuditRecord(id), 16) // не более 16 одновременных вызовов
    .subscribe();
```

## 7. flatMapSequential и concatMap и flatMap

`flatMapSequential` и `concatMap` дают одинаковый **порядок результатов**, 
- но по-разному его добиваются — и это влияет на скорость.

## Ключевое отличие

| Критерий | `concatMap` | `flatMapSequential` |
| :-- | :-- | :-- |
| Когда начинается подписка на следующий элемент | Только после полного завершения предыдущего `Publisher` | Сразу, параллельно с предыдущими (как у `flatMap`) |
| Конкурентность | Нет — строго один за другим | Есть — несколько внутренних `Publisher` работают одновременно |
| Как достигается порядок | Естественно, так как всё выполняется последовательно | Через буферизацию: если "быстрый" элемент завершился раньше "медленного", который стоит перед ним по порядку, его результат ставится в очередь и ждёт |
| Скорость | Медленнее — нет параллелизма | Быстрее — параллелизм есть, но с накладными расходами на буфер |

`concatMap` ждёт завершения одного внутреннего `Publisher`, прежде чем создать и подписаться на следующий.

- Источник: https://stackoverflow.com/questions/71971062/whats-the-difference-between-flatmap-flatmapsequential-and-concatmap-in-project-reactor

EN:

> "this operator waits for one inner to complete before generating the next one and subscribing to it."

RU:

> «этот оператор ждёт завершения одного внутреннего Publisher, прежде чем сгенерировать следующий и подписаться на него».

`flatMapSequential`, наоборот, подписывается на внутренние `Publisher` жадно (eagerly), то есть параллельно, как и `flatMap`, но при этом ставит в очередь результаты элементов, которые завершились раньше "своей очереди", и не отдаёт их наружу, пока не будут отправлены все предыдущие по порядку.

- Источник: https://stackoverflow.com/questions/71971062/whats-the-difference-between-flatmap-flatmapsequential-and-concatmap-in-project-reactor

EN:

> "flatMapSequential has subscribed to all three elements eagerly like flatMap but preserves the order by queuing elements received out of order."

RU:

> «flatMapSequential подписывается на все элементы жадно, как flatMap, но сохраняет порядок за счёт постановки в очередь элементов, полученных не по порядку».

## Практический вывод

- `concatMap` — когда важен и порядок, и **строгая последовательность выполнения** (например, списание со счетов, где нельзя начинать вторую операцию, пока не завершилась первая — тот самый пример из вашего файла).
- `flatMapSequential` — когда важен порядок **результата**, но сами асинхронные вызовы независимы и можно позволить им выполняться параллельно (например, параллельные HTTP-запросы за ценами товаров, но вывести цены нужно в исходном порядке id).

Иначе говоря: `concatMap` — последовательный **и по выполнению, и по результату**; `flatMapSequential` — параллельный по выполнению, но последовательный только по итоговому порядку выдачи.

- Источник: https://eherrera.net/project-reactor-course/04-using-other-reactive-operators/transforming-sequences.html

---
Оба оператора почти сразу подписываются на несколько внутренних `Publisher`. 
- Но дальше они ведут себя по-разному. Reactor прямо описывает `flatMapSequential` как оператор, который запускает асинхронные процессы сразу, а затем переупорядочивает результаты.

- Источник: https://projectreactor.io/docs/core/release/reference/apdx-operatorChoice.html

EN:

> “…retaining the original sequence order: Flux\#flatMapSequential (this triggers the async processes immediately but reorders the results)”

RU:

> «…для сохранения исходного порядка последовательности: `Flux#flatMapSequential` (он сразу запускает асинхронные процессы, но затем переупорядочивает результаты)».

```text
Исходный Flux:     A ─── B ─── C

Внутренние Mono:
A → завершится через 3 секунды
B → завершится через 1 секунду
C → завершится через 2 секунды
```


## `flatMap`

`flatMap` отдаёт результат сразу, как только соответствующий внутренний `Publisher` его отправил. Поэтому здесь получится порядок `B → C → A`.

```text
Подписки:          A, B, C

Завершение:        B ─── C ─── A
Выход flatMap:     B ─── C ─── A
```

`flatMap` объединяет внутренние потоки так, что их элементы могут перемешиваться (`interleave`), поэтому исходный порядок не гарантируется.

- Источник: https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Flux.html

EN:

> “Transform the elements emitted by this `Flux` asynchronously into Publishers, then flatten these inner publishers into a single `Flux` through merging, which allow them to interleave.”

RU:

> «Асинхронно преобразует элементы этого Flux во внутренние Publisher, а затем объединяет их в один Flux; при этом их элементы могут перемешиваться».

## `flatMapSequential`

`flatMapSequential` тоже запускает A, B и C без ожидания завершения друг друга. Но когда B завершится первым, его результат **не выдаётся сразу**: оператор временно сохраняет его в буфере, потому что до B в исходной последовательности был A.

```text
Подписки:                    A, B, C

Фактическое завершение:      B ─── C ─── A
Буфер:                       [B] → [B, C] → очищается
Выход flatMapSequential:     A ─── B ─── C
```

То есть `flatMapSequential` сохраняет порядок **исходных элементов**, а не порядок фактического завершения операций.

- Источник: https://projectreactor.io/docs/core/release/reference/apdx-operatorChoice.html

EN:

> “this triggers the async processes immediately but reorders the results”

RU:

> «этот оператор сразу запускает асинхронные процессы, но затем переупорядочивает результаты».

## В одной фразе

- `flatMap`: «результат готов — сразу отдай его».
- `flatMapSequential`: «результат готов — сохрани его, если перед ним ещё не выданы результаты более ранних элементов».

## 7. Сравнительная таблица

| Оператор | Работает с | Подписка на внутренние Publisher | Порядок результатов | Типичный риск |
|---|---|---|---|---|
| `map` | Значение -> значение (синхронно) | Не применимо (нет Publisher) | Всегда совпадает с исходным | Нет асинхронности — не подходит для походов в БД/сеть |
| `flatMap` | Значение -> Publisher (асинхронно) | Конкурентно, до 256 одновременно по умолчанию | НЕ гарантирован | Нарушение порядка обработки; истощение ресурсов при большом источнике |
| `concatMap` | Значение -> Publisher (асинхронно) | Строго по очереди, одна за одной | Строго гарантирован | Более медленная обработка из-за отсутствия конкурентности |
