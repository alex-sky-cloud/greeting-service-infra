## Задача 1. Сводка по jstat

**Ситуация:**

Дежурный снял статистику сборок раз в 5 секунд, как в [разделе 4 теории](02-jdk-tools.md#4-jstat-сборки-мусора-в-реальном-времени). Глазами считать разницу по сотне строк долго, нужна сводка за окно.

**Что сделать:**

`analyze(List<String> jstatOutput)` — сводка между первой и последней строкой данных.

1. Столбцы искать по имени в заголовке, а не по номеру: набор столбцов зависит от версии JDK и сборщика.
2. Заголовок может повторяться посреди вывода — это не строка данных.
3. Дробная часть может быть через запятую или через точку.
4. Секунды, молодые и полные сборки — разница между последней и первой строкой.
5. Доля времени в GC — прирост общего времени сборок к длине окна, в процентах.
6. Заполнение старого поколения — как есть, из первой и из последней строки.
7. Меньше двух строк данных или нет заголовка — `IllegalArgumentException`.

**Ожидаемый результат:**

| Вход | Секунды | Молодые | Полные | GC, % | Старое поколение, % |
|---|---|---|---|---|---|
| `leak-jstat.txt` целиком | 205,3 | 575 | 44 | 1,887 | 83,06 → 99,37 |
| заголовок и последние 3 строки `leak-jstat.txt` | 10,0 | 39 | 39 | 21,58 | — |
| `churn-jstat.txt` | 28,0 | 1 789 | 0 | 4,921 | 4,53 → 4,80 |
| две строки с точкой и повтором заголовка | 10,0 | 20 | 1 | 5,0 | 20 → 25 |

**После теста ответьте в чате:**

1. Почему у `leak` по всей записи GC «всего» 1,9 %, хотя сервис умирает?
2. У `churn` молодых сборок втрое больше. Почему это не утечка?

## Задача 2. Что выросло между двумя гистограммами

**Ситуация:**

Сняли две переписи живых объектов с разницей в минуту, как в [разделе 5 теории](02-jdk-tools.md#5-гистограмма-кучи-кто-занимает-память). Нужен список того, что прибывает.

**Что сделать:**

`topGrowers(String before, String after, int n)` — до `n` классов, у которых выросли байты.

1. Строка гистограммы: номер с двоеточием, число объектов, байты, имя класса. Суффикс модуля вида ` (java.base@27)` в имя не входит.
2. Строки заголовка, разделителя и `Total` пропускаются.
3. Класса не было в первой гистограмме — рост от нуля.
4. Байты не выросли — класс в ответ не попадает.
5. Порядок — по росту байт от большего к меньшему; при равенстве — по имени класса.

**Ожидаемый результат:**

`leak-histogram-14s.txt` → `leak-histogram-82s.txt`, `n = 5`:

| Класс | Объектов | Байт |
|---|---|---|
| `[B` | +112 408 | +22 485 592 |
| `java.lang.String` | +74 931 | +1 798 344 |
| `com.example.profcourse.t03.UserSession` | +37 477 | +899 448 |
| `java.time.Instant` | +37 477 | +899 448 |
| `java.util.concurrent.ConcurrentHashMap$Node` | +37 475 | +899 400 |

Синтетический случай: `[B` уменьшился, `String` вырос на 20 объектов / 480 байт, новый `com.example.shop.Basket` — 5 объектов / 120 байт. Ответ — `String`, затем `Basket`.

**После теста ответьте в чате:**

1. Какой класс из этого списка вы назовёте в тикете и почему не `[B`?
2. Почему `UserSession`, `Instant` и `ConcurrentHashMap$Node` выросли на одно число?

## Лабораторная. Утечка сессий

Подготовка терминалов — [00-plan.md, раздел «Лаборатория»](00-plan.md#лаборатория).

**Терминал 1** — лаборатория с маленькой кучей и GC-логом:

```bash

mkdir -p build/lab
java -Xmx96m -Xlog:gc:file=build/lab/leak-gc.log \
  -cp build/classes/java/main com.example.profcourse.lab.LabApp leak
```

**Терминал 2** — паспорт процесса:

```bash

PID=$(jcmd | awk '/LabApp leak/ {print $1}')
echo "$PID"
jcmd "$PID" VM.version
jcmd "$PID" VM.flags | tr ' ' '\n' | grep -E 'MaxHeapSize|Use.*GC'
jcmd "$PID" GC.heap_info
```

**Терминал 2** — статистика сборок раз в 5 секунд, до падения лаборатории:

```bash

jstat -gcutil -t "$PID" 5000 | tee build/lab/leak-jstat.txt
```

**Терминал 3** — две гистограммы: сразу и примерно через минуту:

```bash

PID=$(jcmd | awk '/LabApp leak/ {print $1}')
jcmd "$PID" GC.class_histogram > build/lab/histo-1.txt
sleep 60
jcmd "$PID" GC.class_histogram > build/lab/histo-2.txt
head -12 build/lab/histo-2.txt
```

Через 3–4 минуты лаборатория упадёт с `OutOfMemoryError`. После этого:

```bash

grep -c 'Pause Full' build/lab/leak-gc.log
grep 'Heap Inspection' build/lab/leak-gc.log
tail -5 build/lab/leak-gc.log
```

**Ответьте в чате:**

1. Сколько `MaxHeapSize` показал `VM.flags` и совпадает ли с `-Xmx96m`?
2. За сколько секунд до падения `FGC` в `jstat` начал расти каждую строку?
3. Какие строки `Pause Full` в GC-логе вызвали вы сами, а не нехватка памяти?
4. Какой класс приложения растёт между `histo-1.txt` и `histo-2.txt`? Совпало ли с задачей 2?
5. Почему лаборатория сначала печатает «сессий в реестре» больше 1 800 и это уже признак ошибки?
