## Правила

| Задача | Класс решения | Тест |
|---|---|---|
| 1 | `t06/T06ReportBuilder` | `T06TasksTest.Task1` |
| 2 | `t06/T06Reconciler` | `T06TasksTest.Task2` |

Готовые классы:

- `Order` — заказ: номер, номер карты, сумма в копейках, время создания; `Order.sample(n)` — одинаковый набор при каждом запуске;
- `LegacyReportBuilder` — выгрузка, которая ушла в продакшен; её запускает лаборатория `report`;
- `Payment`, `StatementLine` — платёж и строка выписки банка; `Reconciliation` — набор платежей и выписка к нему: каждого 50-го платежа в выписке нет, каждый 77-й зачислен на копейку меньше, порядок выписки перемешан;
- `LegacyReconciler` — сверка, которая ушла в продакшен; её запускает лаборатория `reconcile`.

Тесты сравнивают время «было» и «стало» на вашей машине и печатают его.

## Задача 1. Выгрузка для бухгалтерии

**Ситуация:**

Ежемесячная выгрузка заказов занимает CPU целиком. Профиль из [раздела 5 теории](06-cpu.md#5-интуиция-о-горячем-месте-обманывает) показал, что горит не то, на что думала команда.

**Что сделать:**

`build(List<Order> orders)` — тот же текст, что у `LegacyReportBuilder`, быстрее.

1. Строка на заказ: номер, дата и время `дд.ММ.гггг чч:мм`, номер карты, где все цифры кроме последних четырёх заменены на `*`, сумма в рублях с копейками через точку. Разделитель — `;`, в конце строки — `\n`.
2. Текст должен совпасть со старой выгрузкой символ в символ: бухгалтерия загружает его в свою программу.
3. Пустой список — пустая строка.
4. Начните с того, что горит в профиле. Остальное — если замер покажет, что этого мало.

**Ожидаемый результат:**

- 1 200 заказов — текст равен старому;
- первая строка — `ORD-000001;01.10.2026 09:01;************7919;100.37`;
- 8 000 заказов — минимум в 5 раз быстрее старой выгрузки на той же машине.

**После теста ответьте в чате:**

1. Во сколько раз стало быстрее? Что дало основной выигрыш?
2. Почему одним форматтером можно пользоваться из разных потоков?

## Задача 2. Ночная сверка с банком

**Ситуация:**

Сверка платежей с выпиской банка раньше шла 10 минут, после роста клиентской базы — часами и не успевает к открытию операционного дня. Профиль из [раздела 6 теории](06-cpu.md#6-алгоритм-а-не-микрооптимизация): вся вершина — сравнение строк.

**Что сделать:**

`unmatched(List<Payment> payments, List<StatementLine> statement)` — те же расхождения, что у `LegacyReconciler`, быстрее.

1. Расхождение — платежа нет в выписке или он зачислен на другую сумму.
2. Ответ — номера платежей в порядке списка `payments`.
3. Выписка приходит в произвольном порядке.

**Ожидаемый результат:**

- 3 000 платежей — 98 расхождений, первые — `P-000050`, `P-000077`, `P-000100`; список равен старому;
- 10 000 платежей — минимум в 20 раз быстрее старой сверки на той же машине.

**После теста ответьте в чате:**

1. Во сколько раз стало быстрее на 10 000 платежей? Во сколько станет на 100 000 — и почему не столько же?
2. Почему ускорять сравнение строк было бы бесполезно?

## Лабораторная. Профиль до и после

Подготовка терминалов — [00-plan.md, раздел «Лаборатория»](00-plan.md#лаборатория).

**Часть 1** — сверка без флага точности и с ним, по 20 секунд:

```bash

mkdir -p build/lab
java -XX:StartFlightRecording:settings=profile,duration=20s,filename=build/lab/rec-plain.jfr \
  -cp build/classes/java/main com.example.profcourse.lab.LabApp reconcile
```

Через 25 секунд — `Ctrl+C`, затем:

```bash

java -XX:+UnlockDiagnosticVMOptions -XX:+DebugNonSafepoints \
  -XX:StartFlightRecording:settings=profile,duration=20s,filename=build/lab/rec-dns.jfr \
  -cp build/classes/java/main com.example.profcourse.lab.LabApp reconcile
```

Через 25 секунд — `Ctrl+C`, затем:

```bash

jfr view hot-methods build/lab/rec-plain.jfr | head -10
jfr view hot-methods build/lab/rec-dns.jfr | head -10
```

**Часть 2** — профиль выгрузки, затем flame graph в JMC:

```bash

java -XX:+UnlockDiagnosticVMOptions -XX:+DebugNonSafepoints \
  -XX:StartFlightRecording:settings=profile,duration=20s,filename=build/lab/report-cpu.jfr \
  -cp build/classes/java/main com.example.profcourse.lab.LabApp report
```

Через 25 секунд — `Ctrl+C`. Затем в JMC (запуск с флагом Edge — [тема 05](05-jfr-jmc.md#запуск-jmc)):

1. **File → Open File…** → в поле **Имя файла** путь к `build\lab\report-cpu.jfr` → **Открыть**.

   ![JMC: меню File → Open File](images/05-jmc-open-file-menu.png)

2. В дереве **Outline** — **Java Application → Method Profiling**.
3. Внизу — вкладка **Flame View**; двойной щелчок по её заголовку разворачивает панель.
4. Наведите мышь на самый широкий кадр — подсказка покажет число сэмплов.

Как читать панель — [тема 06, «Flame View в JMC»](06-cpu.md#flame-view-в-jmc).

**Часть 3** — после решения задач: замер «было/стало» из тестов:

```bash

./gradlew test --rerun --tests "com.example.profcourse.t06.*" | grep 'стало'
```

**Ответьте в чате:**

1. Какая вершина у сверки без флага и с флагом? Какой кадр приложения общий?
2. Почему `ArrayList.grow` с 90 % не может быть правдой в этой сверке?
3. Сколько миллисекунд печатает лаборатория `reconcile` на одну сверку?
4. Во flame graph выгрузки: какое плато самое широкое, сколько в нём сэмплов и какой первый кадр приложения на пути от него к корню?
5. Цифры «было/стало» из части 3 для обеих задач.
