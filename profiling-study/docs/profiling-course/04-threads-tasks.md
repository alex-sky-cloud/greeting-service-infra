## Задача 1. Встречные переводы без зависания

**Ситуация:**

Раз в несколько дней переводы между счетами клиентов перестают проходить, помогает только перезапуск. Дамп показал взаимную блокировку в `LegacyTransfers.transfer`, как в [разделе 4 теории](04-threads.md#4-взаимная-блокировка).

**Что сделать:**

`transfer(Account from, Account to, long amount)` — перевод, который не зависает при любом числе встречных переводов.

1. Перевод атомарен: другой поток не видит списание без зачисления.
2. Денег не хватает — `IllegalStateException`, балансы не меняются.
3. Встречные переводы A → B и B → A из разных потоков не должны ждать друг друга вечно.

**Ожидаемый результат:**

| Сценарий | Результат |
|---|---|
| 4 потока: два переводят A → B, два B → A, по 5 000 раз по 3 копейки | всё завершилось за 20 с, взаимной блокировки нет, балансы — по 1 000 000 |
| со счёта со 100 копейками перевести 101 | `IllegalStateException`, балансы 100 и 0 |

**После теста ответьте в чате:**

1. Почему «вероятность мала» — не аргумент для `LegacyTransfers`?
2. Что вы сделаете, если у счетов нет естественного порядка?

## Задача 2. Где стоят обработчики по дампу

**Ситуация:**

Дежурный снял дамп со 120 потоками. Читать его глазами в инциденте долго, нужна сводка, как в [разделе 3 теории](04-threads.md#3-очередь-к-пулу-cpu-свободен-а-всё-стоит).

**Что сделать:**

`hotspots(String dump, String threadPrefix)` — сгруппировать потоки, чьё имя начинается с `threadPrefix`.

1. Поток в дампе — заголовок в кавычках, строка `java.lang.Thread.State: …`, затем кадры `at …`.
2. Ключ группы — состояние и первый кадр нашего кода: класс и метод из пакета `com.example.`, кроме общих утилит `com.example.profcourse.common`.
3. Блок взаимной блокировки в конце дампа повторяет имена потоков без состояния — их второй раз не считать.
4. Порядок — по числу потоков от большего к меньшему; при равенстве — по кадру.
5. Таких потоков нет — пустой список.

**Ожидаемый результат:**

| Дамп | Префикс | Ответ |
|---|---|---|
| `pool-thread-print.txt` | `http-nio-` | `WAITING ConnectionPool.borrow` — 16; `TIMED_WAITING OrderController.chargeCard` — 4 |
| `deadlock-thread-print.txt` | `transfer-` | `BLOCKED LegacyTransfers.transfer` — 2 |
| `pool-thread-print.txt` | `kafka-` | пусто |

Кадр в ответе — полное имя: `com.example.profcourse.t04.ConnectionPool.borrow`.

**После теста ответьте в чате:**

1. Почему кадр `Slow.sleep` пропускается и что стояло бы на его месте в проде?
2. Как по этой сводке понять размер пула, не открывая код?

## Лабораторная. Пул, зависание, журнал

Подготовка терминалов — [00-plan.md, раздел «Лаборатория»](00-plan.md#лаборатория). Каждую лабораторию останавливайте `Ctrl+C` перед следующей.

**Часть 1. Терминал 1** — оформление заказов:

```bash

java -cp build/classes/java/main com.example.profcourse.lab.LabApp pool
```

**Часть 1. Терминал 2** — три дампа и загрузка CPU:

```bash

PID=$(jcmd | awk '/LabApp pool/ {print $1}')
mkdir -p build/lab
for i in 1 2 3; do jcmd "$PID" Thread.print > "build/lab/pool-$i.txt"; sleep 5; done
grep -h -A 8 '"http-nio' build/lab/pool-1.txt | grep -E 'State:|at com.example' | sort | uniq -c | sort -rn | head
top -b -n 1 -p "$PID" | tail -2
```

**Часть 2. Терминал 1** — переводы:

```bash

java -cp build/classes/java/main com.example.profcourse.lab.LabApp deadlock
```

**Часть 2. Терминал 2:**

```bash

PID=$(jcmd | awk '/LabApp deadlock/ {print $1}')
jcmd "$PID" Thread.print | sed -n '/Found one Java-level deadlock/,/Found 1 deadlock/p'
```

**Часть 2. VisualVM** — тот же процесс, не останавливая его:

1. **Applications → Local** — двойной щелчок по `LabApp (pid …)` с аргументом `deadlock` (виден на вкладке **Overview**).
2. Вкладка **Threads**: что написано над шкалой времени и какого цвета строки `transfer-`?
3. Кнопка **Thread Dump**, щелчок в текст дампа, затем `Ctrl+End` — конец дампа.

Где эти элементы — [теория, «То же в VisualVM»](04-threads.md#то-же-в-visualvm).

**Часть 3. Терминал 1** — журнал аудита с записью JFR на 20 секунд:

```bash

java -XX:StartFlightRecording:duration=20s,filename=build/lab/audit.jfr \
  -cp build/classes/java/main com.example.profcourse.lab.LabApp audit
```

**Часть 3. Терминал 2** — дамп сразу, сводка JFR через 20 секунд:

```bash

PID=$(jcmd | awk '/LabApp audit/ {print $1}')
jcmd "$PID" Thread.print | grep -c 'State: BLOCKED'
sleep 25
jfr view contention-by-site build/lab/audit.jfr
```

**Часть 3. JMC** — **File → Open File…** → `build\lab\audit.jfr`, в дереве **Outline** — **Java Application → Lock Instances**. Как читать страницу — [теория, «То же в JMC»](04-threads.md#то-же-в-jmc).

**Ответьте в чате:**

1. `pool`: сколько потоков в каждой группе? Двигаются ли они между тремя дампами?
2. `pool`: сколько CPU занимает процесс? Что бы показал CPU-профиль?
3. `deadlock`: какие счета и в каком порядке держат потоки?
4. `audit`: сколько потоков `BLOCKED`? Среднее и худшее ожидание по JFR?
5. `audit`: почему среднее ожидание в десятки раз больше 5 мс работы `write`?
6. `deadlock` в VisualVM: что показала вкладка Threads до снятия дампа?
7. `audit` в JMC: сколько суммарно ждали все потоки на мониторе и сколько разных потоков ждали?
