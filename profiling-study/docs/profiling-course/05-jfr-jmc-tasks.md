## Задача 1. Горячие методы по записи

**Ситуация:**

Скоринг заявок стал отвечать за 2 секунды вместо 300 мс. Запись JFR снята, но открыть её в JMC на сервере нельзя — нужна сводка из кода, как `hot-methods` в [разделе 5 теории](05-jfr-jmc.md#5-прочитать-запись-jfr-summary-и-jfr-view).

**Что сделать:**

`top(Path recording, int n)` — до `n` методов, которые чаще всего были на вершине стека.

1. Считать только события сэмплов исполнения Java-кода.
2. Метод — верхний кадр стека события: полное имя класса, точка, имя метода. Например, `com.example.profcourse.t05.RiskScoring.simulate`.
3. События без стека пропустить.
4. Порядок — по числу сэмплов от большего к меньшему.

**Ожидаемый результат:**

- запись 2 секунд скоринга, сэмпл раз в 10 мс;
- первый метод — `com.example.profcourse.t05.RiskScoring.simulate`;
- у него больше половины всех сэмплов записи;
- в ответе не больше 3 методов, по убыванию.

**После теста ответьте в чате:**

1. Почему в ответе нет `RiskScoring.score`, хотя весь скоринг идёт через него?
2. Что увидит ваш метод, если поток всё время ждёт ответа базы?

## Задача 2. Запись после медленного запроса

**Ситуация:**

Медленные запросы случаются раз в час, и к приходу дежурного картины уже нет. Решили: сервис сам держит постоянную запись и сохраняет её, как только запрос оказался медленным, как в [разделе 4 теории](05-jfr-jmc.md#4-постоянная-запись-и-выгрузка-после-инцидента).

**Что сделать:**

`T05IncidentRecorder(Path directory, Duration minGap)`:

1. `start()` — постоянная запись по стандартному шаблону для продакшена: хранит последние 5 минут, не больше 50 МБ, данные на диске.
2. `onRequest(String requestId, Duration latency)` — запрос медленный, если длился не меньше `SLOW` (500 мс). Медленный — сохранить запись в `directory/incident-<requestId>.jfr` и вернуть путь.
3. Быстрый запрос — пустой результат.
4. С прошлого сохранения прошло меньше `minGap` — не сохранять: волна медленных запросов не должна забить диск.
5. `close()` — запись остановлена и освобождена.

**Ожидаемый результат:**

| Шаг | Результат |
|---|---|
| после `start()` | работает запись: 5 минут, 50 МБ, на диске, сборки мусора включены |
| `r-1`, 120 мс | пусто |
| `r-2`, 1 700 мс | `incident-r-2.jfr`, в нём есть сэмплы стека и конфигурация кучи |
| сразу `r-3`, 3 с | пусто — прошло меньше 800 мс |
| через 900 мс `r-4`, ровно 500 мс | `incident-r-4.jfr` |
| после `close()` | ни одной работающей записи |

**После теста ответьте в чате:**

1. Почему запись должна идти постоянно, а не начинаться в момент медленного запроса?
2. Что вы добавите, прежде чем отдавать такие файлы наружу?

## Лабораторная. Запись выгрузки для бухгалтерии

Подготовка терминалов — [00-plan.md, раздел «Лаборатория»](00-plan.md#лаборатория).

**Ситуация:**

Ежемесячная выгрузка заказов для бухгалтерии занимает CPU целиком. Команда уверена, что виновата склейка строк.

**Терминал 1** — выгрузка с постоянной записью:

```bash

mkdir -p build/lab
java -XX:StartFlightRecording:name=continuous,maxage=10m,maxsize=100m \
  -cp build/classes/java/main com.example.profcourse.lab.LabApp report
```

**Терминал 2** — через 30 секунд сохранить запись и прочитать:

```bash

PID=$(jcmd | awk '/LabApp report/ {print $1}')
jcmd "$PID" JFR.check
jcmd "$PID" JFR.dump name=continuous filename="$PWD/build/lab/report.jfr"
jfr summary build/lab/report.jfr | head -25
jfr view hot-methods build/lab/report.jfr
```

**Терминал 2** — секундомер на два метода, 15 секунд:

```bash

jcmd "$PID" JFR.start name=timing duration=15s \
  "method-timing=com.example.profcourse.t06.LegacyReportBuilder::build;java.time.format.DateTimeFormatter::ofPattern" \
  filename="$PWD/build/lab/report-timing.jfr"
sleep 20
jfr view method-timing build/lab/report-timing.jfr
```

**Терминал 2** — очистить запись перед передачей:

```bash

jfr scrub --exclude-events InitialEnvironmentVariable,InitialSystemProperty \
  build/lab/report.jfr build/lab/report-clean.jfr
jfr summary build/lab/report.jfr | grep Initial
jfr summary build/lab/report-clean.jfr | grep Initial
```

**JMC** — запуск с флагом Edge, как в [теории](05-jfr-jmc.md#запуск-jmc):

1. **File → Open File…** — в поле **Имя файла** путь к `build\lab\report.jfr` → **Открыть**.

   ![JMC: меню File → Open File](images/05-jmc-open-file-menu.png)

   ![JMC: диалог Open File](images/05-jmc-open-file-dialog.png)

2. Первой откроется страница **Automated Analysis Results**. Щёлкните красное или жёлтое правило — раскроется объяснение.
3. В дереве **Outline** — **Java Application → Method Profiling**: верхняя строка таблицы и панель **Stack Trace** под ней.

Что где на этих страницах — [теория, раздел 6](05-jfr-jmc.md#6-jmc-автоматический-анализ).

**Ответьте в чате:**

1. Какой метод на первом месте в `hot-methods` и сколько процентов? Права ли команда про склейку строк?
2. Сколько раз вызван `ofPattern` и сколько раз `build`? Сколько строк в одной выгрузке?
3. Сколько в среднем длится `build` — и сколько он печатает в терминале 1? Почему почти совпадает?
4. Сколько событий `Initial…` было до `scrub` и после? Какое осталось и стоит ли убрать и его?
5. Какие правила JMC отметил как самые серьёзные? Какие из них про сервис, а какие про машину, на которой шла запись?
6. Какой путь вызова показывает Stack Trace для верхнего метода Method Profiling — до первого кадра приложения?
