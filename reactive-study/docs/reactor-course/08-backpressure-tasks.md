## Задача 1. Читать источник порциями не больше 500

**Ситуация:**

Выгрузка запрашивает все строки сразу. Источник — постраничное чтение, и большие запросы ему вредны.

Строки нужны все.

**Что сделать:**

`inBatchesOf500(Flux<Integer> source)`.

**Ожидаемый результат:**

Для источника из 10 000 чисел:

- приходят все 10 000;
- первый запрос к источнику — 500;
- ни один запрос не больше 500.

## Задача 2. Средняя цена по каждой тысяче котировок

**Ситуация:**

Аналитику нужен грубый график: средняя цена по каждым 1000 котировкам в порядке `id`.

**Что сделать:**

`averagePricePerThousand()`.

1. По одному значению на каждую тысячу котировок.
2. Округление до 2 знаков, половина — вверх (`RoundingMode.HALF_UP`).

**Ожидаемый результат:**

10 значений. Они совпадают с результатом SQL:

```sql
select round(avg(price), 2)
from reactive_study.rc_price_ticks
group by (id - 1) / 1000
order by (id - 1) / 1000;
```

## Задача 3. Журнал аудита пачками по 100

**Ситуация:**

После выгрузки каждый номер заказа нужно записать в журнал аудита:

- по одной строке — слишком много запросов;
- все сразу — слишком большой запрос;
- база не должна получать несколько пачек одновременно.

**Что сделать:**

`auditInBatches(List<Integer> orderIds, AuditBatchWriter writer)` — итог: сколько строк записано.

**Ожидаемый результат:**

| Вход | Итог | Что проверяет тест |
|---|---|---|
| 250 номеров | 250 | пачки `100, 100, 50` в этом порядке; одновременно не больше одной пачки; в `rc_audit_log` 250 строк |
| пустой список | 0 | ни одного обращения к `writer` |

## Задача 4. Табло показывает только последнюю цену

**Ситуация:**

Биржевое табло обновляется медленнее, чем приходят цены.

Старые цены, которые табло не успело показать, не нужны: важна только самая свежая.

**Что сделать:**

`latestOnly(Flux<Integer> prices)`.

**Ожидаемый результат:**

1. Табло ничего не запрашивает. Приходят 101, 102, 103.
2. Табло просит 1 — получает 103.
3. Приходят 104, 105.
4. Табло просит 1 — получает 105.
5. Источник завершился — табло тоже завершается без ошибки.

## Задача 5. Лишние события отбросить и записать

**Ситуация:**

Датчики шлют события непрерывно. Обработчик берёт событие, только когда освободился.

События, пришедшие, пока он занят, обрабатывать не нужно. Но их надо записать для отчёта о потерях.

**Что сделать:**

`dropWhenBusy(Flux<Integer> events, Consumer<Integer> dropped)`.

**Ожидаемый результат:**

1. Пришли 1, 2 без запроса.
2. Обработчик просит 1.
3. Пришли 3, 4 — обработчик получает 3.
4. Отброшены и переданы в `dropped`: `1, 2, 4`.
5. Поток завершается без ошибки переполнения.
