## Правила

- Класс решения: `reactorcourse/t06/T06ErrorTasks`. Тест: `T06ErrorTasksTest`.
- Бизнес-ошибки — готовые классы в `common/CourseExceptions`:
  - `RateUnavailableException`;
  - `InvalidOrderIdException`;
  - `TemporaryFailureException`;
  - `InvalidRequestException`.
- Готовый `FlakyGateway(failuresBeforeSuccess, failure)` — синхронный клиент нестабильной системы:
  - первые `failuresBeforeSuccess` вызовов `call()` бросают исключение от `failure`;
  - следующие возвращают `"OK"`;
  - шлюз считает вызовы и запоминает их время.

## Задача 1. Курс по умолчанию

**Ситуация:**

Сервис курсов валют иногда сообщает «курс недоступен»:

- «курс недоступен» — витрина считает по курсу 1;
- любая другая ошибка — признак поломки, её прятать нельзя.

**Что сделать:**

`rateOrDefault(Mono<BigDecimal> rateCall)`.

**Ожидаемый результат:**

| Ответ сервиса | Результат |
|---|---|
| 92.40 | 92.40 |
| ошибка `RateUnavailableException` | 1 |
| ошибка `IllegalStateException("сломан ключ API")` | та же ошибка |

## Задача 2. Понятная ошибка разбора номеров

**Ситуация:**

Номера заказов приходят строками из CSV. Если номер не число:

- оператор поддержки должен увидеть, какой именно номер битый;
- разработчик — исходную причину.

**Что сделать:**

`parseOrderIds(List<String> raw)` — номера по порядку.

1. Битый номер — ошибка `InvalidOrderIdException` с сообщением `Неверный номер заказа: <строка>`.
2. Причина (`cause`) — исходное `NumberFormatException`.
3. Номера до битого успевают дойти до подписчика.

**Ожидаемый результат:**

| Вход | Результат |
|---|---|
| `"7"`, `"8"`, `"x9"`, `"10"` | 7, 8, затем ошибка «Неверный номер заказа: x9» |
| `"1"`, `"2"` | 1, 2 |

## Задача 3. Пропустить битые номера

**Ситуация:**

Ночной импорт не должен останавливаться из-за одной кривой строки:

- битые номера пропускаются и передаются в журнал отказов;
- остальные обрабатываются до конца.

**Что сделать:**

`parseValidOrderIds(List<String> raw, Consumer<String> rejected)`.

**Ожидаемый результат:**

Вход `"1"`, `"x"`, `"3"`, `""`, `"5"`:

- результат — 1, 3, 5 и нормальное завершение;
- в журнал отказов переданы `"x"` и `""`.

## Задача 4. Повтор с растущей паузой

**Ситуация:**

Партнёрский API иногда отвечает временной ошибкой. Повторять нужно так:

- пауза между повторами растёт, первая — не меньше 100 мс;
- повторов не больше трёх, после этого сдаться.

**Что сделать:**

`callWithBackoff(FlakyGateway gateway)`.

1. Каждая попытка — новый вызов `gateway.call()`.
2. Пауза перед каждым повтором — не меньше 100 мс.
3. Повторов не больше трёх.
4. Вызов метода шлюз не трогает.

**Ожидаемый результат:**

| Шлюз | Результат | Вызовов |
|---|---|---|
| две неудачи, потом успех | `"OK"`; между вызовами не меньше 100 мс | 3 |
| всегда неудача | ошибка, её причина — `TemporaryFailureException` | 4 |
| вызов метода без подписки | — | 0 |

## Задача 5. Остаток со склада или из кэша

**Ситуация:**

Карточка товара ждёт ответа склада не дольше 500 мс:

- не дождались — показываем остаток из кэша;
- склад ответил ошибкой — кэш не подставлять: это уже не медленный ответ, а сбой.

**Что сделать:**

`stockOrCache(Mono<String> liveCall, Mono<String> cache)`.

**Ожидаемый результат:**

| Склад | Результат |
|---|---|
| отвечает за 100 мс `склад: 12` | `склад: 12` |
| молчит 2 секунды | через 500 мс — `кэш: 10` |
| ошибка «склад закрыт» | ошибка «склад закрыт» |

**Внимание:**

Тест идёт в виртуальном времени.

## Задача 6. Повторять только временные сбои

**Ситуация:**

Отправка документа в систему ЭДО:

- временный сбой (`TemporaryFailureException`) стоит повторить до трёх раз сразу, без паузы;
- неверный запрос (`InvalidRequestException`) повторять бессмысленно — сразу вернуть ошибку.

**Что сделать:**

`sendSelective(FlakyGateway gateway)`.

**Ожидаемый результат:**

| Шлюз | Результат | Вызовов |
|---|---|---|
| два временных сбоя, потом успех | `"OK"` | 3 |
| неверный запрос | `InvalidRequestException` | 1 |
| временные сбои всегда | ошибка | 4 |
