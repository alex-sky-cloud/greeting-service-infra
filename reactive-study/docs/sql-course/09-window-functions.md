# Тема 09 — оконные функции

**Оконная функция** считает значение по набору строк, связанных с текущей строкой, — например, по всем сотрудникам того же отдела — и записывает результат рядом с текущей строкой. Сама строка из результата не исчезает.

Это **главное отличие** от `GROUP BY`:

- после группировки остаётся одна строка на группу;
- после **оконного расчёта** сотрудники, заказы или попытки оплаты остаются **отдельными строками**.

## Что меняет OVER

Обычный агрегат без `OVER` собирает все строки в одну.

### Общий синтаксис оконной функции

Сначала записывается функция, затем `OVER (...)`, внутри которого указываются строки, участвующие в расчёте:

```sql

function_name(arguments) OVER (
    PARTITION BY section_column
    ORDER BY sort_column
    ROWS BETWEEN frame_start AND frame_end
)
```

Это общая схема, а не запрос, который нужно запускать целиком. Слова `function_name`, `arguments`, `section_column`, `sort_column`, `frame_start` и `frame_end` — места для подстановки: в настоящем запросе на их место ставят функцию, столбцы таблицы и границы. Каждая часть подробно разобрана в своём разделе ниже, с примером на учебной базе.

- `function_name(arguments)` — что именно вычислять. Это не любая функция SQL, а одна из двух семей, разобранных сразу ниже;
- `PARTITION BY` — необязательное деление строк на независимые секции;
- `ORDER BY` — необязательный порядок строк внутри каждой секции;
- `ROWS BETWEEN ... AND ...` — необязательное ограничение строк секции, участвующих в расчёте для текущей строки.

Все части внутри `OVER` добавляются только тогда, когда нужны задаче.

#### С чем пишется OVER

`OVER` — не отдельная функция и не замена агрегату. Это хвост вызова: он говорит, **по какой корзине строк** считать то, что стоит слева.

Слева бывает два разных семейства.

**1. Обычные агрегаты**, которые уже знакомы без окна: `count`, `sum`, `avg`, `min`, `max`. Без `OVER` они схлопывают набор в одну строку. С `OVER` тот же счёт идёт по корзине, а число дописывается к каждой строке.

```sql

count(*) OVER ()
sum(salary) OVER ()
avg(salary) OVER ()
```

**2. Функции, которые существуют только как оконные.** Они используются **только в связке с `OVER`**. 
- Отдельного вызова `row_number()`, `rank()`, `dense_rank()`, `lag(...)` или `lead(...)` без `OVER` нет: 
  - без хвоста `OVER (...)` база запрос не примет. В этой теме дальше разбираются как раз эти функции; их синтаксис — в своих разделах. 
  
С `OVER` они тоже считают по корзине и пишут результат в каждую строку, но считают не «сумму или количество», а номер, место в порядке или значение соседней строки.

```sql

row_number() OVER ()
```

`lower(full_name)`, `length(full_name)`, `round(salary, 2)` с `OVER` не пишут: они смотрят только на текущую строку и корзина им не нужна.

| Что слева от `OVER` | Можно без `OVER`? | Что получается с `OVER` |
|---|---|---|
| `count(*)`, `sum`, `avg`, `min`, `max` | да: обычный агрегат, одна строка на набор | тот же счёт по корзине, число у каждой строки |
| `row_number`, `rank`, `dense_rank`, `lag`, `lead` | нет: только в связке с `OVER` | номер, место или соседняя строка — тоже у каждой строки |
| `lower`, `length`, `round` и другие функции одной строки | да, и `OVER` им не нужен | — |

**Источник:** https://www.postgresql.org/docs/16/functions-window.html

**EN:**

> The built-in window functions are listed in Table 9.64. Note that these functions must be invoked using window function syntax, i.e., an `OVER` clause is required.
>
> In addition to these functions, any built-in or user-defined ordinary aggregate … can be used as a window function … Aggregate functions act as window functions only when an `OVER` clause follows the call; otherwise they act as plain aggregates and return a single row for the entire set.

**RU:**

> Встроенные оконные функции перечислены в таблице 9.64. Их нужно вызывать синтаксисом оконной функции, то есть предложение `OVER` обязательно.
>
> Кроме этих функций, любой встроенный или пользовательский обычный агрегат … можно использовать как оконную функцию … Агрегатные функции работают как оконные, только когда сразу после вызова стоит предложение `OVER`; иначе они остаются обычными агрегатами и возвращают одну строку на весь набор. 

Самая короткая запись — `OVER ()`: 
 - пустые скобки значат «одна общая корзина». 
 - В неё попадают все строки, которые уже дошли до оконного расчёта. 

Функция считает по этой корзине одно число и **приписывает его к каждой строке** основного результата. 
 - Сами строки не схлопываются: `id`, `full_name`, `salary` остаются на месте.

Это не группировка, хотя счёт внутри корзины похож на агрегат. `GROUP BY` собирает строки в группу и **оставляет одну строку на группу**. Поэтому рядом с `count(*)` без `OVER` нельзя просто вывести имя и зарплату: база не знает, чью строку оставить. `OVER ()` как раз снимает это неудобство: считает по корзине, а к результату дописывает столбец.

Обычный агрегат **не всегда** требует `GROUP BY`. Если в `SELECT` только агрегаты, достаточно одной итоговой строки на весь набор:

```sql

SELECT count(*) FROM employees;
```

`GROUP BY` нужен, когда рядом с агрегатом хотят ещё обычные столбцы. Именно тогда без `OVER` запрос либо не принимается, либо приходится тащить эти столбцы в группировку.

На трёх сотрудниках отдела продаж это видно сразу. Исходные строки после `FROM` и `WHERE`:

| full_name | salary |
|---|---:|
| Сергей Гусев | 180000.00 |
| Мария Зайцева | 120000.00 |
| Денис Волков | 115000.00 |

Если посчитать людей обычным агрегатом, корзина та же, но результат — **одна** строка. Имена пропали:

```sql

SELECT count(*) AS people
FROM employees
WHERE id IN (5, 6, 7);
```

| people |
|---:|
| 3 |

Запрос `SELECT full_name, salary, count(*) FROM employees WHERE id IN (5, 6, 7)` база не примет: рядом с агрегатом стоят обычные столбцы, а группировки нет. Если добавить `GROUP BY full_name, salary`, строки сотрудников останутся, но каждая группа будет из одного человека, и `count(*)` даст `1`. Это уже другой вопрос, не «сколько людей в выбранном наборе».

Тот же счёт через `OVER ()` оставляет всех троих и дописывает одно общее число к каждой строке:

```sql

SELECT full_name,
       salary,
       count(*) OVER () AS people
FROM employees
WHERE id IN (5, 6, 7)
ORDER BY id;
```

| full_name | salary | people |
|---|---:|---:|
| Сергей Гусев | 180000.00 | 3 |
| Мария Зайцева | 120000.00 | 3 |
| Денис Волков | 115000.00 | 3 |

Корзина одна, число одно, но оно стоит у каждого.

Две вещи, чтобы эта картинка не сломалась в следующих разделах:

- Корзина `OVER ()` — не «вся компания навсегда», а строки после `FROM`, `JOIN` и `WHERE`. В примере выше в корзине трое, потому что остальных отсёк `WHERE`. Без фильтра в корзину попадут все 15 сотрудников.
- `PARTITION BY` раскладывает строки по **нескольким** корзинам, например по отделам. Внутри каждой корзины счёт тот же: посчитали и дописали к каждой её строке. `ROWS BETWEEN` ограничивает, какую **часть** корзины брать вокруг текущей строки. Для вопроса «сколько людей в наборе» кадр не нужен: пустые скобки и значат «вся корзина целиком».

**Задача.** HR хочет узнать среднюю зарплату и число сотрудников во всей компании.

```sql

SELECT count(*) AS company_people,
       round(avg(salary), 2) AS company_avg
FROM employees;
```

**Как читается запрос**

- `FROM employees` — берутся все 15 сотрудников.
- `count(*)` считает 15 строк.
- `avg(salary)` считает одно среднее по этим строкам.
- Агрегаты возвращают одну итоговую строку: имена сотрудников в ней уже не видны.

| company_people | company_avg |
|---:|---:|
| 15 | 206533.33 |

Теперь продуктовая задача другая.

**Задача.** В списке сотрудников сохранить каждого человека и рядом показать число людей в компании, среднюю зарплату и отклонение его зарплаты от средней.

```sql

SELECT e.id,
       e.full_name,
       e.salary,
       count(*) OVER () AS company_people,
       round(avg(e.salary) OVER (), 2) AS company_avg,
       e.salary - round(avg(e.salary) OVER (), 2) AS difference_from_avg
FROM employees e
ORDER BY e.id;
```

**Как читается запрос**

- `FROM employees e` — в результате остаются 15 исходных строк. `e` — короткое имя таблицы сотрудников.
- `count(*) OVER ()` — считает по всем строкам, которые видит запрос, но дописывает число `15` к каждой строке.
- `avg(e.salary) OVER ()` — считает среднюю по тем же 15 строкам и дописывает её к каждой.
- Пустые скобки `OVER ()` означают: не делить строки на отдельные секции и не задавать порядок внутри окна.
- `difference_from_avg` вычисляется отдельно для каждого сотрудника: его зарплата минус одна общая средняя.
- `ORDER BY e.id` сортирует готовую выдачу по номеру сотрудника.

**Нюансы**

- `OVER` не создаёт новую таблицу и не соединяет строки. Оно задаёт, по каким строкам функция должна считать значение для текущей строки.
- Оконная функция видит строки после `FROM`, `JOIN`, `WHERE`, `GROUP BY` и `HAVING`. Отфильтрованная строка в окно не входит.

### Почему `GROUP BY` уменьшает число строк, а `OVER` — нет

Возьмём трёх сотрудников отдела продаж.

#### Вариант 1 — `GROUP BY`

**Задача.** Получить одну итоговую строку по отделу продаж и посчитать его сотрудников.

```sql

SELECT d.name AS department,
       count(*) AS people
FROM employees e
JOIN departments d ON d.id = e.department_id
WHERE d.name = 'Отдел продаж'
GROUP BY d.name;
```

| department | people |
|---|---:|
| Отдел продаж | 3 |

**Почему осталась одна строка**

`GROUP BY d.name` собирает все строки с одинаковым названием отдела в одну группу. Три исходные строки сотрудников превращаются в одну итоговую строку отдела. Поэтому отдельно Сергей, Мария и Денис в результате уже не видны.

#### Вариант 2 — `count(*) OVER ()`

**Задача.** Сохранить строки всех сотрудников отдела продаж и рядом с каждым показать число сотрудников в выбранном наборе.

```sql

SELECT e.full_name,
       d.name AS department,
       count(*) OVER () AS people
FROM employees e
JOIN departments d ON d.id = e.department_id
WHERE d.name = 'Отдел продаж'
ORDER BY e.id;
```

| full_name | department | people |
|---|---|---:|
| Сергей Гусев | Отдел продаж | 3 |
| Мария Зайцева | Отдел продаж | 3 |
| Денис Волков | Отдел продаж | 3 |

**Почему остались три строки**

`OVER ()` говорит функции `count(*)`: «посчитай все строки, которые остались после `WHERE`, но не объединяй их». Поэтому функция получает число `3` и дописывает его в каждую из трёх исходных строк.

Короткая памятка:

- `GROUP BY` меняет смысл строки результата: **одна строка — одна группа**;
- оконная функция сохраняет смысл исходной строки: **одна строка — один сотрудник**, а расчёт группы появляется в дополнительном столбце.

**Источник:** https://www.postgresql.org/docs/16/tutorial-window.html

**EN:**

> A window function call always contains an `OVER` clause directly following the window function's name and argument(s). This is what syntactically distinguishes it from a normal function or non-window aggregate.
>
> The rows considered by a window function are those of the “virtual table” produced by the query's `FROM` clause as filtered by its `WHERE`, `GROUP BY`, and `HAVING` clauses if any.

**RU:**

> Вызов оконной функции всегда содержит предложение `OVER`, которое следует непосредственно после имени функции и её аргументов. Именно это синтаксически отличает её от обычной функции или неоконного агрегата.
>
> Оконная функция рассматривает строки «виртуальной таблицы», созданной предложением `FROM` и отфильтрованной предложениями `WHERE`, `GROUP BY` и `HAVING`, если они есть.

## PARTITION BY: отдельное окно для каждого отдела

`PARTITION BY` делит видимые строки на секции — как будто раскладывает их по отдельным корзинам. Одна секция может содержать одну строку или много строк.

Базовый синтаксис:

```sql

function_name(arguments) OVER (
    PARTITION BY section_column
)
```

`section_column` — столбец, по одинаковым значениям которого строки попадут в одну секцию.

Например.

`PARTITION BY d.id` кладёт в одну корзину всех сотрудников с одним номером отдела.

**Цель.** Оставить список сотрудников и рядом с каждым написать число людей, фонд зарплат и среднюю зарплату **его** отдела, а не всей компании.

**Решение.** Пустые скобки `OVER ()` собирают всех в одну корзину. Здесь корзина должна быть отделом, поэтому внутри `OVER` пишут `PARTITION BY d.id`. Сортировку внутри `OVER` не ставят: считают всю корзину отдела целиком, а не «с начала списка до текущей строки». Секция одна на отдел. Число одно. Оно дописывается к **каждой** строке сотрудника этого отдела. Строки не схлопываются.

Например.

В отделе продаж три человека. Их корзина общая:

| full_name | department |
|---|---|
| Сергей Гусев | Отдел продаж |
| Мария Зайцева | Отдел продаж |
| Денис Волков | Отдел продаж |

`count(*)` по этой корзине даёт `3`. Это `3` записывается и Сергею, и Марии, и Денису. То же с суммой и средней: фонд и среднее считают один раз по отделу и ставят в каждую из трёх строк.

В запросе ниже так считают `count(*)`, `sum(e.salary)` и `avg(e.salary)` — у каждого свой `OVER (PARTITION BY d.id)`.

**Задача.** HR открывает список сотрудников. Рядом с каждым человеком нужно показать число сотрудников, фонд зарплат и среднюю зарплату именно его отдела.

```sql

SELECT e.id,
       d.name AS department,
       e.full_name,
       e.salary,
       count(*) OVER (PARTITION BY d.id) AS department_people,
       sum(e.salary) OVER (PARTITION BY d.id) AS department_fund,
       round(avg(e.salary) OVER (PARTITION BY d.id), 2) AS department_avg
FROM employees e
JOIN departments d ON d.id = e.department_id
ORDER BY d.id, e.salary DESC, e.id;
```

**Как читается запрос**

- `FROM employees e JOIN departments d` — к каждому сотруднику добавляется название его отдела. Получается 15 строк.
- `PARTITION BY d.id` — строки мысленно разделяются по номеру отдела.
- В секции «Отдел продаж» три строки: Сергей, Мария и Денис.
- `count(*) OVER (...)` пишет число `3` в каждую из этих трёх строк.
- `sum(e.salary) OVER (...)` пишет фонд `415000.00` в каждую строку отдела продаж.
- `avg(e.salary) OVER (...)` пишет среднее `138333.33`.
- Строки не складываются в одну: имена и зарплаты всех троих остаются.

| 2 | Коммерческий департамент | Павел Морозов | 300000.00 | 1 | 300000.00 | 300000.00 |
| 3 | Логистический департамент | Ольга Крылова | 290000.00 | 1 | 290000.00 | 290000.00 |
| 4 | Технический департамент | Антон Лебедев | 320000.00 | 1 | 320000.00 | 320000.00 |

- В запросе выше `PARTITION BY d.id` создаёт отдельную секцию для каждого отдела. Поэтому Сергей получает число сотрудников своего отдела — `3`, а не число сотрудников всей компании.

- Внешний `ORDER BY d.id, e.salary DESC, e.id` только располагает готовые строки на экране. Он не меняет состав секций, заданных внутри `OVER`.
- Отделы без сотрудников не появляются по другой причине, не связанной с оконными функциями: запрос начинается с `employees`, поэтому его исходная строка — сотрудник. Если в отделе нет ни одного сотрудника, исходной строки для такого отдела здесь нет. Для поставленной задачи «показать расчёты рядом с каждым сотрудником» это ожидаемое поведение.

## ORDER BY внутри OVER и ORDER BY результата

В запросе с оконной функцией `ORDER BY` может стоять в двух местах, и они делают разную работу:

- `ORDER BY` внутри `OVER (...)` задаёт порядок, в котором функция обходит строки, например кому дать номер 1, а кому 2;
- `ORDER BY` в конце запроса только сортирует готовый результат для показа.

Первой функцией, где это важно, будет `row_number()`.

### Что делает `row_number()`

`row_number()` — оконная функция, которая присваивает строкам последовательные номера: `1`, `2`, `3` и далее.

У функции нет аргументов, поэтому после её имени стоят пустые скобки:

```sql

row_number() OVER (
    ORDER BY sort_column
)
```

Правила работы:

- `ORDER BY` внутри `OVER` определяет, какая строка получит номер `1`, какая — `2` и так далее;
- одинаковые значения тоже получают разные номера;
- если нужен однозначный порядок при равенстве, в сортировку добавляют уникальный столбец, например `id`;
- если добавить `PARTITION BY`, нумерация начнётся заново внутри каждой секции.

**Задача.** Присвоить сотрудникам номера от самой большой зарплаты к самой маленькой и вывести отчёт в порядке этих номеров.

```sql

SELECT e.id,
       e.full_name,
       e.salary,
       row_number() OVER (
           ORDER BY e.salary DESC, e.id
       ) AS salary_row
FROM employees e
ORDER BY salary_row;
```

**Как читается запрос**

- `ORDER BY e.salary DESC, e.id` внутри `OVER` определяет, какой сотрудник получит номер 1, 2, 3 и далее.
- `e.id` — дополнительное правило на случай одинаковых зарплат. Без него одинаковые зарплаты не имеют закреплённого взаимного порядка.
- `ORDER BY salary_row` после `FROM` сортирует готовую таблицу для показа.
- Внутренний `ORDER BY` вычисляет номера. Внешний `ORDER BY` определяет расположение строк на экране.

| id | full_name | salary | salary_row |
|---:|---|---:|---:|
| 1 | Ирина Соколова | 450000.00 | 1 |
| 4 | Антон Лебедев | 320000.00 | 2 |
| 2 | Павел Морозов | 300000.00 | 3 |
| 3 | Ольга Крылова | 290000.00 | 4 |
| 11 | Виктор Сомов | 280000.00 | 5 |
| 12 | Алексей Тихонов | 230000.00 | 6 |
| 13 | Юлия Карпова | 220000.00 | 7 |
| 5 | Сергей Гусев | 180000.00 | 8 |
| 14 | Роман Фадеев | 170000.00 | 9 |
| 8 | Елена Орлова | 160000.00 | 10 |
| 6 | Мария Зайцева | 120000.00 | 11 |

| 10 | Наталья Ершова | 88000.00 | 14 |

**Нюансы**

- Если убрать внешний `ORDER BY`, номера останутся правильными, но порядок строк результата SQL не гарантирует.
- Если убрать `e.id` из окна и встретятся одинаковые зарплаты, PostgreSQL может дать таким строкам разные номера в любом взаимном порядке.

## ROW_NUMBER, RANK и DENSE_RANK

Все три функции нумеруют строки в порядке, заданном `ORDER BY` внутри `OVER`. Пока значения в столбце сортировки разные, они дают одинаковый результат: `1, 2, 3, …`.

Разница появляется только тогда, когда у нескольких строк **одинаковое значение в столбце сортировки**. Например, рейтинг начальников строится по числу прямых подчинённых, а у троих из них число одинаковое — по 3 человека. Встаёт вопрос: какое место дать этим троим?

- разные места `1, 2, 3` — хотя результат у них одинаковый;
- одно общее место `1` всем троим.

Каждая из трёх функций отвечает на этот вопрос по-своему. Поэтому для сравнения нужен пример, где одинаковые значения действительно есть. В учебной базе у Ирины Соколовой, Елены Орловой и Виктора Сомова по три прямых подчинённых — на них и видна разница.

### Синтаксис и различие трёх функций

Все три функции не принимают аргументов. Правила сравнения строк задаются в `ORDER BY` внутри `OVER`:

```sql

row_number() OVER (ORDER BY value DESC)
rank() OVER (ORDER BY value DESC)
dense_rank() OVER (ORDER BY value DESC)
```

- `row_number()` всегда выдаёт каждой строке свой номер, даже если значения одинаковые;
- `rank()` выдаёт строкам с одинаковым значением одно общее место. Следующая строка получает место с учётом того, сколько строк уже стоит выше, поэтому номера мест пропускаются;
- `dense_rank()` тоже выдаёт строкам с одинаковым значением одно общее место, но следующая строка получает следующий номер по порядку, без пропусков.

Например, пять строк отсортированы по убыванию значения `3, 3, 3, 2, 1`:

| value | row_number() | rank() | dense_rank() |
|---:|---:|---:|---:|
| 3 | 1 | 1 | 1 |
| 3 | 2 | 1 | 1 |
| 3 | 3 | 1 | 1 |
| 2 | 4 | 4 | 2 |
| 1 | 5 | 5 | 3 |

- У `rank()` значение `2` получает место `4`: выше него уже стоят три строки, поэтому места `2` и `3` пропущены.
- У `dense_rank()` значение `2` получает место `2`: это второе по величине значение, пропусков нет.

Это как результаты соревнований: если трое разделили первое место, `rank()` отдаёт следующему участнику четвёртое место, а `dense_rank()` — второе.

**Задача.** HR строит рейтинг начальников по числу прямых подчинённых и хочет сравнить три способа присвоить место.

```sql

WITH manager_totals AS (
    SELECT boss.id AS manager_id,
           boss.full_name AS manager,
           count(child.id) AS direct_reports
    FROM employees boss
    JOIN employees child ON child.manager_id = boss.id
    GROUP BY boss.id, boss.full_name
)
SELECT manager,
       direct_reports,
       row_number() OVER (
           ORDER BY direct_reports DESC, manager_id
       ) AS row_no,
       rank() OVER (
           ORDER BY direct_reports DESC
       ) AS rank_no,
       dense_rank() OVER (
           ORDER BY direct_reports DESC
       ) AS dense_rank_no
FROM manager_totals
ORDER BY direct_reports DESC, manager_id;
```

**Как читается запрос**

- `manager_totals` сначала возвращает 7 начальников и число их прямых подчинённых.
- Оконные функции работают уже по этим 7 сгруппированным строкам.
- `row_number()` выдаёт каждому начальнику свой номер. Три начальника с числом `3` получают номера 1, 2 и 3. Кто из них первый, решает `manager_id`: меньший номер сотрудника идёт раньше.
- `rank()` даёт всем троим с числом `3` место 1. Сергей Гусев с числом `2` получает место 4, потому что выше него уже три человека.
- `dense_rank()` тоже даёт всем троим место 1, но Сергей Гусев получает место 2: число `2` — второе по величине значение.
- У `rank()` и `dense_rank()` в `ORDER BY` нет `manager_id`: им нужно, чтобы одинаковое число подчинённых давало одинаковое место.

| manager | direct_reports | row_no | rank_no | dense_rank_no |
|---|---:|---:|---:|---:|
| Ирина Соколова | 3 | 1 | 1 | 1 |
| Елена Орлова | 3 | 2 | 1 | 1 |
| Виктор Сомов | 3 | 3 | 1 | 1 |
| Сергей Гусев | 2 | 4 | 4 | 2 |
| Павел Морозов | 1 | 5 | 5 | 3 |
| Ольга Крылова | 1 | 6 | 5 | 3 |
| Антон Лебедев | 1 | 7 | 5 | 3 |

**Как выбрать функцию**

- Нужно выбрать строго определённое число строк, например «ровно два сотрудника от отдела», даже если у них одинаковые зарплаты — `row_number()`. В `ORDER BY` добавляют уникальный столбец, например `id`, чтобы было однозначно решено, кто из людей с одинаковой зарплатой идёт раньше.
- Нужен рейтинг, где люди с одинаковым результатом делят место, а следующие места сдвигаются, как в спортивной таблице — `rank()`.
- Нужно пронумеровать сами различные значения, например «первая, вторая и третья по величине зарплата» без пропусков — `dense_rank()`.

**Источник:** https://www.postgresql.org/docs/16/functions-window.html

**EN:**

> `row_number` — Returns the number of the current row within its partition, counting from 1.
>
> `rank` — Returns the rank of the current row, with gaps; that is, the row number of the first row in its peer group.
>
> `dense_rank` — Returns the rank of the current row, without gaps; this function effectively counts peer groups.

**RU:**

> `row_number` возвращает номер текущей строки внутри её секции, начиная с 1.
>
> `rank` возвращает место текущей строки с пропусками; это номер первой строки в её группе равных строк.
>
> `dense_rank` возвращает место текущей строки без пропусков; фактически эта функция считает группы равных строк.

«Группа равных строк» (peer group) — это строки, у которых одинаковое значение в `ORDER BY` окна. В примере выше это Ирина, Елена и Виктор с числом `3`.

## Два сотрудника с наибольшей зарплатой в каждом отделе

На собеседованиях эту задачу называют **top-N per group** — «первые N строк в каждой группе». Здесь группа — отдел, N = 2. Решение: сначала пронумеровать сотрудников внутри каждого отдела, затем оставить номера 1 и 2.

**Задача.** HR просит не более двух сотрудников с наибольшей зарплатой из каждого отдела. Если в отделе один сотрудник, показать одного.

```sql

WITH ranked AS (
    SELECT d.name AS department,
           e.full_name,
           e.salary,
           row_number() OVER (
               PARTITION BY d.id
               ORDER BY e.salary DESC, e.id
           ) AS salary_row
    FROM employees e
    JOIN departments d ON d.id = e.department_id
)
SELECT department,
       full_name,
       salary,
       salary_row
FROM ranked
WHERE salary_row <= 2
ORDER BY department, salary_row;
```

**Как читается запрос**

- Внутри `ranked` сотрудники разделены по `d.id`.
- В каждом отделе нумерация начинается заново с 1.
- Зарплата сортируется от большей к меньшей; `e.id` закрепляет порядок при равенстве.
- В отделе продаж Сергей получает 1, Мария — 2, Денис — 3.
- Основной запрос после `WITH` видит готовый `salary_row` и оставляет номера 1 и 2.

| department | full_name | salary | salary_row |
|---|---|---:|---:|
| Группа backend | Алексей Тихонов | 230000.00 | 1 |
| Группа frontend | Юлия Карпова | 220000.00 | 1 |
| Доставка | Светлана Ким | 85000.00 | 1 |
| Коммерческий департамент | Павел Морозов | 300000.00 | 1 |
| Компания | Ирина Соколова | 450000.00 | 1 |
| Логистический департамент | Ольга Крылова | 290000.00 | 1 |
| Отдел продаж | Сергей Гусев | 180000.00 | 1 |
| Отдел продаж | Мария Зайцева | 120000.00 | 2 |
| Отдел разработки | Виктор Сомов | 280000.00 | 1 |
| Отдел тестирования | Роман Фадеев | 170000.00 | 1 |
| Склад | Елена Орлова | 160000.00 | 1 |
| Склад | Игорь Беляев | 90000.00 | 2 |
| Технический департамент | Антон Лебедев | 320000.00 | 1 |

**Нюансы**

- Условие `salary_row <= 2`, где номер выдан `row_number()`, даёт не более двух людей в отделе: у каждого человека свой номер.
- Если бы номер выдавал `dense_rank()`, то условие `<= 2` оставило бы всех людей с двумя наибольшими различными зарплатами отдела. Если у трёх человек одинаковая максимальная зарплата, все трое получат номер 1 и попадут в результат, и людей станет больше двух.
- Поэтому на собеседовании важно уточнить: «два лучших» — это два человека или две наибольшие зарплаты.

## Почему оконную функцию нельзя написать в WHERE

**Задача.** Попытаться сразу оставить первые три зарплаты, вычисляя номер строки в `WHERE`.

```sql

SELECT e.full_name,
       row_number() OVER (ORDER BY e.salary DESC) AS salary_row
FROM employees e
WHERE row_number() OVER (ORDER BY e.salary DESC) <= 3;
```

PostgreSQL возвращает ошибку:

```text
ERROR:  window functions are not allowed in WHERE
```

**Как читается ошибка**

- `WHERE` должен определить строки раньше, чем оконная функция рассчитает `salary_row`.
- В этот момент значения `salary_row` ещё нет.
- Поэтому top-N сначала вычисляют внутри CTE или подзапроса, а фильтруют уровнем выше, как в предыдущем разделе.

## Накопительная сумма заказов

### Что такое накопительная сумма

Обычная сумма отвечает на вопрос «сколько всего». Накопительная сумма отвечает на вопрос «сколько набралось с самого начала **по эту строку включительно**» и считается заново для каждой строки.

Пример на первых трёх датах учебной базы: в колонке `order_amount` сумма заказов за одну дату, в колонке «накопительная сумма» сумма за эту дату и все даты до неё.

| order_date | order_amount | накопительная сумма | как получилась |
|---|---:|---:|---|
| 2025-07-29 | 104475.93 | 104475.93 | только 29 июля |
| 2025-07-30 | 282137.82 | 386613.75 | `104475.93 + 282137.82` |
| 2025-07-31 | 280330.90 | 666944.65 | `104475.93 + 282137.82 + 280330.90` |

Чтобы SQL посчитал такую колонку, ему нужно сообщить три вещи:

1. какие числа складывать — дневные суммы;
2. в каком порядке идут строки — по дате, иначе неизвестно, что значит «до этой строки»;
3. какие строки складывать для текущей — от первой строки до текущей.

### Синтаксис

Общая схема записи:

```sql

sum(value_column) OVER (
    ORDER BY sort_column
    ROWS BETWEEN frame_start AND frame_end
)
```

Слова `value_column`, `sort_column`, `frame_start` и `frame_end` — это **места для подстановки**, а не настоящие имена. В запросе на их место ставят столбцы таблицы и границы. Остальные слова — `sum`, `OVER`, `ORDER BY`, `ROWS BETWEEN`, `AND` — пишутся как есть.

| Часть схемы | Что означает | Что подставлено в запросе ниже |
|---|---|---|
| `sum(value_column)` | какой столбец складывать. Это та же `sum` из темы 03, только теперь у неё есть `OVER` | `sum(order_amount)` — дневная сумма заказов |
| `OVER (...)` | считать как оконную функцию: строки не схлопываются, результат пишется рядом с каждой строкой | — |
| `ORDER BY sort_column` | в каком порядке выстроить строки перед подсчётом | `ORDER BY order_date` — от ранней даты к поздней |
| `ROWS BETWEEN frame_start AND frame_end` | от какой строки и до какой складывать для текущей строки. Набор этих строк называется **кадром** | `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` |

Слово `ROWS` в этой схеме отвечает на вопрос: **как отсчитать границы кадра**. Отсчёт идёт по номеру строки в списке, который уже выстроил `ORDER BY order_date`. Не по календарю и не по сумме заказа.

Этот список — та же таблица из раздела «Что такое накопительная сумма»:

| Номер строки | order_date | order_amount |
|---:|---|---:|
| 1 | 2025-07-29 | 104475.93 |
| 2 | 2025-07-30 | 282137.82 |
| 3 | 2025-07-31 | 280330.90 |

**Задача.** Аналитик смотрит три первых дня работы магазина: 29, 30 и 31 июля 2025 года. Нужны четыре столбца.

- Дата.
- Сумма заказов за эту дату.
- Сумма заказов за эту дату плюс сумма за дату, которая в таблице стоит сразу над ней.
  - Для 30 июля это 30 июля + 29 июля.
  - Для 31 июля это 31 июля + 30 июля.
  - Для 29 июля над ней строки нет, остаётся только 29 июля.
- Сумма заказов с 29 июля по эту дату включительно.
  - Для 30 июля это 29 июля + 30 июля.
  - Для 31 июля это 29 июля + 30 июля + 31 июля.

```sql

-- daily: одна строка на календарный день, в ней сумма заказов этого дня
WITH daily AS (
    -- created_at хранит дату и время, например 2025-07-29 14:03:00
    -- ::date отбрасывает время и оставляет день 2025-07-29
    -- иначе GROUP BY собрал бы заказы по секунде, а не по дню
    SELECT created_at::date AS order_date,
           -- складываем суммы заказов одного дня и округляем до копеек
           round(sum(amount), 2) AS order_amount
    FROM orders
    -- все заказы 29 июля, в какое бы время они ни были, попадают в одну группу
    GROUP BY created_at::date
)
-- ниже читаем уже готовую таблицу daily: дата и сумма за этот день
SELECT order_date,
       -- сумма заказов той даты, для которой сейчас строят строку результата
       order_amount,
       -- первое окно: PARTITION BY нет, значит одна секция — все дни из daily
       round(sum(order_amount) OVER (
           -- дни в секции выстраиваются от раннего к позднему: 29, потом 30, потом 31 июля
           ORDER BY order_date
           -- для строки, которую считают сейчас, сложить её и ту, что стоит сразу над ней
           -- 29 июля: над ней никого нет, остаётся только 29 июля
           -- 30 июля: 29 июля + 30 июля
           -- 31 июля: 30 июля + 31 июля, без 29 июля
           ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
       ), 2) AS current_and_one_above,
       -- второе окно: та же секция и тот же порядок дат
       round(sum(order_amount) OVER (
           ORDER BY order_date
           -- UNBOUNDED PRECEDING — самая первая строка секции после сортировки, здесь 29 июля
           -- CURRENT ROW — снова та дата, для которой считают эту строку результата
           -- 29 июля: только 29 июля
           -- 30 июля: 29 июля + 30 июля
           -- 31 июля: 29 июля + 30 июля + 31 июля
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ), 2) AS from_first_to_current
FROM daily
-- итоговую таблицу тоже показываем от ранней даты к поздней
ORDER BY order_date
-- из daily оставляем только 29, 30 и 31 июля
LIMIT 3;
```

**Как читается запрос**

- `daily` — сумма заказов за каждый календарный день.
- `ORDER BY order_date LIMIT 3` во внешнем запросе оставляет 29, 30 и 31 июля.
- `ORDER BY order_date` внутри `OVER` ставит эти дни в том же порядке: 29 июля сверху, 31 июля снизу. `ROWS` потом считает: 29 июля — строка 1, 30 июля — строка 2, 31 июля — строка 3.
- `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` для выбранной даты складывает её сумму и сумму даты, которая стоит сразу над ней. Результат — столбец `current_and_one_above`.
- `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` для выбранной даты складывает все дни с 29 июля по эту дату. Результат — столбец `from_first_to_current`.

Что означают столбцы результата:

| Столбец | По-русски | Какая запись в `OVER` это считает |
|---|---|---|
| `order_date` | день | нет окна, столбец из `daily` |
| `order_amount` | заказы только этого дня | нет окна, столбец из `daily` |
| `current_and_one_above` | этот день плюс день, который в таблице стоит сразу над ним | `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` |
| `from_first_to_current` | 29 июля плюс все дни до этого дня включительно | `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` |

| order_date | order_amount | current_and_one_above | from_first_to_current |
|---|---:|---:|---:|
| 2025-07-29 | 104475.93 | 104475.93 | 104475.93 |
| 2025-07-30 | 282137.82 | 386613.75 | 386613.75 |
| 2025-07-31 | 280330.90 | 562468.72 | 666944.65 |

Одинаковые числа 30 июля — не ошибка и не «одна колонка скопировала другую». Над 30 июля стоит только 29 июля, поэтому «день + сосед сверху» и «с 29 июля по этот день» складывают одни и те же два числа. 31 июля сосед сверху уже 30 июля, а «с 29 июля» по-прежнему берёт три дня. Поэтому столбцы расходятся.

Как сложили `current_and_one_above`. Это считает `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW`: только сосед сверху и этот день.

| День | Что складываем | Счёт | Результат |
|---|---|---|---:|
| 29 июля | 29 июля + ничего сверху | `104475.93 + 0` | 104475.93 |
| 30 июля | 29 июля + 30 июля | `104475.93 + 282137.82` | 386613.75 |
| 31 июля | 30 июля + 31 июля | `282137.82 + 280330.90` | 562468.72 |

29 июля в третьей строке нет.

Как сложили `from_first_to_current`. Это считает `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`: каждый раз заново с 29 июля.

| День | Что складываем | Счёт | Результат |
|---|---|---|---:|
| 29 июля | только 29 июля | `104475.93` | 104475.93 |
| 30 июля | 29 июля + 30 июля | `104475.93 + 282137.82` | 386613.75 |
| 31 июля | 29 июля + 30 июля + 31 июля | `104475.93 + 282137.82 + 280330.90` | 666944.65 |

`666944.65` не берётся из `562468.72` и не из «накопили 386613.75 и прибавили ещё раз». Это три дневные суммы: 29 + 30 + 31 июля. Число `386613.75` на второй строке — те же 29 + 30 июля; если к ним прибавить 31 июля `280330.90`, как раз получится `666944.65`. К 31 июля столбец `current_and_one_above` 30 июля уже не трогает, поэтому там `562468.72`.

Оконная функция идёт по этому результату сверху вниз и для **каждой** строки считает свою сумму. Строка, для которой идёт расчёт в этот момент, называется `CURRENT ROW`. Это не особая дата. Сначала `CURRENT ROW` — 29 июля, потом 30 июля, потом 31 июля.

**Шаг 1.** Считают сумму для 29 июля. `CURRENT ROW` — строка 1.

| Номер | order_date | Роль на этом шаге |
|---:|---|---|
| 1 | 2025-07-29 | `CURRENT ROW` |
| 2 | 2025-07-30 | ещё не считаем |
| 3 | 2025-07-31 | ещё не считаем |

Выше строки 1 ничего нет. Поэтому `1 PRECEDING` на этом шаге пустой: в кадр попадает только 104475.93. В результате оба столбца равны `104475.93`. `UNBOUNDED PRECEDING` здесь тоже строка 1: это начало списка.

**Шаг 2.** Считают сумму для 30 июля. `CURRENT ROW` — строка 2.

| Номер | order_date | Роль на этом шаге |
|---:|---|---|
| 1 | 2025-07-29 | `1 PRECEDING` — на одну позицию выше |
| 2 | 2025-07-30 | `CURRENT ROW` |
| 3 | 2025-07-31 | ещё не считаем |

Складывают 29 июля и 30 июля: 104475.93 + 282137.82 = `386613.75`. Оба столбца совпадают: над 30 июля стоит только 29 июля, и с 29 июля по 30 июля — те же два дня.

**Шаг 3.** Считают сумму для 31 июля. `CURRENT ROW` — строка 3.

| Номер | order_date | Роль на этом шаге |
|---:|---|---|
| 1 | 2025-07-29 | `2 PRECEDING` — на две позиции выше |
| 2 | 2025-07-30 | `1 PRECEDING` — на одну позицию выше |
| 3 | 2025-07-31 | `CURRENT ROW` |

`current_and_one_above` складывает 30 июля и 31 июля: 282137.82 + 280330.90 = `562468.72`. 29 июля сюда не входит: над 31 июля стоит только 30 июля.

`from_first_to_current` складывает все три дня: 104475.93 + 282137.82 + 280330.90 = `666944.65`. Столбцы здесь разные, потому что с 29 июля по 31 июля три дня, а «дата плюс та, что над ней» — только два.

`UNBOUNDED PRECEDING` на любом шаге — строка 1, 29 июля. Это всегда верх списка, а не «какая-то дата назад».

Зачем это отличать от календаря: в `ORDER BY` стоит дата, и кажется, будто `1 PRECEDING` значит «вчера». Нет. Это «строка с номером на один меньше». Если 30 июля из списка убрать, у 31 июля `1 PRECEDING` станет 29 июля — сосед по списку, не предыдущий календарный день.

Режимы `RANGE` и `GROUPS` считают границы иначе: по значению сортировки, а не по номеру строки. Они здесь не нужны. `RANGE` разобран в следующем разделе.

### Какие бывают границы кадра

На место `frame_start` и `frame_end` можно поставить одно из пяти значений:

| Граница | Что означает |
|---|---|
| `UNBOUNDED PRECEDING` | самая первая строка секции |
| `N PRECEDING` | на N строк раньше текущей, например `1 PRECEDING` — предыдущая строка |
| `CURRENT ROW` | текущая строка |
| `N FOLLOWING` | на N строк позже текущей, например `1 FOLLOWING` — следующая строка |
| `UNBOUNDED FOLLOWING` | самая последняя строка секции |

Для накопительной суммы берут `UNBOUNDED PRECEDING AND CURRENT ROW`: «от первой строки до текущей».

Конец кадра можно не писать. Тогда концом считается `CURRENT ROW`, поэтому краткая запись `ROWS UNBOUNDED PRECEDING` означает то же, что `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

Границы нельзя ставить в обратном порядке: начало кадра не может стоять позже его конца.

**Источник:** https://www.postgresql.org/docs/16/sql-expressions.html

**EN:**

> The `frame_clause` specifies the set of rows constituting the window frame, which is a subset of the current partition, for those window functions that act on the frame instead of the whole partition. The set of rows in the frame can vary depending on which row is the current row. The frame can be specified in `RANGE`, `ROWS` or `GROUPS` mode; in each case, it runs from the `frame_start` to the `frame_end`. If `frame_end` is omitted, the end defaults to `CURRENT ROW`.
>
> A `frame_start` of `UNBOUNDED PRECEDING` means that the frame starts with the first row of the partition, and similarly a `frame_end` of `UNBOUNDED FOLLOWING` means that the frame ends with the last row of the partition.
>
> In `ROWS` mode, the `offset` must yield a non-null, non-negative integer, and the option means that the frame starts or ends the specified number of rows before or after the current row.

**RU:**

> Предложение `frame_clause` задаёт набор строк, составляющих оконный кадр. Кадр — это подмножество текущей секции; он используется теми оконными функциями, которые работают с кадром, а не со всей секцией. Набор строк в кадре может меняться в зависимости от того, какая строка является текущей. Кадр можно задать в режиме `RANGE`, `ROWS` или `GROUPS`; в каждом случае он идёт от `frame_start` до `frame_end`. Если `frame_end` не указан, концом по умолчанию считается `CURRENT ROW`.
>
> `frame_start`, равный `UNBOUNDED PRECEDING`, означает, что кадр начинается с первой строки секции; аналогично `frame_end`, равный `UNBOUNDED FOLLOWING`, означает, что кадр заканчивается последней строкой секции.
>
> В режиме `ROWS` смещение `offset` должно давать неотрицательное целое число, не равное `NULL`, и означает, что кадр начинается или заканчивается на указанное число строк раньше или позже текущей строки.

### Как разные границы меняют результат

**Задача.** Аналитик хочет увидеть на первых четырёх датах, как меняется сумма, если задавать разные границы кадра.

```sql

-- daily: первые четыре даты, по одной строке на дату
WITH daily AS (
    SELECT created_at::date AS order_date,
           round(sum(amount), 2) AS order_amount
    FROM orders
    GROUP BY created_at::date
    ORDER BY order_date
    LIMIT 4
)
SELECT order_date,
       order_amount,
       -- от первой строки до текущей
       sum(order_amount) OVER (
           ORDER BY order_date
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS from_start,
       -- предыдущая строка и текущая
       sum(order_amount) OVER (
           ORDER BY order_date
           ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
       ) AS with_previous,
       -- от текущей строки до последней
       sum(order_amount) OVER (
           ORDER BY order_date
           ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
       ) AS to_end,
       -- все строки
       sum(order_amount) OVER (
           ORDER BY order_date
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS whole_set
FROM daily
ORDER BY order_date;
```

**Как читается запрос**

- `WITH daily AS (...)` готовит четыре строки: даты с 29 июля по 1 августа и сумму заказов за каждую. Как именно получается эта таблица, подробно разобрано в следующем запросе.
- `FROM daily` — оконные функции работают с этими четырьмя строками.
- `ORDER BY order_date` внутри каждого `OVER` выстраивает строки по дате. Одинаковый порядок нужен, чтобы сравнивать только границы.
- `from_start` — кадр от первой строки до текущей. Для 31 июля: `104475.93 + 282137.82 + 280330.90 = 666944.65`.
- `with_previous` — кадр из предыдущей и текущей строки. Для 31 июля: `282137.82 + 280330.90 = 562468.72`. У 29 июля предыдущей строки нет, поэтому сумма состоит из одной строки — `104475.93`.
- `to_end` — кадр от текущей строки до последней. Для 31 июля: `280330.90 + 264690.19 = 545021.09`.
- `whole_set` — это `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.
  - `UNBOUNDED PRECEDING` — первая строка `daily`, 29 июля.
  - `UNBOUNDED FOLLOWING` — последняя строка `daily`, 1 августа.
  - В `daily` четыре дня, не три: 29, 30, 31 июля и 1 августа. Число `666944.65` — только 29+30+31 июля. Четвёртый день `264690.19` тоже входит в кадр.
  - Счёт один и тот же на любой текущей строке: `104475.93 + 282137.82 + 280330.90 + 264690.19 = 931634.84`.
  - Поэтому в столбце `whole_set` у всех четырёх дат одно число. Это не «накопили и потащили дальше». Окно каждый раз заново складывает все четыре дневные суммы.

| order_date | order_amount | from_start | with_previous | to_end | whole_set |
|---|---:|---:|---:|---:|---:|
| 2025-07-29 | 104475.93 | 104475.93 | 104475.93 | 931634.84 | 931634.84 |
| 2025-07-30 | 282137.82 | 386613.75 | 386613.75 | 827158.91 | 931634.84 |
| 2025-07-31 | 280330.90 | 666944.65 | 562468.72 | 545021.09 | 931634.84 |
| 2025-08-01 | 264690.19 | 931634.84 | 545021.09 | 264690.19 | 931634.84 |

Как сложили `whole_set`. Это считает `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`: все четыре дня `daily`, с 29 июля по 1 августа.

| Текущая дата | Что складываем | Счёт | Результат |
|---|---|---|---:|
| 29 июля | 29 + 30 + 31 июля + 1 августа | `104475.93 + 282137.82 + 280330.90 + 264690.19` | 931634.84 |
| 30 июля | те же четыре дня | тот же счёт | 931634.84 |
| 31 июля | те же четыре дня | тот же счёт | 931634.84 |
| 1 августа | те же четыре дня | тот же счёт | 931634.84 |

Накопительная сумма — это столбец `from_start`. Остальные столбцы показывают, что тот же `sum` с другими границами отвечает на другой вопрос.

### Накопительная сумма заказов по дням

**Задача.** Операционный дашборд показывает по каждой дате число заказов, сумму заказов за дату и накопительную сумму от первой даты до текущей. Учитываются заказы во всех статусах: это объём созданных заказов, а не фактически полученная выручка. Для разбора нужны первые семь дат.

```sql

-- Шаг 1. daily: одна строка на дату
WITH daily AS (
    SELECT created_at::date AS order_date,
           count(*) AS orders,
           round(sum(amount), 2) AS order_amount
    FROM orders
    GROUP BY created_at::date
)
-- Шаг 2. Накопительная сумма по строкам daily
SELECT order_date,
       orders,
       order_amount,
       sum(order_amount) OVER (
           ORDER BY order_date
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_amount
FROM daily
-- Шаг 3. Порядок вывода и первые семь дат
ORDER BY order_date
LIMIT 7;
```

**Как читается запрос**

**Шаг 1 — `WITH daily AS (...)`**

- `FROM orders` — берутся все 100007 заказов. Каждая строка — один заказ.
- `created_at` — время создания заказа. Тип столбца `timestamp with time zone`: в значении есть дата, время и часовой пояс, например `2025-07-29 16:29:23.682063+00`.
- `created_at::date` — оператор `::` переводит значение в другой тип. Здесь — в тип `date`, то есть оставляет только дату и отбрасывает время. Из `2025-07-29 16:29:23.682063+00` получается `2025-07-29`.
- `AS order_date` — эта дата получает имя `order_date`.

Первые пять заказов по времени создания — что делает `created_at::date`:

| id | created_at | order_date | amount |
|---:|---|---|---:|
| 54635 | 2025-07-29 16:29:23.682063+00 | 2025-07-29 | 516.81 |
| 72884 | 2025-07-29 16:46:50.143768+00 | 2025-07-29 | 1180.59 |
| 29889 | 2025-07-29 16:49:37.248015+00 | 2025-07-29 | 1380.33 |
| 3397 | 2025-07-29 16:57:20.545789+00 | 2025-07-29 | 1365.24 |
| 22820 | 2025-07-29 16:58:35.026529+00 | 2025-07-29 | 1376.96 |

Время у заказов разное, а дата одинаковая. Поэтому они попадут в одну группу.

- `GROUP BY created_at::date` — заказы с одинаковой датой собираются в одну группу. Из 100007 заказов получается 373 группы — по числу разных дат.
- `count(*) AS orders` — число заказов в группе. 29 июля — 90 заказов.
- `round(sum(amount), 2) AS order_amount` — сумма `amount` всех заказов группы, округлённая до двух знаков после запятой. 29 июля — `104475.93`.
- `daily` — имя, под которым эта таблица из 373 строк доступна дальше в запросе.

Первые семь строк `daily`:

| order_date | orders | order_amount |
|---|---:|---:|
| 2025-07-29 | 90 | 104475.93 |
| 2025-07-30 | 290 | 282137.82 |
| 2025-07-31 | 271 | 280330.90 |
| 2025-08-01 | 269 | 264690.19 |
| 2025-08-02 | 272 | 282385.23 |
| 2025-08-03 | 275 | 283994.57 |
| 2025-08-04 | 238 | 231877.81 |

**Шаг 2 — `SELECT … FROM daily`**

- `FROM daily` — основной запрос читает 373 строки из шага 1. Каждая строка теперь — одна дата, а не один заказ.
- `order_date`, `orders`, `order_amount` — переносятся из `daily` без изменений.
- `sum(order_amount) OVER (...)` — складывает дневные суммы, а не суммы отдельных заказов: отдельных заказов в `daily` уже нет.
- `ORDER BY order_date` внутри `OVER` — выстраивает 373 даты от ранней к поздней.
- `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — для каждой даты складываются строки от первой даты до текущей.
- `AS running_amount` — имя нового столбца.

Как получается `running_amount` для первых дат:

| order_date | какие строки в кадре | расчёт | running_amount |
|---|---|---|---:|
| 2025-07-29 | 29.07 | `104475.93` | 104475.93 |
| 2025-07-30 | 29.07–30.07 | `104475.93 + 282137.82` | 386613.75 |
| 2025-07-31 | 29.07–31.07 | `386613.75 + 280330.90` | 666944.65 |
| 2025-08-01 | 29.07–01.08 | `666944.65 + 264690.19` | 931634.84 |

Для краткости в столбце «расчёт» вместо всех слагаемых стоит накопительная сумма предыдущей даты плюс сумма текущей даты. Результат тот же.

**Шаг 3 — `ORDER BY order_date LIMIT 7`**

- `ORDER BY order_date` — сортирует готовый результат для показа. Это другой `ORDER BY`, не тот, что внутри `OVER`.
- `LIMIT 7` — оставляет первые семь строк.
- Оконная функция уже посчитана по всем 373 датам **до** `LIMIT`. `LIMIT` только обрезает показ и суммы не меняет.

Итоговый результат:

| order_date | orders | order_amount | running_amount |
|---|---:|---:|---:|
| 2025-07-29 | 90 | 104475.93 | 104475.93 |
| 2025-07-30 | 290 | 282137.82 | 386613.75 |
| 2025-07-31 | 271 | 280330.90 | 666944.65 |
| 2025-08-01 | 269 | 264690.19 | 931634.84 |
| 2025-08-02 | 272 | 282385.23 | 1214020.07 |
| 2025-08-03 | 275 | 283994.57 | 1498014.64 |
| 2025-08-04 | 238 | 231877.81 | 1729892.45 |

**Нюансы**

- Почему сначала `daily`, а потом окно. Если поставить `sum(amount) OVER (ORDER BY created_at ...)` прямо на таблицу `orders`, получится 100007 строк — накопительная сумма после каждого заказа, а не по дням. Для графика «по дням» сначала нужна одна строка на дату.
- `created_at::date` берёт дату в часовом поясе сессии базы. В учебной базе это `UTC`. Если в другой сессии стоит, например, `Europe/Moscow`, заказ, созданный в `2025-07-29 22:30+00`, попадёт на 30 июля.
- `ROWS` написан явно: итог растёт ровно на одну строку за шаг. Что будет, если границы не писать, а значения в `ORDER BY` повторяются, показано в следующем разделе.

## Кадр ROWS и одинаковые значения сортировки

**Цель.** Понять, чем кадр без слова `ROWS` отличается от кадра `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, когда в `ORDER BY` у нескольких строк одно и то же число.

Берём заказ 32. У него три попытки оплаты, у каждой `amount = 176.72`. После `target` и `JOIN` на листе три строки:

| attempt_no | amount |
|---:|---:|
| 1 | 176.72 |
| 2 | 176.72 |
| 3 | 176.72 |

`PARTITION BY order_id` кладёт все три в одну секцию. Дальше два окна считают `sum(amount)` по-разному.

**Окно без `ROWS`.** В `OVER` есть только `ORDER BY pa.amount`. Границ нет — PostgreSQL сам ставит кадр по значениям сортировки: взять все строки с `amount` не больше текущего. У всех трёх попыток `amount` одинаковый. Значит, для попытки 1, для попытки 2 и для попытки 3 в кадр попадают **сразу все три** строки.

| Считаем попытку | Какие строки в кадре | Счёт | default_range_total |
|---:|---|---|---:|
| 1 | 1, 2 и 3 | `176.72 + 176.72 + 176.72` | 530.16 |
| 2 | 1, 2 и 3 | `176.72 + 176.72 + 176.72` | 530.16 |
| 3 | 1, 2 и 3 | `176.72 + 176.72 + 176.72` | 530.16 |

Накопительной лестницы нет: на первой попытке уже полная сумма трёх.

**Окно с `ROWS`.** Границы написаны явно: `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Кадр считает **строки**, а не одинаковые суммы. Порядок закрепляют `ORDER BY pa.amount, pa.attempt_no`.

| Считаем попытку | Какие строки в кадре | Счёт | explicit_rows_total |
|---:|---|---|---:|
| 1 | только 1 | `176.72` | 176.72 |
| 2 | 1 и 2 | `176.72 + 176.72` | 353.44 |
| 3 | 1, 2 и 3 | `176.72 + 176.72 + 176.72` | 530.16 |

Здесь итог растёт по одной строке.

Если бы суммы в `ORDER BY` были разными, оба окна на этих трёх строках совпали бы. Разница видна только когда значения сортировки повторяются.

**Задача.** Найти первый заказ ровно с тремя попытками оплаты и для каждой его попытки показать оба способа.

```sql

-- target: один заказ, у которого ровно три попытки. Сейчас это заказ 32
WITH target AS (
    SELECT order_id
    FROM payment_attempts
    GROUP BY order_id
    -- корзина заказа из трёх строк
    HAVING count(*) = 3
    ORDER BY order_id
    LIMIT 1
)
SELECT pa.order_id,
       pa.attempt_no,
       pa.amount,
       -- окно без ROWS: кадр по умолчанию
       sum(pa.amount) OVER (
           -- одна секция — все попытки заказа 32
           PARTITION BY pa.order_id
           -- сортируем по сумме не потому что цена меняется: у всех трёх 176.72
           -- одинаковый ключ сортировки как раз и нужен: кадр без ROWS
           -- считает их одной пачкой и сразу даёт 530.16 на каждой строке
           ORDER BY pa.amount
       ) AS default_range_total,
       -- окно с ROWS: кадр по номерам строк
       sum(pa.amount) OVER (
           PARTITION BY pa.order_id
           -- amount один, без второго ключа порядок строк 1-2-3 не закреплён
           -- attempt_no ставит попытку 1 выше попытки 2, затем 3
           ORDER BY pa.amount, pa.attempt_no
           -- от первой строки секции до той, которую считают сейчас
           -- попытка 1: 176.72; попытка 2: 353.44; попытка 3: 530.16
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS explicit_rows_total
FROM payment_attempts pa
-- оставляем только три строки заказа из target
JOIN target t ON t.order_id = pa.order_id
-- показ сверху вниз по номеру попытки
ORDER BY pa.attempt_no;
```

**Как читается запрос**

- `target`: `GROUP BY order_id` + `HAVING count(*) = 3` оставляет заказы с тремя попытками. `ORDER BY order_id LIMIT 1` берёт первый такой номер. Сейчас это заказ 32.
- `JOIN target` оставляет из `payment_attempts` только три строки заказа 32.
- `default_range_total` — `ORDER BY pa.amount` без `ROWS`. Кадр по умолчанию. Расчёт — в таблице выше: на каждой попытке `530.16`.
- `explicit_rows_total` — `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Расчёт — во второй таблице выше: `176.72`, затем `353.44`, затем `530.16`.

| order_id | attempt_no | amount | default_range_total | explicit_rows_total |
|---:|---:|---:|---:|---:|
| 32 | 1 | 176.72 | 530.16 | 176.72 |
| 32 | 2 | 176.72 | 530.16 | 353.44 |
| 32 | 3 | 176.72 | 530.16 | 530.16 |

**Нюансы**

- Если накопительный итог должен расти на каждой строке, явно пишите `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Иначе строки с одинаковым значением в `ORDER BY` получат одну и ту же сумму сразу.
- В `ORDER BY` окна добавляют уникальный столбец (`id`, `attempt_no`), чтобы у строк с одинаковым значением был закреплённый порядок.

## Скользящее среднее за три строки

**Зачем это в работе.** Руководитель склада смотрит сумму заказов по дням, чтобы понять, сколько сборщиков ставить. 

- В учебной базе 29 июля магазин только открылся: 
  - сумма заказов - `104475.93`. 
  - 30 июля сумма заказов уже `282137.82`. 
- Если смотреть только «сегодня», кажется, что нагрузка прыгнула почти втрое и завтра нужно удвоить смену. 
  - На самом деле 29 июля — **короткий первый день**, а 30 и 31 июля уже обычные, около **280 тысяч.**

**Среднее** _за этот день и два предыдущих_ в отчёте отвечает на другой вопрос: **какая нагрузка сейчас типична, если не цепляться за один рваный день**. 
 - Для 31 июля это среднее из 29, 30 и 31 июля, не «только вчера» и не «вся история магазина».

Так же смотрят дневную выручку, число заказов, число отмен: 
 - график дня скачет, среднее за несколько строк отчёта показывает уровень, на который можно опираться при смене и закупке.

**Считать его так:** 
 - для выбранной даты взять её строку и две строки над ней в отчёте и поделить сумму на число этих строк. Это и есть `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`.

**Задача.** Операционный _дашборд_: 
  - **по каждой дате**, сумма заказов за этот день и **среднее** _за этот день плюс два предыдущих дня_ из отчёта. Учитываются все статусы. Для разбора — первые семь дат.

```sql

WITH daily AS (
    SELECT created_at::date AS order_date,
           round(sum(amount), 2) AS order_amount
    FROM orders
    GROUP BY created_at::date
),
report AS (
    SELECT order_date,
           order_amount,
           round(
               avg(order_amount) OVER (
                   ORDER BY order_date
                   ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
               ),
               2
           ) AS moving_avg_3_dates
    FROM daily
)
SELECT order_date,
       order_amount,
       moving_avg_3_dates
FROM report
ORDER BY order_date
LIMIT 7;
```

**Как читается запрос**

- На первой дате предыдущих строк нет, поэтому среднее считается по одной строке: `104475.93`.
- На второй дате доступно две строки: среднее `104475.93` и `282137.82` равно `193306.88`.
- С третьей даты кадр содержит три строки.
- На 2025-08-01 из кадра выходит 2025-07-29; среднее считается по 30 июля, 31 июля и 1 августа.

| order_date | order_amount | moving_avg_3_dates |
|---|---:|---:|
| 2025-07-29 | 104475.93 | 104475.93 |
| 2025-07-30 | 282137.82 | 193306.88 |
| 2025-07-31 | 280330.90 | 222314.88 |
| 2025-08-01 | 264690.19 | 275719.64 |
| 2025-08-02 | 282385.23 | 275802.11 |
| 2025-08-03 | 283994.57 | 277023.33 |
| 2025-08-04 | 231877.81 | 266085.87 |

**Нюансы**

- `2 PRECEDING` означает две предыдущие строки, а не обязательно два календарных дня.
- Здесь в `daily` по одной строке на дату, поэтому три строки соответствуют трём датам, присутствующим в данных.

## LAG и LEAD: предыдущая и следующая строка

`lag` читает значение из предыдущей строки секции, `lead` — из следующей.

### Синтаксис

```sql

lag(value_column) OVER (
    PARTITION BY section_column
    ORDER BY sort_column
)

lead(value_column) OVER (
    PARTITION BY section_column
    ORDER BY sort_column
)
```

- `value_column` — значение, которое нужно взять из соседней строки;
- `PARTITION BY` отделяет независимые последовательности, например попытки разных заказов;
- `ORDER BY` определяет, какая строка считается предыдущей, а какая — следующей;
- если соседней строки нет, функция возвращает `NULL`.

**Задача.** Служба платежей разбирает заказ с тремя попытками. Рядом с каждой попыткой показать предыдущий и следующий статусы.

```sql

WITH target AS (
    SELECT order_id
    FROM payment_attempts
    GROUP BY order_id
    HAVING count(*) = 3
    ORDER BY order_id
    LIMIT 1
)
SELECT pa.order_id,
       pa.attempt_no,
       pa.status,
       pa.amount,
       lag(pa.status) OVER (
           PARTITION BY pa.order_id
           ORDER BY pa.attempt_no
       ) AS previous_status,
       lead(pa.status) OVER (
           PARTITION BY pa.order_id
           ORDER BY pa.attempt_no
       ) AS next_status
FROM payment_attempts pa
JOIN target t ON t.order_id = pa.order_id
ORDER BY pa.attempt_no;
```

**Как читается запрос**

- `target` находит первый по номеру заказ, у которого три попытки. На учебной базе это заказ 32.
- `PARTITION BY pa.order_id` не позволяет читать строку другого заказа.
- `ORDER BY pa.attempt_no` задаёт последовательность попыток.
- Для попытки 2 `lag(status)` читает статус попытки 1, а `lead(status)` — статус попытки 3.
- У первой попытки предыдущей строки нет, поэтому `previous_status` равен `NULL`.
- У последней попытки следующей строки нет, поэтому `next_status` равен `NULL`.

| order_id | attempt_no | status | amount | previous_status | next_status |
|---:|---:|---|---:|---|---|
| 32 | 1 | failed | 176.72 | | failed |
| 32 | 2 | failed | 176.72 | failed | success |
| 32 | 3 | success | 176.72 | failed | |

**Нюансы**

- Без `ORDER BY` слова «предыдущая» и «следующая» не определены.
- При одинаковом значении порядка нужен дополнительный столбец, который закрепит последовательность.
- Сумма попыток оплаты не является выручкой: один заказ может иметь несколько попыток на одну сумму.

## Что обычно спрашивают на собеседованиях

Наиболее частые паттерны:

- отличие `GROUP BY` от оконного агрегата;
- top-N внутри каждой группы;
- последняя или первая строка в группе через `row_number`;
- разница между `row_number`, `rank` и `dense_rank`;
- накопительный итог;
- скользящее среднее;
- предыдущая строка через `lag`;
- почему оконная функция недоступна в `WHERE`;
- зачем нужен явный `ROWS`;
- почему в `ORDER BY` окна нужен дополнительный уникальный столбец.

**Источник:** https://techscreen.app/articles/sql-window-functions-interview-2026

**EN:**

> Problem 1: Top-N per Group
>
> Prompt: Return the top two earners in each department.
>
> This is the single most common window function interview question. LeetCode 185, "Department Top Three Salaries," is the same pattern. The trap is ties, so ask whether "top two" means two people or the top two salary values.

**RU:**

> Задача 1: top-N внутри группы.
>
> Постановка: вернуть двух сотрудников с наибольшей зарплатой в каждом отделе.
>
> Это самый распространённый вопрос на собеседовании по оконным функциям. Задача LeetCode 185 «Три наибольшие зарплаты в отделе» использует тот же паттерн. Ловушка — одинаковые значения, поэтому нужно уточнить, означает ли «два лучших» двух людей или два наибольших значения зарплаты.

## Карта выбора конструкции

| Бизнес-вопрос | Конструкция |
|---|---|
| Одно число по всем строкам, но детали сохранить | агрегат `OVER ()` |
| Одно число внутри каждой группы, детали сохранить | агрегат `OVER (PARTITION BY ...)` |
| Уникально пронумеровать строки | `row_number()` |
| Рейтинг: одинаковый результат — общее место, следующие места пропускаются | `rank()` |
| Рейтинг: одинаковый результат — общее место, места идут без пропусков | `dense_rank()` |
| Ровно N строк из каждой группы | `row_number()` в CTE, затем внешний фильтр |
| Накопительный итог | `sum(...) OVER (ORDER BY ... ROWS ...)` |
| Среднее по последним N строкам | `avg(...) OVER (... ROWS BETWEEN ...)` |
| Прочитать предыдущую строку | `lag(...)` |
| Прочитать следующую строку | `lead(...)` |
