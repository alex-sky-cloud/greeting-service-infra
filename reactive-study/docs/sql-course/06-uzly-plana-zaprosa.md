## Устройство любого плана

Прежде чем разбирать конкретные узлы, нужно понять три вещи, общие для **всех** планов.

### Порядок чтения: сверху вниз — это не порядок выполнения

План печатается как дерево. **Самая верхняя строка — это последний шаг**, тот, который отдаёт готовый результат клиенту. Выполнение же начинается с **самых вложенных** узлов и поднимается наверх.

```text

 Hash Anti Join            ← шаг 3 (последний): соединяет и отдаёт результат
   ->  Seq Scan on orders  ← шаг 2: читает заказы
   ->  Hash                ← шаг 1: строит хеш-таблицу
         ->  Seq Scan on products   ← шаг 0 (первый): читает товары
```

Поэтому `Seq Scan` часто оказывается вверху не потому, что он «главный», а потому что над ним больше ничего нет: запрос состоит из одного чтения и фильтра, и этот `Seq Scan` **и есть** последний шаг.

Практическое следствие: время верхнего узла **включает** время всех узлов под ним. Складывать времена строк плана нельзя — получится двойной счёт.

### Что такое стрелка `->` и отступ

Стрелка `->` в начале строки означает: **это дочерний узел**, он поставляет строки узлу, расположенному выше и левее.

Глубину вложенности показывает **отступ**. Узлы с одинаковым отступом — «братья», дети одного родителя.

```text

 Nested Loop Anti Join                          ← родитель
   ->  Seq Scan on users u                      ← первый ребёнок (внешняя сторона)
   ->  Index Only Scan on orders o              ← второй ребёнок (внутренняя сторона)
         Index Cond: (user_id = u.id)           ← НЕ ребёнок, а свойство узла выше
```

Различайте два типа строк с отступом:

| Строка начинается с | Что это |
|---|---|
| `->` | **новый узел** дерева |
| слова без стрелки (`Filter:`, `Index Cond:`, `Buffers:`, `Rows Removed by Filter:`) | **свойство** ближайшего узла выше, не отдельный шаг |

У соединения два ребёнка, и порядок важен: **первый** ребёнок — внешняя сторона (её строки перебираются), **второй** — внутренняя (в ней ищут пару).

### Что стоит в скобках после имени узла

```text

 Seq Scan on orders o  (cost=0.00..2324.07 rows=100007 width=18) (actual time=0.007..12.000 rows=100007 loops=1)
```

Здесь два блока скобок: первый — **оценка** планировщика, второй — **факт** выполнения (появляется только с опцией `ANALYZE`).

| Обозначение | Что означает |
|---|---|
| `cost=0.00..2324.07` | оценка в **условных единицах**, не в миллисекундах. Первое число — сколько стоит получить **первую** строку, второе — **все** строки |
| `rows=100007` (в первых скобках) | сколько строк планировщик **ожидал** получить |
| `width=18` | средняя ширина строки в байтах |
| `actual time=0.007..12.000` | **реальные миллисекунды**: до первой строки и до последней |
| `rows=100007` (во вторых скобках) | сколько строк узел **реально** отдал |
| `loops=1` | сколько раз узел был **запущен** |

Оценку и факт сравнивают между собой по `rows`, а `cost` с `actual time` сравнивать бессмысленно — это разные единицы.

**Источник:** https://www.postgresql.org/docs/16/using-explain.html

EN:

> Note that the “actual time” values are in milliseconds of real time, whereas the `cost` estimates are expressed in arbitrary units; so they are unlikely to match up. The thing that's usually most important to look for is whether the estimated row counts are reasonably close to reality.

RU:

> Обратите внимание, что значения «actual time» указаны в миллисекундах реального времени, тогда как оценки `cost` выражены в условных единицах, поэтому они вряд ли будут совпадать. Обычно важнее всего смотреть, насколько оценённые количества строк близки к реальности.

**Про `loops` — самое важное для этого документа.** Если `loops` больше единицы, то `actual time` и `rows` показаны **в среднем за один запуск**, а не суммарно.

EN:

> In such cases, the `loops` value reports the total number of executions of the node, and the actual time and rows values shown are averages per-execution. This is done to make the numbers comparable with the way that the cost estimates are shown. Multiply by the `loops` value to get the total time actually spent in the node.

RU:

> В таких случаях значение `loops` сообщает общее число выполнений узла, а показанные значения actual time и rows являются средними за одно выполнение. Это сделано, чтобы числа были сравнимы с тем, как показаны оценки стоимости. Умножьте на значение `loops`, чтобы получить общее время, фактически затраченное в узле.

## Два исхода: подзапрос остался шагом или растворился в соединении

Когда в запросе есть подзапрос, планировщик выбирает одно из двух. Это развилка, определяющая всё остальное.

| Исход | Как выглядит в плане | Обычно |
|---|---|---|
| Подзапрос **остался отдельным шагом** | в плане есть `InitPlan` или `SubPlan` | `InitPlan` — отлично, `SubPlan` — тревожно |
| Подзапрос **превратился в соединение** | в плане есть `Semi Join` или `Anti Join`, слова `SubPlan` нет | хорошо |

Второй исход лучше, потому что соединение планировщик умеет выполнять **тремя разными алгоритмами** и выбрать дешёвый. Для `SubPlan` такого выбора нет — он просто выполняется столько раз, сколько нужно.

Дальше — по одному примеру на каждый случай, с построчным разбором.

---

## InitPlan — подзапрос выполняется один раз

**Запрос.** Заказы дороже средней суммы (scalar-подзапрос):

```sql

EXPLAIN (ANALYZE, COSTS OFF)
SELECT o.id
FROM orders o
WHERE o.amount > (SELECT avg(amount) FROM orders);
```

**Вывод:**

```text

 Seq Scan on orders o (actual time=14.871..28.134 rows=49971 loops=1)
   Filter: (amount > $0)
   Rows Removed by Filter: 50036
   InitPlan 1 (returns $0)
     ->  Aggregate (actual time=14.866..14.867 rows=1 loops=1)
           ->  Seq Scan on orders (actual time=0.001..7.706 rows=100007 loops=1)
 Planning Time: 0.074 ms
 Execution Time: 29.388 ms
```

**Построчный разбор**

| Строка | Разбор |
|---|---|
| `Seq Scan on orders o` | **`Seq Scan`** = sequential scan, «последовательное чтение»: PostgreSQL берёт страницы таблицы по порядку и проверяет каждую строку. Индекс не используется. **`on orders o`** — читается таблица `orders`, `o` — её псевдоним из запроса. Узел стоит **первым сверху**, потому что он последний шаг: над ним ничего нет, запрос состоит из чтения и фильтра |
| `(actual time=14.871..28.134 rows=49971 loops=1)` | первая строка результата появилась через 14.871 мс (ждали, пока посчитается среднее), последняя — через 28.134 мс. Отдано 49 971 строк. Узел запускался **один** раз |
| `Filter: (amount > $0)` | **`Filter:`** — условие, которое проверяется **для каждой прочитанной строки** уже после того, как строка получена. Это свойство узла выше, а не отдельный шаг. **`$0`** — не столбец и не опечатка: это внутренняя **переменная**, куда положен результат `InitPlan` |
| `Rows Removed by Filter: 50036` | сколько строк фильтр **отбросил**. Проверка: `49 971 + 50 036 = 100 007` — вся таблица прочитана |
| `InitPlan 1 (returns $0)` | **`InitPlan`** — подзапрос, который **не зависит** от строк внешнего запроса, поэтому выполняется **однократно** до основной работы. **`returns $0`** — результат сохраняется в переменную `$0`, ту самую, что стоит в `Filter` |
| `-> Aggregate (… rows=1 loops=1)` | стрелка: дочерний узел. **`Aggregate`** — вычисление агрегатной функции, здесь `avg`. **`rows=1`** — агрегат дал одну строку. **`loops=1`** — выполнен **один раз**, это и есть главная ценность `InitPlan` |
| `-> Seq Scan on orders (… rows=100007 loops=1)` | чтобы посчитать среднее, пришлось прочитать все 100 007 заказов. Псевдонима нет, потому что во внутреннем запросе он не задан |
| `Planning Time: 0.074 ms` | сколько заняло **построение** плана |
| `Execution Time: 29.388 ms` | сколько заняло **выполнение** |

**Вывод по узлу.** `InitPlan` — лучший исход для подзапроса. Таблица `orders` прочитана дважды (один раз для среднего, один раз для фильтра), но обе — по одному разу. Слово `InitPlan` в плане означает «подзапрос посчитан заранее, дальше работаем с готовым числом».

## SubPlan — подзапрос выполняется для каждой строки

**Запрос.** Клиенты без заказов, записанные через коррелированный `NOT IN`:

```sql

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT u.id
FROM users u
WHERE u.id NOT IN (SELECT o.user_id FROM orders o WHERE o.user_id = u.id);
```

**Вывод:**

```text

 Seq Scan on users u (actual time=5.346..5.351 rows=4 loops=1)
   Filter: (NOT (SubPlan 1))
   Rows Removed by Filter: 5001
   Buffers: shared hit=10144
   SubPlan 1
     ->  Index Only Scan using idx_orders_user_id on orders o (actual time=0.001..0.001 rows=1 loops=5005)
           Index Cond: (user_id = u.id)
           Heap Fetches: 72
           Buffers: shared hit=10083
 Planning Time: 0.237 ms
 Execution Time: 5.408 ms
```

**Построчный разбор**

| Строка | Разбор |
|---|---|
| `Seq Scan on users u` | полное чтение таблицы `users`. Вверху, потому что это последний шаг |
| `(… rows=4 loops=1)` | итог — 4 клиента без заказов |
| `Filter: (NOT (SubPlan 1))` | условие для каждой строки: «результат подзапроса номер 1, взятый с отрицанием». Слова **`InitPlan` здесь нет** — и это главное отличие от предыдущего примера |
| `Rows Removed by Filter: 5001` | отброшено 5001 клиентов. `4 + 5001 = 5005` — все клиенты проверены |
| `Buffers: shared hit=10144` | **`Buffers`** — сколько 8-КБ **страниц** затребовал узел вместе со всеми детьми. **`shared hit`** — страница нашлась в оперативной памяти PostgreSQL. Было бы `shared read` — страницу пришлось подгружать |
| `SubPlan 1` | **`SubPlan`** — подзапрос, который **зависит** от строки внешнего запроса (коррелированный), поэтому его нельзя посчитать заранее. Номер `1` связывает его со ссылкой в `Filter` |
| `-> Index Only Scan using idx_orders_user_id on orders o` | **`Index Only Scan`** — чтение **только из индекса**, без обращения к самой таблице. Возможно, потому что подзапросу нужен лишь столбец `user_id`, а он в индексе есть. **`using idx_orders_user_id`** — имя использованного индекса. **`on orders o`** — по какой таблице этот индекс |
| `(actual time=0.001..0.001 rows=1 loops=5005)` | **`loops=5005`** — подзапрос выполнен **5005 раз**, по разу на каждого клиента. `rows=1` и `0.001 мс` — это **средние за один запуск**, а не итог. Общее время ≈ `0.001 × 5005 ≈ 5 мс` |
| `Index Cond: (user_id = u.id)` | **`Index Cond:`** — условие, по которому идёт поиск **внутри индекса**. Отличие от `Filter:` принципиальное: `Index Cond` **сужает поиск** ещё до чтения данных, а `Filter` проверяет уже прочитанные строки. Здесь видно и корреляцию: `u.id` приходит из внешнего запроса |
| `Heap Fetches: 72` | сколько раз `Index Only Scan` всё же был вынужден заглянуть в саму таблицу. Так бывает, когда страница таблицы недавно менялась и её видимость нельзя подтвердить по индексу. Чем меньше это число, тем лучше |
| `Buffers: shared hit=10083` | почти все 10 144 страницы верхнего узла потрачены здесь: 5005 запусков × ~2 страницы индекса |

**Про `Index Only Scan` и `Heap Fetches` — официально.**

**Источник:** https://www.postgresql.org/docs/16/indexes-index-only-scans.html

EN:

> An index-only scan, after finding a candidate index entry, checks the visibility map bit for the corresponding heap page. If it's set, the row is known visible and so the data can be returned with no further work. If it's not set, the heap entry must be visited to find out whether it's visible, so no performance advantage is gained over a standard index scan.

RU:

> Сканирование только по индексу, найдя кандидата среди записей индекса, проверяет бит карты видимости для соответствующей страницы кучи. Если бит установлен, строка заведомо видима, и данные можно вернуть без дальнейшей работы. Если бит не установлен, необходимо обратиться к записи в куче, чтобы выяснить, видима ли она, и тогда выигрыша в производительности по сравнению с обычным сканированием по индексу не будет.

**Вывод по узлу.** `SubPlan` с большим `loops` — сигнал «подзапрос не удалось развернуть в соединение». Здесь это обошлось дёшево (5.4 мс), потому что индекс есть, а клиентов всего 5005. Если бы индекса не было, внутри `SubPlan` стоял бы `Seq Scan`, и каждый из 5005 запусков читал бы таблицу целиком.

## Semi Join — «пара нашлась»

**Запрос.** Клиенты, у которых есть хотя бы один заказ:

```sql

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT u.id, u.full_name
FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

**Вывод:**

```text

 Nested Loop Semi Join (actual time=0.013..5.462 rows=5001 loops=1)
   Buffers: shared hit=10144
   ->  Seq Scan on users u (actual time=0.003..0.271 rows=5005 loops=1)
         Buffers: shared hit=61
   ->  Index Only Scan using idx_orders_user_id on orders o (actual time=0.001..0.001 rows=1 loops=5005)
         Index Cond: (user_id = u.id)
         Heap Fetches: 72
         Buffers: shared hit=10083
 Planning Time: 0.548 ms
 Execution Time: 5.627 ms
```

**Построчный разбор**

| Строка | Разбор |
|---|---|
| `Nested Loop Semi Join` | имя узла состоит из **двух частей**. **`Semi Join`** — *что* делается: оставить строки внешней таблицы, у которых пара **нашлась**, причём каждую **один раз**. **`Nested Loop`** — *каким способом* ищется пара (разбор алгоритма ниже) |
| | Приставка **«Semi»** (полу-соединение) означает: столбцы второй таблицы в результат **не попадают**, она нужна только для проверки. Поэтому дублей, как у обычного JOIN, не возникает: клиент с 18 заказами выйдет **один раз** |
| | **Слова `SubPlan` в плане нет** — подзапрос `EXISTS` растворился в узле соединения. Это и есть «хороший исход» |
| `(… rows=5001 loops=1)` | 5001 клиент имеет заказы (из 5005 всего) |
| `-> Seq Scan on users u (rows=5005 loops=1)` | **первый** ребёнок — **внешняя** сторона соединения. Её строки перебираются, каждая по одному разу |
| `-> Index Only Scan … (loops=5005)` | **второй** ребёнок — **внутренняя** сторона. `loops=5005` означает, что поиск запускался для каждой внешней строки. Для `Nested Loop` это норма, а не проблема |
| `Index Cond: (user_id = u.id)` | по этому условию ищется пара в индексе |
| `Buffers` у узлов | 61 страница на чтение клиентов + 10 083 на поиски в индексе = 10 144 у родителя. Числа детей **суммируются** в родителе |

**Откуда берётся `Semi Join`.** Из `EXISTS`, а часто и из `IN` с подзапросом. Документация описывает `EXISTS` так:

**Источник:** https://www.postgresql.org/docs/16/functions-subquery.html

EN:

> The argument of `EXISTS` is an arbitrary `SELECT` statement, or subquery. The subquery is evaluated to determine whether it returns any rows. If it returns at least one row, the result of `EXISTS` is “true”; if the subquery returns no rows, the result of `EXISTS` is “false”.

RU:

> Аргумент `EXISTS` — произвольный оператор `SELECT`, то есть подзапрос. Подзапрос вычисляется, чтобы определить, возвращает ли он какие-либо строки. Если он возвращает хотя бы одну строку, результат `EXISTS` — «истина»; если подзапрос не возвращает строк, результат `EXISTS` — «ложь».

Именно из-за «достаточно одной строки» узел и называется полу-соединением: найдя первую пару, он переходит к следующей внешней строке и не ищет остальные.

## Anti Join — «пары нет»

**Запрос.** Клиенты, у которых заказов нет:

```sql

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT u.id
FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

**Вывод:**

```text

 Nested Loop Anti Join (actual time=5.850..5.855 rows=4 loops=1)
   Buffers: shared hit=10144
   ->  Seq Scan on users u (actual time=0.004..0.351 rows=5005 loops=1)
         Buffers: shared hit=61
   ->  Index Only Scan using idx_orders_user_id on orders o (actual time=0.001..0.001 rows=1 loops=5005)
         Index Cond: (user_id = u.id)
         Heap Fetches: 72
         Buffers: shared hit=10083
 Planning Time: 0.892 ms
 Execution Time: 5.895 ms
```

**Построчный разбор**

| Строка | Разбор |
|---|---|
| `Nested Loop Anti Join` | **`Anti Join`** — зеркало `Semi Join`: оставить строки внешней таблицы, у которых пара **не нашлась**. Получается из `NOT EXISTS` |
| `(… rows=4 loops=1)` | 4 клиента без заказов |
| остальные строки | **дословно совпадают** с предыдущим примером |

**Сравните два плана целиком.** У `Semi Join` и `Anti Join` одинаковое дерево, одинаковые `loops=5005` и одинаковые `Buffers: shared hit=10144`. Отличается **только имя верхнего узла** и число строк на выходе: 5001 против 4.

Это полезно запомнить: `EXISTS` и `NOT EXISTS` стоят **одинаково**. Выбор между ними — вопрос смысла задачи, а не производительности.

**И сравните с разделом про `SubPlan` выше.** Там был тот же вопрос «клиенты без заказов», только записанный через коррелированный `NOT IN`. Числа:

| Запись | Верхний узел | `loops` | `Buffers` | Время |
|---|---|---|---|---|
| `NOT IN` коррелированный | `Seq Scan` + `SubPlan` | 5005 | 10 144 | 5.4 мс |
| `NOT EXISTS` | `Nested Loop Anti Join` | 5005 | 10 144 | 5.9 мс |

Разницы практически нет. Это важная оговорка: `SubPlan` **не всегда** катастрофа. Он становится катастрофой, когда один его запуск дорогой — об этом в конце документа.

**Почему `NOT EXISTS` не боится NULL.** `Anti Join` не сравнивает значения по правилам трёхзначной логики — он отвечает на вопрос «пара нашлась или нет», а этот ответ всегда однозначен. Разбор ловушки NULL у `NOT IN` — в [соседнем документе](06-lovushka-null-i-plan-zaprosa.md).

## Три алгоритма соединения

Слово перед `Semi Join` / `Anti Join` (а также перед обычным `Join`) говорит, **каким способом** ищется пара. Алгоритма три, и каждый хорош в своей ситуации.

### Nested Loop — вложенный цикл

**Как работает.** Берём очередную строку внешней таблицы, идём искать для неё пару во внутренней. Потом следующую. И так далее.

```text

для каждой строки внешней таблицы:
    выполнить поиск во внутренней таблице
    решить, оставлять внешнюю строку или нет
```

Это тот самый алгоритм из примеров выше — отсюда и `loops=5005` у внутреннего узла.

**Когда хорош:** внешняя сторона **маленькая** и во внутренней есть **индекс** по ключу соединения. Тогда каждый проход — дешёвый точечный поиск.

**Когда плох:** внешняя сторона большая. Тысячи или сотни тысяч точечных поисков складываются в огромную работу, даже если каждый отдельный дешёвый.

**Признак в плане:** у внутреннего узла `loops` заметно больше единицы.

### Hash — через хеш-таблицу в памяти

**Запрос.** Заказы, товара которых нет в каталоге:

```sql

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT o.id
FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM products p WHERE p.id = o.product_id);
```

**Вывод:**

```text

 Hash Anti Join (actual time=14.860..18.630 rows=3 loops=1)
   Hash Cond: (o.product_id = p.id)
   Buffers: shared hit=1326
   ->  Seq Scan on orders o (actual time=0.007..10.581 rows=100007 loops=1)
         Buffers: shared hit=1324
   ->  Hash (actual time=0.051..0.053 rows=200 loops=1)
         Buckets: 1024  Batches: 1  Memory Usage: 16kB
         Buffers: shared hit=2
         ->  Seq Scan on products p (actual time=0.005..0.019 rows=200 loops=1)
               Buffers: shared hit=2
 Execution Time: 18.697 ms
```

**Построчный разбор**

| Строка | Разбор |
|---|---|
| `Hash Anti Join` | тот же `Anti Join`, но способ поиска пары другой — через хеш-таблицу |
| `Hash Cond: (o.product_id = p.id)` | **`Hash Cond:`** — по каким столбцам сопоставляются строки. Аналог `Index Cond`, но для хеш-соединения |
| `Buffers: shared hit=1326` | `1324 + 2` — каждая таблица прочитана **ровно один раз**. Сравните с 10 144 у `Nested Loop` выше |
| `-> Seq Scan on orders o (rows=100007 loops=1)` | внешняя сторона: все заказы, прочитаны **однократно**. `loops=1`, а не 100 007 — в этом вся разница |
| `-> Hash (rows=200 loops=1)` | **`Hash`** — отдельный узел, который **строит** хеш-таблицу. Он всегда стоит над тем узлом, чьи строки в неё складывает |
| `Buckets: 1024` | сколько «корзин» в хеш-таблице. Значение хеш-функции определяет номер корзины, где лежит строка |
| `Batches: 1` | сколько **проходов** понадобилось. Единица означает «всё уместилось в памяти». Если бы было больше единицы, часть работы ушла бы во временные файлы на диске — это тревожный признак |
| `Memory Usage: 16kB` | сколько рабочей памяти заняла хеш-таблица |
| `-> Seq Scan on products p (rows=200 loops=1)` | ребёнок узла `Hash`: откуда берутся строки для хеш-таблицы. 200 товаров, прочитаны один раз |

**Механика двумя фразами:**

```text

шаг 1 (build)  — прочитать products один раз и разложить 200 значений id
                 по 1024 корзинам хеш-таблицы (16 КБ)
шаг 2 (probe)  — прочитать orders один раз; для каждого заказа посчитать
                 хеш от product_id и заглянуть сразу в нужную корзину
```

**Когда хорош:** внешняя сторона **большая**, внутренняя **помещается в память**. Обе таблицы читаются по одному разу.

**Когда плох:** если внутренняя сторона в память не влезает — появится `Batches` больше единицы и работа с временными файлами.

### Merge — встречное движение по отсортированным данным

**Как работает.** Обе стороны читаются **в отсортированном порядке** по ключу, и алгоритм идёт по ним одновременно, как при слиянии двух упорядоченных списков.

**Вывод** (получен принудительно, см. эксперимент ниже):

```text

 Merge Anti Join (actual time=11.454..11.463 rows=4 loops=1)
   Merge Cond: (u.id = o.user_id)
   Buffers: shared hit=365
   ->  Index Only Scan using users_pkey on users u (actual time=0.008..0.461 rows=5005 loops=1)
         Heap Fetches: 153
         Buffers: shared hit=20
   ->  Index Only Scan using idx_orders_user_id on orders o (actual time=0.009..6.366 rows=100001 loops=1)
         Heap Fetches: 264
         Buffers: shared hit=345
 Execution Time: 11.504 ms
```

**Построчный разбор**

| Строка | Разбор |
|---|---|
| `Merge Anti Join` | тот же `Anti Join`, способ — слияние отсортированных потоков |
| `Merge Cond: (u.id = o.user_id)` | **`Merge Cond:`** — ключ, по которому обе стороны отсортированы и сопоставляются |
| `-> Index Only Scan using users_pkey` | **`users_pkey`** — индекс первичного ключа `users`. Чтение по индексу выдаёт строки **уже отсортированными** по `id`, поэтому отдельного узла `Sort` в плане нет |
| `-> Index Only Scan using idx_orders_user_id … rows=100001 loops=1` | вторая сторона тоже читается через индекс, то есть по возрастанию `user_id`. Обратите внимание на `rows=100001`: прочитан **весь** индекс заказов, а не выборочные записи |
| `Buffers: shared hit=365` | всего 365 страниц — **меньше**, чем у `Nested Loop` (10 144), потому что индексы читаются подряд, а не тысячами точечных поисков |

**Когда хорош:** обе стороны уже отсортированы по ключу соединения, например читаются через индексы. Тогда сортировать ничего не нужно.

**Когда плох:** если сортировки нет, её придётся выполнить — в плане появится узел `Sort`, и он может съесть весь выигрыш.

**Внимание на ловушку в числах.** У `Merge Anti Join` страниц **меньше** (365 против 10 144), а время **больше** (11.5 мс против 5.9 мс). Противоречия нет: `Nested Loop` трогает много страниц, но это одни и те же горячие страницы индекса, уже лежащие в памяти, а `Merge` вынужден пройти **весь** индекс `orders` — 100 001 запись, и это процессорная работа.

Отсюда правило: сравнивать по `Buffers` корректно, когда планы **одинаковы по форме**. Когда алгоритмы разные, смотреть надо и на `Buffers`, и на время.

## Эксперимент: заставить планировщик ошибиться

Лучший способ понять, почему выбран тот или иной алгоритм, — запретить его и посмотреть, что получится.

### Как временно запретить алгоритм

У планировщика есть переключатели, выключающие отдельные типы планов. Они действуют **только в текущей сессии** и данные не меняют.

```sql

SET enable_nestloop  = off;   -- запретить Nested Loop
SET enable_hashjoin  = off;   -- запретить Hash Join
SET enable_mergejoin = off;   -- запретить Merge Join
```

Вернуть как было:

```sql

RESET enable_nestloop;
RESET enable_hashjoin;
RESET enable_mergejoin;
```

Либо просто закрыть соединение — настройки сессии исчезнут вместе с ним.

**Источник:** https://www.postgresql.org/docs/16/runtime-config-query.html

EN:

> `enable_nestloop` (`boolean`) — Enables or disables the query planner's use of nested-loop join plans. It is impossible to suppress nested-loop joins entirely, but turning this variable off discourages the planner from using one if there are other methods available. The default is `on`.

RU:

> `enable_nestloop` (`boolean`) — Включает или отключает использование планировщиком запросов планов соединения вложенным циклом. Полностью подавить соединения вложенным циклом невозможно, но выключение этой переменной отговаривает планировщик от её использования, если доступны другие методы. Значение по умолчанию — `on`.

Обратите внимание на оговорку «полностью подавить невозможно»: это **подсказки**, а не жёсткие запреты. В продакшене их не используют для «ускорения» запросов — только для исследования, как здесь.

### Случай А — внешняя таблица маленькая

Клиенты без заказов: внешняя сторона `users` = 5 005 строк, на `orders.user_id` есть индекс.

```sql

SET enable_nestloop = off;

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT u.id
FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

RESET enable_nestloop;
```

| Алгоритм | Время | `Buffers` |
|---|---|---|
| `Nested Loop Anti Join` — **выбор планировщика** | **5.9 мс** | 10 144 |
| `Merge Anti Join` — принудительно | 11.5 мс | 365 |

Планировщик выбрал верно: внешних строк мало, индекс есть, каждый из 5005 точечных поисков дёшев.

### Случай Б — внешняя таблица большая

Заказы без товара в каталоге: внешняя сторона `orders` = 100 007 строк, внутренняя `products` = 200 строк.

```sql

SET enable_hashjoin = off;
SET enable_mergejoin = off;

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT o.id
FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM products p WHERE p.id = o.product_id);

RESET enable_hashjoin;
RESET enable_mergejoin;
```

**Что получилось вместо `Hash Anti Join`:**

```text

 Gather (actual time=145.450..231.342 rows=3 loops=1)
   Workers Planned: 1
   Workers Launched: 1
   Buffers: shared hit=201332
   ->  Nested Loop Anti Join (actual time=33.186..42.239 rows=2 loops=2)
         Buffers: shared hit=201332
         ->  Parallel Seq Scan on orders o (actual time=0.005..6.134 rows=50004 loops=2)
               Buffers: shared hit=1324
         ->  Index Only Scan using products_pkey on products p (actual time=0.001..0.001 rows=1 loops=100007)
               Index Cond: (id = o.product_id)
               Heap Fetches: 100004
               Buffers: shared hit=200008
 Execution Time: 236.705 ms
```

**Построчный разбор новых слов**

| Строка | Разбор |
|---|---|
| `Gather` | узел, **собирающий** результаты параллельных процессов в один поток. Появляется только в параллельных планах |
| `Workers Planned: 1` | планировщик рассчитывал задействовать одного помощника **в дополнение** к основному процессу |
| `Workers Launched: 1` | помощник действительно запустился. Бывает, что запланировано больше, чем запущено, — если воркеры заняты другими запросами |
| `Nested Loop Anti Join (… rows=2 loops=2)` | **`loops=2`** — узел выполнялся в двух процессах. Значит `rows=2` — **среднее** на процесс, а суммарно `2 × 2 ≈ 3` строки, что и показывает `Gather` выше |
| `Parallel Seq Scan on orders o (rows=50004 loops=2)` | **`Parallel Seq Scan`** — таблица читается **совместно** несколькими процессами: каждый берёт свою часть страниц. По 50 004 строки на процесс, вместе 100 007 |
| `Index Only Scan … (loops=100007)` | вот она, цена: точечный поиск в `products` выполнен **100 007 раз** |
| `Heap Fetches: 100004` | почти каждый из этих поисков был вынужден обратиться к самой таблице — преимущество `Index Only Scan` здесь потеряно |
| `Buffers: shared hit=200008` | 100 007 поисков × ~2 страницы = 200 тысяч обращений |

**Сравнение:**

| Алгоритм | Время | `Buffers` |
|---|---|---|
| `Hash Anti Join` — **выбор планировщика** | **18.7 мс** | 1 326 |
| `Nested Loop Anti Join` — принудительно | 236.7 мс | 201 332 |

Навязанный `Nested Loop` дал **в 12 раз** больше времени и **в 152 раза** больше обращений к страницам. Причём ему даже разрешили распараллелиться на два процесса — и это не спасло.

## Главный вывод: когда большой loops — это плохо

Соберём наблюдения вместе.

В случае А `Nested Loop Anti Join` имеет `loops=5005` и **побеждает**. В случае Б `Nested Loop Anti Join` имеет `loops=100007` и **проигрывает в 12 раз**.

Значит большой `loops` сам по себе — **не диагноз**. Диагноз — это `loops`, умноженный на стоимость одного прохода:

| Ситуация | Стоимость одного прохода | Итог |
|---|---|---|
| Индекс есть, внешняя таблица мала | точечный поиск, ~2 страницы | 5 005 × 2 ≈ 10 тыс. страниц — приемлемо |
| Индекс есть, внешняя таблица огромна | точечный поиск, ~2 страницы | 100 007 × 2 ≈ 200 тыс. страниц — плохо |
| **Индекса нет** | **полное сканирование таблицы** | катастрофа при любом заметном `loops` |

Третья строка — самый тяжёлый случай. Именно он встречается, когда коррелированный подзапрос остался `SubPlan`, а внутри него стоит `Seq Scan`. Разбор такого плана с временем 707 мс — в [соседнем документе](06-lovushka-null-i-plan-zaprosa.md#вариант-2--not-in-с-корреляцией-правильный-и-в-32-раза-дороже).

**Порядок действий при разборе плана**

1. Найти, есть ли в плане `SubPlan`. Если есть — посмотреть `loops` и **что стоит внутри**: `Index Only Scan` терпимо, `Seq Scan` тревожно.
2. Если вместо `SubPlan` стоит `Semi Join` / `Anti Join` — подзапрос развернулся, это хорошо.
3. Посмотреть слово перед `Join`: соответствует ли алгоритм размеру сторон (маленькая внешняя + индекс → `Nested Loop`; большая внешняя + маленькая внутренняя → `Hash`).
4. У `Hash` проверить `Batches`: единица — хорошо, больше — хеш не влез в память.
5. Сверить `Buffers` с размером таблиц: сильное превышение означает повторное чтение.

## Шпаргалка по всем встреченным словам

### Узлы чтения таблиц

| Слово | Значение |
|---|---|
| `Seq Scan` | последовательное чтение всей таблицы страница за страницей |
| `Parallel Seq Scan` | то же, но страницы поделены между несколькими процессами |
| `Index Scan` | поиск по индексу, затем обращение к таблице за остальными столбцами |
| `Index Only Scan` | всё нужное взято **из индекса**, таблица не читается (или читается редко, см. `Heap Fetches`) |
| `Bitmap Index Scan` / `Bitmap Heap Scan` | индекс строит карту нужных страниц, затем эти страницы читаются |

### Узлы обработки

| Слово | Значение |
|---|---|
| `Aggregate` | вычисление агрегата: `count`, `sum`, `avg`, `min`, `max` |
| `HashAggregate` | группировка через хеш-таблицу, аналог `GROUP BY` |
| `Hash` | построение хеш-таблицы для последующего соединения |
| `Sort` | сортировка строк |
| `Gather` | сбор результатов параллельных процессов в один поток |

### Узлы соединения

| Слово | Значение |
|---|---|
| `Join` | обычное соединение, столбцы обеих таблиц попадают в результат |
| `Semi Join` | оставить внешние строки, у которых пара **есть**, каждую **один раз**; из `EXISTS` и `IN` |
| `Anti Join` | оставить внешние строки, у которых пары **нет**; из `NOT EXISTS` |
| `Left` / `Right` в имени | какая физическая сторона сохраняется целиком |
| `Nested Loop` + | способ: для каждой внешней строки — поиск во внутренней |
| `Hash` + | способ: внутренняя сторона один раз в хеш-таблицу, затем проверка внешней |
| `Merge` + | способ: обе стороны читаются отсортированными и идут навстречу |

### Подзапросы

| Слово | Значение |
|---|---|
| `InitPlan N (returns $0)` | подзапрос **не зависит** от внешних строк, выполнен **один раз**, результат в переменной `$0` |
| `SubPlan N` | подзапрос **зависит** от внешней строки, выполняется заново для каждой |
| `$0`, `$1` | внутренние переменные с результатами `InitPlan` |

### Условия

| Слово | Значение |
|---|---|
| `Filter:` | условие проверяется для **каждой уже прочитанной** строки |
| `Index Cond:` | условие **сужает поиск внутри индекса** ещё до чтения данных |
| `Hash Cond:` | по каким столбцам сопоставляются строки в хеш-соединении |
| `Merge Cond:` | ключ, по которому идёт слияние отсортированных потоков |
| `Recheck Cond:` | повторная точная проверка после `Bitmap Heap Scan` |
| `Group Key:` | по каким столбцам идёт группировка |

### Числа

| Слово | Значение |
|---|---|
| `cost=A..B` | оценка в условных единицах: до первой строки и до последней. **Не миллисекунды** |
| `rows=` в первых скобках | сколько строк планировщик **ожидал** |
| `width=` | средняя ширина строки в байтах |
| `actual time=X..Y` | реальные миллисекунды: до первой и до последней строки |
| `rows=` во вторых скобках | сколько строк узел **реально** отдал (**в среднем за запуск**, если `loops` > 1) |
| `loops=` | сколько раз узел был запущен |
| `Rows Removed by Filter:` | сколько строк отбросило условие `Filter` |
| `Buffers: shared hit=` | страниц по 8 КБ, найденных в памяти PostgreSQL |
| `Buffers: shared read=` | страниц, которые пришлось подгрузить |
| `Heap Fetches:` | сколько раз `Index Only Scan` всё же обратился к таблице |
| `Buckets:` | число корзин в хеш-таблице |
| `Batches:` | число проходов; больше 1 — хеш не поместился в память |
| `Memory Usage:` | сколько рабочей памяти занял узел |
| `Workers Planned` / `Workers Launched` | сколько параллельных помощников запланировано и сколько реально запустилось |
| `never executed` | узел ни разу не запускался: данных на вход не поступило |
| `Planning Time` | время **построения** плана |
| `Execution Time` | время **выполнения** запроса |
