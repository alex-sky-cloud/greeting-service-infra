## Задача, на которой всё разбирается

**Бизнес-вопрос.** «Покажи заказы, у которых товар отсутствует в каталоге `products`».

Зачем это нужно в жизни: такие заказы нельзя ни собрать, ни отгрузить — на них нет позиции склада. Это список для разбора службой поддержки.

**Правильный ответ известен заранее.** В `reactive_study` таких заказов **три** — у них поле `product_id` пустое (NULL), то есть ссылки на товар нет вообще:

```sql

SELECT id, product_name, product_id
FROM orders
WHERE product_id IS NULL
ORDER BY id;
```

```text

   id   |      product_name      | product_id
--------+------------------------+------------
    500 | Bulk order #500        |
 100002 | JOIN-DEMO-NO-PRODUCT-1 |
 100003 | JOIN-DEMO-NO-PRODUCT-2 |
```

Дальше этот же вопрос записан **четырьмя** способами. Все четыре — синтаксически корректный SQL, ни один не падает с ошибкой. Но результаты и цена у них разные.

| № | Как записан | Строк вернул | Время |
|---|---|---|---|
| 1 | `NOT IN` без корреляции | **0** — неверно | 17 мс |
| 2 | `NOT IN` с корреляцией | 3 — верно | **707 мс** |
| 3 | `NOT EXISTS (SELECT 1 …)` | 3 — верно | **22 мс** |
| 4 | `NOT EXISTS (SELECT p.id …)` | 3 — верно | 22 мс |

Задача этого документа — научиться **видеть эту разницу в плане**, а не узнавать о ней от клиента, у которого отчёт оказался пустым.

## Размер данных — без этого план не прочитать

Все числа в плане имеют смысл только относительно размера таблиц. Снимите их один раз:

```sql

SELECT relname, relpages, reltuples::bigint AS rows
FROM pg_class
WHERE relname IN ('orders', 'products');
```

```text

 relname  | relpages | rows
----------+----------+--------
 orders   |     1324 | 100007
 products |        2 |    200
```

**Как это читать.** `relpages` — во сколько **страниц** по 8 КБ уложена таблица (про страницы — [урок 0 руководства](planner-explain.md#урок-0--данные-страницы-и-память)).

| Таблица | Страниц | Строк | Что это значит для плана |
|---|---|---|---|
| `orders` | **1324** | 100 007 | ≈ 10 МБ; прочитать целиком — 1324 обращения к страницам |
| `products` | **2** | 200 | ≈ 16 КБ; прочитать целиком — 2 обращения, это почти бесплатно |

Запомните два числа — **1324** и **2**. Ниже вся арифметика в `Buffers` сойдётся именно из них, и именно поэтому по `Buffers` можно будет точно сказать, сколько раз каждая таблица была прочитана.

## Как снять план запроса

### Три формы EXPLAIN

Отдельной программы «планировщик» нет. Вы дописываете `EXPLAIN` **перед** своим запросом, и PostgreSQL отвечает не данными, а деревом шагов.

| Команда | Запрос выполняется? | Что получите |
|---|---|---|
| `EXPLAIN …` | **нет** | только замысел: дерево узлов, `cost`, ожидаемые `rows` |
| `EXPLAIN (ANALYZE) …` | **да** | плюс факт: `actual time`, `actual rows`, `loops` |
| `EXPLAIN (ANALYZE, BUFFERS) …` | да | плюс сколько 8-КБ страниц узел затребовал |

**Рабочая форма — третья.** Без `ANALYZE` вы правите фантазию планировщика, а не то, что произошло. Без `BUFFERS` не видно объёма работы с данными, а это самый устойчивый показатель: миллисекунды зависят от загрузки машины, а число затребованных страниц — почти нет.

**Источник:** https://www.postgresql.org/docs/16/using-explain.html

EN:

> `EXPLAIN` has a `BUFFERS` option that can be used with `ANALYZE` to get even more run time statistics.

RU:

> У `EXPLAIN` есть опция `BUFFERS`, которую можно использовать вместе с `ANALYZE`, чтобы получить ещё больше статистики времени выполнения.

Синтаксис: опции пишут **в скобках через запятую**, сразу после слова `EXPLAIN`, а дальше идёт обычный запрос:

```sql

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.amount, o.product_id
FROM orders o
WHERE o.product_id IS NULL;
```

Иногда полезна опция `COSTS OFF` — она убирает столбцы оценок и оставляет только факт. Так вывод короче и его легче читать, когда оценки вас пока не интересуют:

```sql

EXPLAIN (ANALYZE, COSTS OFF)
SELECT o.id FROM orders o WHERE o.product_id IS NULL;
```

### Где именно набирать команду

`EXPLAIN` — это обычный SQL. Его набирают там же, где обычные запросы, никакой отдельной консоли не нужно.

| Клиент | Что делать |
|---|---|
| **pgAdmin** (`http://localhost:5050`) | вписать `EXPLAIN (ANALYZE, BUFFERS)` перед запросом и выполнить как обычно; вывод придёт в виде текста плана |
| **DBeaver** | то же самое в SQL-редакторе |
| **psql в контейнере** | команда ниже |

Через `psql` внутри контейнера (так снимались все планы в этом документе):

```bash

docker exec -it reactive-study-postgres psql -U app -d reactive_study
```

Дальше в приглашении `psql`:

```sql

SET search_path TO reactive_study;
EXPLAIN (ANALYZE, BUFFERS) SELECT … ;
```

Если нужно выполнить одну команду и сразу выйти — флаг `-c`. Обратите внимание: `SET search_path` приходится повторять в каждом `-c`, потому что каждый `-c` выполняется отдельно:

```bash

docker exec reactive-study-postgres psql -U app -d reactive_study \
  -c "SET search_path TO reactive_study; EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM orders;"
```

Перед работой контейнер должен быть запущен:

```bash

docker ps --filter name=reactive-study-postgres
```

### Предупреждение про ANALYZE

Слово `ANALYZE` внутри `EXPLAIN` не означает «проанализируй план». Оно означает «**выполни запрос по-настоящему** и покажи, что вышло».

**Источник:** https://www.postgresql.org/docs/16/using-explain.html

EN:

> Keep in mind that because `EXPLAIN ANALYZE` actually runs the query, any side-effects will happen as usual, even though whatever results the query might output are discarded in favor of printing the `EXPLAIN` data.

RU:

> Имейте в виду: поскольку `EXPLAIN ANALYZE` действительно выполняет запрос, любые побочные эффекты произойдут как обычно, даже несмотря на то, что результат, который запрос мог бы вывести, отбрасывается в пользу печати данных `EXPLAIN`.

Для `SELECT` это безопасно: данные не меняются, вы просто ждёте столько же, сколько ждал бы обычный запрос. Для `INSERT`, `UPDATE`, `DELETE` — **строки реально изменятся**. Такое снимают либо на стенде, либо внутри транзакции с откатом:

```sql

BEGIN;
EXPLAIN (ANALYZE, BUFFERS) DELETE FROM orders WHERE id = 100003;
ROLLBACK;
```

## Вариант 1 — NOT IN без корреляции: быстрый и неправильный

Самая очевидная запись вопроса — «`product_id` нет в списке id каталога»:

```sql

SELECT o.id, o.amount, o.product_id
FROM orders o
WHERE o.product_id NOT IN (SELECT p.id FROM products p);
```

Возвращает **0 строк**. Это неверный ответ: три проблемных заказа существуют. Почему так — разобрано в [теме 06](06-subqueries.md#механизм-во-что-postgresql-разворачивает-not-in): `product_id` у них NULL, сравнение с NULL даёт NULL, а `WHERE` пропускает только «истину».

Снимаем план:

```sql

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.amount, o.product_id
FROM orders o
WHERE o.product_id NOT IN (SELECT p.id FROM products p);
```

```text

 Seq Scan on orders o  (cost=4.50..2578.59 rows=50004 width=18) (actual time=17.036..17.038 rows=0 loops=1)
   Filter: (NOT (hashed SubPlan 1))
   Rows Removed by Filter: 100007
   Buffers: shared hit=1326
   SubPlan 1
     ->  Seq Scan on products p  (cost=0.00..4.00 rows=200 width=4) (actual time=0.007..0.028 rows=200 loops=1)
           Buffers: shared hit=2
 Planning Time: 0.106 ms
 Execution Time: 17.079 ms
```

**Разбор построчно**

| Строка плана | Что она говорит |
|---|---|
| `Seq Scan on orders o` | верхний узел: заказы читаются **целиком**, страница за страницей |
| `cost=4.50..2578.59` | оценка в условных единицах: `4.50` — до первой строки, `2578.59` — до последней |
| `rows=50004` | планировщик **ожидал** 50 004 строки на выходе |
| `actual … rows=0` | **фактически** вышло 0 строк |
| `loops=1` | узел запускался один раз |
| `Filter: (NOT (hashed SubPlan 1))` | условие проверяется по хеш-таблице, построенной подзапросом |
| `Rows Removed by Filter: 100007` | фильтр отбросил **все** 100 007 заказов |
| `Buffers: shared hit=1326` | узел вместе с детьми затребовал 1326 страниц, все нашлись в RAM PostgreSQL |
| `SubPlan 1` → `Seq Scan on products p` | подзапрос: товары прочитаны целиком |
| у подзапроса `rows=200 loops=1` | он выполнился **один раз** и дал 200 строк |
| у подзапроса `Buffers: shared hit=2` | это ровно `relpages` таблицы `products` |
| `Execution Time: 17.079 ms` | полное время выполнения |

**Арифметика `Buffers` сходится:** 1324 страницы `orders` + 2 страницы `products` = **1326**. Значит каждая таблица прочитана ровно **по одному разу**. Это дешёвый план.

**Что значит слово `hashed`.** Планировщик увидел, что подзапрос **не зависит** от строк внешнего запроса — он одинаковый для всех заказов. Поэтому он выполнил его **один раз**, сложил 200 значений `products.id` в хеш-таблицу и дальше проверял каждый заказ по этой готовой таблице. Отсюда `loops=1` у подзапроса.

**Где здесь видно, что запрос плохой.** Не во времени — 17 мс это хорошо. Плохое видно в **двух числах строк**:

- `Rows Removed by Filter: 100007` при `actual rows=0` — фильтр удалил **ровно всё**, что прочитал. Отчёт, который по постановке задачи должен что-то находить, не находит ничего;
- `rows=50004` против `actual rows=0` — планировщик ждал половину таблицы, получил ноль. Расхождение в бесконечность.

Обратите внимание, откуда взялось число `50004`: это ровно половина от 100 007 (`100007 / 2 = 50003.5`, округлено вверх). Не из статистики по данным, а из грубого «наверное, пройдёт половина». Так и должно быть: сколько строк отсеет условие `NOT (SubPlan)`, планировщик заранее не знает — результат зависит от содержимого другой таблицы.

Практический навык: увидев в плане оценку, подозрительно похожую на половину или треть таблицы, проверьте её арифметикой. Если она совпадает с простой долей от `reltuples`, значит это не оценка по статистике, а заглушка, и выбранный по ней план может быть случайным.

**Вывод по варианту 1.** План дешёвый, ответ неверный. `EXPLAIN` сам по себе про «неверный» не скажет — он не знает вашей бизнес-задачи. Но пара «отбросил всё, что прочитал» + «оценка разошлась с фактом на порядки» — это повод перепроверить **смысл** запроса, а не его скорость.

## Вариант 2 — NOT IN с корреляцией: правильный и в 32 раза дороже

Ловушку NULL можно обойти, добавив условие связи **внутрь** подзапроса:

```sql

SELECT o.id, o.amount, o.product_id
FROM orders o
WHERE o.product_id NOT IN (
    SELECT p.id
    FROM products p
    WHERE o.product_id = p.id
);
```

Возвращает **3 строки** — правильный ответ.

**Почему ловушка не срабатывает.** Условие `o.product_id = p.id` внутри означает, что подзапрос может дать только два исхода: либо **ноль строк**, либо **ровно одну**, равную левому значению. NULL в столбик подзапроса не попадёт никогда. А при пустом подзапросе `NOT IN` даёт «истину» даже для NULL слева.

**Источник:** https://www.postgresql.org/docs/16/functions-subquery.html

EN:

> The result of `NOT IN` is “true” if only unequal subquery rows are found (including the case where the subquery returns no rows).

RU:

> Результат `NOT IN` — «истина», если найдены только неравные строки подзапроса (включая случай, когда подзапрос не возвращает строк).

Теперь план:

```sql

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.amount, o.product_id
FROM orders o
WHERE o.product_id NOT IN (
    SELECT p.id FROM products p WHERE o.product_id = p.id
);
```

```text

 Seq Scan on orders o  (cost=0.00..227714.85 rows=50004 width=18) (actual time=549.915..681.784 rows=3 loops=1)
   Filter: (NOT (SubPlan 1))
   Rows Removed by Filter: 100004
   Buffers: shared hit=147787
   SubPlan 1
     ->  Seq Scan on products p  (cost=0.00..4.50 rows=1 width=4) (actual time=0.006..0.006 rows=1 loops=100007)
           Filter: (o.product_id = id)
           Rows Removed by Filter: 99
           Buffers: shared hit=146463
 Planning:
   Buffers: shared hit=177
 Planning Time: 0.421 ms
 JIT:
   Functions: 12
   Options: Inlining false, Optimization false, Expressions true, Deforming true
   Timing: Generation 1.710 ms, Inlining 0.000 ms, Optimization 0.533 ms, Emission 13.831 ms, Total 16.074 ms
 Execution Time: 706.736 ms
```

Тот же `Seq Scan on orders` сверху — а время выросло с 17 мс до 707 мс. Разберёмся, куда ушло время.

**Разбор построчно**

| Строка плана | Что она говорит |
|---|---|
| `cost=0.00..227714.85` | оценка выросла с 2578 до **227 714** — планировщик сам предупредил, что план дорогой |
| `actual … rows=3 loops=1` | верхний узел дал 3 строки — **правильный ответ** |
| `Rows Removed by Filter: 100004` | отброшено 100 004 заказа; `100004 + 3 = 100007` — сходится |
| `Filter: (NOT (SubPlan 1))` | слова `hashed` **больше нет** — и это главное отличие |
| `Buffers: shared hit=147787` | затребовано 147 787 страниц вместо 1326 |
| `SubPlan 1` → `loops=100007` | подзапрос выполнился **сто тысяч семь раз** |
| у подзапроса `rows=1` | в среднем за один запуск он давал 1 строку |
| у подзапроса `Rows Removed by Filter: 99` | в среднем за запуск он проверил и отбросил 99 товаров |
| у подзапроса `Buffers: shared hit=146463` | почти вся работа с данными — здесь |
| блок `JIT` | появился только в этом варианте; разбор ниже |
| `Execution Time: 706.736 ms` | в 32 раза больше варианта 1 |

**Почему `loops=100007`, а не `1`.** Подзапрос теперь **коррелированный** — внутри стоит `o.product_id`, значение из текущей строки внешнего запроса. Для каждого заказа подзапрос получается **другой**, значит выполнить его один раз и переиспользовать результат нельзя. Слова `hashed` в фильтре нет именно поэтому: хеш-таблицу строить не из чего.

Так работает вложенный цикл: «для каждой строки внешнего запроса — запустить внутренний заново». `loops` — это и есть счётчик таких запусков.

**Источник:** https://www.postgresql.org/docs/16/using-explain.html

EN:

> In some query plans, it is possible for a subplan node to be executed more than once. For example, the inner index scan will be executed once per outer row in the above nested-loop plan. In such cases, the `loops` value reports the total number of executions of the node, and the actual time and rows values shown are averages per-execution. This is done to make the numbers comparable with the way that the cost estimates are shown. Multiply by the `loops` value to get the total time actually spent in the node.

RU:

> В некоторых планах запросов узел подплана может выполняться более одного раза. Например, внутреннее сканирование по индексу в приведённом выше плане с вложенным циклом будет выполнено один раз для каждой внешней строки. В таких случаях значение `loops` сообщает общее число выполнений узла, а показанные значения actual time и rows являются средними за одно выполнение. Это сделано, чтобы числа были сравнимы с тем, как показаны оценки стоимости. Умножьте на значение `loops`, чтобы получить общее время, фактически затраченное в узле.

**Ключевое следствие из цитаты: `actual time` и `rows` у такого узла — средние за один запуск, а не итог.** Строку `actual time=0.006..0.006 rows=1 loops=100007` нельзя читать как «подзапрос занял 6 микросекунд». Правильное чтение:

```text

один запуск  ≈ 0.006 мс
запусков     = 100 007
итого        ≈ 0.006 × 100 007 ≈ 600 мс
```

Вот и найдены 707 мс: практически всё время запроса — это 100 007 повторений «дешёвого» подзапроса. Отдельный запуск действительно быстрый; смертельно именно их количество.

**Та же проверка по `Buffers`** — и она надёжнее, чем миллисекунды:

```text

страниц у products     = 2
запусков подзапроса    = 100 007
если читать целиком    = 200 014 обращений к страницам
фактически в плане     = 146 463
146 463 / 100 007      ≈ 1.46 страницы за запуск
```

Почему 1.46, а не 2: подзапрос **останавливается**, как только нашёл свою строку, и не дочитывает `products` до конца. Это подтверждает строка `Rows Removed by Filter: 99` — в среднем он просматривал около 100 товаров из 200, то есть примерно половину таблицы, что и даёт ≈ 1.46 страницы из 2.

**Итог по страницам:** 146 463 (подзапрос) + 1324 (чтение `orders`) = **147 787** — ровно то число, что стоит у верхнего узла. Против 1326 в варианте 1 это в **111 раз** больше обращений к страницам за тот же ответ.

**Что за блок `JIT` в конце.** Он появился только здесь, и это не случайность. PostgreSQL умеет компилировать выражения запроса в машинный код, но включает это только для запросов, чья **оценочная стоимость** выше порога `jit_above_cost`.

**Источник:** https://www.postgresql.org/docs/16/jit-decision.html

EN:

> To determine whether JIT compilation should be used, the total estimated cost of a query (see Chapter 76 and Section 20.7.2) is used. The estimated cost of the query will be compared with the setting of `jit_above_cost`. If the cost is higher, JIT compilation will be performed.

RU:

> Чтобы определить, следует ли использовать JIT-компиляцию, применяется полная оценочная стоимость запроса (см. главу 76 и раздел 20.7.2). Оценочная стоимость запроса сравнивается со значением параметра `jit_above_cost`. Если стоимость выше, будет выполнена JIT-компиляция.

Проверьте порог на своей базе:

```sql

SHOW jit;
SHOW jit_above_cost;
```

На `reactive_study`: `jit = on`, `jit_above_cost = 100000`. Стоимость варианта 2 — `227714.85`, это больше порога, поэтому JIT включился. Стоимость варианта 1 — `2578.59`, ниже порога, поэтому в его плане блока `JIT` нет.

Практический смысл: JIT сам потратил ещё **16 мс** (`Total 16.074 ms`) на компиляцию. Он не виноват в медленном запросе — он **следствие** дорогой оценки. Появление блока `JIT` в плане короткого OLTP-запроса — сигнал «планировщик считает этот запрос тяжёлым, посмотри почему».

**Строка `Planning: Buffers: shared hit=177`.** Это страницы, прочитанные **на этапе планирования** — системные каталоги, статистика. К данным запроса отношения не имеет, при разборе производительности её обычно не трогают.

**Где здесь видно, что запрос плохой.** Ответ верный, но план плохой, и это видно по трём признакам:

1. `loops=100007` у вложенного узла — работа умножена на число строк внешней таблицы;
2. `Buffers: shared hit=147787` при том, что обе таблицы вместе занимают 1326 страниц — значит данные перечитывались десятки раз;
3. `cost=227714.85` и как следствие включившийся `JIT`.

**Главная мысль варианта 2.** Оператор `NOT IN` здесь вообще ничего не решает. Если строка нашлась — она равна левому значению, `NOT IN` всегда «ложь». Если не нашлась — подзапрос пуст, `NOT IN` всегда «истина». Ответ определяется исключительно фактом «нашлась строка или нет». Это ровно та работа, для которой существует `EXISTS` — но записанная так, что планировщик теряет возможность её оптимизировать.

## Вариант 3 — NOT EXISTS: правильный и быстрый

```sql

SELECT o.id, o.amount, o.product_id
FROM orders o
WHERE NOT EXISTS (
    SELECT 1
    FROM products p
    WHERE p.id = o.product_id
);
```

Возвращает те же **3 строки**.

Подзапрос здесь **тоже коррелированный** — внутри стоит `o.product_id`. Но конструкция другая, и планировщик распоряжается ей иначе:

```sql

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.amount, o.product_id
FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM products p WHERE p.id = o.product_id);
```

```text

 Hash Anti Join  (cost=6.50..2705.66 rows=1 width=18) (actual time=18.104..22.077 rows=3 loops=1)
   Hash Cond: (o.product_id = p.id)
   Buffers: shared hit=1326
   ->  Seq Scan on orders o  (cost=0.00..2324.07 rows=100007 width=18) (actual time=0.007..12.000 rows=100007 loops=1)
         Buffers: shared hit=1324
   ->  Hash  (cost=4.00..4.00 rows=200 width=4) (actual time=0.074..0.077 rows=200 loops=1)
         Buckets: 1024  Batches: 1  Memory Usage: 16kB
         Buffers: shared hit=2
         ->  Seq Scan on products p  (cost=0.00..4.00 rows=200 width=4) (actual time=0.006..0.034 rows=200 loops=1)
               Buffers: shared hit=2
 Planning Time: 0.567 ms
 Execution Time: 22.124 ms
```

**Первое, что бросается в глаза: `SubPlan` в плане нет вообще.** Подзапрос исчез как отдельный шаг — он **превратился** в узел соединения. Такое преобразование называется разворачиванием подзапроса в соединение, и `NOT EXISTS` позволяет его сделать, а `NOT IN` — нет.

**Разбор построчно**

| Строка плана | Что она говорит |
|---|---|
| `Hash Anti Join` | верхний узел: «анти-соединение через хеш» — разбор ниже |
| `cost=6.50..2705.66` | оценка почти как у варианта 1, в 84 раза дешевле варианта 2 |
| `rows=1` (оценка) против `actual rows=3` | ошибка оценки есть, но в масштабе «1 против 3», а не «50 004 против 0» |
| `Hash Cond: (o.product_id = p.id)` | по какому условию сопоставляются строки |
| `Buffers: shared hit=1326` | 1324 + 2, то есть **каждая таблица прочитана один раз** |
| `-> Seq Scan on orders o … rows=100007 loops=1` | заказы прочитаны целиком **один раз** |
| `-> Hash … rows=200 loops=1` | хеш-таблица построена **один раз** из 200 товаров |
| `Buckets: 1024` | в хеш-таблице 1024 корзины |
| `Batches: 1` | всё уместилось в память за **один** проход; если было бы больше 1 — часть работы ушла бы во временные файлы на диск |
| `Memory Usage: 16kB` | хеш-таблица заняла 16 КБ рабочей памяти |
| `Execution Time: 22.124 ms` | в 32 раза быстрее варианта 2 |

**Что такое `Anti Join`.** Обычный `Join` оставляет строки, у которых **нашлась** пара. `Anti Join` — наоборот: оставляет те, у которых пары **не нашлось**. Именно в такое соединение и превращается `NOT EXISTS`.

Слово `Hash` перед `Anti Join` говорит, каким способом ищется пара: через хеш-таблицу в памяти. Механика:

```text

шаг 1 (build) — прочитать products (2 страницы, 200 строк)
                и разложить id по 1024 корзинам хеш-таблицы (16 КБ)

шаг 2 (probe) — прочитать orders (1324 страницы) один раз;
                для каждого заказа посчитать хеш от product_id,
                заглянуть в нужную корзину
                    пара найдена    → заказ отбросить
                    пары нет        → заказ оставить
```

Сравните с вариантом 2: там `products` перечитывался для каждого заказа, здесь — один раз превращён в справочник, по которому идут мгновенные проверки.

**Почему NULL здесь не ломает ответ.** У трёх проблемных заказов `product_id` = NULL. Условие соединения `o.product_id = p.id` при NULL слева не выполняется ни для одного товара — значит пара не найдена, и `Anti Join` эти три заказа **оставит**. Вопрос стоит как «пара нашлась или нет», и ответ на него всегда однозначный: да или нет. Трёхзначной логики «истина / ложь / неизвестно», из которой и состоит ловушка `NOT IN`, здесь просто не возникает.

**Где здесь видно, что запрос хороший.** Четыре признака, и каждый — зеркало проблем варианта 2:

1. **`loops=1` у всех узлов.** Ни одна работа не умножена на число строк;
2. **`Buffers: shared hit=1326` = 1324 + 2.** Ровно минимум: каждая таблица прочитана по одному разу, лишних обращений нет;
3. **`Batches: 1`.** Хеш уместился в памяти, во временные файлы ничего не ушло;
4. **`Rows Removed by Filter` отсутствует.** Строки не читаются, чтобы потом быть выброшенными фильтром — их отбирает само соединение.

И отдельно: блока `JIT` нет, потому что `cost=2705.66` ниже порога `100000`.

## Вариант 4 — NOT EXISTS с SELECT p.id вместо SELECT 1

Частый вопрос: `SELECT 1` внутри `EXISTS` — это оптимизация или нет?

```sql

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.amount, o.product_id
FROM orders o
WHERE NOT EXISTS (SELECT p.id FROM products p WHERE p.id = o.product_id);
```

```text

 Hash Anti Join  (cost=6.50..2705.66 rows=1 width=18) (actual time=27.855..34.028 rows=3 loops=1)
   Hash Cond: (o.product_id = p.id)
   Buffers: shared hit=1326
   ->  Seq Scan on orders o  (cost=0.00..2324.07 rows=100007 width=18) (actual time=0.010..20.098 rows=100007 loops=1)
         Buffers: shared hit=1324
   ->  Hash  (cost=4.00..4.00 rows=200 width=4) (actual time=0.043..0.045 rows=200 loops=1)
         Buckets: 1024  Batches: 1  Memory Usage: 16kB
         Buffers: shared hit=2
         ->  Seq Scan on products p  (cost=0.00..4.00 rows=200 width=4) (actual time=0.003..0.018 rows=200 loops=1)
               Buffers: shared hit=2
 Planning Time: 0.638 ms
 Execution Time: 34.074 ms
```

**Сравните с вариантом 3 построчно.** Совпадает всё, что зависит от запроса:

| Показатель | Вариант 3 (`SELECT 1`) | Вариант 4 (`SELECT p.id`) |
|---|---|---|
| Верхний узел | `Hash Anti Join` | `Hash Anti Join` |
| `cost` | `6.50..2705.66` | `6.50..2705.66` |
| `Buffers` | 1 326 | 1 326 |
| `Buckets` / `Batches` / `Memory Usage` | 1024 / 1 / 16kB | 1024 / 1 / 16kB |
| `actual rows` | 3 | 3 |
| `Execution Time` | 22.1 мс | **34.1 мс** |

**И вот тут важный урок про чтение планов.** Единственное, что разошлось, — миллисекунды: 34.1 против 22.1. Соблазнительно сделать вывод «`SELECT p.id` в полтора раза медленнее». Вывод был бы неверным.

Смотрите на `Buffers`: 1326 в обоих случаях, до единицы. Объём работы с данными **идентичен**. Разошлось только время — потому что миллисекунды зависят от загрузки машины в момент запуска. Тот же запрос варианта 4 в другом прогоне дал 21.8 мс.

Отсюда практическое правило: **сравнивая два запроса, сначала сравнивайте `Buffers`, `loops` и форму дерева, и только потом время.** Если работа одинаковая, а время разное — это шум, а не разница запросов.

**Оптимизации в `SELECT 1` нет.** `EXISTS` вообще не вычисляет список столбцов подзапроса: ему нужен только факт наличия строки. `SELECT 1` — это **соглашение по оформлению**, чтобы читатель кода сразу видел «здесь столбцы не важны», а не искал, зачем понадобился `p.id`.

**Источник:** https://www.postgresql.org/docs/16/functions-subquery.html

EN:

> Since the result depends only on whether any rows are returned, and not on the contents of those rows, the output list of the subquery is normally unimportant. A common coding convention is to write all `EXISTS` tests in the form `EXISTS(SELECT 1 WHERE ...)`. There are exceptions to this rule however, such as subqueries that use `INTERSECT`.

RU:

> Поскольку результат зависит только от того, возвращаются ли какие-либо строки, а не от содержимого этих строк, список вывода подзапроса обычно не важен. Распространённое соглашение по написанию кода — записывать все проверки `EXISTS` в форме `EXISTS(SELECT 1 WHERE ...)`. Однако у этого правила есть исключения, например подзапросы, использующие `INTERSECT`.

**Полезный вывод для чтения планов:** есть изменения текста запроса, которые вообще не меняют план. Проверять это надо не спором, а снятием двух планов — как сделано здесь.

## Четыре плана рядом

| Показатель | 1. `NOT IN` | 2. `NOT IN` коррелированный | 3. `NOT EXISTS (SELECT 1)` | 4. `NOT EXISTS (SELECT p.id)` |
|---|---|---|---|---|
| Ответ верный? | **нет** (0 строк) | да (3) | да (3) | да (3) |
| Верхний узел | `Seq Scan` + фильтр | `Seq Scan` + фильтр | **`Hash Anti Join`** | **`Hash Anti Join`** |
| Подзапрос в плане | `hashed SubPlan 1` | `SubPlan 1` | развёрнут в соединение | развёрнут в соединение |
| `loops` подзапроса | 1 | **100 007** | — | — |
| `Buffers` | 1 326 | **147 787** | 1 326 | 1 326 |
| `cost` (верхний) | 2 578.59 | **227 714.85** | 2 705.66 | 2 705.66 |
| Оценка `rows` / факт | 50 004 / **0** | 50 004 / 3 | 1 / 3 | 1 / 3 |
| `Rows Removed by Filter` | **100 007** | 100 004 | нет | нет |
| Блок `JIT` | нет | **есть**, 16 мс | нет | нет |
| `Execution Time` | 17 мс | **707 мс** | 22 мс | 22–34 мс (шум) |

Соотношения, которые стоит запомнить по этому кейсу:

```text

страницы:  147 787 / 1 326    ≈ 111 раз
время:     706.7 мс / 22.1 мс ≈  32 раза
оценка:    227 715 / 2 706    ≈  84 раза
```

**Главный вывод таблицы.** В этой задаче `NOT IN` бывает либо **быстрым и неправильным** (вариант 1), либо **правильным и в 32 раза дороже** (вариант 2). `NOT EXISTS` — правильный и быстрый, причём с `SELECT 1` или `SELECT p.id` без разницы.

## Как по плану понять, что запрос отработал плохо

Признаки ниже — не «законы», а **места, куда смотреть**. У каждого рядом стоит число из этого разбора, чтобы было видно, как признак выглядит в жизни.

### Признаки плохой работы

| Что видно в плане | Почему это плохо | Пример отсюда |
|---|---|---|
| Большой `loops` у вложенного узла | работа умножена на число строк внешней таблицы | `loops=100007` в варианте 2 |
| `Buffers` сильно больше суммы `relpages` задействованных таблиц | данные перечитывались по кругу | 147 787 против 1 326 |
| `Rows Removed by Filter` сравнимо с размером таблицы | прочитали много, чтобы почти всё выбросить | 100 007 из 100 007 в варианте 1 |
| Оценка `rows` разошлась с `actual rows` на порядки | планировщик выбирал план по неверным данным | 50 004 против 0 |
| `Batches` больше 1 | хеш не уместился в память, часть работы ушла в файлы | здесь не встретилось — везде `Batches: 1` |
| Блок `JIT` у короткого запроса | оценка перевалила `jit_above_cost` = запрос считается тяжёлым | вариант 2, `cost` 227 715 |
| `SubPlan` вместо узла соединения | подзапрос не развернулся, значит выполняется повторно | вариант 2 |

### Признаки хорошей работы

| Что видно в плане | Почему это хорошо | Пример отсюда |
|---|---|---|
| `loops=1` у всех узлов | ничего не выполняется повторно | вариант 3 |
| `Buffers` ≈ сумма `relpages` нужных таблиц | каждая таблица прочитана один раз, это минимум | 1324 + 2 = 1326 |
| `Batches: 1` | хеш целиком в памяти | `Memory Usage: 16kB` |
| Подзапрос развернулся в `Anti Join` / `Semi Join` | планировщик смог применить эффективный алгоритм | `Hash Anti Join` |
| `Rows Removed by Filter` отсутствует или мало | строки отбираются, а не читаются ради выбрасывания | вариант 3 |

### Чего по плану понять нельзя

**`EXPLAIN` не знает вашей бизнес-задачи.** Вариант 1 — образцово дешёвый план: 1326 страниц, 17 мс, `loops=1` везде. И при этом неверный ответ.

Порядок разбора всегда такой:

1. **Сначала смысл.** Правильное ли число строк вернул запрос? Сверьте с ответом, посчитанным другим способом (здесь — `WHERE product_id IS NULL` дал 3);
2. **Потом цена.** `loops`, `Buffers`, `Rows Removed by Filter`, расхождение оценки с фактом;
3. **Только потом время.** Миллисекунды зависят от загрузки машины и кэша — это самый шумный показатель.

Если поменять порядок, легко «оптимизировать» запрос, отвечающий не на тот вопрос.

### Почему Seq Scan сам по себе не диагноз

`Seq Scan on orders` стоит и в самом плохом варианте (2), и в самом хорошем (3). Полное чтение таблицы плохо только тогда, когда вам нужны **несколько** строк из многих. Здесь же нужно проверить **каждый** заказ, поэтому прочитать `orders` целиком — обязательная работа, и индекс тут не помог бы.

Различие не в `Seq Scan`, а в том, **сколько раз** он выполняется и что делается вокруг него.

## Чеклист для этого класса задач

Класс задач — «найти строки без пары в другой таблице»: заказы без товара, клиенты без заказов, товары без категории.

1. **Проверить, может ли ключ быть пустым.** `SELECT count(*) FROM orders WHERE product_id IS NULL`. Если больше нуля — `NOT IN` уже под подозрением;
2. **Писать `NOT EXISTS`.** Он даёт верный ответ при NULL с любой стороны и разворачивается в `Anti Join`;
3. **Снять план** формой `EXPLAIN (ANALYZE, BUFFERS)`;
4. **Проверить, что подзапрос развернулся.** В плане должен быть `Anti Join`, а не `SubPlan` с большим `loops`;
5. **Сверить `Buffers` с `relpages`.** Сильное превышение суммы страниц таблиц — признак повторного чтения;
6. **Сверить число строк с ответом, полученным другим способом.** Это единственная защита от «дешёвого и неверного» плана.

Отдельно: если очень хочется оставить `NOT IN`, посмотрите в плане на слово `hashed`. Есть `hashed` — подзапрос выполнится один раз (дёшево, но работает ловушка NULL). Нет `hashed` — подзапрос коррелированный и выполнится столько раз, сколько строк во внешней таблице.
