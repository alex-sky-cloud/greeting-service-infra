# Тема 13 — аналитика платежей

Платёж редко проходит у всех и с первого раза: банк отклоняет карту, у клиента не хватает денег, клиент пробует ещё раз. Поэтому магазин хранит не «оплачен / не оплачен», а журнал **попыток оплаты** `payment_attempts`: каждая попытка — отдельная строка.

В этой теме разбирается, как по такому журналу считать успешность платежей и почему результат зависит от того, что считать — попытки или заказы. Ещё разбираются итог оплаты заказа, заказы, спасённые повторной попыткой, время до оплаты и сверки с заказами: отгрузка без оплаты, оплата отменённого заказа, расхождение сумм.

Все числа ниже получены из учебной базы `reactive_study`. Часовой пояс сессии базы — `UTC`. Из прошлых тем понадобятся `LEFT JOIN` (тема 04), `CASE` и `FILTER` (тема 07), `lag` (тема 09), интервалы (тема 10), `string_agg` (тема 12).

## Что лежит в журнале попыток оплаты

Таблица `payment_attempts`:

| Столбец | Что хранит |
|---|---|
| `id` | номер попытки во всём журнале |
| `order_id` | номер заказа из `orders` |
| `attempt_no` | номер попытки внутри заказа: 1, 2, 3… Пара `(order_id, attempt_no)` уникальна |
| `amount` | сумма, которую пытались списать |
| `status` | результат попытки |
| `created_at` | момент попытки, `timestamptz` |

Результаты попытки:

| Статус | Что значит |
|---|---|
| `success` | деньги списаны |
| `failed` | банк отклонил попытку |
| `pending` | попытка отправлена в банк, ответа ещё нет. В учебной базе таких попыток 0 |

В журнале 101600 попыток по 100000 заказам. У 7 заказов попыток нет совсем.

**Задача.** Поддержка разбирает обращения по трём заказам: 1, 32 и 16374. Нужны все попытки оплаты этих заказов.

```sql

SELECT id,
       order_id,
       attempt_no,
       amount,
       status,
       created_at
FROM payment_attempts
WHERE order_id IN (1, 32, 16374)
ORDER BY order_id, attempt_no;
```

**Как читается запрос**

- `WHERE order_id IN (1, 32, 16374)` — попытки трёх заказов.
- `ORDER BY order_id, attempt_no` — по заказу, внутри заказа — по номеру попытки.

| id | order_id | attempt_no | amount | status | created_at |
|---:|---:|---:|---:|---|---|
| 1 | 1 | 1 | 1132.36 | success | 2026-04-05 19:23:01.570686+00 |
| 32 | 32 | 1 | 176.72 | failed | 2025-11-22 12:53:47.799768+00 |
| 100001 | 32 | 2 | 176.72 | failed | 2025-11-22 12:58:47.799768+00 |
| 100002 | 32 | 3 | 176.72 | success | 2025-11-22 13:03:47.799768+00 |
| 16374 | 16374 | 1 | 426.07 | failed | 2026-07-24 17:22:08.15505+00 |

Как это читать:

- Заказ 1 оплачен с первой попытки.
- Заказ 32: две попытки отклонены, третья прошла.
- Заказ 16374: одна попытка, отклонена. Деньги не получены.

## Путь оплаты заказа

Приём из темы 12: склеить результаты попыток в одну строку. Порядок задаёт `attempt_no`.

**Задача.** Платёжная команда хочет знать, какие сценарии оплаты встречаются и сколько заказов на каждом.

```sql

WITH payment_path AS (
    SELECT order_id,
           string_agg(status, ' -> ' ORDER BY attempt_no) AS path
    FROM payment_attempts
    GROUP BY order_id
)
SELECT path,
       count(*) AS orders
FROM payment_path
GROUP BY path
ORDER BY orders DESC;
```

**Как читается запрос**

- `payment_path` — по одной строке на заказ с попытками: 100000 строк. Например, у заказа 32 путь `failed -> failed -> success`.
- Второй шаг группирует одинаковые пути и считает заказы.

| path | orders |
|---|---:|
| success | 95084 |
| failed | 4116 |
| failed -> failed -> success | 800 |

Сумма — 100000. 7 заказов без попыток сюда не попали: у них нет ни одной строки в журнале.

## Успешность: по попыткам и по заказам

«Какой процент платежей успешен» — вопрос с подвохом. Ответ зависит от того, что считать.

- **По попыткам** — какая доля обращений в банк закончилась списанием. Это метрика платёжного провайдера: как часто банк говорит «да».
- **По заказам** — какая доля заказов в итоге оплачена, хотя бы с третьей попытки. Это метрика бизнеса: сколько заказов принесли деньги.

**Задача.** Платёжная команда считает успешность по попыткам.

```sql

SELECT count(*) AS attempts,
       count(*) FILTER (WHERE status = 'success') AS successful_attempts,
       round(100.0 * count(*) FILTER (WHERE status = 'success') / count(*), 2) AS success_pct
FROM payment_attempts;
```

**Как читается запрос**

- Одна строка журнала — одна попытка, поэтому знаменатель — `count(*)`.

| attempts | successful_attempts | success_pct |
|---:|---:|---:|
| 101600 | 95884 | 94.37 |

**Задача.** Финансовый директор считает успешность по заказам: какая доля заказов, по которым была хотя бы одна попытка, в итоге оплачена.

```sql

SELECT count(DISTINCT order_id) AS orders_with_attempts,
       count(DISTINCT order_id) FILTER (WHERE status = 'success') AS paid_orders,
       round(100.0 * count(DISTINCT order_id) FILTER (WHERE status = 'success')
             / count(DISTINCT order_id), 2) AS paid_pct
FROM payment_attempts;
```

**Как читается запрос**

- `count(DISTINCT order_id)` — разных заказов в журнале. У заказа 32 три строки, но заказ один.
- `count(DISTINCT order_id) FILTER (WHERE status = 'success')` — разных заказов, у которых есть успешная попытка.

| orders_with_attempts | paid_orders | paid_pct |
|---:|---:|---:|
| 100000 | 95884 | 95.88 |

Почему числа разные, на примере заказа 32:

| Что считаем | Заказ 32 даёт в знаменатель | Заказ 32 даёт в числитель |
|---|---:|---:|
| Попытки | 3 | 1 |
| Заказы | 1 | 1 |

По попыткам заказ 32 «тянет вниз» успешность: две неудачи на одну удачу. По заказам он просто оплачен.

**Нюансы**

- На собеседовании сначала уточняют, что считать: попытки или заказы. Оба числа правильные, но отвечают на разные вопросы.
- Здесь `paid_orders = successful_attempts = 95884`: у каждого заказа максимум одна успешная попытка. Если бы магазин мог списать деньги дважды, числа разошлись бы — и это была бы отдельная проблема.

## Успешность по номеру попытки

**Задача.** Платёжная команда решает, сколько повторных попыток разрешать клиенту. Нужна успешность отдельно для первых, вторых и третьих попыток.

```sql

SELECT attempt_no,
       count(*) AS attempts,
       count(*) FILTER (WHERE status = 'success') AS successful_attempts,
       round(100.0 * count(*) FILTER (WHERE status = 'success') / count(*), 2) AS success_pct
FROM payment_attempts
GROUP BY attempt_no
ORDER BY attempt_no;
```

**Как читается запрос**

- `GROUP BY attempt_no` — группа первых попыток, группа вторых, группа третьих.

| attempt_no | attempts | successful_attempts | success_pct |
|---:|---:|---:|---:|
| 1 | 100000 | 95084 | 95.08 |
| 2 | 800 | 0 | 0.00 |
| 3 | 800 | 800 | 100.00 |

Как это читать:

- Первая попытка есть у каждого из 100000 заказов, проходит 95.08%.
- Вторую попытку делают только 800 заказов — после неудачной первой. Ни одна вторая не прошла.
- Третья — у тех же 800, проходят все.

**Нюансы**

- `0.00` и `100.00` — особенность учебных данных. В реальных платежах вторая попытка обычно проходит реже первой, но не никогда.
- Заказов с неудачной первой попыткой 100000 − 95084 = 4916. До второй попытки дошли только 800 из них. Остальные 4116 клиентов после первой неудачи больше не пробовали.

## Итог оплаты заказа: bool_or и bool_and

Чтобы ответить «оплачен ли заказ», нужно по всем попыткам заказа сказать: была ли **хотя бы одна** успешная. Для этого есть агрегатные функции над `boolean`.

### Синтаксис

```sql

bool_or(condition)
bool_and(condition)
```

| Функция | Что возвращает для группы строк |
|---|---|
| `bool_or(condition)` | `true`, если условие выполнено **хотя бы в одной** строке |
| `bool_and(condition)` | `true`, если условие выполнено **во всех** строках |

`condition` — любое выражение, дающее `true` или `false`, например `status = 'success'`. Строки, где условие даёт `NULL`, пропускаются. Как любой агрегат, обе функции работают с `GROUP BY`.

**Источник:** https://www.postgresql.org/docs/16/functions-aggregate.html

**EN:**

> `bool_and ( boolean ) → boolean` Returns true if all non-null input values are true, otherwise false.
>
> `bool_or ( boolean ) → boolean` Returns true if any non-null input value is true, otherwise false.

**RU:**

> `bool_and ( boolean ) → boolean` Возвращает true, если все входные значения, не равные null, равны true, иначе false.
>
> `bool_or ( boolean ) → boolean` Возвращает true, если хотя бы одно входное значение, не равное null, равно true, иначе false.

**Задача.** Поддержка хочет по заказам 1, 32 и 16374 видеть: оплачен ли заказ, все ли попытки были неудачными и сколько было попыток.

```sql

SELECT order_id,
       bool_or(status = 'success') AS is_paid,
       bool_and(status = 'failed') AS all_failed,
       count(*) AS attempts
FROM payment_attempts
WHERE order_id IN (1, 32, 16374)
GROUP BY order_id
ORDER BY order_id;
```

**Как читается запрос**

- `status = 'success'` — для каждой попытки даёт `true` или `false`.
- `bool_or(…)` по группе заказа — есть ли среди попыток хоть одна успешная.
- `bool_and(status = 'failed')` — все ли попытки отклонены.

Что видит `bool_or` в группе заказа 32:

| attempt_no | status | `status = 'success'` |
|---:|---|---|
| 1 | failed | false |
| 2 | failed | false |
| 3 | success | true |

↓ `bool_or` ↓ хотя бы одно `true` → `true`

Результат:

| order_id | is_paid | all_failed | attempts |
|---:|---|---|---:|
| 1 | t | f | 1 |
| 32 | t | f | 3 |
| 16374 | f | t | 1 |

`t` и `f` — так `psql` показывает `true` и `false`.

**Нюансы**

- То же самое можно записать через счёт: `count(*) FILTER (WHERE status = 'success') > 0`. `bool_or` короче и сразу читается как «хотя бы один».

## Все заказы по итогу оплаты

Журнал попыток знает только заказы, у которых попытки были. Чтобы увидеть **все** заказы, отчёт строят от `orders` и присоединяют итог оплаты через `LEFT JOIN` (тема 04).

**Задача.** Финансовый директор просит разбить все заказы магазина на три группы: оплачен, не оплачен (были только неудачные попытки), попыток не было. По каждой группе — число заказов и их сумма.

```sql

WITH payment_result AS (
    SELECT order_id,
           bool_or(status = 'success') AS is_paid
    FROM payment_attempts
    GROUP BY order_id
)
SELECT CASE
           WHEN pr.order_id IS NULL THEN 'no_attempts'
           WHEN pr.is_paid THEN 'paid'
           ELSE 'not_paid'
       END AS payment_state,
       count(*) AS orders,
       round(sum(o.amount), 2) AS order_amount
FROM orders o
LEFT JOIN payment_result pr ON pr.order_id = o.id
GROUP BY payment_state
ORDER BY orders DESC;
```

**Как читается запрос**

- `payment_result` — итог по каждому заказу с попытками: 100000 строк.
- `FROM orders o LEFT JOIN payment_result pr` — все 100007 заказов. У заказа без попыток пары не нашлось, и все столбцы `pr` равны `NULL`.
- `CASE` — порядок веток важен. Сначала проверяется «попыток нет» (`pr.order_id IS NULL`), потом «оплачен».
- `GROUP BY payment_state` — группировка по имени столбца из `SELECT`. PostgreSQL так умеет. Можно повторить и всё выражение `CASE`.

Как `LEFT JOIN` выглядит на трёх заказах:

| o.id | pr.order_id | pr.is_paid | payment_state |
|---:|---:|---|---|
| 32 | 32 | t | paid |
| 16374 | 16374 | f | not_paid |
| 100001 | NULL | NULL | no_attempts |

Результат:

| payment_state | orders | order_amount |
|---|---:|---:|
| paid | 95884 | 96612590.20 |
| not_paid | 4116 | 4131062.44 |
| no_attempts | 7 | 1075.33 |

Сумма заказов — 100007. Магазин не получил деньги по 4123 заказам на 4.13 млн.

## Заказы, спасённые повторной попыткой

Повторная попытка — это функция продукта: кнопка «попробовать ещё раз», автоматический повтор. Чтобы понять, окупается ли она, считают, сколько заказов **сначала не прошли**, а **потом** были оплачены.

**Задача.** Продакт-менеджер платёжной страницы хочет знать: у скольких заказов первая попытка была отклонена, сколько из них всё-таки оплачены и какой это процент.

```sql

WITH order_payment AS (
    SELECT order_id,
           bool_or(attempt_no = 1 AND status = 'failed') AS first_failed,
           bool_or(status = 'success') AS is_paid
    FROM payment_attempts
    GROUP BY order_id
)
SELECT count(*) FILTER (WHERE first_failed) AS first_failed_orders,
       count(*) FILTER (WHERE first_failed AND is_paid) AS recovered_orders,
       round(100.0 * count(*) FILTER (WHERE first_failed AND is_paid)
             / count(*) FILTER (WHERE first_failed), 2) AS recovered_pct
FROM order_payment;
```

**Как читается запрос**

- `bool_or(attempt_no = 1 AND status = 'failed')` — есть ли у заказа строка «первая попытка и она отклонена». Такая строка у заказа не больше одной.
- `bool_or(status = 'success')` — оплачен ли заказ в итоге.
- `first_failed AND is_paid` — первая не прошла, но заказ оплачен: спасён повтором.

Как выглядит `order_payment` на трёх заказах:

| order_id | first_failed | is_paid | Спасён? |
|---:|---|---|---|
| 1 | f | t | нет: повтор не понадобился |
| 32 | t | t | да |
| 16374 | t | f | нет: так и не оплачен |

Результат:

| first_failed_orders | recovered_orders | recovered_pct |
|---:|---:|---:|
| 4916 | 800 | 16.27 |

Повтор спас каждый шестой заказ, у которого не прошла первая попытка.

## Сколько ждали оплату и как часто повторяли

**Задача.** Продакт-менеджер хочет знать, через сколько после создания заказа приходит успешная оплата. Нужна раскладка: время ожидания и сколько оплаченных заказов столько ждали.

```sql

SELECT pa.created_at - o.created_at AS wait_for_payment,
       count(*) AS paid_orders
FROM payment_attempts pa
JOIN orders o ON o.id = pa.order_id
WHERE pa.status = 'success'
GROUP BY wait_for_payment
ORDER BY wait_for_payment;
```

**Как читается запрос**

- `JOIN orders` — к каждой успешной попытке пристыковывается заказ, чтобы взять момент его создания.
- `pa.created_at - o.created_at` — разница двух `timestamptz`, получается `interval` (тема 10).

| wait_for_payment | paid_orders |
|---|---:|
| 00:30:00 | 95084 |
| 00:40:00 | 800 |

В учебных данных первая попытка идёт ровно через 30 минут после создания заказа. Заказы, оплаченные с третьей попытки, ждали на 10 минут дольше.

**Задача.** Поддержка хочет видеть, с каким промежутком клиент повторял оплату заказа 32.

```sql

SELECT order_id,
       attempt_no,
       status,
       created_at,
       created_at - lag(created_at) OVER (
           PARTITION BY order_id
           ORDER BY attempt_no
       ) AS since_previous_attempt
FROM payment_attempts
WHERE order_id = 32
ORDER BY attempt_no;
```

**Как читается запрос**

- `lag(created_at) … ORDER BY attempt_no` — момент предыдущей попытки того же заказа (тема 09).
- У первой попытки предыдущей нет — `NULL`.

| order_id | attempt_no | status | created_at | since_previous_attempt |
|---:|---:|---|---|---|
| 32 | 1 | failed | 2025-11-22 12:53:47.799768+00 | NULL |
| 32 | 2 | failed | 2025-11-22 12:58:47.799768+00 | 00:05:00 |
| 32 | 3 | success | 2025-11-22 13:03:47.799768+00 | 00:05:00 |

## Сверка: отгружено без оплаты

Платёжный журнал и статусы заказов ведут разные системы. Сверка между ними ищет ситуации, которые стоят магазину денег. Первая из них — склад отправил товар, а деньги не получены.

**Задача.** Финансовый контролёр ищет заказы, которые переданы в доставку или уже доставлены, но успешной оплаты по ним нет. Это и заказы с одними неудачными попытками, и заказы вовсе без попыток. По каждому из двух статусов — число заказов и их сумма.

```sql

WITH payment_result AS (
    SELECT order_id,
           bool_or(status = 'success') AS is_paid
    FROM payment_attempts
    GROUP BY order_id
)
SELECT o.status,
       count(*) AS unpaid_orders,
       sum(o.amount) AS unpaid_amount
FROM orders o
LEFT JOIN payment_result pr ON pr.order_id = o.id
WHERE o.status IN ('shipped', 'delivered')
  AND coalesce(pr.is_paid, false) = false
GROUP BY o.status
ORDER BY o.status;
```

**Как читается запрос**

- `LEFT JOIN` — чтобы не потерять заказы без попыток.
- `coalesce(pr.is_paid, false)` — у заказа без попыток `is_paid` равен `NULL`. `coalesce` превращает его в `false`: попыток нет — значит, не оплачен. Без `coalesce` условие `NULL = false` дало бы `NULL`, и такие заказы выпали бы из отчёта.

| status | unpaid_orders | unpaid_amount |
|---|---:|---:|
| delivered | 849 | 853014.46 |
| shipped | 830 | 798596.84 |

1679 заказов на 1.65 млн уехали к клиентам без оплаты. В реальном магазине это повод проверять, почему склад не ждёт подтверждения оплаты.

## Сверка: отменено, но оплачено

Вторая опасная ситуация: заказ отменён, а деньги клиента списаны. Такому клиенту нужно вернуть деньги.

**Задача.** Финансовый контролёр готовит список на возврат денег: сколько отменённых заказов имеют успешную оплату и на какую сумму.

```sql

SELECT count(*) AS cancelled_paid_orders,
       sum(pa.amount) AS refund_amount
FROM orders o
JOIN payment_attempts pa
  ON pa.order_id = o.id
 AND pa.status = 'success'
WHERE o.status = 'cancelled';
```

**Как читается запрос**

- `JOIN … AND pa.status = 'success'` — к заказу пристыковывается только успешная попытка. У заказа она одна, поэтому строки не размножаются.
- `WHERE o.status = 'cancelled'` — только отменённые заказы.
- Сумма возврата берётся из `pa.amount` — сколько реально списано, а не сколько стоил заказ.

| cancelled_paid_orders | refund_amount |
|---:|---:|
| 19245 | 19360754.91 |

**Нюансы**

- В учебной базе нет таблицы возвратов, поэтому этот запрос показывает, сколько **нужно** вернуть. В реальной системе к нему добавляют `NOT EXISTS` по таблице возвратов, чтобы оставить только тех, кому ещё не вернули.

## Сверка: сумма оплаты не равна сумме заказа

**Задача.** Финансовый контролёр проверяет, что каждая попытка оплаты пыталась списать ровно сумму заказа.

```sql

SELECT count(*) AS attempts_checked,
       count(*) FILTER (WHERE pa.amount <> o.amount) AS amount_mismatch
FROM payment_attempts pa
JOIN orders o ON o.id = pa.order_id;
```

**Как читается запрос**

- Каждая попытка пристыковывается к своему заказу.
- `pa.amount <> o.amount` — суммы различаются.

| attempts_checked | amount_mismatch |
|---:|---:|
| 101600 | 0 |

Расхождений нет.

## Доля отказов по месяцам

**Задача.** Платёжная команда следит, не стал ли банк чаще отклонять платежи. Нужна доля отклонённых попыток по месяцам.

```sql

SELECT date_trunc('month', created_at)::date AS month_start,
       count(*) AS attempts,
       count(*) FILTER (WHERE status = 'failed') AS failed_attempts,
       round(100.0 * count(*) FILTER (WHERE status = 'failed') / count(*), 2) AS failed_pct
FROM payment_attempts
GROUP BY date_trunc('month', created_at)
ORDER BY month_start;
```

**Как читается запрос**

- `date_trunc('month', created_at)` — месяц попытки (тема 10).
- Доля считается по попыткам: вопрос про то, как часто банк говорит «нет».

## Что обычно спрашивают на собеседованиях

- Чем успешность по попыткам отличается от успешности по заказам. Какую метрику смотрит платёжная команда, а какую — финансы.
- Как определить, оплачен ли заказ, если попыток несколько: `bool_or` или `count(*) FILTER (…) > 0`.
- Как не потерять заказы без попыток: отчёт от `orders` и `LEFT JOIN`, `coalesce` для `NULL`.
- Как посчитать «спасённые повтором» заказы.
- Как найти отгрузку без оплаты и оплату без заказа или отменённого заказа.
- Почему `JOIN` с журналом попыток может размножить строки заказа и как этого избежать: сначала свернуть попытки до одной строки на заказ.
- Как посчитать время от заказа до оплаты и между попытками.

---

## Карта выбора конструкции

| Вопрос | Конструкция |
|---|---|
| Успешность по попыткам | `count(*) FILTER (WHERE status = 'success') / count(*)` |
| Успешность по заказам | `count(DISTINCT order_id) FILTER (…) / count(DISTINCT order_id)` |
| Оплачен ли заказ | `bool_or(status = 'success')` + `GROUP BY order_id` |
| Все ли попытки неудачны | `bool_and(status = 'failed')` |
| Сценарий оплаты одной строкой | `string_agg(status, ' -> ' ORDER BY attempt_no)` |
| Все заказы, включая без попыток | `FROM orders LEFT JOIN (итог по заказу)` |
| `NULL` из `LEFT JOIN` считать «нет» | `coalesce(flag, false)` |
| Время от заказа до оплаты | `pa.created_at - o.created_at` |
| Промежуток между попытками | `created_at - lag(created_at) OVER (PARTITION BY order_id ORDER BY attempt_no)` |
