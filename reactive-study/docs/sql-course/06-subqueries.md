## Что изучаем

В темах 01–05 вы писали **один** запрос к одной или нескольким таблицам.

Иногда внутри него нужен **второй** запрос — **подзапрос** (subquery): `SELECT` в скобках `( … )`.

В этой теме — **три вида** подзапросов. У каждого **свои правила**, сколько строк и столбцов он может вернуть.

Таблицы в примерах — `users` и `orders` базы `reactive_study`.

Перед примерами:

```sql

SET search_path TO reactive_study;
```

## Главное с самого начала — не путать термины

| Термин | Что означает |
|---|---|
| **Подзапрос** | любой `SELECT` в скобках внутри другого запроса — **общее** название |
| **Scalar-подзапрос** | **один** из видов подзапроса: ровно **одно** значение (1 строка, 1 столбец) |

**Частая ошибка:** думать, что «подзапрос = всегда одно число».  
**Так нельзя.** Скобки `(SELECT …)` сами по себе **не говорят**, scalar это или нет.

**Что решает вид подзапроса:** не скобки, а **конструкция снаружи** — что стоит перед `(SELECT …)`.

В таблице ниже `(SELECT …)` — **место** для подзапроса, а не готовый запрос. Полные запросы будут в следующем разделе.

| Снаружи написано | Вид | Строк в результате подзапроса | Столбцов | Что получается |
|---|---|---|---|---|
| `amount > (SELECT …)` | **scalar** | **1** | **1** | одно число (или NULL) |
| `id IN (SELECT …)` | **IN** | **0, 1 или много** | **1** | **список значений** — как `(1, 2, 3)`, только из запроса |
| `EXISTS (SELECT …)` | **EXISTS** | не важно | не важно | только ответ **да / нет** |

Один и тот же `(SELECT …)` читается по-разному в зависимости от того, что перед ним:

| Условие в `WHERE` | Что нужно снаружи |
|---|---|
| `amount > (SELECT …)` | одно число |
| `id IN (SELECT …)` | список значений: много строк, один столбец |
| `EXISTS (SELECT …)` | ответ «нашлось / не нашлось» |

**Запомнить одной фразой:** подзапрос — **контейнер**; scalar / IN / EXISTS — **разные способы** его использовать.

В таблице выше — только три самых частых случая.

**Полный список** операторов (включая `BETWEEN`, `ANY`, `ALL`) — в следующем разделе.

## Какие операторы с каким подзапросом работают

Выше сказано «смотри, что стоит снаружи скобок». Здесь — **полный список**, что там может стоять.

Все операторы делятся на **две группы**.

**Про примеры в этом разделе:** каждый запрос — **целиком**, вместе с `SELECT`, `FROM` и всеми таблицами.

Их можно скопировать в SQL-клиент и выполнить как есть.

### Группа 1 — операторы, которым нужно ОДНО значение (scalar)

Scalar-подзапрос — это **обычное значение**. Его можно поставить **везде**, где допустимо одно число, текст или дата.

**Источник:** https://www.postgresql.org/docs/current/sql-expressions.html#SQL-SYNTAX-SCALAR-SUBQUERIES

EN:

> The `SELECT` query is executed and the single returned value is used in the surrounding value expression.

RU:

> Запрос `SELECT` выполняется, и единственное возвращённое значение используется в окружающем его выражении-значении.

| Оператор / место | Зачем там подзапрос |
|---|---|
| `=`, `<>`, `<`, `>`, `<=`, `>=` | даёт значение, с которым сравниваем |
| `BETWEEN … AND …` | даёт **каждую** границу диапазона — отдельным подзапросом |
| Арифметика `+`, `-`, `*`, `/` | даёт второе число для вычисления |
| Столбец в списке `SELECT` | даёт значение **нового столбца** отчёта |
| `HAVING` | даёт порог, с которым сравниваем группу |
| `ORDER BY` | **не место для нового подзапроса**, если число уже посчитано в `SELECT` — сортируют по **имени столбца** |

Дальше — по одному **полному запросу** на каждый полезный случай. Один и тот же приём второй раз не повторяю.

**Сравнение `>` — заказы дороже средней суммы по магазину:**

```sql

SELECT id, amount
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders)
ORDER BY amount DESC
LIMIT 5;
```

**`BETWEEN` — заказы от самой маленькой суммы до средней** (типичный и «ниже среднего» сегмент):

```sql

SELECT id, amount
FROM orders
WHERE amount BETWEEN (SELECT MIN(amount) FROM orders)
                 AND (SELECT AVG(amount) FROM orders)
ORDER BY amount
LIMIT 5;
```

**Арифметика — в отчёт добавить отклонение от средней суммы:**

```sql

SELECT id,
       amount,
       amount - (SELECT AVG(amount) FROM orders) AS diff_from_avg
FROM orders
ORDER BY amount DESC
LIMIT 5;
```

Сортировка идёт по `amount`: столбец `diff_from_avg` уже посчитан, повторять ту же формулу в `ORDER BY` незачем.

**Столбец в `SELECT` + сортировка по alias — топ клиентов по числу заказов:**

**Ситуация:** менеджер просит пятёрку самых активных клиентов.

```sql

SELECT u.id,
       u.full_name,
       (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS order_count
FROM users u
ORDER BY order_count DESC
LIMIT 5;
```

Порядок работы запроса (как его читает SQL):

| Шаг | Что происходит |
|---|---|
| 1 | `FROM users u` — берём клиентов |
| 2 | `SELECT` — для каждой строки считаем `order_count` (подзапрос один раз) |
| 3 | `ORDER BY order_count DESC` — переставляем **уже готовые** строки |
| 4 | `LIMIT 5` — оставляем верхние пять |

`ORDER BY` **не фильтрует**. Он работает **после** списка `SELECT`, поэтому ему можно дать имя столбца `order_count`.

**Источник:** https://www.postgresql.org/docs/current/sql-select.html

EN:

> An output column's name can be used to refer to the column's value in `ORDER BY` and `GROUP BY` clauses, but not in the `WHERE` or `HAVING` clauses; there you must write out the expression instead.

RU:

> Имя столбца результата можно использовать в `ORDER BY` и `GROUP BY`, но не в `WHERE` и не в `HAVING`; там нужно писать само выражение.

EN:

> Each `expression` can be the name or ordinal number of an output column (`SELECT` list item), or it can be an arbitrary expression formed from input-column values.

RU:

> Каждое выражение может быть именем или порядковым номером столбца результата (элемента списка `SELECT`) либо произвольным выражением из столбцов исходных таблиц.

**Так писать не нужно** — подзапрос посчитается дважды, смысл тот же:

```sql

-- избыточно: то же число уже есть в SELECT как order_count
ORDER BY (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) DESC
```

Результат топ-5 на вашей базе:

| id | full_name | order_count |
|---|---|---|
| 2346 | Load User 2346 | 40 |
| 2639 | Load User 2639 | 37 |
| 459 | Load User 459 | 36 |
| 498 | Load User 498 | 36 |
| 1427 | Load User 1427 | 35 |

Тот же отчёт можно получить через `LEFT JOIN` + `GROUP BY` (темы 03–04). Здесь — другой способ посчитать столбец.

**`HAVING` — статусы, у которых средняя сумма выше средней по всему магазину:**

```sql

SELECT status, AVG(amount) AS avg_amount
FROM orders
GROUP BY status
HAVING AVG(amount) > (SELECT AVG(amount) FROM orders)
ORDER BY avg_amount DESC;
```

В `HAVING` alias `avg_amount` использовать **нельзя** (см. цитату выше) — порог сравнивают с выражением `AVG(amount)`.

**Правило группы 1:** подзапрос обязан вернуть **1 строку и 1 столбец**.

Вернёт 2+ строк — **ошибка**. Вернёт 0 строк — значение станет **NULL**.

### Группа 2 — конструкции, которым нужен список строк

В группе 1 подзапрос отдавал **одно** число: `AVG`, `MIN`, `MAX`, `COUNT`.

Иногда нужно другое: не одно число, а **список** — много строк в одном столбце. Тогда слева от скобок ставят не просто `>`, а `IN`, `ANY`, `ALL` или `EXISTS`.

**Источник:** https://www.postgresql.org/docs/current/functions-subquery.html

EN:

> This section describes the SQL-compliant subquery expressions available in PostgreSQL. All of the expression forms documented in this section return Boolean (true/false) results.

RU:

> В этом разделе описаны соответствующие стандарту SQL выражения с подзапросами, доступные в PostgreSQL. Все формы выражений, описанные в этом разделе, возвращают логический результат (true/false).

#### Чем скобки после `>` отличаются от скобок после `> ALL`

Возьмём учебные заказы `JOIN-DEMO` — на вашей базе их семь, суммы такие:

| id | product_name | amount |
|---|---|---|
| 100002 | JOIN-DEMO-NO-PRODUCT-1 | 11.11 |
| 100003 | JOIN-DEMO-NO-PRODUCT-2 | 22.22 |
| 100001 | JOIN-DEMO-SINGLE-ORDER | 42.00 |
| 100004 | JOIN-DEMO-NO-PAYMENT-1 | 100.00 |
| 100005 | JOIN-DEMO-NO-PAYMENT-2 | 200.00 |
| 100006 | JOIN-DEMO-NO-EVENT-1 | 300.00 |
| 100007 | JOIN-DEMO-NO-EVENT-2 | 400.00 |

**Вариант А — группа 1, одно число.** Спрашиваем: «заказ дороже **самого большого** из этих семи?»

В скобках стоит `MAX`: семь строк сворачиваются в **одно** значение `400.00`. Обычное сравнение `>` это переваривает.

```sql

SELECT id, amount
FROM orders
WHERE amount > (
    SELECT MAX(amount)
    FROM orders
    WHERE product_name LIKE 'JOIN-DEMO%'
)
ORDER BY amount
LIMIT 5;
```

**Вариант Б — группа 2, список.** Тот же вопрос другими словами: «заказ дороже **каждой** суммы из этих семи?»

В скобках **нет** `MAX`. Подзапрос отдаёт столбец из семи чисел: `11.11`, `22.22`, …, `400.00`. Чтобы сравнить одно число со **всем списком**, нужен `ALL`.

```sql

SELECT id, amount
FROM orders
WHERE amount > ALL (
    SELECT amount
    FROM orders
    WHERE product_name LIKE 'JOIN-DEMO%'
)
ORDER BY amount
LIMIT 5;
```

| | Что в скобках | Сколько строк вернёт подзапрос | Что делает внешнее сравнение |
|---|---|---|---|
| `amount > (SELECT MAX(amount) …)` | одно число `400.00` | **1** | «больше 400» |
| `amount > ALL (SELECT amount …)` | список сумм | **7** | «больше 11.11 **и** больше 22.22 **и** … **и** больше 400» |

Ответ у обоих запросов **один и тот же**: чтобы быть больше каждого числа в списке, достаточно быть больше самого большого. Поэтому в рабочем отчёте пишут вариант А (`MAX`). Вариант Б (`ALL`) оставляют на интервью: проверяют, что вы понимаете сравнение со списком.

`> ANY` читается иначе: «больше **хотя бы одного** числа из того же списка семи сумм». Это то же самое, что «больше самого маленького», то есть `11.11`. В отчёте снова проще свернуть список в одно число:

```sql

SELECT id, amount
FROM orders
WHERE amount > (
    SELECT MIN(amount)
    FROM orders
    WHERE product_name LIKE 'JOIN-DEMO%'
)
ORDER BY amount
LIMIT 5;
```

Кратко:

| Хочу сказать | Через список | Через одно число |
|---|---|---|
| больше **каждого** из списка | `amount > ALL (SELECT amount …)` | `amount > (SELECT MAX(amount) …)` |
| больше **хотя бы одного** из списка | `amount > ANY (SELECT amount …)` | `amount > (SELECT MIN(amount) …)` |

`SOME` — другое имя для `ANY`. `IN` — другое имя для `= ANY`. `NOT IN` — другое имя для `<> ALL`.

**Источник:** https://www.postgresql.org/docs/current/functions-subquery.html

EN:

> `SOME` is a synonym for `ANY`. `IN` is equivalent to `= ANY`.

RU:

> `SOME` — синоним `ANY`. `IN` эквивалентно `= ANY`.

EN:

> `NOT IN` is equivalent to `<> ALL`.

RU:

> `NOT IN` эквивалентно `<> ALL`.

#### Формы записи группы 2

В скобках — **что именно выбирает** внутренний `SELECT`. Не «любой SELECT», а столбец или проверка наличия.

| Форма записи | Что внутри скобок | Строк | Столбцов | Смысл |
|---|---|---|---|---|
| `id IN (SELECT user_id FROM orders WHERE amount > 1500)` | столбец id клиентов | сколько найдёт | **1** | «этот id **есть** в списке» |
| `id NOT IN (SELECT user_id FROM orders)` | столбец id клиентов | сколько найдёт | **1** | «этого id **нет** в списке» |
| `id = ANY (SELECT user_id FROM orders WHERE amount > 1500)` | тот же столбец, что у `IN` | сколько найдёт | **1** | то же, что `IN` |
| `amount > ANY (SELECT amount FROM orders WHERE product_name LIKE 'JOIN-DEMO%')` | столбец сумм, без `MIN` | 7 | **1** | «больше **хотя бы одной** из семи сумм» |
| `amount > ALL (SELECT amount FROM orders WHERE product_name LIKE 'JOIN-DEMO%')` | столбец сумм, без `MAX` | 7 | **1** | «больше **каждой** из семи сумм» |
| `id <> ALL (SELECT user_id FROM orders)` | столбец id клиентов | сколько найдёт | **1** | то же, что `NOT IN` |
| `EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id)` | не список значений, а «нашлась строка?» | любое | любое | «у клиента есть хотя бы один заказ» |
| `NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id)` | та же проверка | любое | любое | «заказов нет» |

Полные запросы: `IN` — пример 4, `EXISTS` — пример 7, `NOT EXISTS` — пример 8.

### Почему BETWEEN сюда не входит

`BETWEEN` вы уже видели в группе 1:

```sql

WHERE amount BETWEEN (SELECT MIN(amount) FROM orders)
                 AND (SELECT AVG(amount) FROM orders)
```

Это **два отдельных числа**: нижняя граница и верхняя. Каждая скобка — scalar, как `MAX` в варианте А выше.

`BETWEEN` **не умеет** сравнивать с целым столбцом так, как это делают `IN` и `ALL`. Если во внутреннем `SELECT` забыть `MIN` / `AVG` и выбрать все суммы, PostgreSQL получит ~100 000 строк там, где ждёт **одну** границу — и остановит запрос.

```sql

SELECT id, amount
FROM orders
WHERE amount BETWEEN (SELECT amount FROM orders) AND 1000;
```

Текст ошибки: `more than one row returned by a subquery used as an expression`.

**Источник:** https://www.postgresql.org/docs/current/functions-comparison.html

EN:

> The `BETWEEN` predicate simplifies range tests: `a BETWEEN x AND y` is equivalent to `a >= x AND a <= y`. Notice that `BETWEEN` treats the endpoint values as included in the range.

RU:

> Предикат `BETWEEN` упрощает проверку диапазона: `a BETWEEN x AND y` эквивалентно `a >= x AND a <= y`. Обратите внимание: `BETWEEN` считает граничные значения **включёнными** в диапазон.

Раз обе границы — обычные сравнения `>=` и `<=`, каждая должна быть **одним** значением. Формы `BETWEEN (SELECT amount FROM orders)` в SQL нет: это не `IN` и не `ALL`.

### Сводка: где какой подзапрос

| Задача | Как писать | Что вернёт подзапрос |
|---|---|---|
| сравнить с одним числом | `>`, `<`, `=` и тот же `>` после `AVG` / `MAX` / `MIN` | **1 строка, 1 столбец** |
| проверить диапазон | `BETWEEN` + два scalar (`MIN` и `AVG`) | по **одному** числу на каждую границу |
| проверить попадание в список | `IN` / `NOT IN` | **много строк, 1 столбец** |
| сравнить со всем списком | `> ALL` / `> ANY` — или свернуть список в `MAX` / `MIN` | список **или** одно число |
| узнать «есть / нет связанных строк» | `EXISTS` / `NOT EXISTS` | важен факт строки, не столбцы |
| добавить посчитанный столбец в отчёт | подзапрос в `SELECT` | **1 строка, 1 столбец** |
| отсортировать по этому столбцу | `ORDER BY` **имя столбца** | подзапрос заново не пишут |

**Что разбираем подробно в примерах ниже:** scalar, `IN` / `NOT IN`, `EXISTS` / `NOT EXISTS`.

`ANY` / `ALL` на интервью достаточно узнать по таблице: `IN` = `= ANY`, `NOT IN` = `<> ALL`, а «больше каждого» = `> MAX`.

## Что такое подзапрос

**Подзапрос** — это `SELECT`, записанный **внутри скобок** `( … )` в другом запросе.

```text
Внешний запрос
    └── Внутренний запрос (подзапрос) в скобках
```

**Аналогия.** Внешний запрос — основной отчёт.

Подзапрос — **вспомогательный мини-запрос**, результат которого нужен основному:

- иногда **одно число** (scalar);
- иногда **список id** (`IN`);
- иногда просто ответ **«нашлось / не нашлось»** (`EXISTS`).

Обратите внимание на разницу в том, **что подзапрос отдаёт наружу**:

| Вид | Что отдаёт наружу |
|---|---|
| **Scalar** | **значение** — число, текст, дату |
| `IN`, `EXISTS`, `ANY`, `ALL` | **логический ответ** true / false |

Подзапрос может стоять в разных местах:

| Место | Зачем | Вид |
|---|---|---|
| В `WHERE` после `>`, `<`, `=`, `BETWEEN` | сравнить с **одним значением** | **scalar** |
| В `WHERE` после `IN` / `NOT IN` / `ANY` / `ALL` | проверить **список** значений | **набор строк** |
| В `WHERE` после `EXISTS` / `NOT EXISTS` | проверить **наличие** строк | **набор строк** |
| В `SELECT` | добавить столбец из другой таблицы | **scalar** |
| В `ORDER BY` | только если числа ещё нет в `SELECT`; иначе — **имя столбца** | alias, не второй подзапрос |
| В `FROM` | временная «мини-таблица» | тема **07** (CTE) |

## Три вида подзапросов в этой теме

Сводная таблица — **держите её под рукой** при чтении примеров.

Читать так: **строк** — сколько **горизонтальных** записей вернул подзапрос; **столбцов** — сколько **полей** в каждой записи.

| Вид | Строк | Столбцов | Что в итоге | Полный запрос |
|---|---|---|---|---|
| **Scalar** | **1** | **1** | **одно** значение: число, текст… | пример 1 и 2 ниже |
| **IN** | **0, 1 или много** | **1** | **список** значений в одном столбце | пример 4 и 5 ниже |
| **EXISTS** | любое | любое | только **да / нет** («есть строка?») | пример 7 ниже |

**Scalar vs IN — на пальцах**

| | Scalar | IN |
|---|---|---|
| Строк | **ровно 1** | **сколько угодно** (0, 1, 10, 1000…) |
| Столбцов | **1** | **1** |
| Образ | одна ячейка: `42.5` | столбик чисел — **список**: `7`, `12`, `45`, `7`… |
| Аналогия | «какое **среднее**?» → одно число | «**какие id** подходят?» → перечень, как `(7, 12, 45)` |

Сравните два полных запроса — разница только в том, **что нужно снаружи**.

**Scalar:** подзапрос отдаёт **одно** число (среднюю сумму):

```sql

SELECT id, amount
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders)
ORDER BY amount
LIMIT 5;
```

**IN:** подзапрос отдаёт **столбец** `user_id` — в каждой строке одно значение, строк много:

```sql

SELECT id, full_name
FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 1500)
ORDER BY id
LIMIT 5;
```

Во втором запросе PostgreSQL сравнивает `users.id` с **каждым** значением из столбца `user_id` — так же, как сравнивал бы со списком `(7, 12, 45)`.

**Примеры одной задачи разными словами**

| Бизнес-вопрос | Какой вид |
|---|---|
| Заказы дороже **средней** суммы | scalar — нужно одно число (среднее) |
| Клиенты, у которых **есть** заказ > 1500 | `IN` или `EXISTS` — не scalar |
| Клиенты **без** заказов | `NOT IN` или `NOT EXISTS` — не scalar |

Дальше по документу — сначала **scalar**, потом **IN**, потом **EXISTS**. Это порядок **изложения**, а не «от простого к сложному по важности».

## Scalar-подзапрос — одно значение

**Scalar** (по-русски «скаляр») — **один из видов** подзапроса.

Правило: **ровно одна строка, один столбец** — одно значение (число, текст, дата…).

**Источник:** https://www.postgresql.org/docs/current/sql-expressions.html#SQL-SYNTAX-SCALAR-SUBQUERIES

EN:

> A scalar subquery is an ordinary `SELECT` query in parentheses that returns exactly one row with one column.

RU:

> Scalar-подзапрос — обычный запрос `SELECT` в скобках, который возвращает ровно одну строку с одним столбцом.

Это правило действует **только** там, где подзапрос используется как **scalar** — после `>`, `<`, `=`, в списке `SELECT` как отдельный столбец.

Если тот же `SELECT` стоит после `IN` или `EXISTS` — правила **другие**, см. раздел «Какие операторы с каким подзапросом работают».

### Пример 1 — заказы дороже среднего

**Задача.** Показать заказы, сумма которых **выше средней** по всей таблице `orders`.

Сначала нужно узнать среднее — это отдельный маленький запрос внутри условия:

```sql

SELECT id, amount
FROM orders
WHERE amount > (
    SELECT AVG(amount)
    FROM orders
)
ORDER BY amount DESC
LIMIT 10;
```

**Как читать по шагам**

| Шаг | Что происходит |
|---|---|
| 1 | Подзапрос `(SELECT AVG(amount) FROM orders)` считает **одно число** — среднюю сумму по ~100 000 заказам |
| 2 | Внешний запрос сравнивает `amount` каждого заказа с этим числом |
| 3 | В результат попадают только заказы **строго больше** среднего |
| 4 | `ORDER BY … LIMIT 10` — десять самых дорогих из отобранных |

**Источник:** https://www.postgresql.org/docs/current/sql-expressions.html#SQL-SYNTAX-SCALAR-SUBQUERIES

EN:

> It is an error to use a query that returns more than one row or more than one column as a scalar subquery. (But if, during a particular execution, the subquery returns no rows, there is no error; the scalar result is taken to be null.)

RU:

> Ошибка — использовать в качестве scalar-подзапроса запрос, который возвращает больше одной строки или больше одного столбца. (Если при конкретном выполнении подзапрос не вернул ни одной строки, ошибки нет: scalar-результат считается равным NULL.)

| Ситуация | Что будет |
|---|---|
| Подзапрос вернул **ровно одну** строку с одним числом | всё работает |
| Подзапрос вернул **0** строк | значение = **NULL** (не ошибка) |
| Подзапрос вернул **2+** строк | **ошибка** выполнения |

### Пример 2 — сравнение с одним конкретным заказом

**Задача.** Найти заказы, сумма которых **больше**, чем у заказа **2**.

```sql

SELECT id, amount
FROM orders
WHERE amount > (
    SELECT amount
    FROM orders
    WHERE id = 2
)
ORDER BY amount DESC
LIMIT 10;
```

Подзапрос по `id = 2` всегда возвращает **одну** строку с одним столбцом `amount` — это корректный scalar.

## Scalar в SELECT — «посчитать для каждой строки»

Подзапрос в списке `SELECT` добавляет **новый столбец** к каждой строке внешнего запроса.

### Пример 3 — число заказов у каждого клиента

**Задача.** Для первых пяти клиентов показать имя и **сколько у каждого заказов**.

```sql

SELECT u.id,
       u.full_name,
       (
           SELECT COUNT(*)
           FROM orders o
           WHERE o.user_id = u.id
       ) AS order_count
FROM users u
WHERE u.id <= 5
ORDER BY u.id;
```

**Откуда берутся `u` и `o`**

| Псевдоним | Где объявлен | На что указывает |
|---|---|---|
| `u` | `FROM users u` — внизу запроса | таблица `users` |
| `o` | `FROM orders o` — внутри подзапроса | таблица `orders` |

Псевдоним, объявленный в `FROM`, действует **во всём запросе** — в том числе в строках `SELECT`, которые написаны **выше**. Поэтому `u.full_name` в начале запроса — это `users.full_name`.

**Как читать**

| Часть | Смысл |
|---|---|
| `FROM users u` | внешний запрос перебирает клиентов |
| `WHERE o.user_id = u.id` **внутри** подзапроса | подзапрос **ссылается** на текущую строку `u` |
| `COUNT(*)` | считает заказы **только этого** клиента |

Такой подзапрос называют **коррелированным**: внутренний запрос «знает» про строку снаружи.

**Источник:** https://www.postgresql.org/docs/current/sql-expressions.html#SQL-SYNTAX-SCALAR-SUBQUERIES

EN:

> The subquery can refer to variables from the surrounding query, which will act as constants during any one evaluation of the subquery.

RU:

> Подзапрос может ссылаться на переменные из окружающего запроса; при каждой отдельной оценке подзапроса они ведут себя как константы.

**На практике** для «клиент + число заказов» часто пишут `LEFT JOIN` + `GROUP BY` (вы это уже умеете из тем 03–04). Подзапрос в `SELECT` — **другой способ** записать ту же идею; на интервью спрашивают оба.

## IN с подзапросом — список значений из другой таблицы

**Это уже не scalar.**

Подзапрос после `IN` возвращает **один столбец** и **столько строк, сколько найдёт** — ноль, одну или тысячи.  
Вместе это **список значений**: тот же смысл, что у `IN (7, 12, 45)`, только список **не пишут руками**, а **получают запросом**.

В **теме 02** вы уже писали `IN` со списком вручную:

```sql

SELECT id, full_name
FROM users
WHERE id IN (1, 2, 3)
ORDER BY id;
```

Тот же `IN`, но список берётся из `orders` — руками его никто не перечисляет:

```sql

SELECT id, full_name
FROM users
WHERE id IN (SELECT user_id FROM orders WHERE status = 'cancelled')
ORDER BY id
LIMIT 5;
```

**Что именно отдаёт подзапрос.** Выполните его отдельно:

```sql

SELECT user_id
FROM orders
WHERE status = 'cancelled'
LIMIT 4;
```

На вашей базе первые разные `user_id` среди отменённых заказов такие:

| user_id |
|---|
| 1 |
| 2 |
| 3 |
| 4 |

Это **несколько строк**, **1 столбец** — список значений. Один и тот же клиент может встречаться много раз: у Ann Smith (`user_id = 1`) отменённых заказов несколько, но для `IN` повтор не меняет ответ.

Условие `id IN (…)` проверяет: «`users.id` **равен хотя бы одному** значению из этого столбца?»

Правило для `IN`: строк — сколько угодно, но **столбец обязательно один**.

**Источник:** https://www.postgresql.org/docs/current/functions-subquery.html

EN:

> The right-hand side is a parenthesized subquery, which must return exactly one column. The left-hand expression is evaluated and compared to each row of the subquery result. The result of `IN` is “true” if any equal subquery row is found.

RU:

> Правая часть — подзапрос в скобках, который должен вернуть ровно один столбец. Левое выражение сравнивается с каждой строкой результата подзапроса. Результат `IN` — «истина», если найдена хотя бы одна равная строка подзапроса.

### Пример 4 — клиенты с «крупным» заказом

**Задача.** Найти клиентов, у которых **хотя бы один** заказ на сумму **больше 1500**.

```sql

SELECT id, full_name, email
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
    WHERE amount > 1500
)
ORDER BY id
LIMIT 10;
```

**Как читать**

| Шаг | Что происходит |
|---|---|
| 1 | Подзапрос собирает **столбец** `user_id`: одна строка результата = одно значение, строк **много** |
| 2 | Получился **список** id клиентов с заказом > 1500 (как массив, только из SQL) |
| 3 | Внешний запрос оставляет клиентов, чей `id` **есть** в этом списке |
| 4 | Один клиент с несколькими крупными заказами попадёт в список **несколько раз**, но в ответе — **один раз** |

Ту же задачу можно решить через `INNER JOIN` — сравнение двух запросов будет в разделе «Подзапрос или JOIN?».

### Пример 5 — заказы клиентов из списка email

**Задача.** Показать заказы двух учебных клиентов: `join-demo-no-orders-1@example.com` и `join-demo-single-order@example.com`.

Их id заранее не знаем — берём из `users`:

```sql

SELECT o.id, o.amount, o.status
FROM orders o
WHERE o.user_id IN (
    SELECT id
    FROM users
    WHERE email IN (
        'join-demo-no-orders-1@example.com',
        'join-demo-single-order@example.com'
    )
)
ORDER BY o.id
LIMIT 10;
```

Здесь `IN` с **подзапросом** снаружи и `IN` со **списком** внутри — обычная комбинация.

## NOT IN с подзапросом и ловушка NULL

`NOT IN` — «значение **не входит** в список из подзапроса».

Подзапрос снова отдаёт **один столбец** и **сколько угодно строк** — тот же «столбик значений», что и у `IN`, только проверка обратная: «**нет** в списке».

### Пример 6 — клиенты без заказов (учебные)

**Задача.** Найти учебных клиентов **без единого заказа** (email начинается с `join-demo-no-orders`).

```sql

SELECT id, full_name, email
FROM users
WHERE email LIKE 'join-demo-no-orders%'
  AND id NOT IN (
      SELECT user_id
      FROM orders
  )
ORDER BY email;
```

**Как читать**

| Часть | Смысл |
|---|---|
| `email LIKE 'join-demo-no-orders%'` | только учебные «спящие» клиенты |
| `id NOT IN (SELECT user_id FROM orders)` | id **нет** среди тех, кто что-то заказывал |

Для этой проверки `orders.user_id` **всегда заполнен** (NOT NULL) — `NOT IN` работает предсказуемо.

### Ловушка: NULL внутри NOT IN

**Источник:** https://www.postgresql.org/docs/current/functions-subquery.html

EN:

> Note that if the left-hand expression yields null, or if there are no equal right-hand values and at least one right-hand row yields null, the result of the `NOT IN` construct will be null, not true.

RU:

> Если левое выражение даёт NULL, или среди правых значений нет равных и хотя бы одна правая строка даёт NULL, результат `NOT IN` будет NULL, а не «истина».

### Механизм: во что PostgreSQL разворачивает NOT IN

Чтобы понять цитату, нужно увидеть, **что именно** PostgreSQL вычисляет.

Пусть подзапрос вернул столбик из трёх значений: `10`, `20`, `30`.

Тогда условие `x NOT IN (SELECT …)` разворачивается в цепочку сравнений «**не равно**», склеенных через `AND`:

```
x NOT IN (10, 20, 30)
   ↓
x <> 10  AND  x <> 20  AND  x <> 30
```

Вся ловушка — в одном шаге этой цепочки. В SQL **любое сравнение с NULL даёт не «ложь», а NULL**:

- `99 <> 20` → истина;
- `99 <> NULL` → **NULL** (не «истина» и не «ложь»);
- `NULL <> 20` → **NULL**.

А `AND` с участием NULL ведёт себя так:

| Цепочка | Результат |
|---|---|
| `истина AND истина` | истина |
| `истина AND ложь` | ложь |
| `истина AND NULL` | **NULL** |
| `ложь AND NULL` | ложь |

Отсюда два случая из цитации:

1. **Слева NULL.** Тогда `NULL <> 10` даёт NULL уже на первом сравнении, и вся цепочка = NULL.
2. **Справа встретился NULL.** Тогда одно звено цепочки = NULL. Если остальные звенья — «истина», общий результат = NULL (строка «не подтверждена»). Если какое-то звено дало «ложь» (значение нашлось в списке), общий результат = ложь.

**Почему это «пропажа» строк.** `WHERE` пропускает в результат **только** строки, где условие = **истина**. И «ложь», и NULL строку отбрасывают — молча, без ошибки и без предупреждения.

**Проверьте на базе** — три выражения без всяких таблиц:

```sql

SELECT 99 NOT IN (10, 20)       AS no_null_in_list,
       99 NOT IN (10, NULL, 20) AS null_in_list,
       NULL NOT IN (10, 20)     AS null_on_left;
```

Результат в `reactive_study`:

```
 no_null_in_list | null_in_list | null_on_left
-----------------+--------------+--------------
 t               |              |
```

`t` — это «истина». Две пустые клетки — это **NULL** (psql печатает NULL как пустое место). То есть:

- `99 NOT IN (10, 20)` → истина → строка прошла бы в отчёт;
- `99 NOT IN (10, NULL, 20)` → NULL → строка **выпала бы** из отчёта, хотя 99 в списке действительно нет;
- `NULL NOT IN (10, 20)` → NULL → строка **выпала бы** из отчёта.

### Случай 1 — NULL слева (в проверяемом поле)

**Задача.** Найти заказы, товар которых **отсутствует** в каталоге `products`.

Такие заказы в `reactive_study` есть — у трёх заказов поле `product_id` пустое (NULL), то есть ссылки на товар нет:

```sql

SELECT id, product_name, product_id
FROM orders
WHERE product_id IS NULL
ORDER BY id;
```

Результат — 3 строки:

```
   id   |      product_name      | product_id
--------+------------------------+------------
    500 | Bulk order #500        |
 100002 | JOIN-DEMO-NO-PRODUCT-1 |
 100003 | JOIN-DEMO-NO-PRODUCT-2 |
```

Теперь задаём тот же вопрос через `NOT IN`:

```sql

SELECT id, product_name, product_id
FROM orders
WHERE product_id NOT IN (SELECT id FROM products)
ORDER BY id;
```

Результат — **0 строк**.

**Почему.** Справа — `products.id`, это первичный ключ, NULL там быть не может. А слева у трёх заказов `product_id` = NULL. Для них цепочка выглядит так:

```
NULL <> 1  AND  NULL <> 2  AND  …  AND  NULL <> 200
   ↓
NULL  AND  NULL  AND  …  AND  NULL
   ↓
NULL   →  WHERE отбрасывает строку
```

Остальные 100 004 заказа ссылаются на существующие товары, для них условие = «ложь» — и они тоже отбрасываются, уже законно. В итоге отчёт пустой, и это **неверный ответ** на бизнес-вопрос: заказы без товара в каталоге есть, просто `NOT IN` их не показал.

Тот же вопрос через `NOT EXISTS`:

```sql

SELECT o.id, o.product_name, o.product_id
FROM orders o
WHERE NOT EXISTS (
    SELECT 1
    FROM products p
    WHERE p.id = o.product_id
)
ORDER BY o.id;
```

Результат — **3 строки**, те самые заказы с пустым `product_id`.

**Про `SELECT 1` внутри подзапроса.** `EXISTS` и `NOT EXISTS` смотрят **только** на то, вернул подзапрос строки или нет, а **что** в этих строках — им не важно. Поэтому вместо реального столбца пишут константу `1` — она нужна лишь потому, что синтаксис `SELECT` требует хоть что-нибудь после ключевого слова. Можно было бы написать `SELECT p.id` или `SELECT 'всё равно'` — результат внешнего запроса не изменится. Подробнее — в разделе про [EXISTS](#exists--есть-ли-хотя-бы-одна-строка) ниже.

**Почему `NOT EXISTS` не ломается.** Он не сравнивает левое значение со списком. Он выполняет подзапрос и считает строки. Для заказа с `product_id` = NULL условие `p.id = NULL` не выполняется ни для одной строки `products`, подзапрос возвращает **ноль строк**, `NOT EXISTS` = «истина» — и заказ попадает в отчёт.

### Случай 2 — NULL справа (в столбце подзапроса)

Первый случай ловил NULL в проверяемом поле. Теперь — обратная ситуация: проверяемое поле заполнено, а NULL приходит **из подзапроса**.

**Задача.** Из трёх товаров с `id` 10, 20 и 99 найти те, которые **не заказывались** в учебных заказах `JOIN-DEMO`.

Сначала посмотрим, что отдаёт подзапрос:

```sql

SELECT o.product_id
FROM orders o
WHERE o.product_name LIKE 'JOIN-DEMO%'
ORDER BY o.product_id;
```

Результат — 7 строк, и **две из них пустые**:

```
 product_id
------------
         10
         20
         21
         30
         31


```

Правильный ответ на задачу видно глазами: товары 10 и 20 в списке есть, товара 99 — нет, значит ответ = `99`.

Пишем через `NOT IN`:

```sql

SELECT p.id, p.sku
FROM products p
WHERE p.id IN (10, 20, 99)
  AND p.id NOT IN (
      SELECT o.product_id
      FROM orders o
      WHERE o.product_name LIKE 'JOIN-DEMO%'
  )
ORDER BY p.id;
```

Результат — **0 строк**. Товар 99 потерялся.

**Почему.** Для товара 99 цепочка сравнений такая:

```
99 <> 10  AND  99 <> 20  AND  99 <> 21  AND  99 <> 30  AND  99 <> 31  AND  99 <> NULL  AND  99 <> NULL
   ↓
истина  AND  истина  AND  истина  AND  истина  AND  истина  AND  NULL  AND  NULL
   ↓
NULL   →  WHERE отбрасывает строку
```

Смысл в человеческих словах: PostgreSQL не может утверждать, что 99 нет в списке, потому что два элемента списка **неизвестны**. Может, один из них и есть 99. Ответ — «не знаю», то есть NULL.

Для товаров 10 и 20 результат = «ложь» (они действительно в списке), их отбрасывает законно. Поэтому отчёт пустой.

Тот же вопрос через `NOT EXISTS`:

```sql

SELECT p.id, p.sku
FROM products p
WHERE p.id IN (10, 20, 99)
  AND NOT EXISTS (
      SELECT 1
      FROM orders o
      WHERE o.product_name LIKE 'JOIN-DEMO%'
        AND o.product_id = p.id
  )
ORDER BY p.id;
```

Результат — **1 строка**, правильный ответ:

```
 id |    sku
----+-----------
 99 | SKU-00099
```

### Как писать безопасно

**Вариант 1 (предпочтительный) — `NOT EXISTS`.** Оба запроса выше уже показали: он даёт верный ответ и в случае NULL слева, и в случае NULL справа.

**Вариант 2 — `NOT IN`, но с отсечением NULL.** Если по каким-то причинам нужен именно `NOT IN`, NULL надо убрать **с двух сторон**.

Убираем NULL **справа** — добавляем `IS NOT NULL` внутрь подзапроса:

```sql

SELECT p.id, p.sku
FROM products p
WHERE p.id IN (10, 20, 99)
  AND p.id NOT IN (
      SELECT o.product_id
      FROM orders o
      WHERE o.product_name LIKE 'JOIN-DEMO%'
        AND o.product_id IS NOT NULL
  )
ORDER BY p.id;
```

Результат — **1 строка**, `99 | SKU-00099`: тот же правильный ответ, что у `NOT EXISTS`.

**Что изменилось.** Условие `o.product_id IS NOT NULL` выбросило две пустые строки из столбика подзапроса. Теперь список — `10, 20, 21, 30, 31`, без NULL, и цепочка сравнений для товара 99 даёт чистую «истину»:

```
99 <> 10  AND  99 <> 20  AND  99 <> 21  AND  99 <> 30  AND  99 <> 31
   ↓
истина   →  WHERE пропускает строку
```

Убираем NULL **слева** — добавляем `IS NOT NULL` в `WHERE` внешнего запроса:

```sql

SELECT o.id, o.product_name, o.product_id
FROM orders o
WHERE o.product_id IS NOT NULL
  AND o.product_id NOT IN (
      SELECT p.id
      FROM products p
  )
ORDER BY o.id;
```

Результат — **0 строк**.

**Внимание на смысл.** Здесь пусто уже **честно**: среди заказов с заполненным `product_id` нет ни одного, чей товар отсутствует в каталоге. Но проверка левой части **изменила вопрос** — мы сами исключили из рассмотрения заказы без ссылки на товар.

Если бизнесу нужны и такие заказы (а в задаче «найти заказы, товар которых отсутствует в каталоге» они нужны — это как раз самые проблемные заказы), `NOT IN` не подходит вообще: одна сторона ловушки лечится фильтром, а другая — меняет постановку задачи. Правильный инструмент — `NOT EXISTS`.

**Короткий вывод по разделу**

| Ситуация | `NOT IN` | `NOT EXISTS` |
|---|---|---|
| NULL в проверяемом поле слева | строка **выпадает** из отчёта | строка попадает в отчёт |
| NULL в столбце подзапроса справа | **все** «ненайденные» строки выпадают | ответ верный |
| Ошибка или предупреждение | **нет** — отчёт просто неполный | — |

**Углублённый разбор этой же ловушки** — в отдельном документе [«Ловушка NULL в NOT IN и чтение плана запроса»](06-lovushka-null-i-plan-zaprosa.md). Там тот же бизнес-вопрос записан четырьмя способами, для каждого снят план `EXPLAIN (ANALYZE, BUFFERS)` и по числам плана показано, почему один вариант быстрый и неправильный, другой правильный и в 32 раза дороже, а третий правильный и быстрый.

## EXISTS — «есть ли хотя бы одна строка?»

**Это тоже не scalar.** Подзапрос внутри `EXISTS` может вернуть **сколько угодно строк** — PostgreSQL смотрит только на ответ **да / нет**.

`EXISTS (подзапрос)` отвечает **да или нет**: вернул ли подзапрос **хотя бы одну строку**.

Содержимое столбцов **не важно** — поэтому внутри пишут `SELECT 1`:

```sql

SELECT users.id, users.full_name
FROM users
WHERE EXISTS (SELECT 1 FROM orders WHERE orders.user_id = users.id)
ORDER BY users.id
LIMIT 5;
```

Здесь `SELECT 1` не выбирает никакой столбец — единица стоит просто как заглушка.

**Источник:** https://www.postgresql.org/docs/current/functions-subquery.html

EN:

> If it returns at least one row, the result of `EXISTS` is “true”; if the subquery returns no rows, the result of `EXISTS` is “false”.

RU:

> Если возвращена хотя бы одна строка, результат `EXISTS` — «истина»; если подзапрос не вернул строк, результат `EXISTS` — «ложь».

EN:

> Since the result depends only on whether any rows are returned, and not on the contents of those rows, the output list of the subquery is normally unimportant. A common coding convention is to write all `EXISTS` tests in the form `EXISTS(SELECT 1 WHERE ...)`.

RU:

> Поскольку результат зависит только от того, вернулись ли строки, а не от их содержимого, список столбцов подзапроса обычно не важен. Распространённая запись: `EXISTS(SELECT 1 WHERE …)`.

В **теме 05** вы уже встречали `EXISTS` внутри `ON` при JOIN — там та же логика «есть / нет».

### Пример 7 — клиенты с «крупным» заказом, но через EXISTS

**Задача.** Та же, что в примере 4: клиенты, у которых есть **хотя бы один** заказ дороже **1500**.

Только теперь — через `EXISTS`:

```sql

SELECT u.id, u.full_name, u.email
FROM users u
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.user_id = u.id
      AND o.amount > 1500
)
ORDER BY u.id
LIMIT 10;
```

Псевдонимы здесь свои: `u` объявлен в `FROM users u`, `o` — в `FROM orders o` внутри подзапроса.

**Как читать**

| Шаг | Что происходит |
|---|---|
| 1 | Внешний запрос берёт очередного клиента — строку `u` |
| 2 | Подзапрос ищет в `orders` **хотя бы один** заказ, где `o.user_id` равен `u.id` и сумма > 1500 |
| 3 | Нашёл — `EXISTS` = true, клиент попадает в результат |
| 4 | Не нашёл — клиент отбрасывается |

Подзапрос **коррелированный**: значение `u.id` приходит из строки внешнего запроса.

Результат — **тот же**, что у примера 4 с `IN`. Разница только в форме записи.

## NOT EXISTS — «нет ни одной подходящей строки»

`NOT EXISTS` — «подзапрос **не нашёл** ни одной строки».

### Пример 8 — учебные клиенты без заказов

**Задача.** Найти учебных клиентов с email, начинающимся на `join-demo-no-orders`, у которых **нет ни одного** заказа.

Та же задача была в примере 6 через `NOT IN` — теперь через `NOT EXISTS`:

```sql

SELECT u.id, u.full_name, u.email
FROM users u
WHERE u.email LIKE 'join-demo-no-orders%'
  AND NOT EXISTS (
      SELECT 1
      FROM orders o
      WHERE o.user_id = u.id
  )
ORDER BY u.email;
```

**Смысл:** для каждого клиента `u` проверяем — в `orders` **нет ни одной** строки с его `id`.

`NOT EXISTS` **не ломается** из‑за NULL так, как `NOT IN` — поэтому на собеседованиях его чаще предлагают для задачи «найти строки без пары».

## IN и EXISTS — когда что выбирать

Обе конструкции решают похожие задачи «**есть связанные строки** в другой таблице».

| | `IN` с подзапросом | `EXISTS` с подзапросом |
|---|---|---|
| **Вопрос** | «Значение **в списке**?» | «**Есть** хотя бы одна подходящая строка?» |
| **Строк у подзапроса** | 0, 1 или **много** | **не важно** |
| **Столбцов у подзапроса** | **ровно 1** | **не важно** |
| **Что делает PostgreSQL** | берёт **столбец** значений и сравнивает с левой частью | смотрит только: вернулась **хотя бы одна** строка или нет |
| **NULL в подзапросе** | для `NOT IN` — ловушка: строки молча теряются (разбор выше) | безопасно: NULL на ответ не влияет |
| **Одинаковые значения в подзапросе** | не влияют на ответ и **не** размножают строки внешнего запроса | не влияют |

### Про одинаковые значения в подзапросе

Это важное отличие от JOIN, поэтому разберём отдельно.

**Ситуация.** Подзапрос `SELECT user_id FROM orders WHERE amount > 1500` возвращает `user_id` **каждого крупного заказа**. Один и тот же клиент попадает в этот столбик столько раз, сколько у него крупных заказов.

Возьмём живой пример из `reactive_study` — клиента `2781`. У него **18** заказов дороже 1500, значит его `id` встретится в столбике подзапроса **18 раз**.

**Что делает `IN`.** Он проверяет только одно: «есть такое значение в столбике?». Ответ — «да» или «нет». Сколько раз значение встретилось, на ответ **не влияет**: `2781 IN (2781, 2781, 2781)` и `2781 IN (2781)` — одинаковая «истина».

```sql

SELECT u.id, u.full_name
FROM users u
WHERE u.id = 2781
  AND u.id IN (SELECT o.user_id FROM orders o WHERE o.amount > 1500);
```

Результат — **одна строка**:

```
  id  |   full_name
------+----------------
 2781 | Load User 2781
```

Клиент вышел один раз, потому что внешний запрос перебирает строки `users`, а там клиент `2781` записан **однажды**. Подзапрос на число строк внешнего запроса не влияет — он только отвечает «да» или «нет» для каждой строки.

**Что делает JOIN.** Он не «проверяет», а **склеивает** строки: к каждому подходящему заказу подставляется его клиент.

```sql

SELECT u.id, u.full_name, o.id AS order_id, o.amount
FROM users u
INNER JOIN orders o ON o.user_id = u.id
WHERE u.id = 2781
  AND o.amount > 1500
ORDER BY o.id;
```

Результат — **18 строк**, первые пять:

```
  id  |   full_name    | order_id | amount
------+----------------+----------+---------
 2781 | Load User 2781 |     2664 | 1529.38
 2781 | Load User 2781 |     5544 | 1959.19
 2781 | Load User 2781 |    10116 | 1682.77
 2781 | Load User 2781 |    10282 | 1710.16
 2781 | Load User 2781 |    18440 | 1615.21
```

Клиент один и тот же, а строк восемнадцать — по одной на каждый его крупный заказ. Если менеджеру нужен **список клиентов**, такой результат неверен: в нём один клиент посчитан 18 раз.

**Как вернуться к «одна строка на клиента» при JOIN.** Знакомым по **теме 03** способом — `GROUP BY` по клиенту. Группировка собирает все строки с одинаковым `u.id` в одну:

```sql

SELECT u.id, u.full_name
FROM users u
INNER JOIN orders o ON o.user_id = u.id
WHERE u.id = 2781
  AND o.amount > 1500
GROUP BY u.id, u.full_name;
```

Результат — снова **одна строка**, как у `IN`.

**Тот же эффект на полном отчёте.** Вопрос «сколько всего клиентов имеют заказ дороже 1500»:

```sql

SELECT count(*) AS via_in
FROM users u
WHERE u.id IN (SELECT o.user_id FROM orders o WHERE o.amount > 1500);
```

```sql

SELECT count(*) AS via_join
FROM users u
INNER JOIN orders o ON o.user_id = u.id
WHERE o.amount > 1500;
```

| Запрос | Строк | Что на самом деле посчитано |
|---|---|---|
| через `IN` | **4 971** | клиентов — верный ответ |
| через `INNER JOIN` | **25 354** | крупных заказов, а не клиентов — **ошибка** |

Разница `25 354` против `4 971` — это ровно те самые повторы: у клиента `2781` их 18, у кого-то 2, у кого-то 1.

**Вывод.** При JOIN о повторах нужно помнить и гасить их `GROUP BY`. При `IN` с подзапросом такой ошибки не бывает в принципе: подзапрос не добавляет строк, он только отвечает «да» или «нет».

> **Забегая вперёд.** Тот же результат часто пишут короче — `SELECT DISTINCT u.id …` или с подзапросом в `FROM`. `DISTINCT` и подзапрос в `FROM` разбираются в **теме 07**, поэтому здесь используется только `GROUP BY` из темы 03.

**Правило большого пальца**

- Нужно **одно значение** для сравнения (`>`, `<`, `=`) → **scalar-подзапрос**.
- Нужен **список id** (или других ключей) → **`IN`** с подзапросом.
- Нужна проверка «**есть / нет** связи» → **`EXISTS`** / **`NOT EXISTS`**.

Примеры **4** и **7** решают одну задачу (клиенты с заказом дороже 1500) и дают **одинаковый** результат: один — через `IN`, другой — через `EXISTS`.

То же с примерами **6** и **8** (клиенты без заказов): `NOT IN` и `NOT EXISTS`.

## Подзапрос или JOIN?

Один бизнес-вопрос часто можно записать **и через JOIN, и через подзапрос**.

| Бизнес-вопрос | Через подзапрос | Через JOIN |
|---|---|---|
| «Покажи заказы, сумма которых выше средней суммы по всем заказам» | scalar в `WHERE`: `amount > (SELECT AVG(amount) FROM orders)` | обычным JOIN **не записывается**, нужны конструкции темы 07 — разбор ниже |
| «Покажи клиентов, у которых есть заказ дороже 1500» | `IN` с подзапросом по `orders` (пример 4) | `INNER JOIN orders` + `GROUP BY` — разбор ниже |
| «Покажи клиентов, у которых нет ни одного заказа» | `NOT EXISTS` с подзапросом по `orders` (пример 8) | `LEFT JOIN orders` + условие «строки заказа нет» — тема **04** |

### Первая строка таблицы: почему для JOIN нужен подзапрос в FROM

> **Внимание: этот подраздел — заглядывание вперёд.** Здесь встретятся `CROSS JOIN` и подзапрос в `FROM` — обе конструкции разбираются в **теме 07**, сейчас их знать не нужно и писать самому не требуется. Подраздел нужен только чтобы объяснить, почему в таблице выше для этого вопроса не указан обычный JOIN. **Запоминать нужно один вывод:** для сравнения с одним числом по всей таблице пишут scalar-подзапрос.

**Разберём бизнес-вопрос.** «Заказы, сумма которых выше средней» — это отчёт для менеджера: показать крупные заказы, где «крупный» определяется не фиксированной цифрой, а **средним по всей таблице**. Среднее в `reactive_study` — `1007.38`, значит нужны заказы с суммой больше `1007.38`. Само число в запрос не вписывают: завтра появятся новые заказы, среднее изменится, и запрос должен посчитать его сам.

**Через scalar-подзапрос** — одна строка кода:

```sql

SELECT o.id, o.amount
FROM orders o
WHERE o.amount > (SELECT AVG(amount) FROM orders)
ORDER BY o.amount DESC
LIMIT 5;
```

PostgreSQL один раз считает `AVG(amount)`, получает `1007.38` и сравнивает с ним каждую строку.

**Почему обычный JOIN так не умеет.** JOIN соединяет строки **одной таблицы со строками другой** по условию. А здесь сравнивать надо не с другой таблицей, а с **одним числом**, посчитанным по той же самой `orders`. Строки, в которой лежало бы это число, в базе нет — её нужно сначала **создать**.

**Как это делают через JOIN.** Подзапрос ставят в `FROM`, и он превращается в таблицу из одной строки и одного столбца — её называют **производной таблицей** (derived table):

```sql

SELECT o.id, o.amount
FROM orders o
CROSS JOIN (SELECT AVG(amount) AS avg_amount FROM orders) stats
WHERE o.amount > stats.avg_amount
ORDER BY o.amount DESC
LIMIT 5;
```

**Как читать этот запрос** (обе новые конструкции — из темы 07)

| Часть | Что происходит |
|---|---|
| `(SELECT AVG(amount) AS avg_amount FROM orders) stats` | подзапрос стоит **в `FROM`**, на месте таблицы. Он выполняется первым и даёт «таблицу» из одной строки и одного столбца: `avg_amount = 1007.38`. Слово `stats` после скобок — её имя, дальше к ней обращаются как к обычной таблице: `stats.avg_amount` |
| `CROSS JOIN` | соединение **без условия `ON`**: каждая строка слева соединяется с каждой строкой справа. Справа здесь всего одна строка, поэтому число заказов не меняется — `CROSS JOIN` просто «подвешивает» число `1007.38` к каждому заказу как дополнительный столбец |
| `WHERE o.amount > stats.avg_amount` | среднее стало обычным столбцом, и сравнение превратилось в обычное сравнение двух столбцов |

Оба запроса дают **одинаковый** результат:

```
  id   | amount
-------+---------
  7555 | 2005.00
 16109 | 2004.97
 23969 | 2004.95
 90541 | 2004.92
 13608 | 2004.90
```

**Вывод.** Для вопроса «сравнить с одним числом по всей таблице» scalar-подзапрос короче и понятнее. Вариант с `CROSS JOIN` нужен, когда посчитанное число понадобится **не только в `WHERE`, но и в `SELECT`** — например, вывести рядом и сумму заказа, и среднюю сумму, и отклонение от неё. Подробно подзапросы в `FROM` разбираются в **теме 07**.

### Вторая строка таблицы: клиенты с крупным заказом

Здесь оба способа работают одинаково хорошо — это как раз случай, когда выбор дело вкуса.

Через подзапрос:

```sql

SELECT id, full_name
FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 1500)
ORDER BY id
LIMIT 5;
```

Через JOIN — обязательно с `GROUP BY` (тема 03), иначе клиент повторится столько раз, сколько у него крупных заказов:

```sql

SELECT u.id, u.full_name
FROM users u
INNER JOIN orders o ON o.user_id = u.id
WHERE o.amount > 1500
GROUP BY u.id, u.full_name
ORDER BY u.id
LIMIT 5;
```

Здесь `GROUP BY` стоит не ради подсчётов, а именно чтобы **схлопнуть повторы**: все строки с одинаковым `u.id` собираются в одну. Это ровно тот случай, про который говорит документация PostgreSQL.

**Источник:** https://www.postgresql.org/docs/current/queries-table-expressions.html

EN:

> Grouping without aggregate expressions effectively calculates the set of distinct values in a column. This can also be achieved using the `DISTINCT` clause (see Section 7.3.3).

RU:

> Группировка без агрегатных выражений фактически вычисляет набор различных значений в столбце. Того же можно достичь с помощью предложения `DISTINCT` (см. раздел 7.3.3).

Упомянутое в цитате `DISTINCT` — более короткая запись того же самого, её разберём в **теме 07**.

**Что выбирать на практике**

- Если нужен **отчёт из нескольких таблиц** сразу (имя + сумма + артикул) — чаще **JOIN**.
- Если нужно **одно число для фильтра** или проверка «есть / нет» — часто **подзапрос**.
- На **интервью** важно уметь **оба** варианта и объяснить, что результат совпадает.

Подробнее про читаемые многошаговые запросы — **тема 07 (CTE, `WITH … AS`)**.

## Что спрашивают на интервью

Вопросы записаны так, как их формулирует интервьюер — целыми предложениями. Отвечайте вслух, потом сверяйтесь с правой колонкой.

### Основные понятия

| Вопрос интервьюера | Короткий ответ |
|---|---|
| Что такое подзапрос в SQL? | Это `SELECT`, записанный в скобках внутри другого запроса. «Подзапрос» — **общее** название для всех таких конструкций, независимо от того, сколько строк он возвращает |
| Верно ли, что подзапрос всегда возвращает ровно одно значение? | **Нет.** Ровно одно значение обязан вернуть только **scalar**-подзапрос. Подзапрос внутри `IN` возвращает столбик из любого числа строк, а внутри `EXISTS` число строк вообще не ограничено |
| Сколько строк и столбцов разрешено вернуть scalar-подзапросу? | **Одну строку и один столбец.** Если строк больше одной, PostgreSQL прерывает запрос ошибкой. Если строк ноль, ошибки нет — результатом будет NULL |
| Как, глядя на запрос, определить, является подзапрос scalar или нет? | Смотреть не на скобки, а на то, что стоит **слева от них**. Знак сравнения (`>`, `<`, `=`, `>=`, `<=`, `<>`) требует scalar. Слова `IN`, `NOT IN`, `ANY`, `SOME`, `ALL`, `EXISTS`, `NOT EXISTS` принимают набор строк |
| Какие конструкции SQL умеют принимать подзапрос, возвращающий несколько строк? | Ровно шесть: `IN`, `NOT IN`, `ANY` (он же `SOME`), `ALL`, `EXISTS`, `NOT EXISTS`. Все остальные места, где допустим подзапрос, требуют scalar |

### Различия между операторами

| Вопрос интервьюера | Короткий ответ |
|---|---|
| Чем scalar-подзапрос отличается от подзапроса внутри `IN`? | Scalar даёт **одно значение**, и с ним сравнивают напрямую. Подзапрос внутри `IN` даёт **столбик значений**, и проверяется вхождение в этот столбик |
| Чем scalar-подзапрос отличается от `EXISTS`? | Scalar возвращает **значение**, которое участвует в сравнении. `EXISTS` возвращает только **«да» или «нет»** — содержимое строк ему не важно |
| Чем `IN` с подзапросом отличается от `EXISTS` с подзапросом? | `IN` строит **список значений** (обязательно один столбец) и ищет в нём левое значение. `EXISTS` ничего не сравнивает — он проверяет только, **вернул ли подзапрос хотя бы одну строку** |
| Можно ли использовать подзапрос в операторе `BETWEEN`? | Да, но `BETWEEN` набор строк не принимает. Каждая из двух границ должна быть **отдельным scalar-подзапросом**: `BETWEEN (SELECT …) AND (SELECT …)` |
| Как записать `IN` и `NOT IN` через операторы `ANY` и `ALL`? | `IN` — это то же самое, что `= ANY`. `NOT IN` — то же самое, что `<> ALL` |
| В чём разница между `> ANY` и `> ALL`? | `> ANY` — «больше **хотя бы одного** значения из набора», то есть больше минимума. `> ALL` — «больше **каждого** значения из набора», то есть больше максимума |

### Оператор EXISTS

| Вопрос интервьюера | Короткий ответ |
|---|---|
| Что именно делает оператор `EXISTS`? | Выполняет подзапрос и возвращает «истину», если тот вернул **хотя бы одну** строку, и «ложь», если не вернул ни одной |
| Почему внутри `EXISTS` принято писать `SELECT 1`, а не конкретный столбец? | Потому что `EXISTS` смотрит только на **факт наличия** строки, а её содержимое не вычисляет. Единица стоит как заглушка — синтаксис `SELECT` требует хоть какое-то выражение. Написать `SELECT p.id` можно, результат и план запроса не изменятся |

### NOT IN и ловушка NULL

| Вопрос интервьюера | Короткий ответ |
|---|---|
| В чём заключается опасность оператора `NOT IN`? | `NOT IN` разворачивается в цепочку сравнений «не равно», соединённых через `AND`. Любое сравнение с NULL даёт не «ложь», а NULL, и вся цепочка становится NULL. `WHERE` пропускает **только** «истину», поэтому такая строка молча исчезает из отчёта — без ошибки и без предупреждения |
| Как правильно обойти ловушку NULL в `NOT IN`? | Основной способ — писать `NOT EXISTS`: он проверяет наличие строки, а не сравнивает значения, и NULL его не ломает. Если `NOT IN` нужен обязательно, добавляют `IS NOT NULL` внутрь подзапроса и в `WHERE` внешнего запроса — но второе **меняет постановку задачи**, так как исключает из отчёта строки с пустым ключом |
| Почему `NOT EXISTS` считается безопаснее `NOT IN`? | `NOT EXISTS` не сравнивает левое значение со списком. Он выполняет подзапрос и считает строки. Ответ «строк ноль» однозначен, трёхзначная логика «истина / ложь / неизвестно» здесь не возникает |

### Корреляция и выбор между подзапросом и JOIN

| Вопрос интервьюера | Короткий ответ |
|---|---|
| Какой подзапрос называют коррелированным? | Тот, внутри которого есть ссылка на столбец **внешнего** запроса. Из-за этого подзапрос выполняется заново для каждой строки внешнего запроса — см. примеры 3 и 7 |
| Если подзапрос уже посчитан в списке `SELECT`, нужно ли повторять его в `ORDER BY`? | **Нет, повторять не нужно.** В `SELECT` подзапросу дают псевдоним, и в `ORDER BY` указывают этот псевдоним: `ORDER BY order_count`. Если написать подзапрос в `ORDER BY` второй раз, запрос станет длиннее и труднее для чтения без всякой выгоды |
| Когда выбирать подзапрос, а когда JOIN? | Оба часто дают одинаковый результат. JOIN берут, когда в отчёт нужны **столбцы из нескольких таблиц** сразу. Подзапрос берут, когда нужно **одно число для фильтра** или проверка «есть связанная строка или нет» |
| Почему JOIN может вернуть больше строк, чем подзапрос с `IN`, для одного и того же вопроса? | JOIN **склеивает** строки: если у клиента 18 подходящих заказов, он попадёт в результат 18 раз. `IN` только отвечает «да / нет» для каждой строки внешней таблицы и число строк не увеличивает. При JOIN повторы гасят через `GROUP BY` |

## Типичные ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| «Любой подзапрос = одно значение» | путают scalar с `IN` / `EXISTS` | смотреть, какой оператор стоит **перед** скобками |
| Scalar вернул 2+ строки | PostgreSQL выдаст ошибку `more than one row returned by a subquery used as an expression` | взять агрегат (`MAX`, `MIN`, `AVG`), либо `LIMIT 1`, либо перейти на `IN` |
| Забыли скобки вокруг подзапроса | синтаксическая ошибка | подзапрос всегда внутри `( … )` |
| `NOT IN` по столбцу, где бывает NULL | строки «исчезают» из отчёта | `NOT EXISTS`, либо добавить в подзапрос условие `IS NOT NULL` |
| Проверяют наличие через `COUNT(*) > 0` | лишняя работа: считает **все** строки, хотя нужна только первая | для «есть / нет» — `EXISTS` с `SELECT 1` |
| Соединяют таблицы, когда нужна только проверка | один клиент даёт много одинаковых строк | `IN` или `EXISTS` **без** JOIN; если JOIN нужен — схлопнуть повторы через `GROUP BY` |
| Один и тот же подзапрос в `SELECT` и в `ORDER BY` | число считают дважды | в `ORDER BY` поставить **alias** столбца из `SELECT` |
