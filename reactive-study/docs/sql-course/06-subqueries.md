## Что изучаем

В темах 01–05 вы писали **один** запрос к одной или нескольким таблицам.

Иногда задача звучит так:

- «Заказы **дороже среднего**» — но среднее нужно **сначала посчитать**.
- «Клиенты, у которых **есть** заказы» — список id лежит в другой таблице.
- «Клиенты **без** заказов» — нужно проверить, что подходящих строк **нет**.

Для этого внутри запроса пишут **ещё один** запрос — **подзапрос** (subquery).

| Вид | Вопрос, на который отвечает | Пример |
|---|---|---|
| **Scalar** | «Какое **одно число** (или текст)?» | средняя сумма заказа |
| **IN** | «Значение **входит** в список из другого запроса?» | клиенты с заказом > 1000 |
| **EXISTS** | «**Нашлась** хотя бы одна строка?» | клиенты, у которых есть заказ |

Таблицы в примерах — `users` и `orders` базы `reactive_study`.

## Что такое подзапрос

**Подзапрос** — это `SELECT`, записанный **внутри скобок** `( … )` в другом запросе.

```text
Внешний запрос
    └── Внутренний запрос (подзапрос) в скобках
```

**Аналогия.** Вы заполняете отчёт (внешний запрос).

Перед тем как вписать число в ячейку, вы **открываете вторую таблицу**, считаете там одно значение и **подставляете** его — это подзапрос.

**Источник:** https://www.postgresql.org/docs/current/sql-expressions.html#SQL-SYNTAX-SCALAR-SUBQUERIES

EN:

> A scalar subquery is an ordinary `SELECT` query in parentheses that returns exactly one row with one column.

RU:

> Скalar-подзапрос — обычный запрос `SELECT` в скобках, который возвращает ровно одну строку с одним столбцом.

Подзапрос может стоять:

| Место | Зачем |
|---|---|
| В `SELECT` | добавить столбец, посчитанный из другой таблицы |
| В `WHERE` | сравнить с одним числом или проверить `IN` / `EXISTS` |
| В `FROM` | временная «мини-таблица» (подробнее — в **теме 07**, CTE) |

## Scalar-подзапрос — одно значение

**Scalar** (скalar) — «одно значение»: одна строка, один столбец.

### Пример 1 — заказы дороже среднего

**Задача.** Показать заказы, сумма которых **выше средней** по всей таблице `orders`.

Сначала нужно узнать среднее — это отдельный маленький запрос внутри условия:

```sql

SELECT id, amount
FROM orders
WHERE amount > (
    SELECT AVG(amount)
    FROM orders
)
ORDER BY amount DESC
LIMIT 10;
```

**Как читать по шагам**

| Шаг | Что происходит |
|---|---|
| 1 | Подзапрос `(SELECT AVG(amount) FROM orders)` считает **одно число** — среднюю сумму по ~100 000 заказам |
| 2 | Внешний запрос сравнивает `amount` каждого заказа с этим числом |
| 3 | В результат попадают только заказы **строго больше** среднего |
| 4 | `ORDER BY … LIMIT 10` — десять самых дорогих из отобранных |

**Источник:** https://www.postgresql.org/docs/current/sql-expressions.html#SQL-SYNTAX-SCALAR-SUBQUERIES

EN:

> It is an error to use a query that returns more than one row or more than one column as a scalar subquery. (But if, during a particular execution, the subquery returns no rows, there is no error; the scalar result is taken to be null.)

RU:

> Ошибка — использовать в качестве скalar-подзапроса запрос, который возвращает больше одной строки или больше одного столбца. (Если при конкретном выполнении подзапрос не вернул ни одной строки, ошибки нет: скalar-результат считается равным NULL.)

| Ситуация | Что будет |
|---|---|
| Подзапрос вернул **ровно одну** строку с одним числом | всё работает |
| Подзапрос вернул **0** строк | значение = **NULL** (не ошибка) |
| Подзапрос вернул **2+** строк | **ошибка** выполнения |

### Пример 2 — сравнение с одним конкретным заказом

**Задача.** Найти заказы, сумма которых **больше**, чем у заказа **2**.

```sql

SELECT id, amount
FROM orders
WHERE amount > (
    SELECT amount
    FROM orders
    WHERE id = 2
)
ORDER BY amount DESC
LIMIT 10;
```

Подзапрос по `id = 2` всегда возвращает **одну** строку с одним столбцом `amount` — это корректный scalar.

## Scalar в SELECT — «посчитать для каждой строки»

Подзапрос в списке `SELECT` добавляет **новый столбец** к каждой строке внешнего запроса.

### Пример 3 — число заказов у каждого клиента

**Задача.** Для первых пяти клиентов показать имя и **сколько у каждого заказов**.

```sql

SELECT u.id,
       u.full_name,
       (
           SELECT COUNT(*)
           FROM orders o
           WHERE o.user_id = u.id
       ) AS order_count
FROM users u
WHERE u.id <= 5
ORDER BY u.id;
```

**Как читать**

| Часть | Смысл |
|---|---|
| `FROM users u` | внешний запрос перебирает клиентов |
| `WHERE o.user_id = u.id` **внутри** подзапроса | подзапрос **ссылается** на текущую строку `u` |
| `COUNT(*)` | считает заказы **только этого** клиента |

Такой подзапрос называют **коррелированным**: внутренний запрос «знает» про строку снаружи.

**Источник:** https://www.postgresql.org/docs/current/sql-expressions.html#SQL-SYNTAX-SCALAR-SUBQUERIES

EN:

> The subquery can refer to variables from the surrounding query, which will act as constants during any one evaluation of the subquery.

RU:

> Подзапрос может ссылаться на переменные из окружающего запроса; при каждой отдельной оценке подзапроса они ведут себя как константы.

**На практике** для «клиент + число заказов» часто пишут `LEFT JOIN` + `GROUP BY` (вы это уже умеете из тем 03–04). Подзапрос в `SELECT` — **другой способ** записать ту же идею; на интервью спрашивают оба.

## IN с подзапросом — список из другой таблицы

В **теме 02** вы уже видели `IN` со **списком значений**:

```sql

WHERE id IN (1, 2, 3)
```

Тот же `IN` работает, если справа — **подзапрос**, который возвращает **один столбец** и **много строк**:

```sql

WHERE id IN (SELECT … FROM …)
```

**Источник:** https://www.postgresql.org/docs/current/functions-subquery.html

EN:

> The right-hand side is a parenthesized subquery, which must return exactly one column. The left-hand expression is evaluated and compared to each row of the subquery result. The result of `IN` is “true” if any equal subquery row is found.

RU:

> Правая часть — подзапрос в скобках, который должен вернуть ровно один столбец. Левое выражение сравнивается с каждой строкой результата подзапроса. Результат `IN` — «истина», если найдена хотя бы одна равная строка подзапроса.

### Пример 4 — клиенты с «крупным» заказом

**Задача.** Найти клиентов, у которых **хотя бы один** заказ на сумму **больше 1500**.

```sql

SELECT id, full_name, email
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
    WHERE amount > 1500
)
ORDER BY id
LIMIT 10;
```

**Как читать**

| Шаг | Что происходит |
|---|---|
| 1 | Подзапрос собирает все `user_id` заказов с `amount > 1500` |
| 2 | Внешний запрос оставляет клиентов, чей `id` **есть** в этом списке |
| 3 | Один клиент с несколькими крупными заказами всё равно попадёт **один раз** |

**Эквивалент через JOIN** (для понимания, не обязательно писать так):

```sql

SELECT DISTINCT u.id, u.full_name, u.email
FROM users u
INNER JOIN orders o ON o.user_id = u.id
WHERE o.amount > 1500
ORDER BY u.id
LIMIT 10;
```

Оба запроса отвечают на один бизнес-вопрос. Разница — **форма записи**.

### Пример 5 — заказы клиентов из списка email

**Задача.** Показать заказы учебных клиентов с email `join-demo-no-orders-1@…` и `join-demo-single-order@…`.

Список id заранее не знаем — берём из `users`:

```sql

SELECT o.id, o.amount, o.status
FROM orders o
WHERE o.user_id IN (
    SELECT id
    FROM users
    WHERE email IN (
        'join-demo-no-orders-1@example.com',
        'join-demo-single-order@example.com'
    )
)
ORDER BY o.id
LIMIT 10;
```

Здесь `IN` с **подзапросом** снаружи и `IN` со **списком** внутри — обычная комбинация.

## NOT IN с подзапросом и ловушка NULL

`NOT IN` — «значение **не входит** в список из подзапроса».

### Пример 6 — клиенты без заказов (учебные)

**Задача.** Найти учебных клиентов **без единого заказа** (email начинается с `join-demo-no-orders`).

```sql

SELECT id, full_name, email
FROM users
WHERE email LIKE 'join-demo-no-orders%'
  AND id NOT IN (
      SELECT user_id
      FROM orders
  )
ORDER BY email;
```

**Как читать**

| Часть | Смысл |
|---|---|
| `email LIKE 'join-demo-no-orders%'` | только учебные «спящие» клиенты |
| `id NOT IN (SELECT user_id FROM orders)` | id **нет** среди тех, кто что-то заказывал |

Для этой проверки `orders.user_id` **всегда заполнен** (NOT NULL) — `NOT IN` работает предсказуемо.

### Ловушка: NULL внутри NOT IN

**Источник:** https://www.postgresql.org/docs/current/functions-subquery.html

EN:

> Note that if the left-hand expression yields null, or if there are no equal right-hand values and at least one right-hand row yields null, the result of the `NOT IN` construct will be null, not true.

RU:

> Если левое выражение даёт NULL, или среди правых значений нет равных и хотя бы одна правая строка даёт NULL, результат `NOT IN` будет NULL, а не «истина».

**Простыми словами:** если подзапрос в `NOT IN` может вернуть **NULL** в своём столбце, результат `NOT IN` становится **ненадёжным** — строки могут «пропасть» из отчёта.

Опасный пример (не для копирования как решение, а для понимания):

```sql

-- product_id у части заказов NULL!
SELECT id
FROM orders
WHERE product_id NOT IN (
    SELECT id FROM products
);
```

Если бы в подзапросе оказался NULL — логика сломалась бы. На интервью безопаснее:

- `NOT EXISTS`, или
- `NOT IN (SELECT … WHERE … IS NOT NULL)`.

## EXISTS — «есть ли хотя бы одна строка?»

`EXISTS (подзапрос)` отвечает **да или нет**: вернул ли подзапрос **хотя бы одну строку**.

Содержимое столбцов **не важно** — поэтому пишут `SELECT 1`:

```sql

EXISTS (SELECT 1 FROM … WHERE …)
```

**Источник:** https://www.postgresql.org/docs/current/functions-subquery.html

EN:

> If it returns at least one row, the result of `EXISTS` is “true”; if the subquery returns no rows, the result of `EXISTS` is “false”.

RU:

> Если возвращена хотя бы одна строка, результат `EXISTS` — «истина»; если подзапрос не вернул строк, результат `EXISTS` — «ложь».

EN:

> Since the result depends only on whether any rows are returned, and not on the contents of those rows, the output list of the subquery is normally unimportant. A common coding convention is to write all `EXISTS` tests in the form `EXISTS(SELECT 1 WHERE ...)`.

RU:

> Поскольку результат зависит только от того, вернулись ли строки, а не от их содержимого, список столбцов подзапроса обычно не важен. Распространённая запись: `EXISTS(SELECT 1 WHERE …)`.

В **теме 05** вы уже встречали `EXISTS` внутри `ON` при JOIN — там та же логика «есть / нет».

### Пример 7 — клиенты, у которых есть заказы

**Задача.** Список клиентов, у которых **есть хотя бы один** заказ (первые 10 по id).

```sql

SELECT u.id, u.full_name
FROM users u
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.user_id = u.id
)
ORDER BY u.id
LIMIT 10;
```

**Как читать**

| Шаг | Что происходит |
|---|---|
| 1 | Внешний запрос берёт клиента `u` |
| 2 | Подзапрос ищет **хотя бы один** заказ с `user_id = u.id` |
| 3 | Нашёл — `EXISTS` = true, клиент попадает в результат |
| 4 | Не нашёл — клиент отбрасывается |

Подзапрос **коррелированный**: `u.id` приходит из строки снаружи.

## NOT EXISTS — «нет ни одной подходящей строки»

`NOT EXISTS` — «подзапрос **не нашёл** ни одной строки».

### Пример 8 — учебные клиенты без заказов

**Задача.** Те же «спящие» клиенты, что в примере 6, но через `NOT EXISTS`:

```sql

SELECT u.id, u.full_name, u.email
FROM users u
WHERE u.email LIKE 'join-demo-no-orders%'
  AND NOT EXISTS (
      SELECT 1
      FROM orders o
      WHERE o.user_id = u.id
  )
ORDER BY u.email;
```

**Смысл:** для каждого клиента проверяем — **нет ни одного** заказа с его id.

`NOT EXISTS` **не ломается** из‑за NULL так, как `NOT IN` — поэтому его часто prefer на собеседованиях для «найти строки без пары».

## IN и EXISTS — когда что выбирать

Обе конструкции решают похожие задачи «**есть связанные строки** в другой таблице».

| | `IN (SELECT …)` | `EXISTS (SELECT 1 …)` |
|---|---|---|
| **Вопрос** | «Значение **в списке**?» | «**Есть** хотя бы одна строка?» |
| **Что возвращает подзапрос** | столбец значений | только факт «нашлось / нет» |
| **NULL в подзапросе** | для `NOT IN` — опасно | обычно безопаснее |
| **Дубликаты в подзапросе** | не мешают | не мешают |

**Правило большого пальца**

- Нужно **одно значение** для сравнения (`>`, `<`, `=`) → **scalar-подзапрос**.
- Нужен **список id** (или других ключей) → **`IN (SELECT …)`**.
- Нужна проверка «**есть / нет** связи» → **`EXISTS` / `NOT EXISTS`**.

На вашей базе примеры 4 и 7 (клиенты с заказами) дадут **один и тот же набор id** — это нормально.

## Подзапрос или JOIN?

Один бизнес-вопрос часто можно записать **и через JOIN, и через подзапрос**.

| Задача | Подзапрос | JOIN |
|---|---|---|
| Заказы дороже среднего | `WHERE amount > (SELECT AVG…)` | JOIN с подзапросом в `FROM` (тема 07) |
| Клиенты с крупным заказом | `WHERE id IN (SELECT user_id …)` | `INNER JOIN orders …` + `DISTINCT` |
| Клиенты без заказов | `NOT EXISTS (…)` | `LEFT JOIN … WHERE o.id IS NULL` (тема 04) |

**Что выбирать на практике**

- Если нужен **отчёт из нескольких таблиц** сразу (имя + сумма + артикул) — чаще **JOIN**.
- Если нужно **одно число для фильтра** или проверка «есть / нет» — часто **подзапрос**.
- На **интервью** важно уметь **оба** варианта и объяснить, что результат совпадает.

Подробнее про читаемые многошаговые запросы — **тема 07 (CTE, `WITH … AS`)**.

## Что спрашивают на интервью

| Вопрос | Короткий ответ |
|---|---|
| Что такое подзапрос? | `SELECT` в скобках внутри другого запроса |
| Чем scalar отличается от `IN`? | Scalar — **одно** значение; `IN` — **много** значений в одном столбце |
| Сколько строк может вернуть scalar? | **Одну**; иначе ошибка (0 строк → NULL) |
| Что делает `EXISTS`? | «Истина», если подзапрос вернул **≥ 1** строку |
| Зачем `SELECT 1` в EXISTS? | Столбцы не нужны — важен только факт строки |
| Чем `IN` отличается от `EXISTS`? | `IN` сравнивает **значение со списком**; `EXISTS` — «**нашлась ли** строка» |
| Опасность `NOT IN`? | NULL в списке подзапроса → неожиданный результат |
| Коррелированный подзапрос? | Внутренний запрос ссылается на строку **внешнего** (`o.user_id = u.id`) |
| Подзапрос vs JOIN? | Часто эквивалентны; JOIN — для широкого отчёта, подзапрос — для фильтра и одного числа |

## Типичные ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| Scalar вернул 2+ строки | PostgreSQL выдаст ошибку | добавить `LIMIT 1`, или агрегат `MAX` / `MIN`, или `IN` |
| Забыли скобки вокруг подзапроса | синтаксическая ошибка | `WHERE x IN (SELECT …)` |
| `NOT IN (SELECT product_id …)` при NULL в столбце | строки «исчезают» | `NOT EXISTS` или фильтр `WHERE product_id IS NOT NULL` в подзапросе |
| Путают `EXISTS` и `COUNT(*)` в `WHERE` | `COUNT(*) > 0` в подзапросе без `GROUP BY` считает **все** строки | для «есть / нет» — `EXISTS (SELECT 1 …)` |
| Дублируют строки с `IN` + лишние JOIN | один клиент — много одинаковых строк | достаточно `IN` / `EXISTS` **без** JOIN, или `DISTINCT` |
