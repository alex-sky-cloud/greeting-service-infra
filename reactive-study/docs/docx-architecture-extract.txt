Базовые компоненты: фундамент платформыЧтобы понять, как Spring WebFlux обрабатывает HTTP-запрос, полезно провести аналогию с работой обычной операционной системы Linux. Представьте себе большой call-центр: у входа стоит диспетчер, который принимает звонки и передаёт их операторам, а операторы работают за своими столами, не бегая по всему офису. Именно так работает связка Netty и Linux — от приёма сетевого соединения до его обработки.Аналогия с call-центром: file descriptor = номер стола, Channel = карточка клиента, EventLoop = оператор.1.1 Channel (channel — «канал») в Netty и в операционной системеВ операционной системе Linux сетевое соединение представлено socket (сокет — «гнездо», точка подключения) — особым ресурсом ядра, у которого есть числовой идентификатор, называемый file descriptor (файловый дескриптор — «номер файла»).Сокет — это один из видов ресурсов ядра (сетевой endpoint), а файловый дескриптор — это номер, по которому процесс обращается к этому сокету.Через этот номер ядро ОС знает, куда писать входящие данные и откуда брать исходящие.В Netty поверх этого сокета создаётся объект Channel (channel — «канал»), который является программной оболочкой над файловым дескриптором операционной системы.Важно: сам файловый дескриптор — это не «пакет данных», а целое число-индекс в таблице открытых ресурсов процесса. В таблице дескрипторов по этому номеру лежит ссылка на файловый объект ядра (struct file), который хранит состояние соединения, буферы и ссылку на сам сокет. - Файловый дескриптор — это просто число, но за этим числом спрятана внутренняя структура ядра.  Самих данных в дескрипторе нет — это не буфер, не «пакет», это указатель по номеру. Эта структура живёт в памяти, доступной только коду ядра, и все операции с ней идут через системные вызовы, а пользовательский процесс видит только маленький «ключик» — файловый дескриптор.Картина такова: клиент подключается к серверу, Linux создаёт сокет как ресурс процесса, присваивает ему номер, а Netty через Channel и event loop начинает работать с этим номером и связанным с ним состоянием.Linux создаёт сокет и даёт процессу числовой идентификатор — файловый дескриптор.В таблице дескрипторов по этому номеру лежит ссылка на файловый объект ядра, который ссылается на сокет и хранит состояние соединения.Netty создаёт Channel, в котором хранит этот файловый дескриптор (через JDK NIO) и всю связанную с ним логику (pipeline, состояние), чтобы удобно читать, писать и обрабатывать события.АналогияПонятиеАналогия из call-центраФайловый дескрипторНомер стола, за которым сидит клиентChannelКарточка с данными об этом столе (кто сидит, что нужно сказать, куда передать ответ), которую держит в руках оператор NettyОфициальная документация NettyEN: A channel provides a user: ChannelPipeline which handles all I/O events and requests associated with the channel. Это как охранник на въезде, который не бегает к каждой машине лично, а видит на экране список всех, кто подал сигнал.На уровне Netty за каждым Channel закреплён ChannelPipeline (pipeline — «конвейер») — упорядоченная цепочка объектов ChannelHandler (handler — «обработчик»). Когда ядро ОС сообщает через epoll о новых данных, Netty запускает событие внутри Pipeline, и данные последовательно проходят через все handler'ы, как деталь на заводском конвейере проходит через несколько станков.EN: A ChannelHandler is supposed to interact with the ChannelPipeline it belongs to via a context object. Используя этот объект, ChannelHandler может передавать события вверх или вниз по цепочке, а также динамически изменять сам конвейер.1.3 EventLoopGroup: разница между Boss и Worker EventLoopGroup (event loop group — «группа событийных циклов») — это пул потоков, где каждый поток управляется отдельным объектом EventLoop (event loop — «событийный цикл»). Каждый EventLoop работает по одной и той же схеме: - бесконечно крутит цикл, в котором проверяет через epoll, у каких файловых дескрипторов появились готовые события, обрабатывает эти события, а затем выполняет накопленные задачи (task queue) — то есть выступает одновременно диспетчером событий и исполнителем задач на одном потоке.Источник: https://aws.plainenglish.io/netty-core-component-eventloop-source-code-analysis-cb7e53adc8e5"An EventLoop will be driven by a Thread that will never change, and tasks (Runnable or Callable) can be directly submitted to the EventLoop for execution."RU:"EventLoop управляется потоком, который никогда не меняется, и задачи (Runnable или Callable) можно напрямую отправлять в EventLoop для выполнения."---Netty использует две отдельные группы событийных циклов, потому что у них принципиально разная нагрузка: - Boss (boss — «начальник») и - Worker (worker — «рабочий»).Источник: https://netty.io/wiki/user-guide-for-4.x.html"The first one, often called 'boss', accepts an incoming connection. Сценарий A — реактивная цепочка без блокирующих вызовов Это «идеальный» путь запроса в реактивном приложении: - от момента, когда клиент открывает соединение, до момента, когда сервер отправляет ответ, — всё происходит на одном и том же потоке event loop, без единого переключения контекста. \2.1 Пошаговое описание схемы1. Client Socket (клиентский сокет) инициирует TCP-соединение путём отправки SYN-пакета на сервер.* SYN-пакет (SYN — сокращение от synchronize, «синхронизировать») — это специальный TCP-пакет с установленным флагом SYN, который клиент отправляет серверу первым, чтобы начать установку соединения (первый шаг классического «тройного рукопожатия», three-way handshake)Тройное рукопожатие (three-way handshake) — это обмен из трёх пакетов, с помощью которого клиент и сервер устанавливают TCP-соединение перед началом передачи данных.SYN — клиент отправляет серверу пакет с флагом SYN и своим начальным номером последовательности, «прошу соединение».SYN-ACK — сервер отвечает пакетом с флагами SYN+ACK: подтверждает получение (ACK) и передаёт свой собственный начальный номер (SYN).ACK — клиент подтверждает получение ответа сервера, после чего соединение переходит в состояние ESTABLISHED и можно передавать данные2. Boss EventLoop принимает соединение (accept()), создаёт новый Channel и регистрирует его в одном из потоков Worker EventLoop — эта регистрация выполняется один раз для каждого соединения и дальше поток не меняется.3. Worker EventLoop через механизм epoll получает сигнал, что в сокете появились данные для чтения, и передаёт их в ChannelPipeline — цепочку handler'ов, которые декодируют байты в объект HTTP-запроса.4. HttpHandler передаёт запрос в DispatcherHandler WebFlux — центральный диспетчер, который находит подходящий обработчик (аналог: - администратор в call-центре, который смотрит по номеру звонящего, и понимает к какому специалисту его направить) и вызывает данный подходящий обработчик.2.2 Подписка (subscribe) и callback'и onNext / onComplete / onError Когда обработчик возвращает Mono или Flux (реактивные типы данных, представляющие «обещание одного значения в будущем» или «поток из нескольких значений в будущем» соответственно), сама по себе цепочка операторов ничего не делает — это просто описание того, что нужно сделать, как чертёж здания, а не само здание. Реальная работа запускается только вызовом метода subscribe() (subscribe — «подписаться»), который регистрирует набор callback-функций (callback — «функция обратного вызова»):  - onNext (вызывается на каждый новый элемент данных), onComplete (вызывается при успешном завершении потока) и onError (вызывается при ошибке).Что вообще такое callback-функция в этом контекстеCallback (буквально «функция обратного вызова») — это просто функция, которую ты передаёшь в другой код заранее, а он сам вызовет её позже, когда наступит нужное событие. Ты не вызываешь эту функцию сам — её вызывает библиотека (Reactor), когда у неё появляется повод.Где эти callback'и в твоём кодеВот твой код:orderMono.subscribe(        response -> log.info("onNext: заказ найден {}", response.getBody()),        error -> log.error("onError: ошибка получения заказа", error),        () -> log.info("onComplete: обработка запроса завершена")Метод subscribe() в Reactor принимает до трёх лямбда-выражений (анонимных функций) по позиции — и именно они и есть три твоих callback'а:Первая лямбда response -> log.info(...) — это твоя реализация onNext().Вторая лямбда error -> log.error(...) — это твоя реализация onError().Третья лямбда () -> log.info(...) — это твоя реализация onComplete(). Слова "onNext", "onComplete", "onError" в твоём коде — это просто текст внутри строк лога, они не более чем подпись для человека, читающего логи. Реально эти три функции определены Reactor Core как методы интерфейса Subscriber, а subscribe() с тремя аргументами — это удобная сокращённая форма, которая сама оборачивает твои лямбды в объект, реализующий этот интерфейс.Источник: https://projectreactor.io/docs/core/3.4.7-SNAPSHOT/reference"As in the Reactive Streams spec, these three types of signal translate to calls to a downstream Subscriber's onNext, onComplete, and onError methods."RU:"Как и в спецификации Reactive Streams, эти три типа сигналов преобразуются в вызовы методов onNext, onComplete и onError у нижестоящего Subscriber."Что значит "вызывается на каждый новый элемент данных" Это буквально значит: если бы у тебя был `Flux<Order>` (поток из нескольких заказов, а не один), то твоя лямбда `response -> log.info(...)` вызвалась бы отдельно для каждого заказа в этом потоке — один раз на первый заказ, ещё раз на второй, и так далее, пока элементы не закончатся. У тебя в примере `Mono<ResponseEntity<Order>>` — а Mono гарантированно испускает максимум один элемент, поэтому твоя onNext-лямбда сработает не больше одного раза.Источник: https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html"Most Mono implementations are expected to immediately call Subscriber.onComplete() after having called Subscriber#onNext(T)."RU:"Ожидается, что большинство реализаций Mono вызовут Subscriber.onComplete() сразу же после вызова Subscriber#onNext(T)."Порядок вызовов внутриДля данногго конкретного примера с успешным поиском заказа, события идут строго в таком порядке:Reactor находит заказ в базе → вызывает onNext-лямбду ровно один раз, передав ей найденный ResponseEntity.Сразу после этого, так как Mono больше ничего не пришлёт, Reactor автоматически вызывает твою onComplete-лямбду — без аргументов, просто как сигнал "поток закончился успешно". Если бы при обращении к базе произошла ошибка (например, БД недоступна), сработал бы другой путь:Reactor перехватывает исключение внутри цепочки операторов.Вместо onNext и onComplete вызывается только onError-лямбда, с этим исключением в качестве аргумента — onNext и onComplete в этом случае вообще не срабатывают, поток считается завершённым с ошибкой.Источник: https://habr.com/ru/companies/funcorp/articles/359194/"В Reactor исключения воспринимаются как terminal event (терминальное событие). В качестве вызывающего потока — это тот же Worker EventLoop, который принял исходные байты данного запроса. Это похоже на курьера, который сам довозит посылку от склада до двери клиента, не передавая её другому курьеру на полпути — меньше передач, меньше задержек.EN: Obtaining a Flux or a Mono does not necessarily mean that it runs in a dedicated Thread. Instead, most operators continue working in the Thread on which the previous operator executed.https://projectreactor.io/docs/core/release/reference/coreFeatures/schedulers.htmlRU:  Получение Flux или Mono не означает, что они выполняются в выделенном потоке. Большинство операторов продолжают работать в том потоке, в котором выполнялся предыдущий оператор.2.4 Масштабируемость при малом числе потоков Поскольку один и тот же поток обслуживает запрос от начала до конца без блокировок, серверу не нужно держать отдельный поток на каждое подключение (как это делает классическая модель «один поток — один запрос»).  Небольшое число Worker-потоков (обычно равное числу ядер процессора) способно обслуживать тысячи одновременных соединений, потому что пока один запрос ждёт данные из сети, тот же поток успевает обработать события других соединений.  Это похоже на одного бармена, который принимает заказы у нескольких столиков одновременно, не дожидаясь, пока каждый гость определится с выбором — он просто переключается к следующему готовому заказу.3. Сценарий B — блокирующий вызов к базе данныхИногда приложению приходится использовать библиотеку, которая не умеет работать асинхронно — классический пример: JDBC (Java Database Connectivity — «подключение к базе данных на Java») для обращения к реляционной базе данных.  Такой вызов блокирует поток до получения результата. Ниже показана схема того, как реактивное приложение аккуратно «отодвигает» такую операцию в сторону, чтобы не заблокировать event loop.3.1 Почему блокирующий JDBC-вызов нельзя выполнять на event loop-потокеEvent loop-поток обслуживает не одно, а множество соединений одновременно, постоянно переключаясь между ними с помощью epoll. Если этот поток «застрянет» на блокирующем JDBC-вызове, ожидая ответа от базы данных, все остальные подключения, назначенные на этот же поток, замрут — как если бы диспетчер такси лично поехал везти одного клиента и перестал распределять заказы для всех остальных.EN: The worker thread... must never block. That is, it cannot call wait(), or sleep(), or await results from a Future, or things like that. The reason is that doing this prevents the worker thread (the event loop) from servicing other requests.https://groups.google.com/g/grpc-io/c/LrnAbWFozb0RU: Рабочий поток... никогда не должен блокироваться. То есть он не может вызывать wait(), sleep() или ожидать результат Future и подобное. Механически это происходит не потому, что "поток помнит своё соединение", а потому, что сам Netty обнаруживает, что вызов пришёл не из потока event loop, и автоматически ставит задачу записи в очередь правильного event loop, гарантируя, что операции с этим Channel всегда сериализуются на одном и том же потоке.3.3 Возврат результата обратно в контекст исходного ChannelПосле того как JDBC-запрос завершился на потоке boundedElastic, Reactor вызывает соответствующий callback onNext() на этом же потоке. Если далее по цепочке стоит publishOn(), последующая обработка (например, расшифровка данных или генерация PDF) переключается на указанный Scheduler — как правило, на parallel() для вычислительной нагрузки, а не напрямую на event loop.Финальная запись HTTP-ответа клиенту в любом случае выполняется не на том потоке, где завершилась бизнес-логика, а на конкретном потоке worker-пула Reactor Netty, который жёстко закреплён за данным Channel. Если попытка записи приходит с "чужого" потока — будь то boundedElastic или parallel — сам Netty обнаруживает это и автоматически перенаправляет задачу записи в очередь правильного event loop, а не выполняет её напрямую с текущего потока.Источник: https://netty.io/4.2/xref/io/netty/channel/AbstractChannel.html"eventLoop().execute(task);"RU:Если операция с Channel вызвана не из того потока, что зарегистрирован за этим Channel, Netty не выполняет её напрямую, а передаёт задачу в очередь именно того event loop, который закреплён за данным Channel.Источник: https://stackoverflow.com/questions/50637176/netty-channel-and-thread-and-eventloop"Sharing the same EventLoop for the server and client allows to handle both with the same Thread which means you can transfer data between both without context-switch."RU:"Использование одного и того же EventLoop для сервера и клиента позволяет обрабатывать оба конца одним и тем же потоком, что означает передачу данных между ними без переключения контекста."Аналогия:  это как курьер, который забрал груз со склада (boundedElastic), передал его в сортировочный центр для обработки (parallel), но финальную доставку клиенту в его конкретную квартиру всё равно выполняет только тот курьер, который закреплён именно за этим домом (поток event loop, держащий Channel) — даже если груз прошёл через несколько разных промежуточных станций, последний шаг доставки всегда возвращается к "своему" курьеру.3.4 Риски при неправильной настройке пулаЕсли размер boundedElastic слишком мал по сравнению с числом одновременных блокирующих запросов, новые задачи начнут копиться в очереди и время ответа резко возрастёт — это называется истощением потоков (thread starvation).  Ещё более опасная ошибка — забыть вызвать subscribeOn() вовсе: тогда блокирующий вызов выполнится прямо на event loop-потоке, что вызовет деградацию всего сервера, потому что один медленный запрос к базе данных заблокирует обработку сотен других несвязанных запросов.EN: boundedElastic()... will use thread pool with a default number of threads number of CPU cores x 10 and default queue size of 100000 per thread.https://stackoverflow.com/questions/61304762/difference-between-boundedelastic-vs-parallel-schedulerRU: boundedElastic()... по умолчанию использует пул потоков с числом потоков, равным числу ядер процессора, умноженному на 10, и очередью по умолчанию на 100 000 задач на каждый поток.4. Сценарий C — вызов удалённой системы без реактивного стекаРеактивное приложение может вызывать внешнюю систему (например, legacy REST-сервис — «наследуемый» сервис на старой архитектуре), которая сама по себе не построена на реактивном стеке и может отвечать медленно, вплоть до 15-20 секунд.       Здесь важно показать, что даже долгое ожидание ответа не блокирует поток event loop.4.1 Поток не блокируется, потому что WebClient не ждёт ответ синхронноWebClient — это реактивный HTTP-клиент в Spring WebFlux, построенный на базе Reactor Netty. Он отправляет запрос к внешней системе через сокет и сразу регистрирует callback на этот сокет — сам поток event loop не остаётся привязанным к этому вызову ни на секунду и немедленно переходит к обслуживанию других соединений.WebClient client = WebClient.builder()        .baseUrl("https://legacy-billing.internal")        .build();Mono<Invoice> invoiceMono = client.get()        .uri("/invoices/{id}", invoiceId)        .retrieve()        .bodyToMono(Invoice.class);invoiceMono.subscribe(invoice ->        log.info("Счёт получен, поток: {}", Thread.currentThread().getName()));Бизнес-кейс: - сервис оформления счетов вызывает legacy-модуль биллинга, написанный на старой Java EE-платформе без поддержки неблокирующего ввода-вывода. Даже если legacy-система отвечает через 18-19 секунд, тот же самый поток event loop за это время успевает обслужить множество других запросов от других клиентов.4.2 Механика: почему сама удалённая система не должна быть реактивной, чтобы поток не блокировалсяКлючевой момент: неблокирующее ожидание обеспечивается не тем, что удалённая система реактивна (у неё может быть классический синхронный REST-контроллер на старом сервлет-стеке), а тем, что клиентская сторона (Reactor Netty) работает через неблокирующие сокеты и механизм epoll на уровне ОС.Источник: https://projectreactor.io/docs/netty/release/reference/http-client.html"Reactor Netty uses Reactor Core to provide the low-level networking layer through non-blocking abstractions."RU:"Reactor Netty использует Reactor Core, чтобы обеспечить низкоуровневый сетевой слой через неблокирующие абстракции." Пока legacy-система формирует ответ на своей стороне (тратит все 18-19 секунд на свою внутреннюю обработку), клиентский сокет на стороне Reactor Netty просто ждёт данных без участия потока — сокет зарегистрирован в наборе дескрипторов, которые отслеживает epolle (epolle – это механизм селектора), и событие для него сработает только тогда, когда данные реально прибудут по сети.  То, насколько медленно или синхронно устроена сама legacy-система, не имеет значения для потока клиента — важно лишь то, что клиентский вызов сделан неблокирующим способом.4.3 Backpressure: как ведёт себя приложение, если удалённая система отдаёт поток данныхЕсли legacy-система отдаёт не единый JSON-объект, а поток данных (например, построчный экспорт большого списка счетов через bodyToFlux()), возникает вопрос backpressure — ведь сама legacy-система ничего не знает про этот механизм и просто пишет данные в сокет так быстро, как может.Источник: https://blog.nashtechglobal.com/spring-reactor-backpressure/"Backpressure is the ability of a Consumer to signal the Producer that the rate of emission is higher than what it can handle... The Subscriber makes use of request(n) to request n number of elements at a time."RU:"Backpressure — это способность потребителя (Consumer) сигнализировать производителю (Producer), что скорость эмиссии выше того, что он может обработать... Подписчик использует request(n), чтобы запросить n элементов за раз."На практике регулирование происходит не через явные вызовы в бизнес-коде, а через саму TCP-механику: Reactor Netty читает из сокета следующий chunck байт только тогда, когда downstream-подписчик (например, обработчик, который пишет каждый счёт в БД) реально запросил новую порцию через request(n). Если обработчик не успевает — Netty просто не инициирует очередное чтение из этого конкретного сокета, и буфер данных остаётся невычитанным на уровне ОС, без переполнения памяти приложения.Бизнес-кейс: сервис оформления счетов через bodyToFlux(Invoice.class) получает поток из десятков тысяч архивных счетов от legacy-склада. Если downstream-обработчик, который сохраняет каждый счёт в новую БД, работает медленнее, чем legacy-система готова отдавать данные, чтение следующих счетов из сокета естественным образом приостанавливается до тех пор, пока обработчик не освободится и не запросит следующую порцию — то есть скорость всей цепочки регулируется самым медленным её звеном, а не тем, насколько быстро отдаёт данные legacy-система.4.4 Что происходит, если удалённая система превышает время ответа: глобальные таймауты клиентаЗащита от ситуации, когда legacy-система не отвечает вообще неопределённо долго, настраивается не отдельными вставками в каждый вызов, а глобальными параметрами самого HttpClient, на котором строится WebClient — так это делается в реальной практике.Источник: https://dev.to/yangbongsoo/webclient-timeout-and-connection-pool-strategy-2gpn"CONNECT_TIMEOUT_MILLIS is a waiting time for establishing a connection with the server and It is httpClient level. responseTimeout is a timeout for the whole response."RU:"CONNECT_TIMEOUT_MILLIS — это время ожидания установки соединения с сервером на уровне httpClient. responseTimeout — это таймаут на весь ответ."Эти два параметра решают разные задачи: - connectTimeoutMillis ограничивает только этап установки самого TCP-соединения — если legacy-система вообще не отвечает на попытку подключения (например, недоступна по сети). - responseTimeout ограничивает всё время от момента отправки запроса до получения полного ответа — именно этот параметр реально защищает от ситуации, когда соединение установлено, но legacy-система «зависла» и не формирует ответ дольше ожидаемого.Оба параметра задаются один раз при конфигурации HttpClient, который передаётся в WebClient.builder(), а не прописываются в каждом отдельном вызове к legacy-биллингу. Если legacy-система превышает установленный responseTimeout, Reactor Netty сам обрывает ожидание и завершает Mono ошибкой без участия дополнительного кода внутри цепочки вызова — то есть защита от превышения времени ответа встроена в конфигурацию клиента и применяется одинаково ко всем вызовам через этот WebClient, включая случай с сервисом оформления счетов из предыдущих разделов.
